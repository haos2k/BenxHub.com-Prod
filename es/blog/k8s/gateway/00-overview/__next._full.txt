1b:T3e5c,<p>Si alguna vez has trabajado con tráfico externo en Kubernetes, lo más probable es que hayas empezado con <code>Ingress</code>. Funciona, y para muchos escenarios es genuinamente suficiente. Pero una vez que te enfrentas a requisitos más complejos — múltiples listeners, propiedad multi-equipo, gRPC, TCP, TLS passthrough, políticas de tráfico de grano fino — inevitablemente llegas a una situación donde "mantenerlo vivo con annotations" se convierte en la norma. El YAML empieza a parecer un conjuro, y las personas que lo mantienen sienten que están rompiendo un sello.</p>
<p>Ahí es donde entra <code>Gateway API + Envoy Gateway</code> — es el nuevo conjunto de herramientas. No complica las cosas; separa de forma limpia las responsabilidades que antes estaban entrelazadas, haciendo que el tráfico de entrada, las reglas de enrutamiento, la configuración de seguridad TLS, los tipos de protocolo y la propiedad de los equipos sean mucho más fáciles de razonar.</p>
<h2 id="qué-es-exactamente">Qué Es, Exactamente</h2>
<p>Digámoslo claramente en una sola oración:</p>
<ul>
<li><code>Envoy Proxy</code>: El plano de datos que realmente recibe el tráfico y reenvía las solicitudes — también conocido como Gateway Proxy</li>
<li><code>Envoy Gateway</code>: El plano de control que gestiona Envoy Proxy por ti</li>
<li><code>Gateway API</code>: La interfaz estándar que usas en Kubernetes para declarar reglas de tráfico</li>
</ul>
<p>Piénsalo así:</p>
<ul>
<li><code>Gateway API</code> es donde escribes los requisitos</li>
<li><code>Envoy Gateway</code> es el gestor que traduce y delega</li>
<li><code>Envoy Proxy</code> es el guardia real que está en la puerta</li>
</ul>
<p>La ventaja de esta separación es que no necesitas construir manualmente configuración de bajo nivel de Envoy, ni memorizar cada annotation privada de varios controladores. Declaras recursos de Kubernetes, y Envoy Gateway los traduce en configuración que Envoy Proxy puede ejecutar realmente.</p>
<h2 id="gateway-vs-ingress-cuál-es-la-diferencia">Gateway vs Ingress: Cuál Es la Diferencia</h2>
<p>La respuesta corta: <strong>Ingress no está obsoleto, pero Gateway API está mejor adaptado para sistemas medianos y grandes que necesitan más gobernanza.</strong></p>
<table>
<thead>
<tr>

<p>Si tus requisitos son simplemente:</p>
<ul>
<li>Un solo sitio web o API sencilla</li>
<li>Enrutamiento básico por ruta/host</li>
<li>Equipo pequeño</li>
</ul>
<p>Entonces Ingress sigue siendo válido. Pero si tus requisitos empiezan a incluir:</p>
<ul>
<li>Un ingreso que sirve múltiples protocolos</li>
<li>Múltiples listeners, dominios o certificados</li>
<li>HTTP y gRPC coexistiendo</li>
<li>Separar los permisos de ingreso de plataforma de los de ruta de aplicación</li>
<li>Configuración que se lee como una API real, no como una lista de deseos de annotations</li>
</ul>
<p>Entonces Gateway API empezará a resultar muy atractivo.</p>
<h2 id="por-qué-no-usar-simplemente-ingress">Por Qué No Usar Simplemente Ingress</h2>
<p>El objetivo oficial de Gateway API es abordar varios puntos de dolor comunes con Ingress a escala:</p>
<ul>
<li><strong>Mejor expresividad</strong>: El enrutamiento, TLS, las políticas de tráfico y los tipos de protocolo están definidos de forma más clara</li>
<li><strong>Mejor portabilidad</strong>: Menor dependencia de annotations privadas específicas del controlador</li>
<li><strong>Separación de roles más natural</strong>: Los equipos de plataforma poseen el ingreso, los equipos de aplicación poseen las rutas</li>
</ul>
<p>Por ejemplo, las configuraciones de Ingress a menudo lucen así:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">metadata</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  annotations</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/rewrite-target</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">/</span></span>

<p>No es que no funcione — pero a medida que crecen los requisitos, las annotations fácilmente se convierten en magia negra de YAML misteriosa. Gateway API traslada estas necesidades a campos apropiados. Se lee como "configuración," no como una "lista de deseos."</p>
<h2 id="la-estructura-en-capas">La Estructura en Capas</h2>
<p>La página de conceptos oficial divide Envoy Gateway en tres capas — vale la pena memorizarlas como mapa mental:</p>
<ul>
<li><strong>Configuración de usuario</strong>: Los recursos de <code>Gateway API</code> y los CRDs de extensión de Envoy Gateway que escribes</li>
<li><strong>Controlador de Envoy Gateway</strong>: Lee estos recursos, los traduce en configuración ejecutable</li>
<li><strong>Envoy Proxy</strong>: El plano de datos que realmente maneja el tráfico en vivo</li>
</ul>
<p>En la práctica, pasarás la mayor parte de tu tiempo modificando la "capa declarativa," no conectándote por SSH a instancias de proxy para ajustar configuración de bajo nivel. Esta es la elegancia de ser nativo de Kubernetes.</p>

<h2 id="recursos-principales-que-encontrarás">Recursos Principales que Encontrarás</h2>
<p>Los principiantes suelen tropezar porque asumen que Gateway API solo tiene <code>Gateway</code> y <code>HTTPRoute</code>. En realidad es toda una familia de recursos.</p>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>Define "qué implementación de Gateway usar en este clúster."
Para Envoy Gateway, la clave es que <code>controllerName</code> apunte al controlador correcto.</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>Define "cómo luce el ingreso."
Por ejemplo: qué puertos abrir, en qué protocolos escuchar, cómo se adjunta TLS, qué rutas están permitidas.</p>
<h3 id="listener"><code>Listener</code></h3>
<p><code>Listener</code> es una de las unidades más importantes dentro de un <code>Gateway</code>.
Piénsalo como una ranura orientada hacia el exterior del Gateway — cada ranura define:</p>
<ul>
<li>puerto</li>
<li>protocolo</li>
<li>hostname</li>
<li>configuración TLS</li>
<li><code>allowedRoutes</code></li>
</ul>
<p>Mucha gente piensa en <code>Gateway</code> como una caja negra, pero lo que realmente determina el comportamiento del ingreso es cada <code>listener</code> individual dentro de él.</p>
<h3 id="la-familia-de-route">La Familia de Route</h3>
<ul>
<li><code>HTTPRoute</code>: Tráfico HTTP/HTTPS — el más común</li>
<li><code>GRPCRoute</code>: Tráfico gRPC — puede coincidir en servicio/método</li>
<li><code>TCPRoute</code>: Tráfico TCP puro — no analiza semántica HTTP</li>
<li><code>TLSRoute</code>: Enruta basándose en TLS SNI — común para TLS passthrough</li>
</ul>
<p>Lo que todos los routes comparten:
<strong>No "abren la puerta" — deciden "cómo enrutar el tráfico una vez que entra."</strong></p>

<p>Guarda este mapa en tu cabeza:</p>

25:T3e5c,<p>Si alguna vez has trabajado con tráfico externo en Kubernetes, lo más probable es que hayas empezado con <code>Ingress</code>. Funciona, y para muchos escenarios es genuinamente suficiente. Pero una vez que te enfrentas a requisitos más complejos — múltiples listeners, propiedad multi-equipo, gRPC, TCP, TLS passthrough, políticas de tráfico de grano fino — inevitablemente llegas a una situación donde "mantenerlo vivo con annotations" se convierte en la norma. El YAML empieza a parecer un conjuro, y las personas que lo mantienen sienten que están rompiendo un sello.</p>
<p>Ahí es donde entra <code>Gateway API + Envoy Gateway</code> — es el nuevo conjunto de herramientas. No complica las cosas; separa de forma limpia las responsabilidades que antes estaban entrelazadas, haciendo que el tráfico de entrada, las reglas de enrutamiento, la configuración de seguridad TLS, los tipos de protocolo y la propiedad de los equipos sean mucho más fáciles de razonar.</p>
<h2 id="qué-es-exactamente">Qué Es, Exactamente</h2>
<p>Digámoslo claramente en una sola oración:</p>
<ul>
<li><code>Envoy Proxy</code>: El plano de datos que realmente recibe el tráfico y reenvía las solicitudes — también conocido como Gateway Proxy</li>
<li><code>Envoy Gateway</code>: El plano de control que gestiona Envoy Proxy por ti</li>
<li><code>Gateway API</code>: La interfaz estándar que usas en Kubernetes para declarar reglas de tráfico</li>
</ul>
<p>Piénsalo así:</p>
<ul>
<li><code>Gateway API</code> es donde escribes los requisitos</li>
<li><code>Envoy Gateway</code> es el gestor que traduce y delega</li>
<li><code>Envoy Proxy</code> es el guardia real que está en la puerta</li>
</ul>
<p>La ventaja de esta separación es que no necesitas construir manualmente configuración de bajo nivel de Envoy, ni memorizar cada annotation privada de varios controladores. Declaras recursos de Kubernetes, y Envoy Gateway los traduce en configuración que Envoy Proxy puede ejecutar realmente.</p>
<h2 id="gateway-vs-ingress-cuál-es-la-diferencia">Gateway vs Ingress: Cuál Es la Diferencia</h2>
<p>La respuesta corta: <strong>Ingress no está obsoleto, pero Gateway API está mejor adaptado para sistemas medianos y grandes que necesitan más gobernanza.</strong></p>

<p>Si tus requisitos son simplemente:</p>
<ul>
<li>Un solo sitio web o API sencilla</li>
<li>Enrutamiento básico por ruta/host</li>
<li>Equipo pequeño</li>
</ul>
<p>Entonces Ingress sigue siendo válido. Pero si tus requisitos empiezan a incluir:</p>
<ul>
<li>Un ingreso que sirve múltiples protocolos</li>
<li>Múltiples listeners, dominios o certificados</li>
<li>HTTP y gRPC coexistiendo</li>
<li>Separar los permisos de ingreso de plataforma de los de ruta de aplicación</li>
<li>Configuración que se lee como una API real, no como una lista de deseos de annotations</li>
</ul>
<p>Entonces Gateway API empezará a resultar muy atractivo.</p>
<h2 id="por-qué-no-usar-simplemente-ingress">Por Qué No Usar Simplemente Ingress</h2>
<p>El objetivo oficial de Gateway API es abordar varios puntos de dolor comunes con Ingress a escala:</p>
<ul>
<li><strong>Mejor expresividad</strong>: El enrutamiento, TLS, las políticas de tráfico y los tipos de protocolo están definidos de forma más clara</li>
<li><strong>Mejor portabilidad</strong>: Menor dependencia de annotations privadas específicas del controlador</li>
<li><strong>Separación de roles más natural</strong>: Los equipos de plataforma poseen el ingreso, los equipos de aplicación poseen las rutas</li>
</ul>
<p>Por ejemplo, las configuraciones de Ingress a menudo lucen así:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">metadata</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  annotations</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/rewrite-target</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">/</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/auth-type</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">basic</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/ssl-redirect</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">"true"</span></span></code></pre></figure>
<p>No es que no funcione — pero a medida que crecen los requisitos, las annotations fácilmente se convierten en magia negra de YAML misteriosa. Gateway API traslada estas necesidades a campos apropiados. Se lee como "configuración," no como una "lista de deseos."</p>
<h2 id="la-estructura-en-capas">La Estructura en Capas</h2>
<p>La página de conceptos oficial divide Envoy Gateway en tres capas — vale la pena memorizarlas como mapa mental:</p>
<ul>
<li><strong>Configuración de usuario</strong>: Los recursos de <code>Gateway API</code> y los CRDs de extensión de Envoy Gateway que escribes</li>
<li><strong>Controlador de Envoy Gateway</strong>: Lee estos recursos, los traduce en configuración ejecutable</li>
<li><strong>Envoy Proxy</strong>: El plano de datos que realmente maneja el tráfico en vivo</li>
</ul>
<p>En la práctica, pasarás la mayor parte de tu tiempo modificando la "capa declarativa," no conectándote por SSH a instancias de proxy para ajustar configuración de bajo nivel. Esta es la elegancia de ser nativo de Kubernetes.</p>

<h2 id="recursos-principales-que-encontrarás">Recursos Principales que Encontrarás</h2>
<p>Los principiantes suelen tropezar porque asumen que Gateway API solo tiene <code>Gateway</code> y <code>HTTPRoute</code>. En realidad es toda una familia de recursos.</p>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>Define "qué implementación de Gateway usar en este clúster."
Para Envoy Gateway, la clave es que <code>controllerName</code> apunte al controlador correcto.</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>Define "cómo luce el ingreso."
Por ejemplo: qué puertos abrir, en qué protocolos escuchar, cómo se adjunta TLS, qué rutas están permitidas.</p>
<h3 id="listener"><code>Listener</code></h3>
<p><code>Listener</code> es una de las unidades más importantes dentro de un <code>Gateway</code>.
Piénsalo como una ranura orientada hacia el exterior del Gateway — cada ranura define:</p>
<ul>
<li>puerto</li>
<li>protocolo</li>
<li>hostname</li>
<li>configuración TLS</li>
<li><code>allowedRoutes</code></li>
</ul>
<p>Mucha gente piensa en <code>Gateway</code> como una caja negra, pero lo que realmente determina el comportamiento del ingreso es cada <code>listener</code> individual dentro de él.</p>
<h3 id="la-familia-de-route">La Familia de Route</h3>
<ul>
<li><code>HTTPRoute</code>: Tráfico HTTP/HTTPS — el más común</li>
<li><code>GRPCRoute</code>: Tráfico gRPC — puede coincidir en servicio/método</li>
<li><code>TCPRoute</code>: Tráfico TCP puro — no analiza semántica HTTP</li>
<li><code>TLSRoute</code>: Enruta basándose en TLS SNI — común para TLS passthrough</li>
</ul>
<p>Lo que todos los routes comparten:
<strong>No "abren la puerta" — deciden "cómo enrutar el tráfico una vez que entra."</strong></p>
