b:T5457,<p>La primera impresión que muchas personas tienen del Gateway API es algo como: "La cantidad de términos no es tan alta, pero mi cerebro se siente como si estuviera viendo un reparto lleno de personajes con nombres similares — no puedo distinguir quién es el protagonista y quién es un personaje secundario." Este artículo está aquí para cortar esa confusión, y también cubrirá los tipos de rutas más comunes.</p>
<h2 id="la-arquitectura-general">La Arquitectura General</h2>
<p>Los conceptos oficiales de Envoy Gateway dividen el sistema en tres capas:</p>
<ul>
<li><strong>Configuración del Usuario</strong>: Los recursos de <code>Gateway API</code> y los CRDs de extensión de Envoy Gateway que escribes</li>
<li><strong>Controlador de Envoy Gateway</strong>: Lee los recursos, los valida y traduce la configuración</li>
<li><strong>Envoy Proxy</strong>: El plano de datos que realmente maneja el tráfico</li>
</ul>
<p>Esto significa que lo que generalmente estás editando no es Envoy Proxy en sí — estás "declarando lo que quieres."
Envoy Gateway traduce esas declaraciones en configuración que Envoy Proxy puede ejecutar. Eso es lo que lo hace más agradable que escribir configuración de proxy a mano.</p>
<h2 id="los-roles-clave">Los Roles Clave</h2>
<p>Por ahora, recuerda estos:</p>
<ul>
<li><code>GatewayClass</code>: Define "qué implementación de Gateway usar en este clúster"</li>
<li><code>Gateway</code>: Define "dónde está el ingreso y qué protocolo habla"</li>
<li><code>Listener</code>: Define un slot de ingreso específico por puerto/protocolo/hostname</li>
<li><code>Route</code>: Define "qué solicitudes van a qué Service"</li>
<li><code>Envoy Proxy</code>: El Gateway Proxy real que recibe y reenvía el tráfico</li>
</ul>
<p>En palabras simples:</p>
<ul>
<li><code>GatewayClass</code> es la ficha técnica</li>
<li><code>Gateway</code> es la entrada principal del edificio</li>
<li><code>Listener</code> es la recepción</li>
<li><code>Route</code> es la señalización dentro del edificio</li>
<li><code>Envoy Proxy</code> es el sistema de seguridad que controla el acceso y acompaña a los visitantes</li>
</ul>
<p>Sin alguno de estos, el tráfico no llegará a donde quieres.</p>

<ol>

<li><code>HTTPRoute</code> indica que las solicitudes para <code>www.example.com</code> deben ir a <code>backend:3000</code></li>
<li><code>Envoy Gateway</code> traduce todo esto para <code>Envoy Proxy</code></li>
</ol>
<h2 id="entendiendo-cada-campo">Entendiendo Cada Campo</h2>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>Esta es una definición de tipo de ingreso a nivel de clúster. El campo más crítico suele ser:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  controllerName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">gateway.envoyproxy.io/gatewayclass-controller</span></span></code></pre></figure>
<p>Esto simplemente significa:
"Este <code>GatewayClass</code> está gestionado por el controlador de Envoy Gateway."</p>
<p>Si el controllerName no coincide, es como pedir un delivery a la empresa equivocada — nadie lo recoge.</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>Esto define "cómo se ve el ingreso." El campo más referenciado es <code>listeners</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">listeners</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">http</span></span>
<span data-line=""><span style="color:#7EE787">    protocol</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTP</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">80</span></span></code></pre></figure>
<p>Esto significa:</p>
<ul>
<li>Abrir un listener llamado <code>http</code></li>
<li>Aceptar tráfico HTTP</li>
<li>Escuchar externamente en el puerto <code>80</code></li>
</ul>
<p>Para HTTPS, normalmente agregarías otro listener con <code>protocol: HTTPS</code> y adjuntarías la configuración TLS.</p>
<p><code>Gateway</code> comúnmente gestiona:</p>
<ul>
<li>Puerto externo y protocolo</li>
<li>Hostname por listener</li>
<li>Ubicación de terminación TLS</li>
<li>Qué rutas de qué namespaces pueden adjuntarse</li>
</ul>
<p><code>Gateway</code> es más una preocupación de la capa de plataforma — su propiedad normalmente recae en el equipo de plataforma.</p>
<h3 id="listener"><code>Listener</code></h3>
<p>Este es el rol que los principiantes pasan por alto con más frecuencia, pero en realidad es crucial.</p>
<p>Un <code>listener</code> es un slot de ingreso orientado al exterior en el Gateway. Define:</p>
<ul>
<li><code>name</code></li>
<li><code>port</code></li>
<li><code>protocol</code></li>
<li><code>hostname</code></li>
<li><code>tls</code></li>
<li><code>allowedRoutes</code></li>
</ul>
<p>Ejemplo:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">listeners</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span>
<span data-line=""><span style="color:#7EE787">    protocol</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTPS</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">443</span></span>
<span data-line=""><span style="color:#7EE787">    hostname</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api.example.com</span></span></code></pre></figure>
<p>Esto significa:</p>
<ul>
<li>Este slot se llama <code>https</code></li>
<li>Acepta HTTPS</li>
<li>Escucha en el puerto <code>443</code></li>
<li>Dedicado a <code>api.example.com</code></li>
</ul>
<p>Si tienes múltiples listeners como:</p>
<ul>
<li><code>http</code> para el puerto 80</li>
<li><code>https</code> para el puerto 443</li>
<li><code>grpc</code> para el puerto 50051</li>
</ul>
<p>Estás abriendo múltiples slots de ingreso en el mismo Gateway, cada uno capaz de adjuntar diferentes rutas.</p>
<h3 id="envoy-proxy"><code>Envoy Proxy</code></h3>
<p>Muchas personas se centran solo en el YAML y olvidan que <code>Envoy Proxy</code> es lo que realmente maneja el tráfico en vivo.</p>
<p>Su rol es:</p>
<ul>
<li>Recibir solicitudes de los clientes</li>
<li>Hacer coincidir con la configuración enviada por Envoy Gateway</li>
<li>Reenviar el tráfico al backend apropiado</li>
<li>Manejar TLS, headers, timeouts, reintentos y otros comportamientos del plano de datos</li>
</ul>
<p>Así que piensa en Envoy Gateway como el "plano de control," y en Envoy Proxy como el "plano de datos / Gateway Proxy."</p>
<h3 id="la-familia-de-routes">La Familia de Routes</h3>
<p><code>Route</code> no es solo <code>HTTPRoute</code>. Toda la familia es central en el diseño del Gateway API.</p>
<h4 id="httproute"><code>HTTPRoute</code></h4>
<p>Este es el que escribirás y modificarás con mayor frecuencia. Tres campos clave:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">  hostnames</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#A5D6FF">"www.example.com"</span></span>
<span data-line=""><span style="color:#7EE787">  rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">backend</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">3000</span></span></code></pre></figure>
<ul>
<li><code>parentRefs</code>: A qué Gateway adjuntarse</li>
<li><code>hostnames</code>: Qué header Host activa esta regla</li>
<li><code>backendRefs</code>: A dónde enviar las solicitudes coincidentes</li>
</ul>
<p>La confusión más común: <code>Gateway</code> no es donde escribes el enrutamiento detallado — <code>HTTPRoute</code> es lo que realmente decide "cómo dividir el tráfico."</p>
<h4 id="grpcroute"><code>GRPCRoute</code></h4>
<p>Si manejas gRPC, <code>GRPCRoute</code> es más natural que forzarlo dentro de <code>HTTPRoute</code>.</p>
<p>Puede hacer coincidir por:</p>
<ul>
<li>Hostname de gRPC</li>
<li>Servicio de gRPC</li>
<li>Método de gRPC</li>
<li>Headers</li>
</ul>
<p>Ejemplo:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">matches</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">method</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">      service</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">com.example.User</span></span>
<span data-line=""><span style="color:#7EE787">      method</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">Login</span></span></code></pre></figure>
<p>Esta semántica se alinea naturalmente con gRPC — no solo estás haciendo coincidir rutas de URL, sino que estás haciendo coincidir directamente con el modelo de servicio/método de gRPC.</p>
<p>La documentación oficial también señala: si <code>GRPCRoute</code> y <code>HTTPRoute</code> comparten el mismo listener y tienen hostnames en conflicto, las implementaciones deberían rechazar uno. Básicamente, no dejes que HTTP y gRPC peleen por el mismo hostname.</p>
<h4 id="tcproute"><code>TCPRoute</code></h4>
<p><code>TCPRoute</code> maneja tráfico TCP sin procesar.
A diferencia de <code>HTTPRoute</code>, no entiende la semántica de rutas o headers en L7 — está más cerca del reenvío en L4.</p>
<p>Escenarios apropiados:</p>
<ul>
<li>Servicios con protocolos no HTTP</li>
<li>Servicios TCP puros</li>
<li>Enrutar conexiones a diferentes backends basándose únicamente en el puerto del listener</li>
</ul>
<p>Las bases de datos con protocolos personalizados o protocolos TCP propietarios son casos de uso típicos de <code>TCPRoute</code>.</p>
<h4 id="tlsroute"><code>TLSRoute</code></h4>
<p><code>TLSRoute</code> maneja tráfico TLS y es particularmente común en escenarios de <strong>TLS passthrough</strong>.</p>
<p>Concepto central:</p>
<ul>
<li>El Gateway no necesariamente termina TLS</li>
<li>Puede enrutar el tráfico basándose únicamente en el hostname SNI en el handshake TLS</li>
<li>El tráfico cifrado se preserva hasta el backend</li>
</ul>
<p>Esto importa en escenarios que requieren cifrado de extremo a extremo, o donde no quieres que TLS se termine en el Gateway.</p>
<h2 id="cómo-elegir-un-tipo-de-route">Cómo Elegir un Tipo de Route</h2>
<table>
<thead>
<tr>
<th>Requisito</th>

<h2 id="por-qué-las-routes-son-más-fáciles-de-razonar-que-ingress">Por Qué las Routes Son Más Fáciles de Razonar que Ingress</h2>
<p>Las configuraciones antiguas de Ingress a menudo apretaban demasiadas responsabilidades en un solo recurso, lo que llevaba a algunos puntos de dolor persistentes:</p>
<ul>
<li>Configuración de plataforma y enrutamiento de aplicaciones mezclados</li>
<li>Características avanzadas expresadas mediante anotaciones con poca legibilidad</li>
<li>Expresividad limitada para protocolos no HTTP</li>
</ul>
<p>El enfoque del Gateway API es dividir responsabilidades:</p>
<ul>
<li>Los equipos de plataforma gestionan <code>GatewayClass</code> / <code>Gateway</code></li>
<li>Los equipos de aplicación gestionan sus propios <code>HTTPRoute</code></li>
</ul>
<p>Esta separación funciona bien para la colaboración en equipo. No necesitas tocar toda la capa de ingreso solo para cambiar una ruta — las tasas de conflictos entre equipos bajan significativamente.</p>

<h2 id="la-arquitectura-general">La Arquitectura General</h2>
<p>Los conceptos oficiales de Envoy Gateway dividen el sistema en tres capas:</p>
<ul>
<li><strong>Configuración del Usuario</strong>: Los recursos de <code>Gateway API</code> y los CRDs de extensión de Envoy Gateway que escribes</li>
<li><strong>Controlador de Envoy Gateway</strong>: Lee los recursos, los valida y traduce la configuración</li>
<li><strong>Envoy Proxy</strong>: El plano de datos que realmente maneja el tráfico</li>
</ul>
<p>Esto significa que lo que generalmente estás editando no es Envoy Proxy en sí — estás "declarando lo que quieres."
Envoy Gateway traduce esas declaraciones en configuración que Envoy Proxy puede ejecutar. Eso es lo que lo hace más agradable que escribir configuración de proxy a mano.</p>
<h2 id="los-roles-clave">Los Roles Clave</h2>
<p>Por ahora, recuerda estos:</p>
<ul>
<li><code>GatewayClass</code>: Define "qué implementación de Gateway usar en este clúster"</li>
<li><code>Gateway</code>: Define "dónde está el ingreso y qué protocolo habla"</li>
<li><code>Listener</code>: Define un slot de ingreso específico por puerto/protocolo/hostname</li>
<li><code>Route</code>: Define "qué solicitudes van a qué Service"</li>
<li><code>Envoy Proxy</code>: El Gateway Proxy real que recibe y reenvía el tráfico</li>
</ul>
<p>En palabras simples:</p>
<ul>
<li><code>GatewayClass</code> es la ficha técnica</li>
<li><code>Gateway</code> es la entrada principal del edificio</li>
<li><code>Listener</code> es la recepción</li>
<li><code>Route</code> es la señalización dentro del edificio</li>
<li><code>Envoy Proxy</code> es el sistema de seguridad que controla el acceso y acompaña a los visitantes</li>
</ul>
<p>Sin alguno de estos, el tráfico no llegará a donde quieres.</p>

<h2 id="entendiendo-cada-campo">Entendiendo Cada Campo</h2>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>Esta es una definición de tipo de ingreso a nivel de clúster. El campo más crítico suele ser:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  controllerName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">gateway.envoyproxy.io/gatewayclass-controller</span></span></code></pre></figure>
<p>Esto simplemente significa:
"Este <code>GatewayClass</code> está gestionado por el controlador de Envoy Gateway."</p>
<p>Si el controllerName no coincide, es como pedir un delivery a la empresa equivocada — nadie lo recoge.</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>Esto define "cómo se ve el ingreso." El campo más referenciado es <code>listeners</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">listeners</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">http</span></span>
<span data-line=""><span style="color:#7EE787">    protocol</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTP</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">80</span></span></code></pre></figure>
<p>Esto significa:</p>
<ul>
<li>Abrir un listener llamado <code>http</code></li>
<li>Aceptar tráfico HTTP</li>
<li>Escuchar externamente en el puerto <code>80</code></li>
</ul>
<p>Para HTTPS, normalmente agregarías otro listener con <code>protocol: HTTPS</code> y adjuntarías la configuración TLS.</p>
<p><code>Gateway</code> comúnmente gestiona:</p>
<ul>
<li>Puerto externo y protocolo</li>
<li>Hostname por listener</li>
<li>Ubicación de terminación TLS</li>
<li>Qué rutas de qué namespaces pueden adjuntarse</li>
</ul>
<p><code>Gateway</code> es más una preocupación de la capa de plataforma — su propiedad normalmente recae en el equipo de plataforma.</p>
<h3 id="listener"><code>Listener</code></h3>
<p>Este es el rol que los principiantes pasan por alto con más frecuencia, pero en realidad es crucial.</p>
<p>Un <code>listener</code> es un slot de ingreso orientado al exterior en el Gateway. Define:</p>
<ul>
<li><code>name</code></li>
<li><code>port</code></li>
<li><code>protocol</code></li>
<li><code>hostname</code></li>
<li><code>tls</code></li>
<li><code>allowedRoutes</code></li>
</ul>
<p>Ejemplo:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">listeners</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span>
<span data-line=""><span style="color:#7EE787">    protocol</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTPS</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">443</span></span>
<span data-line=""><span style="color:#7EE787">    hostname</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api.example.com</span></span></code></pre></figure>
<p>Esto significa:</p>
<ul>
<li>Este slot se llama <code>https</code></li>
<li>Acepta HTTPS</li>
<li>Escucha en el puerto <code>443</code></li>
<li>Dedicado a <code>api.example.com</code></li>
</ul>
<p>Si tienes múltiples listeners como:</p>
<ul>
<li><code>http</code> para el puerto 80</li>
<li><code>https</code> para el puerto 443</li>
<li><code>grpc</code> para el puerto 50051</li>
</ul>
<p>Estás abriendo múltiples slots de ingreso en el mismo Gateway, cada uno capaz de adjuntar diferentes rutas.</p>
<h3 id="envoy-proxy"><code>Envoy Proxy</code></h3>
<p>Muchas personas se centran solo en el YAML y olvidan que <code>Envoy Proxy</code> es lo que realmente maneja el tráfico en vivo.</p>
<p>Su rol es:</p>
<ul>
<li>Recibir solicitudes de los clientes</li>
<li>Hacer coincidir con la configuración enviada por Envoy Gateway</li>
<li>Reenviar el tráfico al backend apropiado</li>
<li>Manejar TLS, headers, timeouts, reintentos y otros comportamientos del plano de datos</li>
</ul>
<p>Así que piensa en Envoy Gateway como el "plano de control," y en Envoy Proxy como el "plano de datos / Gateway Proxy."</p>
<h3 id="la-familia-de-routes">La Familia de Routes</h3>
<p><code>Route</code> no es solo <code>HTTPRoute</code>. Toda la familia es central en el diseño del Gateway API.</p>
<h4 id="httproute"><code>HTTPRoute</code></h4>
<p>Este es el que escribirás y modificarás con mayor frecuencia. Tres campos clave:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">  hostnames</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#A5D6FF">"www.example.com"</span></span>
<span data-line=""><span style="color:#7EE787">  rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">backend</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">3000</span></span></code></pre></figure>
<ul>
<li><code>parentRefs</code>: A qué Gateway adjuntarse</li>
<li><code>hostnames</code>: Qué header Host activa esta regla</li>
<li><code>backendRefs</code>: A dónde enviar las solicitudes coincidentes</li>
</ul>
<p>La confusión más común: <code>Gateway</code> no es donde escribes el enrutamiento detallado — <code>HTTPRoute</code> es lo que realmente decide "cómo dividir el tráfico."</p>
<h4 id="grpcroute"><code>GRPCRoute</code></h4>
<p>Si manejas gRPC, <code>GRPCRoute</code> es más natural que forzarlo dentro de <code>HTTPRoute</code>.</p>
<p>Puede hacer coincidir por:</p>
<ul>
<li>Hostname de gRPC</li>
<li>Servicio de gRPC</li>
<li>Método de gRPC</li>
<li>Headers</li>
</ul>
<p>Ejemplo:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">matches</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">method</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">      service</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">com.example.User</span></span>
<span data-line=""><span style="color:#7EE787">      method</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">Login</span></span></code></pre></figure>
<p>Esta semántica se alinea naturalmente con gRPC — no solo estás haciendo coincidir rutas de URL, sino que estás haciendo coincidir directamente con el modelo de servicio/método de gRPC.</p>
<p>La documentación oficial también señala: si <code>GRPCRoute</code> y <code>HTTPRoute</code> comparten el mismo listener y tienen hostnames en conflicto, las implementaciones deberían rechazar uno. Básicamente, no dejes que HTTP y gRPC peleen por el mismo hostname.</p>
<h4 id="tcproute"><code>TCPRoute</code></h4>
<p><code>TCPRoute</code> maneja tráfico TCP sin procesar.
A diferencia de <code>HTTPRoute</code>, no entiende la semántica de rutas o headers en L7 — está más cerca del reenvío en L4.</p>
<p>Escenarios apropiados:</p>
<ul>
<li>Servicios con protocolos no HTTP</li>
<li>Servicios TCP puros</li>
<li>Enrutar conexiones a diferentes backends basándose únicamente en el puerto del listener</li>
</ul>
<p>Las bases de datos con protocolos personalizados o protocolos TCP propietarios son casos de uso típicos de <code>TCPRoute</code>.</p>
<h4 id="tlsroute"><code>TLSRoute</code></h4>
<p><code>TLSRoute</code> maneja tráfico TLS y es particularmente común en escenarios de <strong>TLS passthrough</strong>.</p>
<p>Concepto central:</p>
<ul>
<li>El Gateway no necesariamente termina TLS</li>
<li>Puede enrutar el tráfico basándose únicamente en el hostname SNI en el handshake TLS</li>
<li>El tráfico cifrado se preserva hasta el backend</li>
</ul>
<p>Esto importa en escenarios que requieren cifrado de extremo a extremo, o donde no quieres que TLS se termine en el Gateway.</p>
<h2 id="cómo-elegir-un-tipo-de-route">Cómo Elegir un Tipo de Route</h2>
<table>
<thead>
<tr>
<th>Requisito</th>
<th>Usar Esto</th>
</tr>
</thead>
<tbody>

<p>Esta tabla importa porque muchas personas instintivamente escriben <code>HTTPRoute</code> para todo. Pero si realmente estás manejando gRPC o TCP, forzarlo en <code>HTTPRoute</code> solo hace que el YAML sea cada vez más torpe.</p>
<h2 id="por-qué-las-routes-son-más-fáciles-de-razonar-que-ingress">Por Qué las Routes Son Más Fáciles de Razonar que Ingress</h2>
<p>Las configuraciones antiguas de Ingress a menudo apretaban demasiadas responsabilidades en un solo recurso, lo que llevaba a algunos puntos de dolor persistentes:</p>
<ul>
<li>Configuración de plataforma y enrutamiento de aplicaciones mezclados</li>
<li>Características avanzadas expresadas mediante anotaciones con poca legibilidad</li>
<li>Expresividad limitada para protocolos no HTTP</li>
</ul>
<p>El enfoque del Gateway API es dividir responsabilidades:</p>
<ul>
<li>Los equipos de plataforma gestionan <code>GatewayClass</code> / <code>Gateway</code></li>
<li>Los equipos de aplicación gestionan sus propios <code>HTTPRoute</code></li>
</ul>
<p>Esta separación funciona bien para la colaboración en equipo. No necesitas tocar toda la capa de ingreso solo para cambiar una ruta — las tasas de conflictos entre equipos bajan significativamente.</p>
<h2 id="empieza-a-prestar-atención-al-status">Empieza a Prestar Atención al Status</h2>
<p>Más allá de <code>spec</code>, construye gradualmente el hábito de revisar <code>status</code>. Especialmente para <code>HTTPRoute</code> y <code>Gateway</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#A5D6FF"> eg</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span>

<p>Comienza revisando:</p>
<ul>
<li>Si la ruta fue <code>Accepted</code></li>
<li>Si el listener del gateway está Ready</li>
<li>Si se asignó correctamente una dirección</li>
</ul>
<p>Es como revisar los resultados de un examen. No solo verifiques que lo enviaste — verifica que fue calificado y aprobado.</p>
