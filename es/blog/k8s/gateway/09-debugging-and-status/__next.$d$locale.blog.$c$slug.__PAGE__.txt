c:T37c3,<p>El escenario de ingeniería más temido no es un mensaje de error — es:</p>
<p><strong>Aplicaste el YAML, <code>kubectl apply</code> tuvo éxito, pero el tráfico sigue sin fluir.</strong></p>
<p>Si en este punto solo te quedas mirando el <code>spec</code>, empezarás a sentir que estás leyendo el poso del café.
La información diagnóstica real en Gateway API vive en <code>status</code>.</p>
<p>Este artículo tiene un solo objetivo: darte el camino de debugging más corto posible. Cuando un <code>Gateway</code>, <code>HTTPRoute</code> o <code>Listener</code> no surte efecto, sabrás dónde mirar primero — en lugar de cuestionarte de inmediato si el universo tiene sentido.</p>

<p>El objetivo no es releer el YAML cien veces más — es verificar si el controlador realmente aceptó tu configuración.</p>
<p>Piensa en <code>status</code> como una hoja de calificaciones de examen:</p>
<ul>
<li><code>spec</code> es la respuesta que enviaste</li>
<li><code>status</code> es el resultado corregido por el sistema</li>
</ul>
<p>Mirar solo lo que enviaste, sin revisar nunca la calificación — eso es solo consuelo emocional, no debugging.</p>
<h2 id="las-tres-conditions-más-importantes-domínalas-y-estarás-cubierto">Las tres conditions más importantes: domínalas y estarás cubierto</h2>
<h3 id="accepted"><code>Accepted</code></h3>
<p>Esto normalmente indica si el recurso fue aceptado por su padre.
Para una ruta, suele significar:</p>
<ul>
<li>Si se adjuntó correctamente al Gateway/listener previsto</li>
<li>Si las reglas tienen algún conflicto obvio o configuración inválida</li>
</ul>
<p>Si <code>Accepted</code> es <code>False</code>, sospecha primero de:</p>
<ul>
<li><code>parentRefs</code> apuntando al Gateway o listener equivocado</li>
<li>Condiciones de hostname/listener que no coinciden</li>
<li>El listener rechazando este tipo de ruta</li>
<li><code>allowedRoutes</code> bloqueándote</li>
</ul>
<h3 id="resolvedrefs"><code>ResolvedRefs</code></h3>
<p>Esto indica si los objetos referenciados dentro del recurso se resolvieron correctamente.
Por ejemplo:</p>
<ul>
<li>¿Existe el <code>Service</code> referenciado en <code>backendRefs</code>?</li>
<li>¿Puede referenciarse legalmente el <code>Secret</code> en <code>certificateRefs</code>?</li>
<li>¿Está <code>ReferenceGrant</code> correctamente configurado para referencias entre namespaces?</li>
</ul>
<p>Esta condition es extremadamente útil.
Muchos fallos de configuración no son por lógica de enrutamiento incorrecta — son por cosas referenciadas que simplemente no existen, o a las que no tienes permiso de acceder.</p>
<h3 id="programmed"><code>Programmed</code></h3>
<p>Esto normalmente indica si la configuración fue efectivamente aplicada en la capa de implementación.
Piénsalo como:</p>
<ul>
<li>El controlador aceptó la configuración</li>
<li>Y la envió al data plane o la infraestructura</li>
</ul>
<p>Si <code>Accepted</code> ya es <code>True</code> pero el tráfico sigue sin fluir, es el momento en que vale la pena revisar <code>Programmed</code>, la dirección del Gateway, el estado de los listeners y los recursos de Envoy subyacentes.</p>
<blockquote>
<p>💡 Distintos recursos pueden exponer diferentes conjuntos de conditions, pero <code>Accepted</code>, <code>ResolvedRefs</code> y <code>Programmed</code> son el primer grupo sobre el que conviene desarrollar intuición.</p>
</blockquote>
<h2 id="flujo-de-debugging-más-corto-este-orden-suele-funcionar">Flujo de debugging más corto: este orden suele funcionar</h2>
<h3 id="paso-1-verificar-si-el-gateway-está-realmente-en-ejecución">Paso 1: Verificar si el Gateway está realmente en ejecución</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> gateway</span><span style="color:#79B8FF"> -A</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> gateway</span><span style="color:#9ECBFF"> eg</span><span style="color:#79B8FF"> -o</span><span style="color:#9ECBFF"> yaml</span></span></code></pre></figure>
<p>Verifica:</p>
<ul>
<li>¿Tiene <code>status.addresses</code> algún valor?</li>
<li>¿Hay alguna condition de listener anormal?</li>
<li>¿El hostname/protocol/port del listener coincide con lo que esperas?</li>
</ul>
<p>Si el Gateway no tiene dirección, incluso el YAML de ruta más hermoso es solo escritura creativa.</p>
<h3 id="paso-2-verificar-si-la-ruta-se-adjuntó-correctamente">Paso 2: Verificar si la ruta se adjuntó correctamente</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> httproute</span><span style="color:#79B8FF"> -A</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> httproute</span><span style="color:#9ECBFF"> app-route</span><span style="color:#79B8FF"> -o</span><span style="color:#9ECBFF"> yaml</span></span></code></pre></figure>
<p>Prioriza:</p>
<ul>
<li><code>status.parents</code></li>
<li><code>Accepted</code></li>
<li><code>ResolvedRefs</code></li>
<li><code>observedGeneration</code></li>
</ul>
<p><code>observedGeneration</code> vale la pena vigilarlo.
Si no ha alcanzado a <code>metadata.generation</code>, es posible que el controlador aún no haya procesado tu última versión de configuración.</p>
<h3 id="paso-3-verificar-si-los-recursos-referenciados-realmente-existen">Paso 3: Verificar si los recursos referenciados realmente existen</h3>
<p>Este paso se omite con más frecuencia que cualquier otro:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> svc</span><span style="color:#79B8FF"> -A</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> secret</span><span style="color:#79B8FF"> -A</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> referencegrant</span><span style="color:#79B8FF"> -A</span></span></code></pre></figure>
<p>Problemas comunes:</p>
<ul>
<li>El nombre del servicio de backend es incorrecto</li>
<li>El puerto es incorrecto</li>
<li>El Secret no está en el namespace que crees</li>
<li>La referencia entre namespaces no tiene <code>ReferenceGrant</code></li>
</ul>
<p>Si <code>ResolvedRefs</code> es <code>False</code>, rastrea el problema siguiendo este camino.</p>
<h3 id="paso-4-verificar-el-data-plane-y-el-controlador">Paso 4: Verificar el data plane y el controlador</h3>
<p>Si el status del Gateway y de la ruta parecen más o menos correctos pero el tráfico sigue sin fluir, profundiza más:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> pods</span><span style="color:#79B8FF"> -n</span><span style="color:#9ECBFF"> envoy-gateway-system</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> logs</span><span style="color:#79B8FF"> -n</span><span style="color:#9ECBFF"> envoy-gateway-system</span><span style="color:#9ECBFF"> deployment/envoy-gateway</span></span></code></pre></figure>
<p>En este punto ya no estás depurando "¿se aceptó la regla?" — estás verificando si el control plane y el data plane funcionan con normalidad.</p>
<p>Si tienes <code>egctl</code> instalado, puede ayudarte a inspeccionar el estado rápidamente.
Pero incluso sin él, <code>kubectl get/describe -o yaml</code> puede resolver la mayoría de los problemas.</p>
<h2 id="los-cuatro-patrones-de-fallo-más-comunes">Los cuatro patrones de fallo más comunes</h2>
<h3 id="1-la-ruta-es-correcta-pero-no-se-adjuntó-al-listener-previsto">1. La ruta es correcta, pero no se adjuntó al listener previsto</h3>
<p>Síntomas:</p>
<ul>
<li>El YAML parece correcto</li>
<li>Pero el tráfico no está llegando a la regla</li>
</ul>
<p>Comprueba:</p>
<ul>
<li><code>parentRefs.name</code></li>
<li><code>parentRefs.sectionName</code></li>
<li>Si el nombre del listener del Gateway coincide exactamente</li>
</ul>
<p>En configuraciones multi-listener, un solo error tipográfico en <code>sectionName</code> es suficiente para desperdiciar una sesión de debugging entera.</p>
<h3 id="2-accepted-tiene-éxito-pero-resolvedrefs-falla">2. <code>Accepted</code> tiene éxito, pero <code>ResolvedRefs</code> falla</h3>
<p>Esto suele significar que la lógica puede adjuntarse, pero algo referenciado tiene un problema.
Causas más comunes:</p>
<ul>
<li>El Service de backend no existe</li>
<li>El nombre del Secret es incorrecto</li>
<li>Referencia entre namespaces sin autorización</li>
</ul>
<p>Lo más frustrante de este tipo de fallo es que parece que ya casi llegaste — pero en realidad está atascado en la capa de referencia.</p>
<h3 id="3-el-gateway-tiene-listeners-pero-no-tiene-la-dirección-esperada">3. El Gateway tiene listeners pero no tiene la dirección esperada</h3>
<p>Esto aparece con frecuencia en clústeres locales o entornos sin una implementación de <code>LoadBalancer</code>.
No es que Gateway API esté roto — simplemente la infraestructura subyacente no está aprovisionando una dirección externa.</p>
<p>Opciones:</p>
<ul>
<li>Verificar si el clúster tiene capacidad <code>LoadBalancer</code></li>
<li>Usar <code>port-forward</code> para validar el camino de enrutamiento</li>
</ul>
<h3 id="4-el-yaml-surtió-efecto-pero-las-solicitudes-devuelven-404--503">4. El YAML surtió efecto, pero las solicitudes devuelven 404 / 503</h3>
<p>En este punto normalmente no es un solo campo incorrecto — es una cadena rota en algún punto:</p>
<ul>
<li>Header Host incorrecto</li>
<li>El path no coincide con ninguna regla</li>
<li>El Pod de backend no está saludable</li>
<li>El selector del Service no está seleccionando ningún Pod</li>
</ul>
<p>Los problemas de ingreso a veces parecen un fallo del proxy, pero el backend simplemente no estaba listo. No culpes de todo a la capa de proxy — ya tiene suficiente trabajo.</p>
<h2 id="resumen-en-una-línea">Resumen en una línea</h2>
<p>La forma más efectiva de depurar Gateway API no es cambiar el YAML constantemente — es aprender a leer <code>status</code>.
<code>Accepted</code> te dice si se recogió la orden. <code>ResolvedRefs</code> te dice si las referencias se resolvieron. <code>Programmed</code> te dice si la configuración fue efectivamente aplicada. Examina esas tres capas por separado y la velocidad de resolución de problemas aumenta drásticamente.</p>

<h2 id="las-tres-conditions-más-importantes-domínalas-y-estarás-cubierto">Las tres conditions más importantes: domínalas y estarás cubierto</h2>
<h3 id="accepted"><code>Accepted</code></h3>
<p>Esto normalmente indica si el recurso fue aceptado por su padre.
Para una ruta, suele significar:</p>
<ul>
<li>Si se adjuntó correctamente al Gateway/listener previsto</li>
<li>Si las reglas tienen algún conflicto obvio o configuración inválida</li>
</ul>
<p>Si <code>Accepted</code> es <code>False</code>, sospecha primero de:</p>
<ul>
<li><code>parentRefs</code> apuntando al Gateway o listener equivocado</li>
<li>Condiciones de hostname/listener que no coinciden</li>
<li>El listener rechazando este tipo de ruta</li>
<li><code>allowedRoutes</code> bloqueándote</li>
</ul>
<h3 id="resolvedrefs"><code>ResolvedRefs</code></h3>
<p>Esto indica si los objetos referenciados dentro del recurso se resolvieron correctamente.
Por ejemplo:</p>
<ul>
<li>¿Existe el <code>Service</code> referenciado en <code>backendRefs</code>?</li>
<li>¿Puede referenciarse legalmente el <code>Secret</code> en <code>certificateRefs</code>?</li>
<li>¿Está <code>ReferenceGrant</code> correctamente configurado para referencias entre namespaces?</li>
</ul>
<p>Esta condition es extremadamente útil.
Muchos fallos de configuración no son por lógica de enrutamiento incorrecta — son por cosas referenciadas que simplemente no existen, o a las que no tienes permiso de acceder.</p>
<h3 id="programmed"><code>Programmed</code></h3>
<p>Esto normalmente indica si la configuración fue efectivamente aplicada en la capa de implementación.
Piénsalo como:</p>
<ul>
<li>El controlador aceptó la configuración</li>
<li>Y la envió al data plane o la infraestructura</li>
</ul>
<p>Si <code>Accepted</code> ya es <code>True</code> pero el tráfico sigue sin fluir, es el momento en que vale la pena revisar <code>Programmed</code>, la dirección del Gateway, el estado de los listeners y los recursos de Envoy subyacentes.</p>
<blockquote>
<p>💡 Distintos recursos pueden exponer diferentes conjuntos de conditions, pero <code>Accepted</code>, <code>ResolvedRefs</code> y <code>Programmed</code> son el primer grupo sobre el que conviene desarrollar intuición.</p>
</blockquote>

<p>Verifica:</p>
<ul>

</ul>
<p>Si el Gateway no tiene dirección, incluso el YAML de ruta más hermoso es solo escritura creativa.</p>

Si no ha alcanzado a <code>metadata.generation</code>, es posible que el controlador aún no haya procesado tu última versión de configuración.</p>

<p>En este punto ya no estás depurando "¿se aceptó la regla?" — estás verificando si el control plane y el data plane funcionan con normalidad.</p>
<p>Si tienes <code>egctl</code> instalado, puede ayudarte a inspeccionar el estado rápidamente.
Pero incluso sin él, <code>kubectl get/describe -o yaml</code> puede resolver la mayoría de los problemas.</p>
<h2 id="los-cuatro-patrones-de-fallo-más-comunes">Los cuatro patrones de fallo más comunes</h2>
<h3 id="1-la-ruta-es-correcta-pero-no-se-adjuntó-al-listener-previsto">1. La ruta es correcta, pero no se adjuntó al listener previsto</h3>
<p>Síntomas:</p>
<ul>
<li>El YAML parece correcto</li>
<li>Pero el tráfico no está llegando a la regla</li>
</ul>
<p>Comprueba:</p>
<ul>
<li><code>parentRefs.name</code></li>
<li><code>parentRefs.sectionName</code></li>
<li>Si el nombre del listener del Gateway coincide exactamente</li>
</ul>
<p>En configuraciones multi-listener, un solo error tipográfico en <code>sectionName</code> es suficiente para desperdiciar una sesión de debugging entera.</p>
<h3 id="2-accepted-tiene-éxito-pero-resolvedrefs-falla">2. <code>Accepted</code> tiene éxito, pero <code>ResolvedRefs</code> falla</h3>
<p>Esto suele significar que la lógica puede adjuntarse, pero algo referenciado tiene un problema.
Causas más comunes:</p>
<ul>
<li>El Service de backend no existe</li>
<li>El nombre del Secret es incorrecto</li>
<li>Referencia entre namespaces sin autorización</li>
</ul>
<p>Lo más frustrante de este tipo de fallo es que parece que ya casi llegaste — pero en realidad está atascado en la capa de referencia.</p>
<h3 id="3-el-gateway-tiene-listeners-pero-no-tiene-la-dirección-esperada">3. El Gateway tiene listeners pero no tiene la dirección esperada</h3>
<p>Esto aparece con frecuencia en clústeres locales o entornos sin una implementación de <code>LoadBalancer</code>.
No es que Gateway API esté roto — simplemente la infraestructura subyacente no está aprovisionando una dirección externa.</p>
<p>Opciones:</p>
<ul>
<li>Verificar si el clúster tiene capacidad <code>LoadBalancer</code></li>
<li>Usar <code>port-forward</code> para validar el camino de enrutamiento</li>
</ul>
<h3 id="4-el-yaml-surtió-efecto-pero-las-solicitudes-devuelven-404--503">4. El YAML surtió efecto, pero las solicitudes devuelven 404 / 503</h3>
<p>En este punto normalmente no es un solo campo incorrecto — es una cadena rota en algún punto:</p>
<ul>
<li>Header Host incorrecto</li>
<li>El path no coincide con ninguna regla</li>
<li>El Pod de backend no está saludable</li>
<li>El selector del Service no está seleccionando ningún Pod</li>
</ul>
<p>Los problemas de ingreso a veces parecen un fallo del proxy, pero el backend simplemente no estaba listo. No culpes de todo a la capa de proxy — ya tiene suficiente trabajo.</p>
<h2 id="resumen-en-una-línea">Resumen en una línea</h2>
<p>La forma más efectiva de depurar Gateway API no es cambiar el YAML constantemente — es aprender a leer <code>status</code>.
<code>Accepted</code> te dice si se recogió la orden. <code>ResolvedRefs</code> te dice si las referencias se resolvieron. <code>Programmed</code> te dice si la configuración fue efectivamente aplicada. Examina esas tres capas por separado y la velocidad de resolución de problemas aumenta drásticamente.</p>
