1d:T42da,<p>Si has leído los artículos anteriores, la pregunta que probablemente te está bloqueando ahora no es "no entiendo Gateway API" — sino:</p>
<p><strong>"Bien, pero ¿cuál escribo realmente — <code>HTTPRoute</code>, <code>GRPCRoute</code>, <code>TCPRoute</code> o <code>TLSRoute</code>?"</strong></p>
<p>Este artículo existe precisamente para aclarar eso. Guárdalo como referencia de bolsillo. Cuando aparezca un nuevo servicio, consúltalo primero — te ahorrará escribir YAML a ciegas y recibir una lección a través de los condition statuses.</p>
<h2 id="la-conclusión-primero-cuatro-tipos-de-ruta-cuatro-propósitos">La conclusión primero: cuatro tipos de ruta, cuatro propósitos</h2>
<table>
<thead>
<tr>
<th>Tipo de ruta</th>
<th>Capa de tráfico</th>
<th>Qué inspecciona</th>
<th>Ideal para</th>
<th>No apto para</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>HTTPRoute</code></td>
<td>L7 HTTP/HTTPS</td>
<td>host, path, header, query, method</td>
<td>Sitios web, REST APIs, tráfico web general</td>
<td>TCP sin procesar, TLS passthrough</td>
</tr>
<tr>
<td><code>GRPCRoute</code></td>
<td>L7 gRPC</td>
<td>hostname, service, method, header</td>
<td>Enrutamiento por servicio/método gRPC</td>
<td>REST APIs generales, TCP sin procesar</td>
</tr>
<tr>
<td><code>TCPRoute</code></td>
<td>L4 TCP</td>
<td>Información de listener y nivel de conexión</td>
<td>Bases de datos, protocolos TCP personalizados, servicios no HTTP</td>
<td>Escenarios que requieren inspección de path/header</td>
</tr>
<tr>
<td><code>TLSRoute</code></td>
<td>L4/L5 TLS</td>
<td>TLS SNI hostname</td>
<td>TLS passthrough, preservar cifrado extremo a extremo</td>
<td>Necesitar inspeccionar detalles HTTP tras el descifrado</td>
</tr>
</tbody>
</table>
<p>Si quieres una versión ultracorta:</p>
<ul>
<li>Inspeccionar <code>path</code> o <code>header</code> → <code>HTTPRoute</code></li>
<li>Inspeccionar <code>service/method</code> de gRPC → <code>GRPCRoute</code></li>
<li>Solo reenviar conexiones TCP → <code>TCPRoute</code></li>
<li>Sin terminación TLS, solo enrutamiento por SNI → <code>TLSRoute</code></li>
</ul>
<h2 id="decisión-en-tres-pasos-deja-de-adivinar">Decisión en tres pasos: deja de adivinar</h2>
<p>Usa este orden:</p>
<ol>
<li>¿Parseará el Gateway semántica HTTP de este tráfico?</li>
<li>Si es sí, ¿es HTTP/REST normal o gRPC?</li>
<li>Si es no, ¿es TCP sin procesar o TLS passthrough?</li>
</ol>
<p>Resumido:</p>
<ul>
<li>Tiene path/header/method HTTP que inspeccionar → <code>HTTPRoute</code></li>
<li>Tiene service/method de gRPC que inspeccionar → <code>GRPCRoute</code></li>
<li>Sin reglas L7, solo reenvío TCP → <code>TCPRoute</code></li>
<li>Quiere TLS preservado hasta el backend → <code>TLSRoute</code></li>
</ul>
<p>Esta decisión importa mucho. Mucha gente escribe <code>HTTPRoute</code> instintivamente primero y luego se da cuenta a mitad de camino de que está tratando con tráfico de base de datos. Todo el YAML entra en modo "¿qué estoy haciendo?".</p>

<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">apiVersion</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">gateway.networking.k8s.io/v1alpha2</span></span>
<span data-line=""><span style="color:#7EE787">kind</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">TLSRoute</span></span>
<span data-line=""><span style="color:#7EE787">metadata</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">passthrough-route</span></span>
<span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">      sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">tls</span></span>
<span data-line=""><span style="color:#7EE787">  hostnames</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#A5D6FF">"db.example.com"</span></span>
<span data-line=""><span style="color:#7EE787">  rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">db-service</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">5432</span></span></code></pre></figure>
<p>Normalmente se combina con un listener <code>protocol: TLS</code>. El foco no es el descifrado — es el enrutamiento basado en SNI.</p>
<blockquote>
<p>💡 <code>TCPRoute</code> y <code>TLSRoute</code> suelen vivir en el canal experimental según la versión de Gateway API. Verifica la versión del CRD instalada en tu clúster antes de aplicar.</p>
</blockquote>
<h2 id="cuatro-errores-comunes">Cuatro errores comunes</h2>
<h3 id="1-grpc-no-necesita-obligatoriamente-grpcroute">1. gRPC no necesita obligatoriamente <code>GRPCRoute</code></h3>
<p>Si solo necesitas que fluya tráfico gRPC, algunas implementaciones pueden soportarlo vía <code>HTTPRoute</code> ya que gRPC corre sobre HTTP/2.
Pero si quieres hacer matching sobre semántica de service/method de gRPC, <code>GRPCRoute</code> es la opción más correcta y legible.</p>
<h3 id="2-tlsroute-no-es-https-pero-avanzado">2. <code>TLSRoute</code> no es "HTTPS pero avanzado"</h3>
<p>Este es el malentendido más común.</p>
<ul>
<li><code>HTTPS listener + HTTPRoute</code>: el Gateway termina TLS, luego aplica reglas HTTP</li>
<li><code>TLS listener + TLSRoute</code>: el Gateway NO termina TLS, enruta solo basándose en SNI</li>
</ul>
<p>Uno descifra y opera en L7. El otro mantiene el tráfico cifrado y hace passthrough. Mundos completamente distintos.</p>
<h3 id="3-tcproute-no-puede-ver-pathheader">3. <code>TCPRoute</code> no puede ver path/header</h3>
<p>Si tu requisito es:</p>
<ul>
<li><code>/api</code> va a A</li>
<li><code>/admin</code> va a B</li>
</ul>
<p>Ese no es el trabajo de <code>TCPRoute</code>.
<code>TCPRoute</code> no entiende detalles HTTP. Forzar esos requisitos en él es prepararse para la frustración.</p>
<h3 id="4-parentrefssectionname-es-importante">4. <code>parentRefs.sectionName</code> es importante</h3>
<p>Cuando un Gateway tiene múltiples listeners, usa <code>sectionName</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">    sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span></code></pre></figure>
<p>Esto asegura que tu ruta se adjunte exactamente al listener que pretendes.
Sin él, podrías creer que estás reservando la sala VIP y terminar en el salón equivocado.</p>
<h2 id="resumen-en-una-línea">Resumen en una línea</h2>
<p>Primero identifica con qué estás trabajando: <strong>HTTP, gRPC, TCP o TLS passthrough</strong> — luego elige el tipo de ruta correcto.
Acierta con la ruta y el 80% de tu YAML fluye naturalmente. Falla y quedarás atrapado en una batalla con los condition statuses.</p>

2a:T42da,<p>Si has leído los artículos anteriores, la pregunta que probablemente te está bloqueando ahora no es "no entiendo Gateway API" — sino:</p>
<p><strong>"Bien, pero ¿cuál escribo realmente — <code>HTTPRoute</code>, <code>GRPCRoute</code>, <code>TCPRoute</code> o <code>TLSRoute</code>?"</strong></p>
<p>Este artículo existe precisamente para aclarar eso. Guárdalo como referencia de bolsillo. Cuando aparezca un nuevo servicio, consúltalo primero — te ahorrará escribir YAML a ciegas y recibir una lección a través de los condition statuses.</p>
<h2 id="la-conclusión-primero-cuatro-tipos-de-ruta-cuatro-propósitos">La conclusión primero: cuatro tipos de ruta, cuatro propósitos</h2>
<table>
<thead>
<tr>
<th>Tipo de ruta</th>
<th>Capa de tráfico</th>
<th>Qué inspecciona</th>
<th>Ideal para</th>
<th>No apto para</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>HTTPRoute</code></td>
<td>L7 HTTP/HTTPS</td>
<td>host, path, header, query, method</td>
<td>Sitios web, REST APIs, tráfico web general</td>
<td>TCP sin procesar, TLS passthrough</td>
</tr>
<tr>
<td><code>GRPCRoute</code></td>
<td>L7 gRPC</td>
<td>hostname, service, method, header</td>
<td>Enrutamiento por servicio/método gRPC</td>
<td>REST APIs generales, TCP sin procesar</td>
</tr>
<tr>
<td><code>TCPRoute</code></td>
<td>L4 TCP</td>
<td>Información de listener y nivel de conexión</td>
<td>Bases de datos, protocolos TCP personalizados, servicios no HTTP</td>
<td>Escenarios que requieren inspección de path/header</td>
</tr>
<tr>
<td><code>TLSRoute</code></td>
<td>L4/L5 TLS</td>
<td>TLS SNI hostname</td>
<td>TLS passthrough, preservar cifrado extremo a extremo</td>
<td>Necesitar inspeccionar detalles HTTP tras el descifrado</td>
</tr>
</tbody>
</table>
<p>Si quieres una versión ultracorta:</p>
<ul>
<li>Inspeccionar <code>path</code> o <code>header</code> → <code>HTTPRoute</code></li>
<li>Inspeccionar <code>service/method</code> de gRPC → <code>GRPCRoute</code></li>
<li>Solo reenviar conexiones TCP → <code>TCPRoute</code></li>
<li>Sin terminación TLS, solo enrutamiento por SNI → <code>TLSRoute</code></li>
</ul>
<h2 id="decisión-en-tres-pasos-deja-de-adivinar">Decisión en tres pasos: deja de adivinar</h2>
<p>Usa este orden:</p>
<ol>
<li>¿Parseará el Gateway semántica HTTP de este tráfico?</li>
<li>Si es sí, ¿es HTTP/REST normal o gRPC?</li>
<li>Si es no, ¿es TCP sin procesar o TLS passthrough?</li>
</ol>
<p>Resumido:</p>
<ul>
<li>Tiene path/header/method HTTP que inspeccionar → <code>HTTPRoute</code></li>
<li>Tiene service/method de gRPC que inspeccionar → <code>GRPCRoute</code></li>
<li>Sin reglas L7, solo reenvío TCP → <code>TCPRoute</code></li>
<li>Quiere TLS preservado hasta el backend → <code>TLSRoute</code></li>
</ul>
<p>Esta decisión importa mucho. Mucha gente escribe <code>HTTPRoute</code> instintivamente primero y luego se da cuenta a mitad de camino de que está tratando con tráfico de base de datos. Todo el YAML entra en modo "¿qué estoy haciendo?".</p>

<span data-line=""><span style="color:#7EE787">      sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">tls</span></span>
<span data-line=""><span style="color:#7EE787">  hostnames</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#A5D6FF">"db.example.com"</span></span>
<span data-line=""><span style="color:#7EE787">  rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">db-service</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">5432</span></span></code></pre></figure>
<p>Normalmente se combina con un listener <code>protocol: TLS</code>. El foco no es el descifrado — es el enrutamiento basado en SNI.</p>
<blockquote>
<p>💡 <code>TCPRoute</code> y <code>TLSRoute</code> suelen vivir en el canal experimental según la versión de Gateway API. Verifica la versión del CRD instalada en tu clúster antes de aplicar.</p>
</blockquote>
<h2 id="cuatro-errores-comunes">Cuatro errores comunes</h2>
<h3 id="1-grpc-no-necesita-obligatoriamente-grpcroute">1. gRPC no necesita obligatoriamente <code>GRPCRoute</code></h3>
<p>Si solo necesitas que fluya tráfico gRPC, algunas implementaciones pueden soportarlo vía <code>HTTPRoute</code> ya que gRPC corre sobre HTTP/2.
Pero si quieres hacer matching sobre semántica de service/method de gRPC, <code>GRPCRoute</code> es la opción más correcta y legible.</p>
<h3 id="2-tlsroute-no-es-https-pero-avanzado">2. <code>TLSRoute</code> no es "HTTPS pero avanzado"</h3>
<p>Este es el malentendido más común.</p>
<ul>
<li><code>HTTPS listener + HTTPRoute</code>: el Gateway termina TLS, luego aplica reglas HTTP</li>
<li><code>TLS listener + TLSRoute</code>: el Gateway NO termina TLS, enruta solo basándose en SNI</li>
</ul>
<p>Uno descifra y opera en L7. El otro mantiene el tráfico cifrado y hace passthrough. Mundos completamente distintos.</p>
<h3 id="3-tcproute-no-puede-ver-pathheader">3. <code>TCPRoute</code> no puede ver path/header</h3>
<p>Si tu requisito es:</p>
<ul>
<li><code>/api</code> va a A</li>
<li><code>/admin</code> va a B</li>
</ul>
<p>Ese no es el trabajo de <code>TCPRoute</code>.
<code>TCPRoute</code> no entiende detalles HTTP. Forzar esos requisitos en él es prepararse para la frustración.</p>
<h3 id="4-parentrefssectionname-es-importante">4. <code>parentRefs.sectionName</code> es importante</h3>
<p>Cuando un Gateway tiene múltiples listeners, usa <code>sectionName</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">    sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span></code></pre></figure>
<p>Esto asegura que tu ruta se adjunte exactamente al listener que pretendes.
Sin él, podrías creer que estás reservando la sala VIP y terminar en el salón equivocado.</p>
<h2 id="resumen-en-una-línea">Resumen en una línea</h2>
<p>Primero identifica con qué estás trabajando: <strong>HTTP, gRPC, TCP o TLS passthrough</strong> — luego elige el tipo de ruta correcto.
Acierta con la ruta y el 80% de tu YAML fluye naturalmente. Falla y quedarás atrapado en una batalla con los condition statuses.</p>
