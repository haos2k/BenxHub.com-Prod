1c:T3d3f,<p>L'une des plus grandes valeurs de Gateway API n'est pas seulement de produire un YAML plus propre : c'est qu'il répond enfin clairement à une vieille question :</p>
<p><strong>Qui possède la couche d'entrée ? Qui peut changer les routes ? Les namespaces peuvent-ils se référencer entre eux ?</strong></p>
<p>Beaucoup de douleurs autour d'Ingress venaient du fait que tout était emmêlé.
Les équipes plateforme craignaient des changements d'exposition non autorisés. Les équipes applicatives avaient l'impression de devoir ouvrir un ticket juste pour changer un path. Au final, tout le monde se torturait mutuellement dans le YAML.</p>
<p>L'approche de Gateway API consiste à dire clairement :</p>
<ul>
<li>L'entrée plateforme peut être gouvernée indépendamment</li>
<li>Les routes peuvent être déléguées aux équipes applicatives</li>
<li>Les comportements inter-namespace nécessitent une autorisation explicite</li>
</ul>
<p>Cet article explique ce modèle de responsabilité de haut en bas.</p>
<h2 id="commencez-ici--attachement-et-référence-sont-deux-choses-différentes">Commencez ici : attachement et référence sont deux choses différentes</h2>
<p>C'est la distinction la plus souvent confondue.</p>
<h3 id="attachement-dune-route-à-un-gateway--listener">Attachement d'une Route à un Gateway / Listener</h3>
<p>Cela est gouverné par :</p>
<ul>
<li>Les <code>parentRefs</code> de la route</li>
<li>Les <code>allowedRoutes</code> du listener</li>
</ul>
<p>Autrement dit, la possibilité pour une route de s'attacher à un listener n'est pas déterminée par <code>ReferenceGrant</code>, mais par le fait que le listener accepte ou non cet attachement.</p>
<h3 id="références-inter-namespace-à-des-ressources">Références inter-namespace à des ressources</h3>
<p>C'est là que <code>ReferenceGrant</code> entre généralement en jeu.
Par exemple :</p>
<ul>
<li>Un <code>Gateway</code> veut référencer un <code>Secret</code> dans un autre namespace</li>
<li>Un <code>HTTPRoute</code> veut référencer un <code>Service</code> dans un autre namespace</li>
</ul>
<p>La question n'est pas celle de l'attachement, mais plutôt : "le namespace cible vous a-t-il officiellement autorisé à utiliser ses ressources ?"</p>
<p>Beaucoup de gens mélangent ces deux idées et commencent à douter de leur santé mentale. Les règles sont beaucoup moins mystérieuses une fois les rôles séparés.</p>
<h2 id="allowedroutes--décidez-dabord-qui-peut-sattacher"><code>allowedRoutes</code> : décidez d'abord qui peut s'attacher</h2>
<p>Le listener le plus restrictif ressemble à ceci :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">apiVersion</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.networking.k8s.io/v1</span></span>
<span data-line=""><span style="color:#85E89D">kind</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">Gateway</span></span>
<span data-line=""><span style="color:#85E89D">metadata</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">shared-gateway</span></span>
<span data-line=""><span style="color:#85E89D">  namespace</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">infra</span></span>
<span data-line=""><span style="color:#85E89D">spec</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  gatewayClassName</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">eg</span></span>
<span data-line=""><span style="color:#85E89D">  listeners</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">https</span></span>
<span data-line=""><span style="color:#85E89D">      protocol</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">HTTPS</span></span>
<span data-line=""><span style="color:#85E89D">      port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">443</span></span>
<span data-line=""><span style="color:#85E89D">      allowedRoutes</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">        namespaces</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">          from</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">Same</span></span></code></pre></figure>
<p>Cela signifie que seules les routes du namespace <code>infra</code> peuvent s'attacher à ce listener.</p>
<p>Pour autoriser des namespaces d'équipe spécifiques à s'attacher, utilisez <code>Selector</code> :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">allowedRoutes</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  namespaces</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">    from</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">Selector</span></span>
<span data-line=""><span style="color:#85E89D">    selector</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">      matchLabels</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">        shared-gateway-access</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">"true"</span></span></code></pre></figure>
<p>Ce pattern fonctionne bien pour les équipes plateforme.
Vous n'avez pas besoin de tout verrouiller complètement, mais vous n'êtes pas non plus obligé d'ouvrir en <code>from: All</code> et de laisser tout le monde entrer sans limite. Vous pouvez exiger qu'un namespace mérite le droit de s'attacher en portant un label spécifique.</p>
<blockquote>
<p>💡 <code>allowedRoutes</code> s'applique par listener, pas par Gateway. Différents listeners peuvent donc avoir différentes politiques d'accès.</p>
</blockquote>
<h2 id="referencegrant--cest-le-namespace-cible-qui-décide"><code>ReferenceGrant</code> : c'est le namespace cible qui décide</h2>
<p>Si une route ou un gateway veut référencer des ressources dans un autre namespace, le namespace cible doit l'autoriser.</p>
<p>Par exemple, le <code>HTTPRoute</code> d'une équipe applicative veut envoyer du trafic vers un backend dans un namespace partagé :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">apiVersion</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.networking.k8s.io/v1</span></span>
<span data-line=""><span style="color:#85E89D">kind</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">HTTPRoute</span></span>
<span data-line=""><span style="color:#85E89D">metadata</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">app-route</span></span>
<span data-line=""><span style="color:#85E89D">  namespace</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">team-a</span></span>
<span data-line=""><span style="color:#85E89D">spec</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  parentRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">shared-gateway</span></span>
<span data-line=""><span style="color:#85E89D">      namespace</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">infra</span></span>
<span data-line=""><span style="color:#85E89D">      sectionName</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">https</span></span>
<span data-line=""><span style="color:#85E89D">  rules</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">        - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">shared-api</span></span>
<span data-line=""><span style="color:#85E89D">          namespace</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">shared-services</span></span>
<span data-line=""><span style="color:#85E89D">          port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">8080</span></span></code></pre></figure>
<p>Le namespace <code>shared-services</code> doit alors fournir un <code>ReferenceGrant</code> :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">apiVersion</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.networking.k8s.io/v1beta1</span></span>
<span data-line=""><span style="color:#85E89D">kind</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">ReferenceGrant</span></span>
<span data-line=""><span style="color:#85E89D">metadata</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">allow-team-a-route</span></span>
<span data-line=""><span style="color:#85E89D">  namespace</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">shared-services</span></span>
<span data-line=""><span style="color:#85E89D">spec</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  from</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">group</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.networking.k8s.io</span></span>
<span data-line=""><span style="color:#85E89D">      kind</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">HTTPRoute</span></span>
<span data-line=""><span style="color:#85E89D">      namespace</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">team-a</span></span>
<span data-line=""><span style="color:#85E89D">  to</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">group</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">""</span></span>
<span data-line=""><span style="color:#85E89D">      kind</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">Service</span></span></code></pre></figure>
<p>En français simple :</p>
<ul>
<li>Les ressources <code>HTTPRoute</code> dans <code>team-a</code></li>
<li>Sont autorisées à référencer des ressources <code>Service</code> dans <code>shared-services</code></li>
</ul>
<p>Notez bien que l'autorisation est <strong>créée par le namespace cible, pas par la source</strong>.
La source ne peut pas simplement déclarer qu'elle veut un accès : c'est le propriétaire de la ressource qui décide. Cette conception est en réalité très saine, car les propriétaires doivent contrôler qui accède à leurs ressources.</p>
<h2 id="répartition-courante-entre-équipe-plateforme-et-équipes-applicatives">Répartition courante entre équipe plateforme et équipes applicatives</h2>
<p>Le modèle de responsabilité le plus courant ressemble à ceci :</p>
<h3 id="léquipe-plateforme-possède">L'équipe plateforme possède</h3>
<ul>
<li><code>GatewayClass</code></li>
<li><code>Gateway</code></li>
<li><code>Listener</code></li>
<li>La gestion des certificats TLS</li>
<li>Les politiques <code>allowedRoutes</code></li>
</ul>
<h3 id="les-équipes-applicatives-possèdent">Les équipes applicatives possèdent</h3>
<ul>
<li><code>HTTPRoute</code> / <code>GRPCRoute</code> dans leurs propres namespaces</li>
<li>Les services backend</li>
<li>Les ajustements de règles de routage</li>
</ul>
<p>Les bénéfices de cette séparation sont clairs :</p>
<ul>
<li>L'équipe plateforme protège le périmètre d'exposition et la frontière de sécurité de l'entrée</li>
<li>Les équipes applicatives peuvent quand même avancer vite sur leurs propres règles de trafic</li>
<li>Personne n'a besoin de toucher au Gateway partagé simplement pour changer un path</li>
</ul>
<p>Vous pouvez aussi donner tous les droits à un seul groupe, ce n'est pas faux.
Mais dans les grandes équipes, ce modèle a tendance à évoluer vers "tout le monde peut le modifier, donc quand ça casse personne ne sait qui a fait quoi".</p>
<h2 id="conseils-pratiques--comment-éviter-les-catastrophes-multi-tenant">Conseils pratiques : comment éviter les catastrophes multi-tenant</h2>
<p>Habitudes réellement utiles :</p>
<ul>
<li>Les Gateways partagés utilisent par défaut <code>allowedRoutes.namespaces.from: Selector</code></li>
<li>Les conventions de labels de namespace doivent être stables, ne renommez pas <code>team-a</code> en <code>allow-gw</code> le mois prochain</li>
<li>Toutes les références inter-namespace vers backend/Secret passent par <code>ReferenceGrant</code></li>
<li>Les noms de routes doivent indiquer l'équipe ou le service, par exemple <code>team-a-api-route</code></li>
<li>Les listeners partagés doivent toujours utiliser <code>sectionName</code> pour éviter que les routes s'attachent à la mauvaise entrée</li>
</ul>
<p>Un principe à garder :</p>
<p><strong>Si vous pouvez faire respecter une frontière au niveau de la couche d'entrée, ne comptez pas uniquement sur la documentation et l'espoir que chacun s'auto-discipline.</strong></p>
<p>En ingénierie, le processus l'emporte sur l'accord verbal. On dirait un conseil de quelqu'un de beaucoup plus âgé, mais c'est sincèrement utile.</p>
<h2 id="résumé-en-une-ligne">Résumé en une ligne</h2>
<p>Dans Gateway API, <code>allowedRoutes</code> contrôle "qui peut entrer", et <code>ReferenceGrant</code> contrôle "à quoi ces personnes peuvent accéder une fois dedans".
Gardez bien ces deux idées distinctes, et les scénarios multi-namespace / multi-équipes deviennent beaucoup plus gérables.</p>

28:T3d3f,<p>L'une des plus grandes valeurs de Gateway API n'est pas seulement de produire un YAML plus propre : c'est qu'il répond enfin clairement à une vieille question :</p>
<p><strong>Qui possède la couche d'entrée ? Qui peut changer les routes ? Les namespaces peuvent-ils se référencer entre eux ?</strong></p>
<p>Beaucoup de douleurs autour d'Ingress venaient du fait que tout était emmêlé.
Les équipes plateforme craignaient des changements d'exposition non autorisés. Les équipes applicatives avaient l'impression de devoir ouvrir un ticket juste pour changer un path. Au final, tout le monde se torturait mutuellement dans le YAML.</p>
<p>L'approche de Gateway API consiste à dire clairement :</p>
<ul>
<li>L'entrée plateforme peut être gouvernée indépendamment</li>
<li>Les routes peuvent être déléguées aux équipes applicatives</li>
<li>Les comportements inter-namespace nécessitent une autorisation explicite</li>
</ul>
<p>Cet article explique ce modèle de responsabilité de haut en bas.</p>
<h2 id="commencez-ici--attachement-et-référence-sont-deux-choses-différentes">Commencez ici : attachement et référence sont deux choses différentes</h2>
<p>C'est la distinction la plus souvent confondue.</p>
<h3 id="attachement-dune-route-à-un-gateway--listener">Attachement d'une Route à un Gateway / Listener</h3>
<p>Cela est gouverné par :</p>
<ul>
<li>Les <code>parentRefs</code> de la route</li>
<li>Les <code>allowedRoutes</code> du listener</li>
</ul>
<p>Autrement dit, la possibilité pour une route de s'attacher à un listener n'est pas déterminée par <code>ReferenceGrant</code>, mais par le fait que le listener accepte ou non cet attachement.</p>
<h3 id="références-inter-namespace-à-des-ressources">Références inter-namespace à des ressources</h3>
<p>C'est là que <code>ReferenceGrant</code> entre généralement en jeu.
Par exemple :</p>
<ul>
<li>Un <code>Gateway</code> veut référencer un <code>Secret</code> dans un autre namespace</li>
<li>Un <code>HTTPRoute</code> veut référencer un <code>Service</code> dans un autre namespace</li>
</ul>
<p>La question n'est pas celle de l'attachement, mais plutôt : "le namespace cible vous a-t-il officiellement autorisé à utiliser ses ressources ?"</p>
<p>Beaucoup de gens mélangent ces deux idées et commencent à douter de leur santé mentale. Les règles sont beaucoup moins mystérieuses une fois les rôles séparés.</p>
<h2 id="allowedroutes--décidez-dabord-qui-peut-sattacher"><code>allowedRoutes</code> : décidez d'abord qui peut s'attacher</h2>
<p>Le listener le plus restrictif ressemble à ceci :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">apiVersion</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.networking.k8s.io/v1</span></span>
<span data-line=""><span style="color:#85E89D">kind</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">Gateway</span></span>
<span data-line=""><span style="color:#85E89D">metadata</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">shared-gateway</span></span>
<span data-line=""><span style="color:#85E89D">  namespace</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">infra</span></span>
<span data-line=""><span style="color:#85E89D">spec</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  gatewayClassName</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">eg</span></span>
<span data-line=""><span style="color:#85E89D">  listeners</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">https</span></span>
<span data-line=""><span style="color:#85E89D">      protocol</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">HTTPS</span></span>
<span data-line=""><span style="color:#85E89D">      port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">443</span></span>
<span data-line=""><span style="color:#85E89D">      allowedRoutes</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">        namespaces</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">          from</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">Same</span></span></code></pre></figure>
<p>Cela signifie que seules les routes du namespace <code>infra</code> peuvent s'attacher à ce listener.</p>
<p>Pour autoriser des namespaces d'équipe spécifiques à s'attacher, utilisez <code>Selector</code> :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">allowedRoutes</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  namespaces</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">    from</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">Selector</span></span>
<span data-line=""><span style="color:#85E89D">    selector</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">      matchLabels</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">        shared-gateway-access</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">"true"</span></span></code></pre></figure>
<p>Ce pattern fonctionne bien pour les équipes plateforme.
Vous n'avez pas besoin de tout verrouiller complètement, mais vous n'êtes pas non plus obligé d'ouvrir en <code>from: All</code> et de laisser tout le monde entrer sans limite. Vous pouvez exiger qu'un namespace mérite le droit de s'attacher en portant un label spécifique.</p>
<blockquote>
<p>💡 <code>allowedRoutes</code> s'applique par listener, pas par Gateway. Différents listeners peuvent donc avoir différentes politiques d'accès.</p>
</blockquote>
<h2 id="referencegrant--cest-le-namespace-cible-qui-décide"><code>ReferenceGrant</code> : c'est le namespace cible qui décide</h2>
<p>Si une route ou un gateway veut référencer des ressources dans un autre namespace, le namespace cible doit l'autoriser.</p>
<p>Par exemple, le <code>HTTPRoute</code> d'une équipe applicative veut envoyer du trafic vers un backend dans un namespace partagé :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">apiVersion</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.networking.k8s.io/v1</span></span>

<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">shared-gateway</span></span>
<span data-line=""><span style="color:#85E89D">      namespace</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">infra</span></span>

<span data-line=""><span style="color:#85E89D">  rules</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>

<span data-line=""><span style="color:#85E89D">          namespace</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">shared-services</span></span>
<span data-line=""><span style="color:#85E89D">          port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">8080</span></span></code></pre></figure>
<p>Le namespace <code>shared-services</code> doit alors fournir un <code>ReferenceGrant</code> :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">apiVersion</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.networking.k8s.io/v1beta1</span></span>
