b:T3a23,<p>Le scénario d'ingénierie le plus pénible n'est pas un message d'erreur, c'est plutôt :</p>
<p><strong>Vous avez appliqué le YAML, <code>kubectl apply</code> a réussi, mais le trafic ne circule toujours pas.</strong></p>
<p>Si, à ce stade, vous ne faites que fixer <code>spec</code>, vous finirez par avoir l'impression de lire dans des feuilles de thé.
La vraie information de diagnostic dans Gateway API vit dans <code>status</code>.</p>
<p>Cet article a un seul objectif : vous donner le chemin de débogage le plus court possible. Quand un <code>Gateway</code>, <code>HTTPRoute</code> ou <code>Listener</code> ne prend pas effet, vous saurez où regarder d'abord, au lieu de commencer immédiatement à douter du sens de l'univers.</p>
<h2 id="commencez-ici--déboguez-en-lisant-status-pas-en-changeant-spec">Commencez ici : déboguez en lisant <code>status</code>, pas en changeant <code>spec</code></h2>
<p>Les commandes les plus utiles :</p>

<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> describe</span><span style="color:#A5D6FF"> gateway</span><span style="color:#FF7B72"> &#x3C;</span><span style="color:#A5D6FF">nam</span><span style="color:#E6EDF3">e</span><span style="color:#FF7B72">></span></span>

<p>Le but n'est pas de relire le YAML cent fois de plus, mais de vérifier si le contrôleur a réellement accepté votre configuration.</p>
<p>Voyez <code>status</code> comme le relevé de notes d'un examen :</p>
<ul>
<li><code>spec</code> est la copie que vous avez rendue</li>
<li><code>status</code> est le résultat corrigé par le système</li>
</ul>
<p>Ne regarder que ce que vous avez soumis, sans jamais vérifier la note, ce n'est pas du débogage, c'est juste du réconfort émotionnel.</p>
<h2 id="les-trois-conditions-les-plus-importantes--maîtrisez-les-et-vous-êtes-couvert">Les trois conditions les plus importantes : maîtrisez-les et vous êtes couvert</h2>
<h3 id="accepted"><code>Accepted</code></h3>
<p>Cela indique généralement si la ressource a été acceptée par son parent.
Pour une route, cela signifie souvent :</p>
<ul>
<li>Si elle s'est correctement attachée au Gateway/listener visé</li>
<li>Si les règles comportent des conflits évidents ou une configuration invalide</li>
</ul>
<p>Si <code>Accepted</code> vaut <code>False</code>, soupçonnez d'abord :</p>
<ul>
<li>Des <code>parentRefs</code> pointant vers le mauvais Gateway ou listener</li>
<li>Des conditions de hostname/listener qui ne correspondent pas</li>
<li>Un listener qui rejette ce type de route</li>
<li><code>allowedRoutes</code> qui vous bloque</li>
</ul>
<h3 id="resolvedrefs"><code>ResolvedRefs</code></h3>
<p>Cela indique si les objets référencés à l'intérieur de la ressource ont bien été résolus.
Par exemple :</p>
<ul>
<li>Le <code>Service</code> référencé dans <code>backendRefs</code> existe-t-il ?</li>
<li>Le <code>Secret</code> dans <code>certificateRefs</code> peut-il être référencé légalement ?</li>
<li><code>ReferenceGrant</code> est-il bien configuré pour les références inter-namespace ?</li>
</ul>
<p>Cette condition est extrêmement utile.
Beaucoup d'échecs de configuration ne viennent pas d'une logique de routage erronée, mais d'éléments référencés qui n'existent tout simplement pas, ou auxquels vous n'avez pas le droit d'accéder.</p>
<h3 id="programmed"><code>Programmed</code></h3>
<p>Cela indique généralement si la configuration a réellement été appliquée au niveau de l'implémentation.
Pensez-y comme ceci :</p>
<ul>
<li>Le contrôleur a accepté la configuration</li>
<li>Et il l'a poussée dans le plan de données ou l'infrastructure</li>
</ul>
<p>Si <code>Accepted</code> vaut déjà <code>True</code> mais que le trafic ne circule toujours pas, c'est le moment où il devient utile de vérifier <code>Programmed</code>, l'adresse du Gateway, le status des listeners et les ressources Envoy sous-jacentes.</p>
<blockquote>
<p>💡 Différentes ressources peuvent exposer des ensembles de conditions différents, mais <code>Accepted</code>, <code>ResolvedRefs</code> et <code>Programmed</code> sont le premier trio sur lequel construire votre intuition.</p>
</blockquote>
<h2 id="le-flux-de-débogage-le-plus-court--cet-ordre-fonctionne-généralement">Le flux de débogage le plus court : cet ordre fonctionne généralement</h2>
<h3 id="étape-1--vérifier-que-le-gateway-tourne-réellement">Étape 1 : vérifier que le Gateway tourne réellement</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#A5D6FF"> eg</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span></code></pre></figure>
<p>Vérifiez :</p>
<ul>
<li><code>status.addresses</code> contient-il une valeur ?</li>
<li>Y a-t-il des conditions anormales sur les listeners ?</li>
<li>Le hostname/protocole/port du listener correspond-il à ce que vous attendez ?</li>
</ul>
<p>Si le Gateway n'a pas d'adresse, même le plus beau YAML de route n'est que de l'écriture créative.</p>
<h3 id="étape-2--vérifier-que-la-route-sest-bien-attachée">Étape 2 : vérifier que la Route s'est bien attachée</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#A5D6FF"> app-route</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span></code></pre></figure>
<p>Priorité à :</p>
<ul>
<li><code>status.parents</code></li>
<li><code>Accepted</code></li>
<li><code>ResolvedRefs</code></li>
<li><code>observedGeneration</code></li>
</ul>
<p><code>observedGeneration</code> mérite qu'on y prête attention.
S'il n'a pas rattrapé <code>metadata.generation</code>, le contrôleur n'a peut-être pas encore traité la dernière version de votre configuration.</p>
<h3 id="étape-3--vérifier-que-les-ressources-référencées-existent-vraiment">Étape 3 : vérifier que les ressources référencées existent vraiment</h3>
<p>Cette étape est plus souvent sautée que toutes les autres :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> svc</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> secret</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> referencegrant</span><span style="color:#79C0FF"> -A</span></span></code></pre></figure>
<p>Problèmes courants :</p>
<ul>
<li>Le nom du service backend est faux</li>
<li>Le port est faux</li>
<li>Le Secret n'est pas dans le namespace que vous imaginez</li>
<li>La référence inter-namespace n'a pas de <code>ReferenceGrant</code></li>
</ul>
<p>Si <code>ResolvedRefs</code> vaut <code>False</code>, remontez la piste par ici.</p>
<h3 id="étape-4--vérifier-le-plan-de-données-et-le-contrôleur">Étape 4 : vérifier le plan de données et le contrôleur</h3>
<p>Si les status du Gateway et de la Route semblent globalement corrects mais que le trafic ne circule toujours pas, allez plus loin :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> pods</span><span style="color:#79C0FF"> -n</span><span style="color:#A5D6FF"> envoy-gateway-system</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> logs</span><span style="color:#79C0FF"> -n</span><span style="color:#A5D6FF"> envoy-gateway-system</span><span style="color:#A5D6FF"> deployment/envoy-gateway</span></span></code></pre></figure>
<p>À ce stade, vous ne déboguez plus "la règle a-t-elle été acceptée", vous vérifiez si le plan de contrôle et le plan de données fonctionnent normalement.</p>
<p>Si vous avez <code>egctl</code> installé, il peut vous aider à inspecter rapidement le status.
Mais même sans lui, <code>kubectl get/describe -o yaml</code> permet de résoudre la plupart des problèmes.</p>
<h2 id="quatre-patterns-déchec-les-plus-courants">Quatre patterns d'échec les plus courants</h2>
<h3 id="1-la-route-est-correcte-mais-ne-sest-pas-attachée-au-listener-voulu">1. La route est correcte, mais ne s'est pas attachée au listener voulu</h3>
<p>Symptômes :</p>
<ul>
<li>Le YAML semble correct</li>
<li>Mais le trafic ne touche pas la règle</li>
</ul>
<p>Vérifiez :</p>
<ul>
<li><code>parentRefs.name</code></li>
<li><code>parentRefs.sectionName</code></li>
<li>Si le nom du listener du Gateway correspond exactement</li>
</ul>
<p>Dans les setups multi-listeners, une simple faute de frappe dans <code>sectionName</code> suffit pour gaspiller toute une session de débogage.</p>
<h3 id="2-accepted-réussit-mais-resolvedrefs-échoue">2. <code>Accepted</code> réussit, mais <code>ResolvedRefs</code> échoue</h3>
<p>Cela signifie généralement que la logique d'attachement est bonne, mais qu'un élément référencé pose problème.
Causes les plus fréquentes :</p>
<ul>
<li>Le Service backend n'existe pas</li>
<li>Le nom du Secret est incorrect</li>
<li>Référence inter-namespace sans autorisation</li>
</ul>
<p>Ce type d'échec est particulièrement frustrant parce qu'il donne l'impression que vous êtes presque arrivé, alors qu'en réalité vous êtes encore bloqué à l'étape des références.</p>
<h3 id="3-le-gateway-a-des-listeners-mais-pas-ladresse-attendue">3. Le Gateway a des listeners, mais pas l'adresse attendue</h3>
<p>Cela apparaît fréquemment dans les clusters locaux ou dans les environnements sans implémentation <code>LoadBalancer</code>.
Ce n'est pas que Gateway API soit cassé, c'est simplement que l'infrastructure sous-jacente ne provisionne pas d'adresse externe.</p>
<p>Options :</p>
<ul>
<li>Vérifier si le cluster possède la capacité <code>LoadBalancer</code></li>
<li>Utiliser <code>port-forward</code> pour valider le chemin de routage</li>
</ul>
<h3 id="4-le-yaml-a-pris-effet-mais-les-requêtes-renvoient-404--503">4. Le YAML a pris effet, mais les requêtes renvoient 404 / 503</h3>
<p>À ce stade, ce n'est généralement pas un seul champ erroné, mais une chaîne cassée quelque part :</p>
<ul>
<li>Mauvais header Host</li>
<li>Le path ne matche aucune règle</li>
<li>Le Pod backend n'est pas sain</li>
<li>Le selector du Service ne sélectionne aucun Pod</li>
</ul>
<p>Les problèmes d'entrée ressemblent parfois à un échec du proxy, alors que le backend n'était tout simplement pas prêt. N'accusez pas tout de suite la couche proxy, elle en a déjà assez sur les épaules.</p>
<h2 id="résumé-en-une-ligne">Résumé en une ligne</h2>
<p>La manière la plus efficace de déboguer Gateway API n'est pas de modifier sans cesse le YAML, mais d'apprendre à lire <code>status</code>.
<code>Accepted</code> vous dit si la demande a été prise en compte. <code>ResolvedRefs</code> vous dit si les références ont été résolues. <code>Programmed</code> vous dit si la configuration a réellement été appliquée. Examinez ces trois couches séparément et la vitesse de dépannage augmentera fortement.</p>

d:T3a23,<p>Le scénario d'ingénierie le plus pénible n'est pas un message d'erreur, c'est plutôt :</p>
<p><strong>Vous avez appliqué le YAML, <code>kubectl apply</code> a réussi, mais le trafic ne circule toujours pas.</strong></p>
<p>Si, à ce stade, vous ne faites que fixer <code>spec</code>, vous finirez par avoir l'impression de lire dans des feuilles de thé.
La vraie information de diagnostic dans Gateway API vit dans <code>status</code>.</p>
<p>Cet article a un seul objectif : vous donner le chemin de débogage le plus court possible. Quand un <code>Gateway</code>, <code>HTTPRoute</code> ou <code>Listener</code> ne prend pas effet, vous saurez où regarder d'abord, au lieu de commencer immédiatement à douter du sens de l'univers.</p>
<h2 id="commencez-ici--déboguez-en-lisant-status-pas-en-changeant-spec">Commencez ici : déboguez en lisant <code>status</code>, pas en changeant <code>spec</code></h2>

<p>Le but n'est pas de relire le YAML cent fois de plus, mais de vérifier si le contrôleur a réellement accepté votre configuration.</p>
<p>Voyez <code>status</code> comme le relevé de notes d'un examen :</p>
<ul>
<li><code>spec</code> est la copie que vous avez rendue</li>
<li><code>status</code> est le résultat corrigé par le système</li>
</ul>
<p>Ne regarder que ce que vous avez soumis, sans jamais vérifier la note, ce n'est pas du débogage, c'est juste du réconfort émotionnel.</p>
<h2 id="les-trois-conditions-les-plus-importantes--maîtrisez-les-et-vous-êtes-couvert">Les trois conditions les plus importantes : maîtrisez-les et vous êtes couvert</h2>
<h3 id="accepted"><code>Accepted</code></h3>
<p>Cela indique généralement si la ressource a été acceptée par son parent.
Pour une route, cela signifie souvent :</p>
<ul>
<li>Si elle s'est correctement attachée au Gateway/listener visé</li>
<li>Si les règles comportent des conflits évidents ou une configuration invalide</li>
</ul>
<p>Si <code>Accepted</code> vaut <code>False</code>, soupçonnez d'abord :</p>
<ul>
<li>Des <code>parentRefs</code> pointant vers le mauvais Gateway ou listener</li>
<li>Des conditions de hostname/listener qui ne correspondent pas</li>
<li>Un listener qui rejette ce type de route</li>
<li><code>allowedRoutes</code> qui vous bloque</li>
</ul>
<h3 id="resolvedrefs"><code>ResolvedRefs</code></h3>
<p>Cela indique si les objets référencés à l'intérieur de la ressource ont bien été résolus.
Par exemple :</p>
<ul>
<li>Le <code>Service</code> référencé dans <code>backendRefs</code> existe-t-il ?</li>
<li>Le <code>Secret</code> dans <code>certificateRefs</code> peut-il être référencé légalement ?</li>
<li><code>ReferenceGrant</code> est-il bien configuré pour les références inter-namespace ?</li>
</ul>
<p>Cette condition est extrêmement utile.
Beaucoup d'échecs de configuration ne viennent pas d'une logique de routage erronée, mais d'éléments référencés qui n'existent tout simplement pas, ou auxquels vous n'avez pas le droit d'accéder.</p>
<h3 id="programmed"><code>Programmed</code></h3>
<p>Cela indique généralement si la configuration a réellement été appliquée au niveau de l'implémentation.
Pensez-y comme ceci :</p>
<ul>
<li>Le contrôleur a accepté la configuration</li>
<li>Et il l'a poussée dans le plan de données ou l'infrastructure</li>
</ul>
<p>Si <code>Accepted</code> vaut déjà <code>True</code> mais que le trafic ne circule toujours pas, c'est le moment où il devient utile de vérifier <code>Programmed</code>, l'adresse du Gateway, le status des listeners et les ressources Envoy sous-jacentes.</p>
<blockquote>
<p>💡 Différentes ressources peuvent exposer des ensembles de conditions différents, mais <code>Accepted</code>, <code>ResolvedRefs</code> et <code>Programmed</code> sont le premier trio sur lequel construire votre intuition.</p>
</blockquote>
<h2 id="le-flux-de-débogage-le-plus-court--cet-ordre-fonctionne-généralement">Le flux de débogage le plus court : cet ordre fonctionne généralement</h2>
<h3 id="étape-1--vérifier-que-le-gateway-tourne-réellement">Étape 1 : vérifier que le Gateway tourne réellement</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#79C0FF"> -A</span></span>

<p>Vérifiez :</p>
<ul>
<li><code>status.addresses</code> contient-il une valeur ?</li>
<li>Y a-t-il des conditions anormales sur les listeners ?</li>
<li>Le hostname/protocole/port du listener correspond-il à ce que vous attendez ?</li>
</ul>
<p>Si le Gateway n'a pas d'adresse, même le plus beau YAML de route n'est que de l'écriture créative.</p>
<h3 id="étape-2--vérifier-que-la-route-sest-bien-attachée">Étape 2 : vérifier que la Route s'est bien attachée</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#A5D6FF"> app-route</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span></code></pre></figure>
<p>Priorité à :</p>
<ul>
<li><code>status.parents</code></li>
<li><code>Accepted</code></li>
<li><code>ResolvedRefs</code></li>
<li><code>observedGeneration</code></li>
</ul>
<p><code>observedGeneration</code> mérite qu'on y prête attention.
S'il n'a pas rattrapé <code>metadata.generation</code>, le contrôleur n'a peut-être pas encore traité la dernière version de votre configuration.</p>
<h3 id="étape-3--vérifier-que-les-ressources-référencées-existent-vraiment">Étape 3 : vérifier que les ressources référencées existent vraiment</h3>
<p>Cette étape est plus souvent sautée que toutes les autres :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> svc</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> secret</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> referencegrant</span><span style="color:#79C0FF"> -A</span></span></code></pre></figure>
<p>Problèmes courants :</p>
<ul>
<li>Le nom du service backend est faux</li>
<li>Le port est faux</li>
<li>Le Secret n'est pas dans le namespace que vous imaginez</li>
<li>La référence inter-namespace n'a pas de <code>ReferenceGrant</code></li>
</ul>
<p>Si <code>ResolvedRefs</code> vaut <code>False</code>, remontez la piste par ici.</p>
<h3 id="étape-4--vérifier-le-plan-de-données-et-le-contrôleur">Étape 4 : vérifier le plan de données et le contrôleur</h3>
<p>Si les status du Gateway et de la Route semblent globalement corrects mais que le trafic ne circule toujours pas, allez plus loin :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> pods</span><span style="color:#79C0FF"> -n</span><span style="color:#A5D6FF"> envoy-gateway-system</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> logs</span><span style="color:#79C0FF"> -n</span><span style="color:#A5D6FF"> envoy-gateway-system</span><span style="color:#A5D6FF"> deployment/envoy-gateway</span></span></code></pre></figure>
<p>À ce stade, vous ne déboguez plus "la règle a-t-elle été acceptée", vous vérifiez si le plan de contrôle et le plan de données fonctionnent normalement.</p>
<p>Si vous avez <code>egctl</code> installé, il peut vous aider à inspecter rapidement le status.
Mais même sans lui, <code>kubectl get/describe -o yaml</code> permet de résoudre la plupart des problèmes.</p>
<h2 id="quatre-patterns-déchec-les-plus-courants">Quatre patterns d'échec les plus courants</h2>
<h3 id="1-la-route-est-correcte-mais-ne-sest-pas-attachée-au-listener-voulu">1. La route est correcte, mais ne s'est pas attachée au listener voulu</h3>
<p>Symptômes :</p>
<ul>
<li>Le YAML semble correct</li>
<li>Mais le trafic ne touche pas la règle</li>
</ul>
<p>Vérifiez :</p>
<ul>
<li><code>parentRefs.name</code></li>
<li><code>parentRefs.sectionName</code></li>
<li>Si le nom du listener du Gateway correspond exactement</li>
</ul>
<p>Dans les setups multi-listeners, une simple faute de frappe dans <code>sectionName</code> suffit pour gaspiller toute une session de débogage.</p>
<h3 id="2-accepted-réussit-mais-resolvedrefs-échoue">2. <code>Accepted</code> réussit, mais <code>ResolvedRefs</code> échoue</h3>
<p>Cela signifie généralement que la logique d'attachement est bonne, mais qu'un élément référencé pose problème.
Causes les plus fréquentes :</p>
<ul>
<li>Le Service backend n'existe pas</li>
<li>Le nom du Secret est incorrect</li>
<li>Référence inter-namespace sans autorisation</li>
</ul>
<p>Ce type d'échec est particulièrement frustrant parce qu'il donne l'impression que vous êtes presque arrivé, alors qu'en réalité vous êtes encore bloqué à l'étape des références.</p>
<h3 id="3-le-gateway-a-des-listeners-mais-pas-ladresse-attendue">3. Le Gateway a des listeners, mais pas l'adresse attendue</h3>
<p>Cela apparaît fréquemment dans les clusters locaux ou dans les environnements sans implémentation <code>LoadBalancer</code>.
Ce n'est pas que Gateway API soit cassé, c'est simplement que l'infrastructure sous-jacente ne provisionne pas d'adresse externe.</p>
<p>Options :</p>
<ul>
<li>Vérifier si le cluster possède la capacité <code>LoadBalancer</code></li>
<li>Utiliser <code>port-forward</code> pour valider le chemin de routage</li>
</ul>
<h3 id="4-le-yaml-a-pris-effet-mais-les-requêtes-renvoient-404--503">4. Le YAML a pris effet, mais les requêtes renvoient 404 / 503</h3>
<p>À ce stade, ce n'est généralement pas un seul champ erroné, mais une chaîne cassée quelque part :</p>
<ul>
<li>Mauvais header Host</li>
<li>Le path ne matche aucune règle</li>
<li>Le Pod backend n'est pas sain</li>
<li>Le selector du Service ne sélectionne aucun Pod</li>
</ul>
<p>Les problèmes d'entrée ressemblent parfois à un échec du proxy, alors que le backend n'était tout simplement pas prêt. N'accusez pas tout de suite la couche proxy, elle en a déjà assez sur les épaules.</p>
<h2 id="résumé-en-une-ligne">Résumé en une ligne</h2>
<p>La manière la plus efficace de déboguer Gateway API n'est pas de modifier sans cesse le YAML, mais d'apprendre à lire <code>status</code>.
<code>Accepted</code> vous dit si la demande a été prise en compte. <code>ResolvedRefs</code> vous dit si les références ont été résolues. <code>Programmed</code> vous dit si la configuration a réellement été appliquée. Examinez ces trois couches séparément et la vitesse de dépannage augmentera fortement.</p>
