1b:T411f,<p>Si vous avez déjà géré du trafic externe sur Kubernetes, il y a de fortes chances que vous ayez commencé par <code>Ingress</code>. Ça fonctionne, et pour beaucoup de scénarios c'est sincèrement suffisant. Mais dès que les exigences deviennent plus complexes — plusieurs listeners, gouvernance multi-équipes, gRPC, TCP, TLS passthrough, politiques de trafic plus fines — vous finissez inévitablement dans une situation où "tenir le tout en vie avec des annotations" devient la norme. Le YAML commence à ressembler à une incantation, et les personnes qui le maintiennent ont l'impression de briser un sceau.</p>
<p>C'est là que <code>Gateway API + Envoy Gateway</code> entre en jeu : c'est le nouvel outillage. Il ne rend pas les choses plus compliquées ; il sépare proprement des responsabilités qui étaient auparavant entremêlées, ce qui rend beaucoup plus facile de raisonner sur le trafic entrant, les règles de routage, les paramètres TLS, les types de protocole et la répartition des responsabilités entre équipes.</p>
<h2 id="quest-ce-que-cest-exactement">Qu'est-ce que c'est, exactement</h2>
<p>Disons-le clairement en une phrase :</p>
<ul>
<li><code>Envoy Proxy</code> : le plan de données qui reçoit réellement le trafic et transfère les requêtes, aussi appelé Gateway Proxy</li>
<li><code>Envoy Gateway</code> : le plan de contrôle qui gère Envoy Proxy pour vous</li>
<li><code>Gateway API</code> : l'interface standard que vous utilisez dans Kubernetes pour déclarer les règles de trafic</li>
</ul>
<p>Pensez-y comme ceci :</p>
<ul>
<li><code>Gateway API</code> est l'endroit où vous écrivez vos besoins</li>
<li><code>Envoy Gateway</code> est le responsable qui traduit et délègue</li>
<li><code>Envoy Proxy</code> est le vrai gardien posté à la porte</li>
</ul>
<p>L'avantage de cette séparation, c'est que vous n'avez pas besoin de fabriquer à la main une configuration Envoy bas niveau, ni de mémoriser toutes les annotations privées de différents contrôleurs. Vous déclarez des ressources Kubernetes, et Envoy Gateway les traduit en une configuration que Envoy Proxy peut réellement exécuter.</p>
<h2 id="gateway-vs-ingress--quelle-différence">Gateway vs Ingress : quelle différence</h2>
<p>La réponse courte : <strong>Ingress n'est pas obsolète, mais Gateway API est mieux adaptée aux systèmes de taille moyenne à grande qui ont besoin de plus de gouvernance.</strong></p>

<p>Si vos besoins sont simplement :</p>
<ul>
<li>Un seul site web ou une API simple</li>
<li>Un routage basique par chemin/hôte</li>
<li>Une petite équipe</li>
</ul>
<p>Alors Ingress reste parfaitement acceptable. Mais si vos besoins commencent à inclure :</p>
<ul>
<li>Une même entrée qui sert plusieurs protocoles</li>
<li>Plusieurs listeners, domaines ou certificats</li>
<li>HTTP et gRPC qui coexistent</li>
<li>Une séparation entre l'entrée plateforme et les autorisations de routage applicatif</li>
<li>Une configuration qui ressemble à une vraie API, pas à une liste de souhaits via annotations</li>
</ul>
<p>Alors Gateway API commencera à devenir très attirante.</p>
<h2 id="pourquoi-ne-pas-simplement-utiliser-ingress">Pourquoi ne pas simplement utiliser Ingress</h2>
<p>L'objectif officiel de Gateway API est de résoudre plusieurs points de douleur fréquents avec Ingress à grande échelle :</p>
<ul>
<li><strong>Meilleure expressivité</strong> : le routage, TLS, les politiques de trafic et les types de protocole sont définis plus clairement</li>
<li><strong>Meilleure portabilité</strong> : moins de dépendance aux annotations privées propres aux contrôleurs</li>
<li><strong>Séparation des rôles plus naturelle</strong> : les équipes plateforme possèdent l'entrée, les équipes applicatives possèdent les routes</li>
</ul>
<p>Par exemple, les configurations Ingress ressemblent souvent à ceci :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">metadata</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  annotations</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/rewrite-target</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">/</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/auth-type</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">basic</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/ssl-redirect</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">"true"</span></span></code></pre></figure>
<p>Ce n'est pas que ça ne marche pas, mais quand les besoins grossissent, les annotations deviennent facilement une sorte de magie noire YAML mystérieuse. Gateway API fait remonter ces besoins dans de vrais champs. Ça se lit comme une "configuration", pas comme une "liste de souhaits".</p>
<h2 id="la-structure-en-couches">La structure en couches</h2>
<p>La page de concepts officielle découpe Envoy Gateway en trois couches ; cela vaut la peine de les mémoriser comme carte mentale :</p>
<ul>
<li><strong>User Configuration</strong> : les ressources <code>Gateway API</code> et les CRD d'extension Envoy Gateway que vous écrivez</li>
<li><strong>Envoy Gateway Controller</strong> : lit ces ressources et les traduit en configuration exécutable</li>
<li><strong>Envoy Proxy</strong> : le plan de données qui gère réellement le trafic en direct</li>
</ul>
<p>En pratique, vous passerez l'essentiel de votre temps à modifier la "couche déclarative", pas à vous connecter en SSH sur des instances de proxy pour ajuster une config bas niveau. C'est toute l'élégance d'une approche native Kubernetes.</p>

<h2 id="les-ressources-principales-que-vous-allez-rencontrer">Les ressources principales que vous allez rencontrer</h2>
<p>Les débutants trébuchent souvent parce qu'ils supposent que Gateway API ne contient que <code>Gateway</code> et <code>HTTPRoute</code>. En réalité, c'est toute une famille de ressources.</p>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>Définit "quelle implémentation de Gateway utiliser dans ce cluster".
Pour Envoy Gateway, l'essentiel est que <code>controllerName</code> pointe vers le bon contrôleur.</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>Définit "à quoi ressemble l'entrée".
Par exemple : quels ports ouvrir, quels protocoles écouter, comment le TLS est rattaché, quelles routes sont autorisées.</p>
<h3 id="listener"><code>Listener</code></h3>
<p><code>Listener</code> est l'une des unités les plus importantes à l'intérieur d'un <code>Gateway</code>.
Pensez-y comme un point d'entrée exposé vers l'extérieur sur le Gateway ; chaque point définit :</p>
<ul>
<li>port</li>
<li>protocol</li>
<li>hostname</li>
<li>TLS config</li>
<li><code>allowedRoutes</code></li>
</ul>
<p>Beaucoup de gens voient <code>Gateway</code> comme une boîte noire, mais ce qui détermine réellement le comportement de l'entrée, c'est chaque <code>listener</code> individuel qu'il contient.</p>
<h3 id="la-famille-route">La famille Route</h3>
<ul>
<li><code>HTTPRoute</code> : trafic HTTP/HTTPS — le plus courant</li>
<li><code>GRPCRoute</code> : trafic gRPC — peut faire du matching sur service/method</li>
<li><code>TCPRoute</code> : trafic TCP brut — n'interprète pas la sémantique HTTP</li>
<li><code>TLSRoute</code> : route en fonction du SNI TLS — courant pour le TLS passthrough</li>
</ul>
<p>Ce que toutes les routes ont en commun :
<strong>Elles n'"ouvrent pas la porte" — elles décident "comment router le trafic une fois qu'il est entré".</strong></p>
<h2 id="modèle-mental-minimal">Modèle mental minimal</h2>
<p>Gardez cette carte en tête :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#9ECBFF">GatewayClass</span><span style="color:#6A737D">  # Which Gateway implementation to use in this cluster</span></span>
<span data-line=""><span style="color:#9ECBFF">Gateway</span><span style="color:#6A737D">       # Which listeners this ingress opens</span></span>
<span data-line=""><span style="color:#9ECBFF">Listener</span><span style="color:#6A737D">      # A port / protocol / hostname / TLS slot</span></span>
<span data-line=""><span style="color:#9ECBFF">Route</span><span style="color:#6A737D">         # How to distribute traffic once it enters</span></span>
<span data-line=""><span style="color:#9ECBFF">Service</span><span style="color:#6A737D">       # The backend actually serving requests in the cluster</span></span>
<span data-line=""><span style="color:#9ECBFF">Envoy Proxy</span><span style="color:#6A737D">   # The data plane that ultimately handles the traffic</span></span></code></pre></figure>
<p>Un exemple minimal ressemble à ceci :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">apiVersion</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.networking.k8s.io/v1</span></span>

<ul>

<li><code>hostnames</code> : quel domaine doit correspondre à cette règle</li>

25:T411f,<p>Si vous avez déjà géré du trafic externe sur Kubernetes, il y a de fortes chances que vous ayez commencé par <code>Ingress</code>. Ça fonctionne, et pour beaucoup de scénarios c'est sincèrement suffisant. Mais dès que les exigences deviennent plus complexes — plusieurs listeners, gouvernance multi-équipes, gRPC, TCP, TLS passthrough, politiques de trafic plus fines — vous finissez inévitablement dans une situation où "tenir le tout en vie avec des annotations" devient la norme. Le YAML commence à ressembler à une incantation, et les personnes qui le maintiennent ont l'impression de briser un sceau.</p>
<p>C'est là que <code>Gateway API + Envoy Gateway</code> entre en jeu : c'est le nouvel outillage. Il ne rend pas les choses plus compliquées ; il sépare proprement des responsabilités qui étaient auparavant entremêlées, ce qui rend beaucoup plus facile de raisonner sur le trafic entrant, les règles de routage, les paramètres TLS, les types de protocole et la répartition des responsabilités entre équipes.</p>
<h2 id="quest-ce-que-cest-exactement">Qu'est-ce que c'est, exactement</h2>
<p>Disons-le clairement en une phrase :</p>
<ul>
<li><code>Envoy Proxy</code> : le plan de données qui reçoit réellement le trafic et transfère les requêtes, aussi appelé Gateway Proxy</li>
<li><code>Envoy Gateway</code> : le plan de contrôle qui gère Envoy Proxy pour vous</li>
<li><code>Gateway API</code> : l'interface standard que vous utilisez dans Kubernetes pour déclarer les règles de trafic</li>
</ul>
<p>Pensez-y comme ceci :</p>
<ul>
<li><code>Gateway API</code> est l'endroit où vous écrivez vos besoins</li>
<li><code>Envoy Gateway</code> est le responsable qui traduit et délègue</li>
<li><code>Envoy Proxy</code> est le vrai gardien posté à la porte</li>
</ul>
<p>L'avantage de cette séparation, c'est que vous n'avez pas besoin de fabriquer à la main une configuration Envoy bas niveau, ni de mémoriser toutes les annotations privées de différents contrôleurs. Vous déclarez des ressources Kubernetes, et Envoy Gateway les traduit en une configuration que Envoy Proxy peut réellement exécuter.</p>
<h2 id="gateway-vs-ingress--quelle-différence">Gateway vs Ingress : quelle différence</h2>
<p>La réponse courte : <strong>Ingress n'est pas obsolète, mais Gateway API est mieux adaptée aux systèmes de taille moyenne à grande qui ont besoin de plus de gouvernance.</strong></p>

<p>Si vos besoins sont simplement :</p>
<ul>
<li>Un seul site web ou une API simple</li>
<li>Un routage basique par chemin/hôte</li>
<li>Une petite équipe</li>
</ul>
<p>Alors Ingress reste parfaitement acceptable. Mais si vos besoins commencent à inclure :</p>
<ul>
<li>Une même entrée qui sert plusieurs protocoles</li>
<li>Plusieurs listeners, domaines ou certificats</li>
<li>HTTP et gRPC qui coexistent</li>
<li>Une séparation entre l'entrée plateforme et les autorisations de routage applicatif</li>
<li>Une configuration qui ressemble à une vraie API, pas à une liste de souhaits via annotations</li>
</ul>
<p>Alors Gateway API commencera à devenir très attirante.</p>
<h2 id="pourquoi-ne-pas-simplement-utiliser-ingress">Pourquoi ne pas simplement utiliser Ingress</h2>
<p>L'objectif officiel de Gateway API est de résoudre plusieurs points de douleur fréquents avec Ingress à grande échelle :</p>
<ul>
<li><strong>Meilleure expressivité</strong> : le routage, TLS, les politiques de trafic et les types de protocole sont définis plus clairement</li>
<li><strong>Meilleure portabilité</strong> : moins de dépendance aux annotations privées propres aux contrôleurs</li>
<li><strong>Séparation des rôles plus naturelle</strong> : les équipes plateforme possèdent l'entrée, les équipes applicatives possèdent les routes</li>
</ul>
<p>Par exemple, les configurations Ingress ressemblent souvent à ceci :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">metadata</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  annotations</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/rewrite-target</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">/</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/auth-type</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">basic</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/ssl-redirect</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">"true"</span></span></code></pre></figure>
<p>Ce n'est pas que ça ne marche pas, mais quand les besoins grossissent, les annotations deviennent facilement une sorte de magie noire YAML mystérieuse. Gateway API fait remonter ces besoins dans de vrais champs. Ça se lit comme une "configuration", pas comme une "liste de souhaits".</p>
<h2 id="la-structure-en-couches">La structure en couches</h2>
<p>La page de concepts officielle découpe Envoy Gateway en trois couches ; cela vaut la peine de les mémoriser comme carte mentale :</p>
<ul>
<li><strong>User Configuration</strong> : les ressources <code>Gateway API</code> et les CRD d'extension Envoy Gateway que vous écrivez</li>
<li><strong>Envoy Gateway Controller</strong> : lit ces ressources et les traduit en configuration exécutable</li>
<li><strong>Envoy Proxy</strong> : le plan de données qui gère réellement le trafic en direct</li>
</ul>
<p>En pratique, vous passerez l'essentiel de votre temps à modifier la "couche déclarative", pas à vous connecter en SSH sur des instances de proxy pour ajuster une config bas niveau. C'est toute l'élégance d'une approche native Kubernetes.</p>

<h2 id="les-ressources-principales-que-vous-allez-rencontrer">Les ressources principales que vous allez rencontrer</h2>
<p>Les débutants trébuchent souvent parce qu'ils supposent que Gateway API ne contient que <code>Gateway</code> et <code>HTTPRoute</code>. En réalité, c'est toute une famille de ressources.</p>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>Définit "quelle implémentation de Gateway utiliser dans ce cluster".
Pour Envoy Gateway, l'essentiel est que <code>controllerName</code> pointe vers le bon contrôleur.</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>Définit "à quoi ressemble l'entrée".
Par exemple : quels ports ouvrir, quels protocoles écouter, comment le TLS est rattaché, quelles routes sont autorisées.</p>
<h3 id="listener"><code>Listener</code></h3>
<p><code>Listener</code> est l'une des unités les plus importantes à l'intérieur d'un <code>Gateway</code>.
Pensez-y comme un point d'entrée exposé vers l'extérieur sur le Gateway ; chaque point définit :</p>
<ul>
<li>port</li>
<li>protocol</li>
<li>hostname</li>
<li>TLS config</li>
<li><code>allowedRoutes</code></li>
</ul>
<p>Beaucoup de gens voient <code>Gateway</code> comme une boîte noire, mais ce qui détermine réellement le comportement de l'entrée, c'est chaque <code>listener</code> individuel qu'il contient.</p>
<h3 id="la-famille-route">La famille Route</h3>
<ul>
<li><code>HTTPRoute</code> : trafic HTTP/HTTPS — le plus courant</li>
<li><code>GRPCRoute</code> : trafic gRPC — peut faire du matching sur service/method</li>
<li><code>TCPRoute</code> : trafic TCP brut — n'interprète pas la sémantique HTTP</li>
<li><code>TLSRoute</code> : route en fonction du SNI TLS — courant pour le TLS passthrough</li>
</ul>
<p>Ce que toutes les routes ont en commun :
<strong>Elles n'"ouvrent pas la porte" — elles décident "comment router le trafic une fois qu'il est entré".</strong></p>
