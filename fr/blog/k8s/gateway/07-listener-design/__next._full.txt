1c:T3db7,<p>Beaucoup de gens qui apprennent Gateway API traitent <code>Listener</code> comme "ah oui, c'est juste le champ <code>port: 80</code>."
Mais dans les déploiements réels, <code>Listener</code> est loin d'être un figurant : c'est plutôt le centre de contrôle du trafic pour toute votre couche d'entrée.</p>
<p>Un listener ne se contente pas d'ouvrir un port. Il définit :</p>
<ul>
<li>Quel protocole accepter</li>
<li>Quel hostname accepter</li>
<li>S'il faut effectuer TLS</li>
<li>Quels types de routes sont autorisés à s'attacher</li>
</ul>
<p>Autrement dit, <strong>un listener est un contrat d'entrée</strong>. Écrivez des contrats propres, et les routes en aval, la répartition des responsabilités d'équipe et la complexité du débogage deviennent plus propres elles aussi.</p>
<h2 id="construire-le-bon-modèle-mental--un-listener--un-slot-dentrée">Construire le bon modèle mental : un listener = un slot d'entrée</h2>

<p>Ce n'est pas juste "un Gateway avec trois trous". Voyez-le plutôt comme :</p>
<ul>
<li>Le listener <code>http</code> : pour le HTTP en clair</li>
<li>Le listener <code>https</code> : pour <code>app.example.com</code></li>
<li>Le listener <code>grpc</code> : un point d'entrée dédié aux services gRPC</li>
</ul>
<p>Une fois que vous pensez ainsi, beaucoup de décisions de conception deviennent immédiatement claires.
Vous n'assemblez pas seulement du YAML, vous dessinez des frontières d'entrée.</p>
<h2 id="trois-patterns-de-découpage-courants">Trois patterns de découpage courants</h2>
<h3 id="pattern-1--découper-par-protocole">Pattern 1 : découper par protocole</h3>
<p>L'approche la plus intuitive :</p>
<ul>
<li>HTTP sur un listener</li>
<li>HTTPS sur un listener</li>
<li>gRPC sur un listener</li>
<li>TCP/TLS passthrough séparés à part</li>
</ul>
<p>Cela donne des responsabilités claires.
Même si gRPC et les API web générales peuvent tous deux tourner sur HTTP/2, leurs modèles de service diffèrent. Les garder séparés évite que les routes interfèrent les unes avec les autres.</p>
<h3 id="pattern-2--découper-par-hostname">Pattern 2 : découper par hostname</h3>
<p>Si vous avez plusieurs domaines, un pattern courant consiste à mettre un listener par hostname principal :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">listeners</span><span style="color:#E1E4E8">:</span></span>

<span data-line=""><span style="color:#85E89D">    port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">443</span></span>

<span data-line=""><span style="color:#85E89D">    port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">443</span></span></code></pre></figure>
<p>Cela fonctionne bien pour :</p>
<ul>
<li>Séparer la gouvernance publique et la gouvernance d'administration</li>
<li>Des hostnames différents nécessitant des certificats différents</li>
<li>Garder des frontières d'attachement de routes bien nettes</li>
</ul>
<h3 id="pattern-3--découper-par-responsabilité-déquipe-ou-denvironnement">Pattern 3 : découper par responsabilité d'équipe ou d'environnement</h3>
<p>Dans les setups multi-équipes, les listeners peuvent servir de frontières de gouvernance :</p>
<ul>
<li><code>public-api</code> pour le trafic produit externe</li>
<li><code>internal-api</code> pour les systèmes internes</li>
<li><code>partner-api</code> pour les intégrations partenaires</li>
</ul>
<p>Ici, la valeur du listener dépasse la simple configuration technique : il devient une frontière de permissions et de responsabilités.
Ce pattern change réellement la donne dans les équipes moyennes à grandes, car il réduit la catastrophe du "même point d'entrée où tout le monde peut attacher n'importe quoi".</p>

<span data-line=""><span style="color:#85E89D">    protocol</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">HTTPS</span></span>
<span data-line=""><span style="color:#85E89D">    port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">443</span></span>
<span data-line=""><span style="color:#85E89D">    allowedRoutes</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">      namespaces</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">        from</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">Same</span></span></code></pre></figure>
<p>Cela signifie que seules les routes présentes dans le même namespace que le <code>Gateway</code> peuvent s'attacher.
Valeurs courantes :</p>
<ul>
<li><code>Same</code> : uniquement le même namespace</li>
<li><code>All</code> : n'importe quel namespace</li>
<li><code>Selector</code> : uniquement les namespaces correspondant à un sélecteur de labels</li>
</ul>
<p>Si vous voulez construire délibérément des frontières de plateforme, ce champ est très puissant.
Il décide lui-même, au niveau du listener, de "qui peut s'attacher à cette entrée".</p>
<h2 id="conseil-pratique--comment-structurer-les-listeners-sans-le-regretter-plus-tard">Conseil pratique : comment structurer les listeners sans le regretter plus tard</h2>
<p>Un principe très utile :</p>
<p><strong>Chaque listener porte une responsabilité clairement définie.</strong></p>
<p>Par exemple :</p>
<ul>
<li>Un listener sert un groupe principal de hostnames</li>
<li>Un listener gère un type de protocole principal</li>
<li>Un listener est ouvert à un type de route ou à un ensemble fixe de namespaces</li>
</ul>
<p>Ne concentrez pas tout le trafic dans un listener universel en espérant que les routes s'organiseront ensuite toutes seules.
Ce pattern a l'air efficace au début, mais trois mois plus tard il ressemble au tiroir à câbles mystérieux qu'on finit tous par avoir chez soi : tout est dedans, rien n'est retrouvable.</p>
<p>Suggestions concrètes :</p>
<ul>
<li>Les noms de listeners doivent être sémantiques : <code>https-public</code>, <code>grpc-internal</code></li>
<li>Dans les setups multi-listeners, utilisez toujours <code>sectionName</code></li>
<li>Ne mélangez pas des hostnames importants dans un même listener</li>
<li>Commencez par restreindre <code>allowedRoutes</code> par défaut, ne démarrez pas avec <code>from: All</code></li>
</ul>
<h2 id="résumé-en-une-ligne">Résumé en une ligne</h2>
<p>Traitez <code>Listener</code> comme un contrat d'entrée, pas comme un simple réglage de port.
Des frontières propres côté listener signifient que les routes s'attachent correctement, que les équipes possèdent naturellement leur périmètre et que le débogage ressemble moins à la poursuite d'un chat dans un labyrinthe.</p>

28:T3db7,<p>Beaucoup de gens qui apprennent Gateway API traitent <code>Listener</code> comme "ah oui, c'est juste le champ <code>port: 80</code>."
Mais dans les déploiements réels, <code>Listener</code> est loin d'être un figurant : c'est plutôt le centre de contrôle du trafic pour toute votre couche d'entrée.</p>
<p>Un listener ne se contente pas d'ouvrir un port. Il définit :</p>
<ul>
<li>Quel protocole accepter</li>
<li>Quel hostname accepter</li>
<li>S'il faut effectuer TLS</li>
<li>Quels types de routes sont autorisés à s'attacher</li>
</ul>
<p>Autrement dit, <strong>un listener est un contrat d'entrée</strong>. Écrivez des contrats propres, et les routes en aval, la répartition des responsabilités d'équipe et la complexité du débogage deviennent plus propres elles aussi.</p>

<p>Une fois que vous pensez ainsi, beaucoup de décisions de conception deviennent immédiatement claires.
Vous n'assemblez pas seulement du YAML, vous dessinez des frontières d'entrée.</p>
<h2 id="trois-patterns-de-découpage-courants">Trois patterns de découpage courants</h2>
<h3 id="pattern-1--découper-par-protocole">Pattern 1 : découper par protocole</h3>
<p>L'approche la plus intuitive :</p>
<ul>
<li>HTTP sur un listener</li>
<li>HTTPS sur un listener</li>
<li>gRPC sur un listener</li>
<li>TCP/TLS passthrough séparés à part</li>
</ul>
<p>Cela donne des responsabilités claires.
Même si gRPC et les API web générales peuvent tous deux tourner sur HTTP/2, leurs modèles de service diffèrent. Les garder séparés évite que les routes interfèrent les unes avec les autres.</p>
<h3 id="pattern-2--découper-par-hostname">Pattern 2 : découper par hostname</h3>
<p>Si vous avez plusieurs domaines, un pattern courant consiste à mettre un listener par hostname principal :</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">listeners</span><span style="color:#E1E4E8">:</span></span>

<p>Cela fonctionne bien pour :</p>
<ul>
<li>Séparer la gouvernance publique et la gouvernance d'administration</li>
<li>Des hostnames différents nécessitant des certificats différents</li>
<li>Garder des frontières d'attachement de routes bien nettes</li>
</ul>
<h3 id="pattern-3--découper-par-responsabilité-déquipe-ou-denvironnement">Pattern 3 : découper par responsabilité d'équipe ou d'environnement</h3>
<p>Dans les setups multi-équipes, les listeners peuvent servir de frontières de gouvernance :</p>
<ul>
<li><code>public-api</code> pour le trafic produit externe</li>
<li><code>internal-api</code> pour les systèmes internes</li>
<li><code>partner-api</code> pour les intégrations partenaires</li>
</ul>
<p>Ici, la valeur du listener dépasse la simple configuration technique : il devient une frontière de permissions et de responsabilités.
Ce pattern change réellement la donne dans les équipes moyennes à grandes, car il réduit la catastrophe du "même point d'entrée où tout le monde peut attacher n'importe quoi".</p>
