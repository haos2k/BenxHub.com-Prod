b:T458a,<p>前の記事まで読んできたなら、今あなたを止めているのは「Gateway API がわからない」ではなく、むしろこれかもしれません。</p>
<p><strong>「で、実際どれを書くの? <code>HTTPRoute</code>, <code>GRPCRoute</code>, <code>TCPRoute</code>, <code>TLSRoute</code> のどれ?」</strong></p>
<p>この記事はその混線をほどくためのものです。ポケットリファレンスとして残しておいてください。新しい service が出てきたらまずこれを見れば、やみくもに YAML を書いて condition status に説教されるのをかなり減らせます。</p>
<h2 id="先に結論-4-つの-route-type4-つの役割">先に結論: 4 つの Route Type、4 つの役割</h2>
<table>
<thead>
<tr>
<th>Route Type</th>
<th>トラフィック層</th>
<th>何を見ているか</th>
<th>向いているもの</th>
<th>向いていないもの</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>HTTPRoute</code></td>
<td>L7 HTTP/HTTPS</td>
<td>host, path, header, query, method</td>
<td>Web サイト、REST API、一般的な web traffic</td>
<td>生の TCP、TLS passthrough</td>
</tr>
<tr>
<td><code>GRPCRoute</code></td>
<td>L7 gRPC</td>
<td>hostname, service, method, header</td>
<td>gRPC service/method routing</td>
<td>一般的な REST API、生の TCP</td>
</tr>
<tr>
<td><code>TCPRoute</code></td>
<td>L4 TCP</td>
<td>Listener と接続レベルの情報</td>
<td>database、独自 TCP protocol、非 HTTP service</td>
<td>path/header の判定が必要な場面</td>
</tr>
<tr>
<td><code>TLSRoute</code></td>
<td>L4/L5 TLS</td>
<td>TLS SNI hostname</td>
<td>TLS passthrough、end-to-end 暗号化維持</td>
<td>復号後に HTTP 詳細を見たい場面</td>
</tr>
</tbody>
</table>
<p>超短縮版が欲しいならこうです。</p>
<ul>
<li><code>path</code> や <code>header</code> を見たい → <code>HTTPRoute</code></li>
<li>gRPC の <code>service/method</code> を見たい → <code>GRPCRoute</code></li>
<li>TCP 接続をそのまま流したい → <code>TCPRoute</code></li>
<li>TLS を terminate せず SNI だけで route したい → <code>TLSRoute</code></li>
</ul>
<h2 id="3-ステップ判断法-勘で選ばない">3 ステップ判断法: 勘で選ばない</h2>
<p>この順番で考えてください。</p>
<ol>
<li>Gateway はこのトラフィックから HTTP の意味を解釈するか?</li>
<li>するなら、それは通常の HTTP/REST か、gRPC か?</li>
<li>しないなら、生の TCP か、それとも TLS passthrough か?</li>
</ol>
<p>対応させると:</p>
<ul>
<li>HTTP の path/header/method を見たい → <code>HTTPRoute</code></li>
<li>gRPC の service/method を見たい → <code>GRPCRoute</code></li>
<li>L7 ルール不要で TCP 転送だけしたい → <code>TCPRoute</code></li>
<li>TLS を backend まで保ちたい → <code>TLSRoute</code></li>
</ul>
<p>この判断はかなり重要です。多くの人は reflex 的に <code>HTTPRoute</code> から書き始めて、途中で実は database traffic を扱っていたことに気づきます。そこで YAML 全体が「私は今何をしているんだ」状態に入ります。</p>

<h2 id="よくある-4-つの落とし穴">よくある 4 つの落とし穴</h2>
<h3 id="1-grpc-だからといって必ず-grpcroute-とは限らない">1. gRPC だからといって必ず <code>GRPCRoute</code> とは限らない</h3>
<p>単に gRPC traffic を通したいだけなら、実装によっては gRPC が HTTP/2 上で動くため <code>HTTPRoute</code> でも扱える場合があります。
ですが、gRPC の service/method でマッチしたいなら <code>GRPCRoute</code> のほうが正しく、読みやすい選択です。</p>
<h3 id="2-tlsroute-は上級-httpsではない">2. <code>TLSRoute</code> は「上級 HTTPS」ではない</h3>
<p>これが最も多い誤解です。</p>
<ul>
<li><code>HTTPS listener + HTTPRoute</code>: Gateway が TLS を terminate してから HTTP ルールを適用する</li>
<li><code>TLS listener + TLSRoute</code>: Gateway は TLS を terminate せず、SNI だけで route する</li>
</ul>
<p>片方は復号して L7 で処理します。もう片方は暗号化を維持したまま passthrough します。まったく別世界です。</p>
<h3 id="3-tcproute-では-pathheader-は見えない">3. <code>TCPRoute</code> では Path/Header は見えない</h3>
<p>要件が次なら:</p>
<ul>
<li><code>/api</code> は A へ</li>
<li><code>/admin</code> は B へ</li>
</ul>
<p>それは <code>TCPRoute</code> の仕事ではありません。
<code>TCPRoute</code> は HTTP の詳細を理解しません。そこへその要件を押し込むのは、自分で自分に苦行を課しているだけです。</p>
<h3 id="4-parentrefssectionname-は重要">4. <code>parentRefs.sectionName</code> は重要</h3>
<p>Gateway に複数 listener があるなら、<code>sectionName</code> を使いましょう。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">    sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span></code></pre></figure>
<p>これで route が意図した listener に正確に attach されます。
これがないと、VIP ルームを予約したつもりで別会場に入っていた、みたいな事故が起きます。</p>
<h2 id="一文まとめ">一文まとめ</h2>
<p>まず自分が扱っているのが <strong>HTTP、gRPC、TCP、それとも TLS passthrough</strong> のどれかを見極めてから、正しい route type を選んでください。
route が合っていれば YAML の 8 割は自然に流れます。間違えると condition status との格闘生活が始まります。</p>

<p>超短縮版が欲しいならこうです。</p>

<li>gRPC の <code>service/method</code> を見たい → <code>GRPCRoute</code></li>
<li>TCP 接続をそのまま流したい → <code>TCPRoute</code></li>
<li>TLS を terminate せず SNI だけで route したい → <code>TLSRoute</code></li>
</ul>
<h2 id="3-ステップ判断法-勘で選ばない">3 ステップ判断法: 勘で選ばない</h2>
<p>この順番で考えてください。</p>
<ol>
<li>Gateway はこのトラフィックから HTTP の意味を解釈するか?</li>
<li>するなら、それは通常の HTTP/REST か、gRPC か?</li>
<li>しないなら、生の TCP か、それとも TLS passthrough か?</li>
</ol>
<p>対応させると:</p>
<ul>
<li>HTTP の path/header/method を見たい → <code>HTTPRoute</code></li>
<li>gRPC の service/method を見たい → <code>GRPCRoute</code></li>
<li>L7 ルール不要で TCP 転送だけしたい → <code>TCPRoute</code></li>
<li>TLS を backend まで保ちたい → <code>TLSRoute</code></li>
</ul>
<p>この判断はかなり重要です。多くの人は reflex 的に <code>HTTPRoute</code> から書き始めて、途中で実は database traffic を扱っていたことに気づきます。そこで YAML 全体が「私は今何をしているんだ」状態に入ります。</p>

<h2 id="よくある-4-つの落とし穴">よくある 4 つの落とし穴</h2>
<h3 id="1-grpc-だからといって必ず-grpcroute-とは限らない">1. gRPC だからといって必ず <code>GRPCRoute</code> とは限らない</h3>
<p>単に gRPC traffic を通したいだけなら、実装によっては gRPC が HTTP/2 上で動くため <code>HTTPRoute</code> でも扱える場合があります。
ですが、gRPC の service/method でマッチしたいなら <code>GRPCRoute</code> のほうが正しく、読みやすい選択です。</p>
<h3 id="2-tlsroute-は上級-httpsではない">2. <code>TLSRoute</code> は「上級 HTTPS」ではない</h3>
<p>これが最も多い誤解です。</p>
<ul>
<li><code>HTTPS listener + HTTPRoute</code>: Gateway が TLS を terminate してから HTTP ルールを適用する</li>
<li><code>TLS listener + TLSRoute</code>: Gateway は TLS を terminate せず、SNI だけで route する</li>
</ul>
<p>片方は復号して L7 で処理します。もう片方は暗号化を維持したまま passthrough します。まったく別世界です。</p>
<h3 id="3-tcproute-では-pathheader-は見えない">3. <code>TCPRoute</code> では Path/Header は見えない</h3>
<p>要件が次なら:</p>
<ul>
<li><code>/api</code> は A へ</li>
<li><code>/admin</code> は B へ</li>
</ul>
<p>それは <code>TCPRoute</code> の仕事ではありません。
<code>TCPRoute</code> は HTTP の詳細を理解しません。そこへその要件を押し込むのは、自分で自分に苦行を課しているだけです。</p>
<h3 id="4-parentrefssectionname-は重要">4. <code>parentRefs.sectionName</code> は重要</h3>
<p>Gateway に複数 listener があるなら、<code>sectionName</code> を使いましょう。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">    sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span></code></pre></figure>
<p>これで route が意図した listener に正確に attach されます。
これがないと、VIP ルームを予約したつもりで別会場に入っていた、みたいな事故が起きます。</p>
<h2 id="一文まとめ">一文まとめ</h2>
<p>まず自分が扱っているのが <strong>HTTP、gRPC、TCP、それとも TLS passthrough</strong> のどれかを見極めてから、正しい route type を選んでください。
route が合っていれば YAML の 8 割は自然に流れます。間違えると condition status との格闘生活が始まります。</p>
