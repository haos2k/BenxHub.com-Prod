1c:T2a61,<p>「動く」と「システムとして安定している」は、まったく別の宇宙の話です。入口層の事故の多くは Envoy Gateway の機能不足ではなく、設定をラフに作りすぎて、運用がずっとサプライズボックス化してしまうことから起きます。この記事では、実践上かなり効く推奨事項を checklist としてまとめます。</p>
<h2 id="推奨プラクティス">推奨プラクティス</h2>
<h3 id="1-gateway-を誰が持ちroute-を誰が持つかを明確にする">1. Gateway を誰が持ち、Route を誰が持つかを明確にする</h3>
<p>複数人が関わるなら、責務を分けましょう。</p>
<ul>
<li>Platform team が <code>GatewayClass</code>, <code>Gateway</code> を管理する</li>
<li>App team が各自の <code>HTTPRoute</code> を管理する</li>
</ul>
<p>この分担の利点は、入口層のセキュリティや公開面が各 app によって無秩序に変わらず、それでいて app team は routing の柔軟性を持てることです。これこそ Gateway API の設計価値なので、せっかくの分離をまた巨大な YAML の塊に戻さないことです。</p>
<h3 id="2-最初から-tls-をデフォルトとして扱う">2. 最初から TLS をデフォルトとして扱う</h3>
<p>「まず HTTP、あとで HTTPS」を前提にしないでください。
その「あとで」はだいたい金曜夜の緊急対応になります。</p>
<p>最低限:</p>
<ul>
<li>外向き listener は HTTPS をデフォルトにする</li>
<li>証明書の取得元と管理プロセスを決めておく</li>
<li>テスト用、self-signed、本番 CA のフローを分ける</li>
</ul>
<p>すでに cert-manager があるなら連携しましょう。更新のたびに Secret を手 patch するより、証明書ローテーションを自動化したほうが圧倒的に信頼できます。</p>
<h3 id="3-route-ルールは明示的に書き便利さのために省略しすぎない">3. Route ルールは明示的に書き、便利さのために省略しすぎない</h3>
<p>次のような rule は便利ですが、ブラックホール化しやすいです。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">backend</span></span>
<span data-line=""><span style="color:#7EE787">        port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span></code></pre></figure>
<p>間違いではありません。ただ、システムが育つにつれて、「何でも受ける」rule が増えるとデバッグがかなり痛くなります。
<code>hostnames</code> を書けるなら書く、<code>path</code> を書けるなら書く。はっきり書くほうが後で助かります。</p>
<h3 id="4-トラフィックは小さく切りいきなり全振りしない">4. トラフィックは小さく切り、いきなり全振りしない</h3>
<p>新 version を出すときは、最初に小さい割合だけ流します。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-v1</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span>
<span data-line=""><span style="color:#7EE787">    weight</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">90</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-v2</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span>
<span data-line=""><span style="color:#7EE787">    weight</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">10</span></span></code></pre></figure>
<p>これは「service selector を一撃で全切り替え」するよりずっと穏やかです。
問題が起きたときの rollback も圧倒的に速いので、深夜 3 時の自分が本当に感謝します。</p>
<h3 id="5-status-と-event-を見る習慣を持つ">5. <code>status</code> と event を見る習慣を持つ</h3>
<p>YAML を読むだけでは足りません。controller が実際に設定を受け取ったか確認する必要があります。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> describe</span><span style="color:#A5D6FF"> gateway</span><span style="color:#A5D6FF"> eg</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> describe</span><span style="color:#A5D6FF"> httproute</span><span style="color:#A5D6FF"> app-route</span></span></code></pre></figure>
<p>次の種類の問題は <code>spec</code> だけでは見抜きにくいです。</p>
<ul>
<li>Route が accepted されていない</li>
<li>Cross-namespace reference がブロックされている</li>
<li>Listener status が異常</li>
</ul>
<p>最悪なのは bug そのものより、「効いたと思っていたが、そもそも一度も取り込まれていなかった」です。</p>
<h2 id="よくある落とし穴">よくある落とし穴</h2>
<h3 id="pitfall-1-envoy-gateway-をただの転送箱だと思う">Pitfall 1: Envoy Gateway をただの転送箱だと思う</h3>
<p>これは単に packet を A から B に送るだけの箱ではありません。
公式ドキュメントでも、Kubernetes-native な API Gateway として位置づけられており、トラフィックやセキュリティポリシーを積み上げる余地があります。Ingress 置き換えだけに使うなら、かなり持て余しています。</p>
<h3 id="pitfall-2-referencegrant-なしで-cross-namespace-証明書を参照する">Pitfall 2: <code>ReferenceGrant</code> なしで Cross-Namespace 証明書を参照する</h3>
<p><code>certificateRefs</code> に namespace field が書けるのを見て、そのまま別 namespace を指して「なぜ何も起きないのか」と悩む人は多いです。
原因はたいてい怪奇現象ではなく、<code>ReferenceGrant</code> の不足です。</p>
<h3 id="pitfall-3-happy-path-しか試さない">Pitfall 3: Happy path しか試さない</h3>
<p>次だけを確認して終わらせないでください。</p>
<ul>
<li><code>curl http://...</code> が 1 回成功する</li>
</ul>
<p>あわせて次も試してください。</p>
<ul>
<li>異なる hostname</li>
<li>異なる path</li>
<li>TLS 証明書の妥当性</li>
<li>traffic split の比率が想定通りか</li>
</ul>
<p>入口層が怖いのは、happy path だけ完璧に見えて、端のケースで即死することです。</p>
<h3 id="pitfall-4-デモ設定をそのまま本番へ持ち込む">Pitfall 4: デモ設定をそのまま本番へ持ち込む</h3>
<p>公式 quickstart は学習用としてとても優秀ですが、あくまで quickstart です。
本番では最低でも次を足しましょう。</p>
<ul>
<li>証明書自動化</li>
<li>監視と alerting</li>
<li>変更管理プロセス</li>
<li>Route の命名規約</li>
</ul>
<p>そうしないと、今日の quickstart は明日の事故の種になります。</p>
<h2 id="最小の本番前-checklist">最小の本番前 checklist</h2>
<p>本番公開前にこれを使ってください。</p>
<ul>
<li><code>Gateway</code> listener は HTTP / HTTPS を明確に分けているか</li>
<li>certificate Secret と rotation 手順は明確か</li>
<li><code>HTTPRoute</code> に明確な <code>hostnames</code> / <code>matches</code> があるか</li>
<li>重要な変更は小さな traffic cut で出しているか</li>
<li><code>status</code> と event から素早く問題箇所を特定できるか</li>
</ul>
<p>この 5 つがそろっていれば、「動いてるから大丈夫」の段階よりかなり上です。</p>
<h2 id="一文まとめ">一文まとめ</h2>
<p>Envoy Gateway の本当の価値は、単にトラフィックを流すことではなく、入口層の設定をより標準化し、分割可能にし、ガバナンスしやすくすることです。機能は一時的ですが、運用は長期戦です。未来の自分に優しくするのは、本当に意味があります。</p>

28:T2a61,<p>「動く」と「システムとして安定している」は、まったく別の宇宙の話です。入口層の事故の多くは Envoy Gateway の機能不足ではなく、設定をラフに作りすぎて、運用がずっとサプライズボックス化してしまうことから起きます。この記事では、実践上かなり効く推奨事項を checklist としてまとめます。</p>
<h2 id="推奨プラクティス">推奨プラクティス</h2>
<h3 id="1-gateway-を誰が持ちroute-を誰が持つかを明確にする">1. Gateway を誰が持ち、Route を誰が持つかを明確にする</h3>
<p>複数人が関わるなら、責務を分けましょう。</p>
<ul>
<li>Platform team が <code>GatewayClass</code>, <code>Gateway</code> を管理する</li>
<li>App team が各自の <code>HTTPRoute</code> を管理する</li>
</ul>
<p>この分担の利点は、入口層のセキュリティや公開面が各 app によって無秩序に変わらず、それでいて app team は routing の柔軟性を持てることです。これこそ Gateway API の設計価値なので、せっかくの分離をまた巨大な YAML の塊に戻さないことです。</p>
<h3 id="2-最初から-tls-をデフォルトとして扱う">2. 最初から TLS をデフォルトとして扱う</h3>
<p>「まず HTTP、あとで HTTPS」を前提にしないでください。
その「あとで」はだいたい金曜夜の緊急対応になります。</p>
<p>最低限:</p>
<ul>
<li>外向き listener は HTTPS をデフォルトにする</li>
<li>証明書の取得元と管理プロセスを決めておく</li>
<li>テスト用、self-signed、本番 CA のフローを分ける</li>
</ul>
<p>すでに cert-manager があるなら連携しましょう。更新のたびに Secret を手 patch するより、証明書ローテーションを自動化したほうが圧倒的に信頼できます。</p>
<h3 id="3-route-ルールは明示的に書き便利さのために省略しすぎない">3. Route ルールは明示的に書き、便利さのために省略しすぎない</h3>
<p>次のような rule は便利ですが、ブラックホール化しやすいです。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">backend</span></span>
<span data-line=""><span style="color:#7EE787">        port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span></code></pre></figure>
<p>間違いではありません。ただ、システムが育つにつれて、「何でも受ける」rule が増えるとデバッグがかなり痛くなります。
<code>hostnames</code> を書けるなら書く、<code>path</code> を書けるなら書く。はっきり書くほうが後で助かります。</p>
<h3 id="4-トラフィックは小さく切りいきなり全振りしない">4. トラフィックは小さく切り、いきなり全振りしない</h3>
<p>新 version を出すときは、最初に小さい割合だけ流します。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-v1</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span>
<span data-line=""><span style="color:#7EE787">    weight</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">90</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-v2</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span>
<span data-line=""><span style="color:#7EE787">    weight</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">10</span></span></code></pre></figure>
<p>これは「service selector を一撃で全切り替え」するよりずっと穏やかです。
問題が起きたときの rollback も圧倒的に速いので、深夜 3 時の自分が本当に感謝します。</p>
<h3 id="5-status-と-event-を見る習慣を持つ">5. <code>status</code> と event を見る習慣を持つ</h3>
<p>YAML を読むだけでは足りません。controller が実際に設定を受け取ったか確認する必要があります。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> describe</span><span style="color:#A5D6FF"> gateway</span><span style="color:#A5D6FF"> eg</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> describe</span><span style="color:#A5D6FF"> httproute</span><span style="color:#A5D6FF"> app-route</span></span></code></pre></figure>
<p>次の種類の問題は <code>spec</code> だけでは見抜きにくいです。</p>
<ul>
<li>Route が accepted されていない</li>
<li>Cross-namespace reference がブロックされている</li>
<li>Listener status が異常</li>
</ul>
<p>最悪なのは bug そのものより、「効いたと思っていたが、そもそも一度も取り込まれていなかった」です。</p>
<h2 id="よくある落とし穴">よくある落とし穴</h2>
<h3 id="pitfall-1-envoy-gateway-をただの転送箱だと思う">Pitfall 1: Envoy Gateway をただの転送箱だと思う</h3>
<p>これは単に packet を A から B に送るだけの箱ではありません。
公式ドキュメントでも、Kubernetes-native な API Gateway として位置づけられており、トラフィックやセキュリティポリシーを積み上げる余地があります。Ingress 置き換えだけに使うなら、かなり持て余しています。</p>
<h3 id="pitfall-2-referencegrant-なしで-cross-namespace-証明書を参照する">Pitfall 2: <code>ReferenceGrant</code> なしで Cross-Namespace 証明書を参照する</h3>
<p><code>certificateRefs</code> に namespace field が書けるのを見て、そのまま別 namespace を指して「なぜ何も起きないのか」と悩む人は多いです。
原因はたいてい怪奇現象ではなく、<code>ReferenceGrant</code> の不足です。</p>
<h3 id="pitfall-3-happy-path-しか試さない">Pitfall 3: Happy path しか試さない</h3>
<p>次だけを確認して終わらせないでください。</p>
<ul>
<li><code>curl http://...</code> が 1 回成功する</li>
</ul>
<p>あわせて次も試してください。</p>
<ul>
<li>異なる hostname</li>
<li>異なる path</li>
<li>TLS 証明書の妥当性</li>
<li>traffic split の比率が想定通りか</li>
</ul>
<p>入口層が怖いのは、happy path だけ完璧に見えて、端のケースで即死することです。</p>
<h3 id="pitfall-4-デモ設定をそのまま本番へ持ち込む">Pitfall 4: デモ設定をそのまま本番へ持ち込む</h3>
<p>公式 quickstart は学習用としてとても優秀ですが、あくまで quickstart です。
本番では最低でも次を足しましょう。</p>
<ul>
<li>証明書自動化</li>
<li>監視と alerting</li>
<li>変更管理プロセス</li>
<li>Route の命名規約</li>
</ul>
<p>そうしないと、今日の quickstart は明日の事故の種になります。</p>
<h2 id="最小の本番前-checklist">最小の本番前 checklist</h2>
<p>本番公開前にこれを使ってください。</p>
<ul>
<li><code>Gateway</code> listener は HTTP / HTTPS を明確に分けているか</li>
<li>certificate Secret と rotation 手順は明確か</li>
<li><code>HTTPRoute</code> に明確な <code>hostnames</code> / <code>matches</code> があるか</li>
<li>重要な変更は小さな traffic cut で出しているか</li>
<li><code>status</code> と event から素早く問題箇所を特定できるか</li>
</ul>
<p>この 5 つがそろっていれば、「動いてるから大丈夫」の段階よりかなり上です。</p>
<h2 id="一文まとめ">一文まとめ</h2>
<p>Envoy Gateway の本当の価値は、単にトラフィックを流すことではなく、入口層の設定をより標準化し、分割可能にし、ガバナンスしやすくすることです。機能は一時的ですが、運用は長期戦です。未来の自分に優しくするのは、本当に意味があります。</p>
