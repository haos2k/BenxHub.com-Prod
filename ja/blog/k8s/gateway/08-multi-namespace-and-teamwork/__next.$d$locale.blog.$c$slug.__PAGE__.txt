c:T3c1b,<p>Gateway API の大きな価値は、YAML がきれいになることだけではありません。長年ぼんやりしていた問いに、ようやく明確な答えを出してくれることです。</p>
<p><strong>入口層を誰が持つのか? Route を誰が変えられるのか? Namespace をまたいで相互参照できるのか?</strong></p>
<p>Ingress で痛みが出やすかった理由の一つは、全部が一緒くたに絡んでいたことです。
Platform team は無断の公開変更を怖がり、app team は path を変えるだけでも ticket を切る感覚になり、最終的にみんなで YAML を拷問し合う構図になりがちでした。</p>
<p>Gateway API の考え方は明快です。</p>
<ul>
<li>Platform の ingress は独立してガバナンスできる</li>
<li>Route は app team に委譲できる</li>
<li>Cross-namespace の挙動には明示的な許可が必要</li>
</ul>
<p>この記事では、その ownership model を上から下まで整理します。</p>
<h2 id="最初にここ-attachment-と-reference-は別物">最初にここ: Attachment と Reference は別物</h2>
<p>ここが最も混同されやすいポイントです。</p>
<h3 id="route-の-gateway--listener-への-attachment">Route の Gateway / Listener への Attachment</h3>
<p>これは次で決まります。</p>
<ul>
<li>route の <code>parentRefs</code></li>
<li>listener の <code>allowedRoutes</code></li>
</ul>
<p>つまり、route が listener に attach できるかどうかは <code>ReferenceGrant</code> では決まりません。listener 側が受け入れるかどうかで決まります。</p>
<h3 id="cross-namespace-の-resource-reference">Cross-Namespace の Resource Reference</h3>
<p>ここで登場するのが通常 <code>ReferenceGrant</code> です。
たとえば:</p>
<ul>
<li><code>Gateway</code> が別 namespace の <code>Secret</code> を参照したい</li>
<li><code>HTTPRoute</code> が別 namespace の <code>Service</code> を参照したい</li>
</ul>
<p>これは attachment の話ではなく、「対象 namespace が、自分の資源を使ってよいと正式に認可したか」です。</p>
<p>この 2 つを一つに混ぜると、だいたい正気を疑い始めます。役割を分ければ、ルールはそこまで神秘的ではありません。</p>
<h2 id="allowedroutes-まず誰が-attach-できるかを決める"><code>allowedRoutes</code>: まず誰が attach できるかを決める</h2>
<p>最も厳しく絞った listener はこうです。</p>

<p>これは <code>infra</code> namespace にある route だけがこの listener に attach できることを意味します。</p>
<p>特定 team の namespace を許可したい場合は <code>Selector</code> を使います。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">allowedRoutes</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  namespaces</span><span style="color:#E1E4E8">:</span></span>

<span data-line=""><span style="color:#85E89D">    selector</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">      matchLabels</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">        shared-gateway-access</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">"true"</span></span></code></pre></figure>
<p>このパターンは platform team に向いています。
すべてを完全封鎖しなくてもいいし、かといって <code>from: All</code> で誰でも入れてしまう必要もありません。特定 label を持つ namespace だけが attach できるようにできます。</p>
<blockquote>
<p>💡 <code>allowedRoutes</code> は Gateway 単位ではなく listener 単位です。listener ごとに異なる access policy を持たせられます。</p>
</blockquote>
<h2 id="referencegrant-決めるのは対象-namespace-側"><code>ReferenceGrant</code>: 決めるのは対象 Namespace 側</h2>
<p>route や gateway が他 namespace の resource を参照したい場合、対象 namespace 側が許可を出す必要があります。</p>
<p>たとえば app team の <code>HTTPRoute</code> が共有 namespace の backend へトラフィックを送りたい場合:</p>

<p><code>shared-services</code> namespace 側には <code>ReferenceGrant</code> が必要です。</p>

<p>平たく言うと:</p>
<ul>
<li><code>team-a</code> にある <code>HTTPRoute</code> が</li>
<li><code>shared-services</code> にある <code>Service</code> を参照してよい</li>
</ul>
<p>ここで重要なのは、認可を作るのは <strong>source 側ではなく target 側</strong> だということです。
source が「使いたい」と宣言するだけでは足りず、resource owner が決めます。この設計はかなり筋が良くて、所有者が誰にアクセスを許すかを制御できるべきだからです。</p>
<h2 id="よくある-platform--app-team-の分担">よくある Platform / App Team の分担</h2>
<p>最も一般的な ownership model はこうです。</p>
<h3 id="platform-team-が持つもの">Platform Team が持つもの</h3>
<ul>
<li><code>GatewayClass</code></li>
<li><code>Gateway</code></li>
<li><code>Listener</code></li>
<li>TLS 証明書管理</li>
<li><code>allowedRoutes</code> policy</li>
</ul>
<h3 id="app-team-が持つもの">App Team が持つもの</h3>
<ul>
<li>自分たちの namespace にある <code>HTTPRoute</code> / <code>GRPCRoute</code></li>
<li>Backend service</li>
<li>Routing rule の調整</li>
</ul>
<p>この分担の利点は明確です。</p>
<ul>
<li>Platform team は入口の公開面と security boundary を守れる</li>
<li>App team は自分たちの traffic rule を素早く変えられる</li>
<li>path を変えるためだけに共有 Gateway を触る必要がない</li>
</ul>
<p>もちろん、すべての権限を 1 グループに集めても間違いではありません。
ただし team が大きくなると、そのモデルは「誰でも変えられるので、壊れたとき誰が何をしたかわからない」に育ちがちです。</p>
<h2 id="実践アドバイス-multi-tenant-事故を避けるには">実践アドバイス: Multi-Tenant 事故を避けるには</h2>
<p>本当に役立つ習慣を挙げると:</p>
<ul>
<li>共有 Gateway は <code>allowedRoutes.namespaces.from: Selector</code> をデフォルトにする</li>
<li>Namespace label の命名規約は安定させる。来月になって <code>team-a</code> を <code>allow-gw</code> に変えたりしない</li>
<li>Cross-namespace の backend/Secret reference はすべて <code>ReferenceGrant</code> 経由にする</li>
<li>Route 名には team または service がわかる情報を入れる。例: <code>team-a-api-route</code></li>
<li>共有 listener では必ず <code>sectionName</code> を使い、誤 attach を防ぐ</li>
</ul>
<p>一つ持っておきたい原則があります。</p>
<p><strong>入口層で境界を強制できるなら、文書だけ置いて「みんなが自律的に守ってくれるはず」に期待しないこと。</strong></p>
<p>エンジニアリングでは、口約束より仕組みのほうが強いです。ちょっと年上の人の説教みたいですが、実際かなり使えます。</p>
<h2 id="一文まとめ">一文まとめ</h2>
<p>Gateway API では、<code>allowedRoutes</code> が「誰が入れるか」を制御し、<code>ReferenceGrant</code> が「入ったあと何にアクセスできるか」を制御します。
この 2 つをきちんと分けて理解すると、複数 namespace・複数 team の構成がかなり扱いやすくなります。</p>

e:T3c1b,<p>Gateway API の大きな価値は、YAML がきれいになることだけではありません。長年ぼんやりしていた問いに、ようやく明確な答えを出してくれることです。</p>
<p><strong>入口層を誰が持つのか? Route を誰が変えられるのか? Namespace をまたいで相互参照できるのか?</strong></p>
<p>Ingress で痛みが出やすかった理由の一つは、全部が一緒くたに絡んでいたことです。
Platform team は無断の公開変更を怖がり、app team は path を変えるだけでも ticket を切る感覚になり、最終的にみんなで YAML を拷問し合う構図になりがちでした。</p>
<p>Gateway API の考え方は明快です。</p>
<ul>
<li>Platform の ingress は独立してガバナンスできる</li>
<li>Route は app team に委譲できる</li>
<li>Cross-namespace の挙動には明示的な許可が必要</li>
</ul>
<p>この記事では、その ownership model を上から下まで整理します。</p>
<h2 id="最初にここ-attachment-と-reference-は別物">最初にここ: Attachment と Reference は別物</h2>
<p>ここが最も混同されやすいポイントです。</p>
<h3 id="route-の-gateway--listener-への-attachment">Route の Gateway / Listener への Attachment</h3>
<p>これは次で決まります。</p>
<ul>
<li>route の <code>parentRefs</code></li>
<li>listener の <code>allowedRoutes</code></li>
</ul>
<p>つまり、route が listener に attach できるかどうかは <code>ReferenceGrant</code> では決まりません。listener 側が受け入れるかどうかで決まります。</p>
<h3 id="cross-namespace-の-resource-reference">Cross-Namespace の Resource Reference</h3>
<p>ここで登場するのが通常 <code>ReferenceGrant</code> です。
たとえば:</p>
<ul>
<li><code>Gateway</code> が別 namespace の <code>Secret</code> を参照したい</li>
<li><code>HTTPRoute</code> が別 namespace の <code>Service</code> を参照したい</li>
</ul>
<p>これは attachment の話ではなく、「対象 namespace が、自分の資源を使ってよいと正式に認可したか」です。</p>
<p>この 2 つを一つに混ぜると、だいたい正気を疑い始めます。役割を分ければ、ルールはそこまで神秘的ではありません。</p>
<h2 id="allowedroutes-まず誰が-attach-できるかを決める"><code>allowedRoutes</code>: まず誰が attach できるかを決める</h2>
<p>最も厳しく絞った listener はこうです。</p>

<h2 id="よくある-platform--app-team-の分担">よくある Platform / App Team の分担</h2>
<p>最も一般的な ownership model はこうです。</p>
<h3 id="platform-team-が持つもの">Platform Team が持つもの</h3>
<ul>
<li><code>GatewayClass</code></li>
<li><code>Gateway</code></li>
<li><code>Listener</code></li>
<li>TLS 証明書管理</li>
<li><code>allowedRoutes</code> policy</li>
</ul>
<h3 id="app-team-が持つもの">App Team が持つもの</h3>
<ul>
<li>自分たちの namespace にある <code>HTTPRoute</code> / <code>GRPCRoute</code></li>
<li>Backend service</li>
<li>Routing rule の調整</li>
</ul>
<p>この分担の利点は明確です。</p>
<ul>
<li>Platform team は入口の公開面と security boundary を守れる</li>
<li>App team は自分たちの traffic rule を素早く変えられる</li>
<li>path を変えるためだけに共有 Gateway を触る必要がない</li>
</ul>
<p>もちろん、すべての権限を 1 グループに集めても間違いではありません。
ただし team が大きくなると、そのモデルは「誰でも変えられるので、壊れたとき誰が何をしたかわからない」に育ちがちです。</p>
<h2 id="実践アドバイス-multi-tenant-事故を避けるには">実践アドバイス: Multi-Tenant 事故を避けるには</h2>
<p>本当に役立つ習慣を挙げると:</p>
<ul>
<li>共有 Gateway は <code>allowedRoutes.namespaces.from: Selector</code> をデフォルトにする</li>
<li>Namespace label の命名規約は安定させる。来月になって <code>team-a</code> を <code>allow-gw</code> に変えたりしない</li>
<li>Cross-namespace の backend/Secret reference はすべて <code>ReferenceGrant</code> 経由にする</li>
<li>Route 名には team または service がわかる情報を入れる。例: <code>team-a-api-route</code></li>
<li>共有 listener では必ず <code>sectionName</code> を使い、誤 attach を防ぐ</li>
</ul>
<p>一つ持っておきたい原則があります。</p>
<p><strong>入口層で境界を強制できるなら、文書だけ置いて「みんなが自律的に守ってくれるはず」に期待しないこと。</strong></p>
<p>エンジニアリングでは、口約束より仕組みのほうが強いです。ちょっと年上の人の説教みたいですが、実際かなり使えます。</p>
<h2 id="一文まとめ">一文まとめ</h2>
<p>Gateway API では、<code>allowedRoutes</code> が「誰が入れるか」を制御し、<code>ReferenceGrant</code> が「入ったあと何にアクセスできるか」を制御します。
この 2 つをきちんと分けて理解すると、複数 namespace・複数 team の構成がかなり扱いやすくなります。</p>
