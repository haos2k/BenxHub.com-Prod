c:T3ce9,<p>Gateway API を学び始めた人の多くは、<code>Listener</code> を「まあ <code>port: 80</code> の field だよね」くらいに見がちです。
でも実運用では <code>Listener</code> は端役どころか、入口層全体の traffic control center に近い存在です。</p>
<p>listener は単に port を開けるだけではありません。次を定義します。</p>
<ul>
<li>どの protocol を受けるか</li>
<li>どの hostname を受けるか</li>
<li>TLS を行うか</li>
<li>どの route type を attach 可能にするか</li>
</ul>
<p>つまり <strong>listener は ingress 契約</strong> です。契約をきれいに書けば、下流の route、チーム分担、デバッグ難易度まで連鎖的にきれいになります。</p>
<h2 id="正しいメンタルモデルを作る-1-listener--1-ingress-slot">正しいメンタルモデルを作る: 1 Listener = 1 Ingress Slot</h2>

<p>これは「穴が 3 つある Gateway」ではありません。むしろ次のように考えます。</p>
<ul>
<li><code>http</code> listener: 平文 HTTP 用</li>
<li><code>https</code> listener: <code>app.example.com</code> 用</li>
<li><code>grpc</code> listener: gRPC service 専用の入口スロット</li>
</ul>
<p>こう捉えると、多くの設計判断がすぐ明確になります。
YAML を組み立てているのではなく、入口の境界を設計しているのです。</p>
<h2 id="よくある-3-つの分割パターン">よくある 3 つの分割パターン</h2>
<h3 id="pattern-1-protocol-で分ける">Pattern 1: Protocol で分ける</h3>
<p>最も直感的なやり方です。</p>
<ul>
<li>HTTP は 1 listener</li>
<li>HTTPS は 1 listener</li>
<li>gRPC は 1 listener</li>
<li>TCP/TLS passthrough は別で分ける</li>
</ul>
<p>責務がはっきりします。
gRPC と通常の web API はどちらも HTTP/2 上に乗ることがありますが、service モデルは異なります。分けておくことで route の干渉を防ぎやすくなります。</p>
<h3 id="pattern-2-hostname-で分ける">Pattern 2: Hostname で分ける</h3>
<p>複数 domain があるなら、主要 hostname ごとに 1 listener というパターンがよく使われます。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">listeners</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">app</span></span>
<span data-line=""><span style="color:#7EE787">    hostname</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">app.example.com</span></span>
<span data-line=""><span style="color:#7EE787">    protocol</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTPS</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">443</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">admin</span></span>
<span data-line=""><span style="color:#7EE787">    hostname</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">admin.example.com</span></span>
<span data-line=""><span style="color:#7EE787">    protocol</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTPS</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">443</span></span></code></pre></figure>
<p>これは次に向いています。</p>
<ul>
<li>公開系と管理系のガバナンス分離</li>
<li>hostname ごとに別証明書が必要</li>
<li>route の attach 境界を明確に保つ</li>
</ul>
<h3 id="pattern-3-team-または環境責務で分ける">Pattern 3: Team または環境責務で分ける</h3>
<p>複数 team 構成では、listener 自体を governance 境界として使えます。</p>
<ul>
<li><code>public-api</code> は外部向け product traffic</li>
<li><code>internal-api</code> は内部システム向け</li>
<li><code>partner-api</code> は partner 連携向け</li>
</ul>
<p>ここで listener の価値は技術設定を超え、権限と責任の境界になります。
中規模以上の team では特に効きます。誰でも何でも attach できる「1 つの巨大 ingress」の事故を減らせます。</p>
<h2 id="sectionname-と-allowedroutes-重要な-2-field"><code>sectionName</code> と <code>allowedRoutes</code>: 重要な 2 field</h2>
<p>route は <code>parentRefs.sectionName</code> で特定 listener に attach します。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">apiVersion</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">gateway.networking.k8s.io/v1</span></span>

<span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">      sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span>
<span data-line=""><span style="color:#7EE787">  hostnames</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#A5D6FF">"app.example.com"</span></span>
<span data-line=""><span style="color:#7EE787">  rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>

<p>この route は <code>https</code> listener だけを探します。
<code>sectionName</code> を指定しない場合は attach 可能な listener を探すためのルールが働きますが、複数 listener がある構成では明示したほうがほぼ安全です。</p>
<p>もう一つの重要 field が <code>allowedRoutes</code> です。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">listeners</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">public</span></span>
<span data-line=""><span style="color:#7EE787">    protocol</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTPS</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">443</span></span>
<span data-line=""><span style="color:#7EE787">    allowedRoutes</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">      namespaces</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">        from</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">Same</span></span></code></pre></figure>
<p>これは、<code>Gateway</code> と同じ namespace にある route だけが attach できることを意味します。
代表的な値:</p>
<ul>
<li><code>Same</code>: 同じ namespace のみ</li>
<li><code>All</code>: どの namespace でも可</li>
<li><code>Selector</code>: label selector に合う namespace のみ</li>
</ul>
<p>platform 境界を意図的に作りたいなら、この field はかなり強力です。
「誰がこの ingress に attach できるか」を listener レベルで決められます。</p>
<h2 id="実践アドバイス-後悔しない-listener-構造">実践アドバイス: 後悔しない Listener 構造</h2>
<p>かなり役立つ原則が一つあります。</p>
<p><strong>各 listener には、1 つの明確な責務だけを持たせる。</strong></p>
<p>たとえば:</p>
<ul>
<li>1 listener は 1 つの主要 hostname 群に対応する</li>
<li>1 listener は 1 つの主要 protocol type を扱う</li>
<li>1 listener は 1 つの route type、または固定された namespace 群に開く</li>
</ul>
<p>すべての traffic を万能 listener 1 個に詰め込んで、下流で route が自動的に整理されることを期待しないでください。
最初は効率的に見えても、3 か月後にはどの家にもある謎ケーブル引き出しみたいになります。全部入っているのに、何も見つかりません。</p>
<p>具体的な提案:</p>
<ul>
<li>Listener 名は意味を持たせる: <code>https-public</code>, <code>grpc-internal</code></li>
<li>複数 listener 構成では必ず <code>sectionName</code> とセットで使う</li>
<li>重要な hostname を 1 listener に混ぜ込まない</li>
<li><code>allowedRoutes</code> はまず制限寄りに始める。最初から <code>from: All</code> にしない</li>
</ul>
<h2 id="一文まとめ">一文まとめ</h2>
<p><code>Listener</code> は単なる port 設定ではなく ingress 契約として扱ってください。
listener 境界がきれいだと、route は正しく attach し、team は自然に担当範囲を持ち、デバッグも迷路で猫を追いかける感じがかなり減ります。</p>

e:T3ce9,<p>Gateway API を学び始めた人の多くは、<code>Listener</code> を「まあ <code>port: 80</code> の field だよね」くらいに見がちです。
でも実運用では <code>Listener</code> は端役どころか、入口層全体の traffic control center に近い存在です。</p>
<p>listener は単に port を開けるだけではありません。次を定義します。</p>
<ul>
<li>どの protocol を受けるか</li>
<li>どの hostname を受けるか</li>
<li>TLS を行うか</li>
<li>どの route type を attach 可能にするか</li>
</ul>
<p>つまり <strong>listener は ingress 契約</strong> です。契約をきれいに書けば、下流の route、チーム分担、デバッグ難易度まで連鎖的にきれいになります。</p>

<h2 id="よくある-3-つの分割パターン">よくある 3 つの分割パターン</h2>
<h3 id="pattern-1-protocol-で分ける">Pattern 1: Protocol で分ける</h3>
<p>最も直感的なやり方です。</p>
<ul>
<li>HTTP は 1 listener</li>
<li>HTTPS は 1 listener</li>
<li>gRPC は 1 listener</li>
<li>TCP/TLS passthrough は別で分ける</li>
</ul>
<p>責務がはっきりします。
gRPC と通常の web API はどちらも HTTP/2 上に乗ることがありますが、service モデルは異なります。分けておくことで route の干渉を防ぎやすくなります。</p>
<h3 id="pattern-2-hostname-で分ける">Pattern 2: Hostname で分ける</h3>
<p>複数 domain があるなら、主要 hostname ごとに 1 listener というパターンがよく使われます。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">listeners</span><span style="color:#E6EDF3">:</span></span>

<p>これは次に向いています。</p>
<ul>
<li>公開系と管理系のガバナンス分離</li>
<li>hostname ごとに別証明書が必要</li>
<li>route の attach 境界を明確に保つ</li>
</ul>
<h3 id="pattern-3-team-または環境責務で分ける">Pattern 3: Team または環境責務で分ける</h3>
<p>複数 team 構成では、listener 自体を governance 境界として使えます。</p>
<ul>
<li><code>public-api</code> は外部向け product traffic</li>
<li><code>internal-api</code> は内部システム向け</li>
<li><code>partner-api</code> は partner 連携向け</li>
</ul>
<p>ここで listener の価値は技術設定を超え、権限と責任の境界になります。
中規模以上の team では特に効きます。誰でも何でも attach できる「1 つの巨大 ingress」の事故を減らせます。</p>
<h2 id="sectionname-と-allowedroutes-重要な-2-field"><code>sectionName</code> と <code>allowedRoutes</code>: 重要な 2 field</h2>
<p>route は <code>parentRefs.sectionName</code> で特定 listener に attach します。</p>

<p>もう一つの重要 field が <code>allowedRoutes</code> です。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">listeners</span><span style="color:#E6EDF3">:</span></span>

<p>これは、<code>Gateway</code> と同じ namespace にある route だけが attach できることを意味します。
代表的な値:</p>
<ul>
<li><code>Same</code>: 同じ namespace のみ</li>
<li><code>All</code>: どの namespace でも可</li>
<li><code>Selector</code>: label selector に合う namespace のみ</li>
</ul>
<p>platform 境界を意図的に作りたいなら、この field はかなり強力です。
「誰がこの ingress に attach できるか」を listener レベルで決められます。</p>
<h2 id="実践アドバイス-後悔しない-listener-構造">実践アドバイス: 後悔しない Listener 構造</h2>
<p>かなり役立つ原則が一つあります。</p>
<p><strong>各 listener には、1 つの明確な責務だけを持たせる。</strong></p>
<p>たとえば:</p>
<ul>
<li>1 listener は 1 つの主要 hostname 群に対応する</li>
<li>1 listener は 1 つの主要 protocol type を扱う</li>
<li>1 listener は 1 つの route type、または固定された namespace 群に開く</li>
</ul>
<p>すべての traffic を万能 listener 1 個に詰め込んで、下流で route が自動的に整理されることを期待しないでください。
最初は効率的に見えても、3 か月後にはどの家にもある謎ケーブル引き出しみたいになります。全部入っているのに、何も見つかりません。</p>
<p>具体的な提案:</p>
<ul>
<li>Listener 名は意味を持たせる: <code>https-public</code>, <code>grpc-internal</code></li>
<li>複数 listener 構成では必ず <code>sectionName</code> とセットで使う</li>
<li>重要な hostname を 1 listener に混ぜ込まない</li>
<li><code>allowedRoutes</code> はまず制限寄りに始める。最初から <code>from: All</code> にしない</li>
</ul>
<h2 id="一文まとめ">一文まとめ</h2>
<p><code>Listener</code> は単なる port 設定ではなく ingress 契約として扱ってください。
listener 境界がきれいだと、route は正しく attach し、team は自然に担当範囲を持ち、デバッグも迷路で猫を追いかける感じがかなり減ります。</p>
