3:T4276,<p>Kubernetes の外部トラフィックを触ったことがあるなら、最初に <code>Ingress</code> から入った可能性は高いと思います。実際ちゃんと動きますし、多くの場面では本当にそれで十分です。ですが、要件が少し複雑になってくると、たとえば複数 listener、複数チームでの運用、gRPC、TCP、TLS passthrough、細かなトラフィックポリシーなどにぶつかった瞬間、結局は「annotation で延命する」が常態化しがちです。YAML は呪文集みたいになり、保守する側も封印を解いている気分になります。</p>
<p>そこで登場するのが <code>Gateway API + Envoy Gateway</code> です。これが新しい道具立てです。複雑さを増やすのではなく、これまで一つに絡まりがちだった責務をきれいに分離してくれるので、入口トラフィック、ルーティングルール、TLS セキュリティ設定、プロトコル種別、チームごとの責任分界をずっと整理して考えやすくなります。</p>
<h2 id="つまり何なのか">つまり何なのか</h2>
<p>まずは一文でまっすぐ言うとこうです。</p>
<ul>
<li><code>Envoy Proxy</code>: 実際にトラフィックを受けてリクエストを転送するデータプレーン。Gateway Proxy と呼ばれることもあります</li>
<li><code>Envoy Gateway</code>: Envoy Proxy をあなたの代わりに管理するコントロールプレーン</li>
<li><code>Gateway API</code>: Kubernetes 上でトラフィックルールを宣言するための標準インターフェース</li>
</ul>
<p>イメージとしてはこうです。</p>
<ul>
<li><code>Gateway API</code> は要件を書く場所</li>
<li><code>Envoy Gateway</code> は翻訳して采配するマネージャー</li>
<li><code>Envoy Proxy</code> は実際に入口に立つガード</li>
</ul>
<p>この分離の利点は、低レベルな Envoy の設定を手で組まなくてよいこと、さらに各 controller 独自の private annotation を全部暗記しなくてよいことです。Kubernetes リソースとして宣言すれば、Envoy Gateway がそれを Envoy Proxy が実行できる設定へ変換してくれます。</p>
<h2 id="gateway-と-ingress-の違い">Gateway と Ingress の違い</h2>
<p>短く言うと、<strong>Ingress が時代遅れになったわけではないけれど、ガバナンスが必要な中規模以上のシステムでは Gateway API のほうが向いています。</strong></p>
<table>
<thead>
<tr>
<th>比較項目</th>
<th>Ingress</th>
<th>Gateway API</th>
</tr>
</thead>
<tbody>
<tr>
<td>Ingress モデル</td>
<td>多くは入口とルーティングを 1 オブジェクトにまとめる</td>
<td><code>GatewayClass</code>、<code>Gateway</code>、<code>Route</code> に分離</td>
</tr>
<tr>
<td>表現力</td>
<td>主に HTTP/HTTPS。高度な機能は annotation 依存</td>
<td>複数の Route type をネイティブに表現でき、field も明確</td>
</tr>
<tr>
<td>拡張モデル</td>
<td>多くの機能が controller 独自 annotation 依存</td>
<td>標準 field を持ち、CRD による拡張点もある</td>
</tr>
<tr>
<td>プロトコル対応</td>
<td>基本は HTTP/Web 中心</td>
<td><code>HTTPRoute</code>、<code>GRPCRoute</code>、<code>TCPRoute</code>、<code>TLSRoute</code> をサポート</td>
</tr>
<tr>
<td>チーム分担</td>
<td>Platform と app の設定が混ざりやすい</td>
<td>Platform team が入口、app team が route を持ちやすい</td>
</tr>
<tr>
<td>可搬性</td>
<td>annotation が特定 controller に縛られがち</td>
<td>より標準化され、実装間でも読みやすい</td>
</tr>
</tbody>
</table>
<p>要件が例えば次の程度なら:</p>
<ul>
<li>単一サイトかシンプルな API</li>
<li>基本的な path/host ルーティング</li>
<li>小規模チーム</li>
</ul>
<p>Ingress のままでも十分です。ですが、要件が次のようになってくると:</p>
<ul>
<li>一つの入口で複数プロトコルを扱う</li>
<li>複数 listener、ドメイン、証明書がある</li>
<li>HTTP と gRPC が共存する</li>
<li>Platform の入口管理と app の route 権限を分けたい</li>
<li>annotation の寄せ集めではなく、ちゃんと API っぽく読める設定にしたい</li>
</ul>
<p>Gateway API がかなり魅力的に見えてきます。</p>
<h2 id="なぜ-ingress-ではなくこちらなのか">なぜ Ingress ではなくこちらなのか</h2>
<p>Gateway API の公式な狙いは、スケールした Ingress のよくある痛みを解消することです。</p>
<ul>
<li><strong>より高い表現力</strong>: Routing、TLS、traffic policy、protocol type がより明確</li>
<li><strong>より高い可搬性</strong>: controller 固有の private annotation への依存を減らせる</li>
<li><strong>より自然な責務分離</strong>: Platform team が入口を持ち、app team が route を持つ</li>
</ul>
<p>たとえば Ingress の設定は、しばしばこんな感じになります。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">metadata</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  annotations</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/rewrite-target</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/auth-type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">basic</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/ssl-redirect</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"true"</span></span></code></pre></figure>
<p>動かないわけではありません。でも要件が増えるほど、annotation は謎めいた YAML 黒魔術になりやすい。Gateway API はそれを正規の field に引き上げてくれます。読むと「願望リスト」ではなく「設定」に見えます。</p>
<h2 id="レイヤー構造">レイヤー構造</h2>
<p>公式の概念ページでは Envoy Gateway を 3 層に分けています。この図は頭に入れておく価値があります。</p>
<ul>
<li><strong>User Configuration</strong>: あなたが書く <code>Gateway API</code> リソースと Envoy Gateway 拡張 CRD</li>
<li><strong>Envoy Gateway Controller</strong>: それらを読み取り、実行可能な設定へ変換する</li>
<li><strong>Envoy Proxy</strong>: 実際のライブトラフィックを処理するデータプレーン</li>
</ul>
<p>実運用では、SSH で proxy に入って低レベル設定をいじるより、ほとんどの時間をこの「宣言レイヤー」の更新に使います。これが Kubernetes-native であることの美しさです。</p>

<h2 id="これから出てくる主要リソース">これから出てくる主要リソース</h2>
<p>初学者がつまずきやすいのは、Gateway API は <code>Gateway</code> と <code>HTTPRoute</code> だけだと思い込むことです。実際にはリソースのファミリーがあります。</p>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>「この cluster でどの Gateway 実装を使うか」を定義します。
Envoy Gateway では <code>controllerName</code> が正しい controller を指していることが重要です。</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>「この入口がどう見えるか」を定義します。
たとえば、どの port を開けるか、どの protocol を受けるか、TLS をどう付けるか、どの route を許可するか、などです。</p>
<h3 id="listener"><code>Listener</code></h3>
<p><code>Listener</code> は <code>Gateway</code> の中でも最重要クラスの一つです。
Gateway の外向きスロットのようなもので、各スロットが次を定義します。</p>
<ul>
<li>port</li>
<li>protocol</li>
<li>hostname</li>
<li>TLS config</li>
<li><code>allowedRoutes</code></li>
</ul>
<p><code>Gateway</code> を黒箱のように捉える人は多いですが、実際に入口の挙動を決めているのは、その中の各 <code>listener</code> です。</p>
<h3 id="route-ファミリー">Route ファミリー</h3>
<ul>
<li><code>HTTPRoute</code>: HTTP/HTTPS トラフィック。最も一般的</li>
<li><code>GRPCRoute</code>: gRPC トラフィック。service/method でマッチできる</li>
<li><code>TCPRoute</code>: 生の TCP トラフィック。HTTP の意味は解釈しない</li>
<li><code>TLSRoute</code>: TLS SNI ベースでルーティング。TLS passthrough でよく使う</li>
</ul>
<p>すべての route に共通すること:
<strong>「ドアを開ける」のではなく、「入ってきた後にどう流すか」を決めるのが route です。</strong></p>
<h2 id="最小メンタルモデル">最小メンタルモデル</h2>
<p>この地図を頭に置いてください。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#A5D6FF">GatewayClass</span><span style="color:#8B949E">  # この cluster でどの Gateway 実装を使うか</span></span>

<span data-line=""><span style="color:#A5D6FF">Route</span><span style="color:#8B949E">         # 入ってきた後のトラフィック分配方法</span></span>
<span data-line=""><span style="color:#A5D6FF">Service</span><span style="color:#8B949E">       # cluster 内で実際にリクエストを処理する backend</span></span>

<span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  parentRefs</span><span style="color:#E6EDF3">:</span></span>

<p>今すべての field を暗記する必要はありません。何をしているかだけ把握すれば十分です。</p>
<ul>
<li><code>parentRefs</code>: このルールがどの Gateway にぶら下がるか</li>
<li><code>hostnames</code>: どのドメインに対してこのルールを適用するか</li>
<li><code>backendRefs</code>: どの Service に流すか</li>
</ul>

<h2 id="一文まとめ">一文まとめ</h2>
<p><code>Envoy Gateway</code> は、また一つ覚えるだけの用語ではありません。Kubernetes の外部トラフィックを「とりあえず動く」から「ちゃんと工学っぽいシステム」へ引き上げるためのやり方です。</p>
<blockquote>
<p>💡 このスタックが初めてなら、最初からすべての CRD を覚えようとしなくて大丈夫です。まずインストールして、最初のリクエストを通してから概念に戻るほうが、吸収速度はかなり上がります。</p>
</blockquote>

9:T4276,<p>Kubernetes の外部トラフィックを触ったことがあるなら、最初に <code>Ingress</code> から入った可能性は高いと思います。実際ちゃんと動きますし、多くの場面では本当にそれで十分です。ですが、要件が少し複雑になってくると、たとえば複数 listener、複数チームでの運用、gRPC、TCP、TLS passthrough、細かなトラフィックポリシーなどにぶつかった瞬間、結局は「annotation で延命する」が常態化しがちです。YAML は呪文集みたいになり、保守する側も封印を解いている気分になります。</p>
<p>そこで登場するのが <code>Gateway API + Envoy Gateway</code> です。これが新しい道具立てです。複雑さを増やすのではなく、これまで一つに絡まりがちだった責務をきれいに分離してくれるので、入口トラフィック、ルーティングルール、TLS セキュリティ設定、プロトコル種別、チームごとの責任分界をずっと整理して考えやすくなります。</p>
<h2 id="つまり何なのか">つまり何なのか</h2>
<p>まずは一文でまっすぐ言うとこうです。</p>
<ul>
<li><code>Envoy Proxy</code>: 実際にトラフィックを受けてリクエストを転送するデータプレーン。Gateway Proxy と呼ばれることもあります</li>
<li><code>Envoy Gateway</code>: Envoy Proxy をあなたの代わりに管理するコントロールプレーン</li>
<li><code>Gateway API</code>: Kubernetes 上でトラフィックルールを宣言するための標準インターフェース</li>
</ul>
<p>イメージとしてはこうです。</p>
<ul>
<li><code>Gateway API</code> は要件を書く場所</li>
<li><code>Envoy Gateway</code> は翻訳して采配するマネージャー</li>
<li><code>Envoy Proxy</code> は実際に入口に立つガード</li>
</ul>
<p>この分離の利点は、低レベルな Envoy の設定を手で組まなくてよいこと、さらに各 controller 独自の private annotation を全部暗記しなくてよいことです。Kubernetes リソースとして宣言すれば、Envoy Gateway がそれを Envoy Proxy が実行できる設定へ変換してくれます。</p>
<h2 id="gateway-と-ingress-の違い">Gateway と Ingress の違い</h2>
<p>短く言うと、<strong>Ingress が時代遅れになったわけではないけれど、ガバナンスが必要な中規模以上のシステムでは Gateway API のほうが向いています。</strong></p>
<table>
<thead>
<tr>
<th>比較項目</th>
<th>Ingress</th>
<th>Gateway API</th>
</tr>
</thead>
<tbody>
<tr>
<td>Ingress モデル</td>
<td>多くは入口とルーティングを 1 オブジェクトにまとめる</td>
<td><code>GatewayClass</code>、<code>Gateway</code>、<code>Route</code> に分離</td>
</tr>
<tr>
<td>表現力</td>
<td>主に HTTP/HTTPS。高度な機能は annotation 依存</td>
<td>複数の Route type をネイティブに表現でき、field も明確</td>
</tr>
<tr>
<td>拡張モデル</td>
<td>多くの機能が controller 独自 annotation 依存</td>
<td>標準 field を持ち、CRD による拡張点もある</td>
</tr>
<tr>
<td>プロトコル対応</td>
<td>基本は HTTP/Web 中心</td>
<td><code>HTTPRoute</code>、<code>GRPCRoute</code>、<code>TCPRoute</code>、<code>TLSRoute</code> をサポート</td>
</tr>
<tr>

</tr>

<p>要件が例えば次の程度なら:</p>
<ul>
<li>単一サイトかシンプルな API</li>
<li>基本的な path/host ルーティング</li>
<li>小規模チーム</li>
</ul>
<p>Ingress のままでも十分です。ですが、要件が次のようになってくると:</p>
<ul>
<li>一つの入口で複数プロトコルを扱う</li>
<li>複数 listener、ドメイン、証明書がある</li>
<li>HTTP と gRPC が共存する</li>
<li>Platform の入口管理と app の route 権限を分けたい</li>
<li>annotation の寄せ集めではなく、ちゃんと API っぽく読める設定にしたい</li>
</ul>
<p>Gateway API がかなり魅力的に見えてきます。</p>
<h2 id="なぜ-ingress-ではなくこちらなのか">なぜ Ingress ではなくこちらなのか</h2>
<p>Gateway API の公式な狙いは、スケールした Ingress のよくある痛みを解消することです。</p>
<ul>
<li><strong>より高い表現力</strong>: Routing、TLS、traffic policy、protocol type がより明確</li>
<li><strong>より高い可搬性</strong>: controller 固有の private annotation への依存を減らせる</li>
<li><strong>より自然な責務分離</strong>: Platform team が入口を持ち、app team が route を持つ</li>
</ul>
<p>たとえば Ingress の設定は、しばしばこんな感じになります。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">metadata</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  annotations</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/rewrite-target</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/auth-type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">basic</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/ssl-redirect</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"true"</span></span></code></pre></figure>
<p>動かないわけではありません。でも要件が増えるほど、annotation は謎めいた YAML 黒魔術になりやすい。Gateway API はそれを正規の field に引き上げてくれます。読むと「願望リスト」ではなく「設定」に見えます。</p>
<h2 id="レイヤー構造">レイヤー構造</h2>
<p>公式の概念ページでは Envoy Gateway を 3 層に分けています。この図は頭に入れておく価値があります。</p>
<ul>
<li><strong>User Configuration</strong>: あなたが書く <code>Gateway API</code> リソースと Envoy Gateway 拡張 CRD</li>
<li><strong>Envoy Gateway Controller</strong>: それらを読み取り、実行可能な設定へ変換する</li>
<li><strong>Envoy Proxy</strong>: 実際のライブトラフィックを処理するデータプレーン</li>
</ul>
<p>実運用では、SSH で proxy に入って低レベル設定をいじるより、ほとんどの時間をこの「宣言レイヤー」の更新に使います。これが Kubernetes-native であることの美しさです。</p>

<h2 id="これから出てくる主要リソース">これから出てくる主要リソース</h2>
<p>初学者がつまずきやすいのは、Gateway API は <code>Gateway</code> と <code>HTTPRoute</code> だけだと思い込むことです。実際にはリソースのファミリーがあります。</p>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>「この cluster でどの Gateway 実装を使うか」を定義します。
Envoy Gateway では <code>controllerName</code> が正しい controller を指していることが重要です。</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>「この入口がどう見えるか」を定義します。
たとえば、どの port を開けるか、どの protocol を受けるか、TLS をどう付けるか、どの route を許可するか、などです。</p>
<h3 id="listener"><code>Listener</code></h3>
<p><code>Listener</code> は <code>Gateway</code> の中でも最重要クラスの一つです。
Gateway の外向きスロットのようなもので、各スロットが次を定義します。</p>
<ul>
<li>port</li>
<li>protocol</li>
<li>hostname</li>
<li>TLS config</li>
<li><code>allowedRoutes</code></li>
</ul>
<p><code>Gateway</code> を黒箱のように捉える人は多いですが、実際に入口の挙動を決めているのは、その中の各 <code>listener</code> です。</p>
<h3 id="route-ファミリー">Route ファミリー</h3>
<ul>
<li><code>HTTPRoute</code>: HTTP/HTTPS トラフィック。最も一般的</li>
<li><code>GRPCRoute</code>: gRPC トラフィック。service/method でマッチできる</li>
<li><code>TCPRoute</code>: 生の TCP トラフィック。HTTP の意味は解釈しない</li>
<li><code>TLSRoute</code>: TLS SNI ベースでルーティング。TLS passthrough でよく使う</li>
</ul>
<p>すべての route に共通すること:
<strong>「ドアを開ける」のではなく、「入ってきた後にどう流すか」を決めるのが route です。</strong></p>
<h2 id="最小メンタルモデル">最小メンタルモデル</h2>
<p>この地図を頭に置いてください。</p>

<p><code>Envoy Gateway</code> は、また一つ覚えるだけの用語ではありません。Kubernetes の外部トラフィックを「とりあえず動く」から「ちゃんと工学っぽいシステム」へ引き上げるためのやり方です。</p>

</blockquote>
