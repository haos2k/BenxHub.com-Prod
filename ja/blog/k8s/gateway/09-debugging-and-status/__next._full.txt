<h2 id="最重要の-3-condition-まずこれを掴めば足りる">最重要の 3 condition: まずこれを掴めば足りる</h2>
<h3 id="accepted"><code>Accepted</code></h3>
<p>これは通常、その resource が parent に受け入れられたかを示します。
route なら、だいたい次を意味します。</p>
<ul>
<li>意図した Gateway / listener に正常に attach できたか</li>
<li>ルールに明らかな衝突や invalid な設定がないか</li>
</ul>
<p><code>Accepted</code> が <code>False</code> なら、まず疑うのは:</p>
<ul>
<li><code>parentRefs</code> が間違った Gateway や listener を指している</li>
<li>hostname / listener 条件が噛み合っていない</li>
<li>listener がこの route type を拒否している</li>
<li><code>allowedRoutes</code> に阻まれている</li>
</ul>
<h3 id="resolvedrefs"><code>ResolvedRefs</code></h3>
<p>これは resource 内で参照しているオブジェクトが正しく解決できたかを示します。
たとえば:</p>
<ul>
<li><code>backendRefs</code> で参照した <code>Service</code> は存在するか</li>
<li><code>certificateRefs</code> の <code>Secret</code> は正しく参照可能か</li>
<li>Cross-namespace reference 用の <code>ReferenceGrant</code> は適切か</li>
</ul>
<p>この condition はかなり便利です。
設定失敗の多くは routing logic の間違いではなく、参照先が存在しない、または参照権限がないことです。</p>
<h3 id="programmed"><code>Programmed</code></h3>
<p>これは通常、その設定が実装レイヤーに実際に適用されたかを示します。
感覚としてはこうです。</p>
<ul>
<li>controller は設定を受理した</li>
<li>そしてそれを data plane や基盤側へ push した</li>
</ul>
<p><code>Accepted</code> がすでに <code>True</code> なのにトラフィックが流れないなら、ここで <code>Programmed</code>、Gateway address、listener status、下の Envoy リソースを見る価値が出てきます。</p>
<blockquote>
<p>💡 resource によって出る condition の組は多少違いますが、まず直感を作るべき最初の 3 つは <code>Accepted</code>、<code>ResolvedRefs</code>、<code>Programmed</code> です。</p>
</blockquote>
<h2 id="最短-debugging-フロー-たいていこの順でよい">最短 Debugging フロー: たいていこの順でよい</h2>

<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> gateway</span><span style="color:#79B8FF"> -A</span></span>

<p>確認ポイント:</p>
<ul>
<li><code>status.addresses</code> に値があるか</li>

<li>listener の hostname / protocol / port は想定通りか</li>
</ul>
<p>Gateway に address がなければ、どれだけ美しい route YAML でも、それは創作活動です。</p>

<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> httproute</span><span style="color:#79B8FF"> -A</span></span>

<p>優先して見る項目:</p>
<ul>
<li><code>status.parents</code></li>
<li><code>Accepted</code></li>
<li><code>ResolvedRefs</code></li>
<li><code>observedGeneration</code></li>
</ul>
<p><code>observedGeneration</code> も意外と大事です。
<code>metadata.generation</code> に追いついていないなら、controller がまだ最新の設定 version を処理していない可能性があります。</p>
<h3 id="step-3-参照先-resource-が本当に存在するかを見る">Step 3: 参照先 resource が本当に存在するかを見る</h3>
<p>ここは一番よく飛ばされるステップです。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> svc</span><span style="color:#79B8FF"> -A</span></span>

<li>Cross-namespace reference に <code>ReferenceGrant</code> がない</li>
</ul>
<p><code>ResolvedRefs</code> が <code>False</code> なら、この線で追うのが定石です。</p>
<h3 id="step-4-data-plane-と-controller-を見る">Step 4: Data Plane と Controller を見る</h3>
<p>Gateway と Route の status がどちらもそれなりに正しそうなのに、まだトラフィックが流れないなら、さらに下を見ます。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> pods</span><span style="color:#79B8FF"> -n</span><span style="color:#9ECBFF"> envoy-gateway-system</span></span>

<p>この段階では「rule が受理されたか」を見ているのではなく、control plane と data plane が正常に動いているかを見ています。</p>
<p><code>egctl</code> が入っていれば status 確認がより楽になります。
ですが、なくても <code>kubectl get/describe -o yaml</code> で大半の問題は解けます。</p>
<h2 id="よくある-4-つの失敗パターン">よくある 4 つの失敗パターン</h2>
<h3 id="1-route-自体は正しいが意図した-listener-に-attach-されていない">1. Route 自体は正しいが、意図した Listener に attach されていない</h3>
<p>症状:</p>
<ul>
<li>YAML は正しそう</li>
<li>でもトラフィックが rule に当たらない</li>
</ul>
<p>確認すること:</p>
<ul>
<li><code>parentRefs.name</code></li>
<li><code>parentRefs.sectionName</code></li>
<li>Gateway の listener 名が完全一致しているか</li>
</ul>
<p>複数 listener 構成では、<code>sectionName</code> の typo 1 つで debugging セッションが丸ごと溶けます。</p>
<h3 id="2-accepted-は通るが-resolvedrefs-が失敗する">2. <code>Accepted</code> は通るが <code>ResolvedRefs</code> が失敗する</h3>
<p>これは通常、attach そのものは可能でも、参照している何かに問題があることを意味します。
よくある原因:</p>
<ul>
<li>Backend Service が存在しない</li>
<li>Secret 名が違う</li>
<li>Cross-namespace reference に認可がない</li>
</ul>
<p>このタイプの失敗がいやらしいのは、「もう少しで通りそう」に見えるのに、実際は参照レイヤーで止まっていることです。</p>
<h3 id="3-gateway-に-listener-はあるのに想定した-address-がない">3. Gateway に Listener はあるのに想定した Address がない</h3>
<p>これはローカル cluster や <code>LoadBalancer</code> 実装のない環境でよく起きます。
Gateway API が壊れているわけではなく、単に基盤が外部 address を払い出していません。</p>
<p>対処:</p>
<ul>
<li>cluster に <code>LoadBalancer</code> 機能があるか確認する</li>
<li><code>port-forward</code> で routing path を検証する</li>
</ul>
<h3 id="4-yaml-は効いたように見えるのにrequest-が-404--503-を返す">4. YAML は効いたように見えるのに、request が 404 / 503 を返す</h3>
<p>この段階では、単一 field のミスというより、どこかのチェーンが切れていることが多いです。</p>
<ul>
<li>Host header が違う</li>
<li>path がどの rule にもマッチしていない</li>
<li>Backend Pod が unhealthy</li>
<li>Service selector がどの Pod も選んでいない</li>
</ul>
<p>入口の問題に見えても、backend 側がまだ ready でないだけ、ということはよくあります。何でも proxy 層のせいにしないことです。向こうも忙しいです。</p>
<h2 id="一文まとめ">一文まとめ</h2>
<p>Gateway API を最速で debug する方法は、YAML を何度もいじることではなく <code>status</code> を読む力をつけることです。
<code>Accepted</code> は受理されたか、<code>ResolvedRefs</code> は参照が解決できたか、<code>Programmed</code> は実際に適用されたかを示します。この 3 層を分けて見るだけで、トラブルシュート速度はかなり上がります。</p>

<h2 id="最重要の-3-condition-まずこれを掴めば足りる">最重要の 3 condition: まずこれを掴めば足りる</h2>
<h3 id="accepted"><code>Accepted</code></h3>
<p>これは通常、その resource が parent に受け入れられたかを示します。
route なら、だいたい次を意味します。</p>
<ul>
<li>意図した Gateway / listener に正常に attach できたか</li>
<li>ルールに明らかな衝突や invalid な設定がないか</li>
</ul>
<p><code>Accepted</code> が <code>False</code> なら、まず疑うのは:</p>
<ul>
<li><code>parentRefs</code> が間違った Gateway や listener を指している</li>
<li>hostname / listener 条件が噛み合っていない</li>
<li>listener がこの route type を拒否している</li>
<li><code>allowedRoutes</code> に阻まれている</li>
</ul>
<h3 id="resolvedrefs"><code>ResolvedRefs</code></h3>
<p>これは resource 内で参照しているオブジェクトが正しく解決できたかを示します。
たとえば:</p>
<ul>
<li><code>backendRefs</code> で参照した <code>Service</code> は存在するか</li>
<li><code>certificateRefs</code> の <code>Secret</code> は正しく参照可能か</li>
<li>Cross-namespace reference 用の <code>ReferenceGrant</code> は適切か</li>
</ul>
<p>この condition はかなり便利です。
設定失敗の多くは routing logic の間違いではなく、参照先が存在しない、または参照権限がないことです。</p>
<h3 id="programmed"><code>Programmed</code></h3>
<p>これは通常、その設定が実装レイヤーに実際に適用されたかを示します。
感覚としてはこうです。</p>
<ul>
<li>controller は設定を受理した</li>
<li>そしてそれを data plane や基盤側へ push した</li>
</ul>
<p><code>Accepted</code> がすでに <code>True</code> なのにトラフィックが流れないなら、ここで <code>Programmed</code>、Gateway address、listener status、下の Envoy リソースを見る価値が出てきます。</p>
<blockquote>
<p>💡 resource によって出る condition の組は多少違いますが、まず直感を作るべき最初の 3 つは <code>Accepted</code>、<code>ResolvedRefs</code>、<code>Programmed</code> です。</p>
</blockquote>
<h2 id="最短-debugging-フロー-たいていこの順でよい">最短 Debugging フロー: たいていこの順でよい</h2>
<h3 id="step-1-gateway-自体がちゃんと動いているかを見る">Step 1: Gateway 自体がちゃんと動いているかを見る</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> gateway</span><span style="color:#79B8FF"> -A</span></span>

<ul>

</ul>

<code>metadata.generation</code> に追いついていないなら、controller がまだ最新の設定 version を処理していない可能性があります。</p>
<h3 id="step-3-参照先-resource-が本当に存在するかを見る">Step 3: 参照先 resource が本当に存在するかを見る</h3>

<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> svc</span><span style="color:#79B8FF"> -A</span></span>
