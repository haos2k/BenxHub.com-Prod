1d:T55c9,<p>Gateway API を初めて見たとき、多くの人はこう感じます。「用語の数はそこまで多くないのに、似た名前の登場人物が一気に出てくる感じで、誰が主役で誰が脇役かわからない。」この記事はその混乱を切り分けるためのものです。あわせて代表的な route type も一通り整理します。</p>
<h2 id="全体アーキテクチャ">全体アーキテクチャ</h2>
<p>Envoy Gateway の公式概念では、全体を 3 層に分けています。</p>
<ul>
<li><strong>User Configuration</strong>: あなたが書く <code>Gateway API</code> リソースと Envoy Gateway 拡張 CRD</li>
<li><strong>Envoy Gateway Controller</strong>: リソースを読み、検証し、設定へ変換する</li>
<li><strong>Envoy Proxy</strong>: 実際にトラフィックを処理するデータプレーン</li>
</ul>
<p>つまり、普段あなたが編集するのは Envoy Proxy そのものではなく、「どうしたいかの宣言」です。
Envoy Gateway がその宣言を Envoy Proxy が実行できる設定に変換します。これが proxy 設定を手で書くより気持ちよい理由です。</p>
<h2 id="主要な役割">主要な役割</h2>
<p>今はこの対応関係だけ覚えておけば十分です。</p>
<ul>
<li><code>GatewayClass</code>: 「この cluster でどの Gateway 実装を使うか」を定義する</li>
<li><code>Gateway</code>: 「入口がどこにあり、どの protocol を話すか」を定義する</li>
<li><code>Listener</code>: 特定の port/protocol/hostname の入口スロットを定義する</li>
<li><code>Route</code>: 「どのリクエストをどの Service に送るか」を定義する</li>
<li><code>Envoy Proxy</code>: 実際にトラフィックを受けて転送する Gateway Proxy</li>
</ul>
<p>平たく言うと:</p>
<ul>
<li><code>GatewayClass</code> は仕様書</li>
<li><code>Gateway</code> は建物の正面入口</li>
<li><code>Listener</code> は受付窓口</li>
<li><code>Route</code> は館内の案内表示</li>
<li><code>Envoy Proxy</code> は入退室管理と案内を実行するセキュリティシステム</li>
</ul>
<p>このどれか一つが欠けても、トラフィックは意図した場所へ届きません。</p>

<h2 id="各-field-の理解">各 field の理解</h2>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>これは cluster-level の入口タイプ定義です。最重要 field はたいていこれです。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">spec</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  controllerName</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.envoyproxy.io/gatewayclass-controller</span></span></code></pre></figure>
<p>意味は単純です。
「この <code>GatewayClass</code> は Envoy Gateway controller に管理される。」</p>
<p>controllerName が一致しないと、配達先を別会社にしているようなものです。誰も受け取りません。</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>これは「入口がどう見えるか」を定義します。最もよく参照する field は <code>listeners</code> です。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">listeners</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">http</span></span>
<span data-line=""><span style="color:#85E89D">    protocol</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">HTTP</span></span>
<span data-line=""><span style="color:#85E89D">    port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">80</span></span></code></pre></figure>
<p>意味は次の通りです。</p>
<ul>
<li><code>http</code> という名前の listener を開く</li>
<li>HTTP トラフィックを受ける</li>
<li>外部向けに port <code>80</code> を listen する</li>
</ul>
<p>HTTPS なら、通常は <code>protocol: HTTPS</code> の listener を追加し、TLS 設定を付けます。</p>
<p><code>Gateway</code> がよく管理するもの:</p>
<ul>
<li>外部向けの port と protocol</li>
<li>listener ごとの hostname</li>
<li>TLS termination の位置</li>
<li>どの namespace の route を attach 可能にするか</li>
</ul>
<p><code>Gateway</code> は app 側というより platform 層の関心事であることが多く、所有者も platform team になるのが一般的です。</p>
<h3 id="listener"><code>Listener</code></h3>
<p>初心者に最も見落とされやすい役割ですが、実はかなり重要です。</p>
<p><code>listener</code> は Gateway 上の外向き入口スロットです。次を定義します。</p>
<ul>
<li><code>name</code></li>
<li><code>port</code></li>
<li><code>protocol</code></li>
<li><code>hostname</code></li>
<li><code>tls</code></li>
<li><code>allowedRoutes</code></li>
</ul>
<p>例:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">listeners</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">https</span></span>
<span data-line=""><span style="color:#85E89D">    protocol</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">HTTPS</span></span>
<span data-line=""><span style="color:#85E89D">    port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">443</span></span>
<span data-line=""><span style="color:#85E89D">    hostname</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">api.example.com</span></span></code></pre></figure>
<p>意味:</p>
<ul>
<li>このスロット名は <code>https</code></li>
<li>HTTPS を受ける</li>
<li>port <code>443</code> を listen する</li>
<li><code>api.example.com</code> 専用</li>
</ul>
<p>たとえば複数 listener を持つなら:</p>
<ul>
<li>port 80 用の <code>http</code></li>
<li>port 443 用の <code>https</code></li>
<li>port 50051 用の <code>grpc</code></li>
</ul>
<p>同じ Gateway の中に複数の入口スロットを開いており、それぞれに別の route を attach できます。</p>
<h3 id="envoy-proxy"><code>Envoy Proxy</code></h3>
<p>YAML ばかり見て、実際にライブトラフィックを処理するのが <code>Envoy Proxy</code> だという点を忘れる人は少なくありません。</p>
<p>役割は次の通りです。</p>
<ul>
<li>クライアントリクエストを受ける</li>
<li>Envoy Gateway から push された設定にマッチさせる</li>
<li>適切な backend へ転送する</li>
<li>TLS、header、timeout、retry などの data-plane 振る舞いを処理する</li>
</ul>
<p>なので、Envoy Gateway は「control plane」、Envoy Proxy は「data plane / Gateway Proxy」と考えると整理しやすいです。</p>
<h3 id="route-ファミリー">Route ファミリー</h3>
<p><code>Route</code> は <code>HTTPRoute</code> だけではありません。このファミリー全体が Gateway API の中心です。</p>
<h4 id="httproute"><code>HTTPRoute</code></h4>
<p>最もよく書き換えるのはこれです。代表的な 3 field は次の通りです。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">spec</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  parentRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">eg</span></span>
<span data-line=""><span style="color:#85E89D">  hostnames</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#9ECBFF">"www.example.com"</span></span>
<span data-line=""><span style="color:#85E89D">  rules</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">        - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">backend</span></span>
<span data-line=""><span style="color:#85E89D">          port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">3000</span></span></code></pre></figure>
<ul>
<li><code>parentRefs</code>: どの Gateway に attach するか</li>
<li><code>hostnames</code>: どの Host header がこのルールを発火させるか</li>
<li><code>backendRefs</code>: マッチしたリクエストをどこへ送るか</li>
</ul>
<p>よくある誤解は、細かいルーティングを <code>Gateway</code> に書くと思ってしまうことです。実際に「どう振り分けるか」を決めるのは <code>HTTPRoute</code> のほうです。</p>
<h4 id="grpcroute"><code>GRPCRoute</code></h4>
<p>gRPC を扱うなら、無理に <code>HTTPRoute</code> に押し込むより <code>GRPCRoute</code> のほうが自然です。</p>
<p>マッチできる対象:</p>
<ul>
<li>gRPC hostname</li>
<li>gRPC service</li>
<li>gRPC method</li>
<li>headers</li>
</ul>
<p>例:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">matches</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">method</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">      service</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">com.example.User</span></span>
<span data-line=""><span style="color:#85E89D">      method</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">Login</span></span></code></pre></figure>
<p>この意味論は gRPC に自然に一致します。単なる URL path ではなく、gRPC の service/method モデルそのものにマッチできます。</p>
<p>公式ドキュメントでも、<code>GRPCRoute</code> と <code>HTTPRoute</code> が同じ listener を共有し、hostname が衝突した場合は実装側が片方を reject すべきだとされています。要するに、HTTP と gRPC に同じ hostname の取り合いをさせないことです。</p>
<h4 id="tcproute"><code>TCPRoute</code></h4>
<p><code>TCPRoute</code> は生の TCP トラフィックを扱います。
<code>HTTPRoute</code> と違って L7 の path や header は理解しません。L4 に近い転送です。</p>
<p>向いている場面:</p>
<ul>
<li>非 HTTP protocol の service</li>
<li>純粋な TCP service</li>
<li>listener port だけを見て異なる backend へ接続を振り分ける</li>
</ul>
<p>独自 protocol の database や proprietary な TCP protocol は <code>TCPRoute</code> の典型例です。</p>
<h4 id="tlsroute"><code>TLSRoute</code></h4>
<p><code>TLSRoute</code> は TLS トラフィックを扱い、特に <strong>TLS passthrough</strong> の場面でよく使われます。</p>
<p>コア概念:</p>
<ul>
<li>Gateway が TLS を終端しない場合がある</li>
<li>TLS handshake の SNI hostname だけでルーティングすることがある</li>
<li>暗号化トラフィックを backend までそのまま保つ</li>
</ul>
<p>これは、end-to-end の暗号化が必要な場面や、Gateway で TLS を終端したくない場面で重要です。</p>
<h2 id="route-type-の選び方">Route type の選び方</h2>
<table>
<thead>
<tr>
<th>要件</th>
<th>使うもの</th>
</tr>
</thead>
<tbody>
<tr>
<td>Web サイト、REST API、一般的な web traffic</td>
<td><code>HTTPRoute</code></td>
</tr>
<tr>
<td>gRPC service/method routing</td>
<td><code>GRPCRoute</code></td>
</tr>
<tr>
<td>生の TCP トラフィック</td>
<td><code>TCPRoute</code></td>
</tr>
<tr>
<td>TLS passthrough / SNI ベース routing</td>
<td><code>TLSRoute</code></td>
</tr>
</tbody>
</table>
<p>この表が大事なのは、多くの人が何でも <code>HTTPRoute</code> で書き始めてしまうからです。実際には gRPC や TCP を扱っているのに <code>HTTPRoute</code> に押し込むと、YAML がどんどん不自然になります。</p>
<h2 id="なぜ-route-のほうが-ingress-より整理しやすいのか">なぜ Route のほうが Ingress より整理しやすいのか</h2>
<p>従来の Ingress 設定は 1 つのリソースに責務を詰め込みすぎることが多く、いくつかの痛みがありました。</p>
<ul>
<li>Platform 設定と app routing が混ざる</li>
<li>高度な機能が annotation で表現され、読みづらい</li>
<li>非 HTTP protocol の表現力が弱い</li>
</ul>
<p>Gateway API は責務を分ける方向で設計されています。</p>
<ul>
<li>Platform team が <code>GatewayClass</code> / <code>Gateway</code> を管理する</li>
<li>App team が自分たちの <code>HTTPRoute</code> を管理する</li>
</ul>
<p>この分離は複数人の協業でかなり効きます。path を変えるだけなのに入口全体を触る必要がなくなり、チーム同士で踏み合う事故が大きく減ります。</p>
<h2 id="status-を見る習慣をつける"><code>status</code> を見る習慣をつける</h2>
<p><code>spec</code> だけでなく、徐々に <code>status</code> も見る習慣をつけましょう。特に <code>HTTPRoute</code> と <code>Gateway</code> は重要です。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> gateway</span><span style="color:#9ECBFF"> eg</span><span style="color:#79B8FF"> -o</span><span style="color:#9ECBFF"> yaml</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> httproute</span><span style="color:#9ECBFF"> backend</span><span style="color:#79B8FF"> -o</span><span style="color:#9ECBFF"> yaml</span></span></code></pre></figure>
<p>最初は次を見るだけでも十分です。</p>
<ul>
<li>route が <code>Accepted</code> されたか</li>
<li>gateway listener が Ready か</li>
<li>address が割り当てられたか</li>
</ul>
<p>提出しただけで終わりにせず、採点されて合格したかまで見る。そんな感覚です。</p>
<h2 id="一文まとめ">一文まとめ</h2>
<p><code>GatewayClass</code>、<code>Gateway</code>、<code>Listener</code>、<code>Route</code>、<code>Envoy Proxy</code> を、「誰が管理し、入口がどう開き、各スロットがどうつながり、トラフィックがどう分かれ、誰が実行するのか」として捉えられれば、コア概念の 8 割はもう掴めています。</p>
<blockquote>
<p>💡 初心者はすぐ CRD の細部に突っ込みがちです。でも焦らなくて大丈夫です。まずこの役割分担を整理すると、YAML が毎回初対面の他人に見える感じがかなり減ります。</p>
</blockquote>

<h2 id="全体アーキテクチャ">全体アーキテクチャ</h2>
<p>Envoy Gateway の公式概念では、全体を 3 層に分けています。</p>
<ul>
<li><strong>User Configuration</strong>: あなたが書く <code>Gateway API</code> リソースと Envoy Gateway 拡張 CRD</li>
<li><strong>Envoy Gateway Controller</strong>: リソースを読み、検証し、設定へ変換する</li>
<li><strong>Envoy Proxy</strong>: 実際にトラフィックを処理するデータプレーン</li>
</ul>
<p>つまり、普段あなたが編集するのは Envoy Proxy そのものではなく、「どうしたいかの宣言」です。
Envoy Gateway がその宣言を Envoy Proxy が実行できる設定に変換します。これが proxy 設定を手で書くより気持ちよい理由です。</p>
<h2 id="主要な役割">主要な役割</h2>
<p>今はこの対応関係だけ覚えておけば十分です。</p>
<ul>
<li><code>GatewayClass</code>: 「この cluster でどの Gateway 実装を使うか」を定義する</li>
<li><code>Gateway</code>: 「入口がどこにあり、どの protocol を話すか」を定義する</li>
<li><code>Listener</code>: 特定の port/protocol/hostname の入口スロットを定義する</li>
<li><code>Route</code>: 「どのリクエストをどの Service に送るか」を定義する</li>
<li><code>Envoy Proxy</code>: 実際にトラフィックを受けて転送する Gateway Proxy</li>
</ul>
<p>平たく言うと:</p>
<ul>
<li><code>GatewayClass</code> は仕様書</li>
<li><code>Gateway</code> は建物の正面入口</li>
<li><code>Listener</code> は受付窓口</li>
<li><code>Route</code> は館内の案内表示</li>
<li><code>Envoy Proxy</code> は入退室管理と案内を実行するセキュリティシステム</li>
</ul>
<p>このどれか一つが欠けても、トラフィックは意図した場所へ届きません。</p>

<p>連鎖としてはこうなります。</p>
<ol>
<li><code>GatewayClass</code> が <code>Envoy Gateway</code> controller を担当者として示す</li>
<li><code>Gateway</code> が port <code>80</code> の HTTP 入口を 1 つ宣言する</li>
<li><code>HTTPRoute</code> が <code>www.example.com</code> へのリクエストを <code>backend:3000</code> に送ると定義する</li>
<li><code>Envoy Gateway</code> がこれらをまとめて <code>Envoy Proxy</code> 用に変換する</li>
</ol>
<h2 id="各-field-の理解">各 field の理解</h2>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>これは cluster-level の入口タイプ定義です。最重要 field はたいていこれです。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">spec</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  controllerName</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.envoyproxy.io/gatewayclass-controller</span></span></code></pre></figure>
<p>意味は単純です。
「この <code>GatewayClass</code> は Envoy Gateway controller に管理される。」</p>
<p>controllerName が一致しないと、配達先を別会社にしているようなものです。誰も受け取りません。</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>これは「入口がどう見えるか」を定義します。最もよく参照する field は <code>listeners</code> です。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">listeners</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">http</span></span>
<span data-line=""><span style="color:#85E89D">    protocol</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">HTTP</span></span>
<span data-line=""><span style="color:#85E89D">    port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">80</span></span></code></pre></figure>
<p>意味は次の通りです。</p>
<ul>
<li><code>http</code> という名前の listener を開く</li>
<li>HTTP トラフィックを受ける</li>
<li>外部向けに port <code>80</code> を listen する</li>
</ul>
<p>HTTPS なら、通常は <code>protocol: HTTPS</code> の listener を追加し、TLS 設定を付けます。</p>
<p><code>Gateway</code> がよく管理するもの:</p>
<ul>
<li>外部向けの port と protocol</li>
<li>listener ごとの hostname</li>
<li>TLS termination の位置</li>
<li>どの namespace の route を attach 可能にするか</li>
</ul>
<p><code>Gateway</code> は app 側というより platform 層の関心事であることが多く、所有者も platform team になるのが一般的です。</p>
<h3 id="listener"><code>Listener</code></h3>
<p>初心者に最も見落とされやすい役割ですが、実はかなり重要です。</p>
<p><code>listener</code> は Gateway 上の外向き入口スロットです。次を定義します。</p>
<ul>
<li><code>name</code></li>
<li><code>port</code></li>
<li><code>protocol</code></li>
<li><code>hostname</code></li>
<li><code>tls</code></li>
<li><code>allowedRoutes</code></li>
</ul>
<p>例:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">listeners</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">https</span></span>
<span data-line=""><span style="color:#85E89D">    protocol</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">HTTPS</span></span>
<span data-line=""><span style="color:#85E89D">    port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">443</span></span>
<span data-line=""><span style="color:#85E89D">    hostname</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">api.example.com</span></span></code></pre></figure>
<p>意味:</p>
<ul>
<li>このスロット名は <code>https</code></li>
<li>HTTPS を受ける</li>
<li>port <code>443</code> を listen する</li>
<li><code>api.example.com</code> 専用</li>
</ul>
<p>たとえば複数 listener を持つなら:</p>
<ul>
<li>port 80 用の <code>http</code></li>
<li>port 443 用の <code>https</code></li>
<li>port 50051 用の <code>grpc</code></li>
</ul>
<p>同じ Gateway の中に複数の入口スロットを開いており、それぞれに別の route を attach できます。</p>
<h3 id="envoy-proxy"><code>Envoy Proxy</code></h3>
<p>YAML ばかり見て、実際にライブトラフィックを処理するのが <code>Envoy Proxy</code> だという点を忘れる人は少なくありません。</p>
<p>役割は次の通りです。</p>
<ul>
<li>クライアントリクエストを受ける</li>
<li>Envoy Gateway から push された設定にマッチさせる</li>
<li>適切な backend へ転送する</li>
<li>TLS、header、timeout、retry などの data-plane 振る舞いを処理する</li>
</ul>
<p>なので、Envoy Gateway は「control plane」、Envoy Proxy は「data plane / Gateway Proxy」と考えると整理しやすいです。</p>
<h3 id="route-ファミリー">Route ファミリー</h3>
<p><code>Route</code> は <code>HTTPRoute</code> だけではありません。このファミリー全体が Gateway API の中心です。</p>
<h4 id="httproute"><code>HTTPRoute</code></h4>
<p>最もよく書き換えるのはこれです。代表的な 3 field は次の通りです。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">spec</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  parentRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">eg</span></span>
<span data-line=""><span style="color:#85E89D">  hostnames</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#9ECBFF">"www.example.com"</span></span>
<span data-line=""><span style="color:#85E89D">  rules</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">        - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">backend</span></span>
<span data-line=""><span style="color:#85E89D">          port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">3000</span></span></code></pre></figure>
<ul>
<li><code>parentRefs</code>: どの Gateway に attach するか</li>
<li><code>hostnames</code>: どの Host header がこのルールを発火させるか</li>
<li><code>backendRefs</code>: マッチしたリクエストをどこへ送るか</li>
</ul>
<p>よくある誤解は、細かいルーティングを <code>Gateway</code> に書くと思ってしまうことです。実際に「どう振り分けるか」を決めるのは <code>HTTPRoute</code> のほうです。</p>
<h4 id="grpcroute"><code>GRPCRoute</code></h4>
<p>gRPC を扱うなら、無理に <code>HTTPRoute</code> に押し込むより <code>GRPCRoute</code> のほうが自然です。</p>
<p>マッチできる対象:</p>
<ul>
<li>gRPC hostname</li>
<li>gRPC service</li>
<li>gRPC method</li>
<li>headers</li>
</ul>
<p>例:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">matches</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">method</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">      service</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">com.example.User</span></span>
<span data-line=""><span style="color:#85E89D">      method</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">Login</span></span></code></pre></figure>
<p>この意味論は gRPC に自然に一致します。単なる URL path ではなく、gRPC の service/method モデルそのものにマッチできます。</p>
<p>公式ドキュメントでも、<code>GRPCRoute</code> と <code>HTTPRoute</code> が同じ listener を共有し、hostname が衝突した場合は実装側が片方を reject すべきだとされています。要するに、HTTP と gRPC に同じ hostname の取り合いをさせないことです。</p>
<h4 id="tcproute"><code>TCPRoute</code></h4>
<p><code>TCPRoute</code> は生の TCP トラフィックを扱います。
<code>HTTPRoute</code> と違って L7 の path や header は理解しません。L4 に近い転送です。</p>
<p>向いている場面:</p>
<ul>
<li>非 HTTP protocol の service</li>
<li>純粋な TCP service</li>
<li>listener port だけを見て異なる backend へ接続を振り分ける</li>
</ul>
<p>独自 protocol の database や proprietary な TCP protocol は <code>TCPRoute</code> の典型例です。</p>
<h4 id="tlsroute"><code>TLSRoute</code></h4>
<p><code>TLSRoute</code> は TLS トラフィックを扱い、特に <strong>TLS passthrough</strong> の場面でよく使われます。</p>
<p>コア概念:</p>
<ul>
<li>Gateway が TLS を終端しない場合がある</li>
<li>TLS handshake の SNI hostname だけでルーティングすることがある</li>
<li>暗号化トラフィックを backend までそのまま保つ</li>
</ul>
<p>これは、end-to-end の暗号化が必要な場面や、Gateway で TLS を終端したくない場面で重要です。</p>
<h2 id="route-type-の選び方">Route type の選び方</h2>
<table>
<thead>
<tr>
<th>要件</th>
<th>使うもの</th>
</tr>
</thead>
<tbody>
<tr>
<td>Web サイト、REST API、一般的な web traffic</td>
<td><code>HTTPRoute</code></td>
</tr>
<tr>
<td>gRPC service/method routing</td>
<td><code>GRPCRoute</code></td>
</tr>
<tr>
<td>生の TCP トラフィック</td>
<td><code>TCPRoute</code></td>
</tr>
<tr>
<td>TLS passthrough / SNI ベース routing</td>
<td><code>TLSRoute</code></td>
</tr>
</tbody>
</table>
<p>この表が大事なのは、多くの人が何でも <code>HTTPRoute</code> で書き始めてしまうからです。実際には gRPC や TCP を扱っているのに <code>HTTPRoute</code> に押し込むと、YAML がどんどん不自然になります。</p>
<h2 id="なぜ-route-のほうが-ingress-より整理しやすいのか">なぜ Route のほうが Ingress より整理しやすいのか</h2>
<p>従来の Ingress 設定は 1 つのリソースに責務を詰め込みすぎることが多く、いくつかの痛みがありました。</p>
<ul>
<li>Platform 設定と app routing が混ざる</li>
<li>高度な機能が annotation で表現され、読みづらい</li>
<li>非 HTTP protocol の表現力が弱い</li>
</ul>
<p>Gateway API は責務を分ける方向で設計されています。</p>
<ul>
<li>Platform team が <code>GatewayClass</code> / <code>Gateway</code> を管理する</li>
<li>App team が自分たちの <code>HTTPRoute</code> を管理する</li>
</ul>
<p>この分離は複数人の協業でかなり効きます。path を変えるだけなのに入口全体を触る必要がなくなり、チーム同士で踏み合う事故が大きく減ります。</p>
<h2 id="status-を見る習慣をつける"><code>status</code> を見る習慣をつける</h2>
<p><code>spec</code> だけでなく、徐々に <code>status</code> も見る習慣をつけましょう。特に <code>HTTPRoute</code> と <code>Gateway</code> は重要です。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> gateway</span><span style="color:#9ECBFF"> eg</span><span style="color:#79B8FF"> -o</span><span style="color:#9ECBFF"> yaml</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> httproute</span><span style="color:#9ECBFF"> backend</span><span style="color:#79B8FF"> -o</span><span style="color:#9ECBFF"> yaml</span></span></code></pre></figure>
<p>最初は次を見るだけでも十分です。</p>
<ul>
<li>route が <code>Accepted</code> されたか</li>
<li>gateway listener が Ready か</li>
<li>address が割り当てられたか</li>
</ul>
<p>提出しただけで終わりにせず、採点されて合格したかまで見る。そんな感覚です。</p>
<h2 id="一文まとめ">一文まとめ</h2>
<p><code>GatewayClass</code>、<code>Gateway</code>、<code>Listener</code>、<code>Route</code>、<code>Envoy Proxy</code> を、「誰が管理し、入口がどう開き、各スロットがどうつながり、トラフィックがどう分かれ、誰が実行するのか」として捉えられれば、コア概念の 8 割はもう掴めています。</p>
<blockquote>
<p>💡 初心者はすぐ CRD の細部に突っ込みがちです。でも焦らなくて大丈夫です。まずこの役割分担を整理すると、YAML が毎回初対面の他人に見える感じがかなり減ります。</p>
</blockquote>
