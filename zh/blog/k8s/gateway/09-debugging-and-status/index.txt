<p><strong>YAML 套上去了，<code>kubectl apply</code> 也成功了，但流量就是沒通。</strong></p>
<p>這時候如果你只盯著 <code>spec</code> 看，很容易越看越像在占卜。<br>
Gateway API 真正的救命資訊，很多都在 <code>status</code> 裡。</p>
<p>這篇的目標很簡單：幫你建立一套最短除錯路徑。讓你遇到 <code>Gateway</code>、<code>HTTPRoute</code>、<code>Listener</code> 不生效時，知道先看哪裡，而不是一開場就懷疑宇宙。</p>
<h2 id="先記住除錯先看-status不是先改-yaml">先記住：除錯先看 <code>status</code>，不是先改 YAML</h2>
<p>最常用的幾個指令：</p>

<p>重點不是把 YAML 再讀一百遍，而是看 controller 有沒有真的接受你的設定。</p>
<p>你可以把 <code>status</code> 想成考試成績單：</p>
<ul>
<li><code>spec</code> 是你交上去的答案</li>
<li><code>status</code> 是系統批改後的結果</li>
</ul>
<p>只看交卷內容，不看成績，很多時候真的只是心靈安慰。</p>
<h2 id="三個最常見的-condition先看懂這些就夠用了">三個最常見的 condition：先看懂這些就夠用了</h2>
<h3 id="accepted"><code>Accepted</code></h3>
<p>這通常表示資源有沒有被父層接納。<br>
以 route 來說，意思通常接近：</p>
<ul>
<li>有沒有成功附掛到對應 Gateway / listener</li>
<li>規則本身有沒有明顯衝突或不合法</li>
</ul>
<p>如果 <code>Accepted</code> 是 <code>False</code>，先懷疑：</p>
<ul>
<li><code>parentRefs</code> 指錯 Gateway 或 listener</li>
<li>hostname / listener 條件不匹配</li>
<li>該 listener 不接受這種 route 類型</li>
<li><code>allowedRoutes</code> 把你擋掉了</li>
</ul>
<h3 id="resolvedrefs"><code>ResolvedRefs</code></h3>
<p>這表示資源裡引用到的其他物件有沒有成功解析。<br>
例如：</p>
<ul>
<li><code>backendRefs</code> 指到的 Service 存不存在</li>
<li><code>certificateRefs</code> 指到的 Secret 能不能合法引用</li>
<li>跨 namespace 引用有沒有配好 <code>ReferenceGrant</code></li>
</ul>
<p>這個 condition 超實用。<br>
因為很多設定不是路由邏輯有錯，而是你引用的東西根本不存在，或沒有權限引用。</p>
<h3 id="programmed"><code>Programmed</code></h3>
<p>這通常代表設定有沒有真的被實作層落地。<br>
你可以把它理解成：</p>
<ul>
<li>controller 已經接受</li>
<li>也把設定推進資料面或基礎設施</li>
</ul>
<p>如果 <code>Accepted</code> 已經是 <code>True</code>，但實際流量還是不通，這時就值得去看 <code>Programmed</code>、Gateway address、listener 狀態，以及底下的 Envoy 相關資源。</p>
<blockquote>
<p>💡 不同資源會看到的 condition 可能不完全相同，但 <code>Accepted</code>、<code>ResolvedRefs</code>、<code>Programmed</code> 是最值得優先建立感覺的一組。</p>
</blockquote>
<h2 id="最短排錯流程照這個順序通常夠用">最短排錯流程：照這個順序通常夠用</h2>
<h3 id="第一步先看-gateway-有沒有真的站起來">第一步：先看 Gateway 有沒有真的站起來</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#A5D6FF"> eg</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span></code></pre></figure>
<p>先確認：</p>
<ul>
<li><code>status.addresses</code> 有沒有值</li>
<li>listener condition 有沒有異常</li>
<li>listener 的 hostname / protocol / port 是不是你以為的那組</li>
</ul>
<p>如果連 Gateway 都沒 address，後面 route 寫得再漂亮都只是文學創作。</p>
<h3 id="第二步看-route-有沒有被接上">第二步：看 Route 有沒有被接上</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#A5D6FF"> app-route</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span></code></pre></figure>
<p>優先看：</p>
<ul>
<li><code>status.parents</code></li>
<li><code>Accepted</code></li>
<li><code>ResolvedRefs</code></li>
<li><code>observedGeneration</code></li>
</ul>
<p><code>observedGeneration</code> 很值得注意。<br>
如果它還沒追上 <code>metadata.generation</code>，代表 controller 可能還沒處理到你最新那版設定。</p>
<h3 id="第三步看引用資源是不是都存在">第三步：看引用資源是不是都存在</h3>
<p>這一步超多人漏掉：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> svc</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> secret</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> referencegrant</span><span style="color:#79C0FF"> -A</span></span></code></pre></figure>
<p>常見問題像是：</p>
<ul>
<li>backend service 名字打錯</li>
<li>port 寫錯</li>
<li>Secret 不在你以為的 namespace</li>
<li>跨 namespace 引用少了 <code>ReferenceGrant</code></li>
</ul>
<p>如果 <code>ResolvedRefs</code> 是 <code>False</code>，幾乎就該沿著這條線查。</p>
<h3 id="第四步再看資料面與-controller">第四步：再看資料面與 controller</h3>
<p>如果 Gateway 與 Route 狀態都看起來差不多對了，但流量還是不通，再往下看：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> pods</span><span style="color:#79C0FF"> -n</span><span style="color:#A5D6FF"> envoy-gateway-system</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> logs</span><span style="color:#79C0FF"> -n</span><span style="color:#A5D6FF"> envoy-gateway-system</span><span style="color:#A5D6FF"> deployment/envoy-gateway</span></span></code></pre></figure>
<p>這時候你在查的已經不是「規則有沒有被接受」，而是控制平面與資料面有沒有正常工作。</p>
<p>如果你有裝 <code>egctl</code>，也可以用它快速看狀態。<br>
但就算沒有，<code>kubectl get/describe -o yaml</code> 其實已經能解大部分問題。</p>
<h2 id="四個超常見故障模式">四個超常見故障模式</h2>
<h3 id="1-route-寫對了但沒掛到你以為的-listener">1. Route 寫對了，但沒掛到你以為的 listener</h3>
<p>症狀：</p>
<ul>
<li>YAML 很像對</li>
<li>但流量沒有命中規則</li>
</ul>
<p>先查：</p>
<ul>
<li><code>parentRefs.name</code></li>
<li><code>parentRefs.sectionName</code></li>
<li>Gateway listener 名稱有沒有拼對</li>
</ul>
<p>多 listener 場景裡，<code>sectionName</code> 拼錯一個字就足夠讓你白忙一輪。</p>
<h3 id="2-accepted-成功但-resolvedrefs-失敗">2. <code>Accepted</code> 成功，但 <code>ResolvedRefs</code> 失敗</h3>
<p>這通常代表邏輯上可以掛，但引用的東西有問題。<br>
最常見就是：</p>
<ul>
<li>backend Service 不存在</li>
<li>Secret 名稱錯</li>
<li>cross-namespace reference 沒授權</li>
</ul>
<p>這種問題最煩的地方在於，表面上看起來「快好了」，結果其實只是卡在引用層。</p>
<h3 id="3-gateway-有-listener卻沒有你預期的-address">3. Gateway 有 listener，卻沒有你預期的 address</h3>
<p>這很常出現在本地叢集或沒有 <code>LoadBalancer</code> 實作的環境。<br>
不是 Gateway API 壞掉，而是底層根本沒有幫你配出外部位址。</p>
<p>這時可以：</p>
<ul>
<li>檢查叢集有沒有 <code>LoadBalancer</code> 能力</li>
<li>改用 <code>port-forward</code> 先驗證路徑</li>
</ul>
<h3 id="4-yaml-生效了但請求還是-404--503">4. YAML 生效了，但請求還是 404 / 503</h3>
<p>這時通常不是單一欄位錯，而是鏈路某一段沒接上：</p>
<ul>
<li>Host header 不對</li>
<li>path 沒命中</li>
<li>backend Pod 不健康</li>
<li>Service selector 沒對到 Pod</li>
</ul>
<p>入口層問題有時候看起來像 Gateway 壞掉，實際上只是後端根本沒站好。不要把所有鍋都丟給代理層，代理層也很委屈。</p>
<h2 id="一句話總結">一句話總結</h2>
<p>除錯 Gateway API 最有效的方式，不是一直改 YAML，而是先讀懂 <code>status</code>。<br>
<code>Accepted</code> 看有沒有接單，<code>ResolvedRefs</code> 看引用有沒有通，<code>Programmed</code> 看設定有沒有真的落地。這三層拆開看，排錯速度會快很多。</p>

28:T31aa,<p>工程師最怕的不是報錯，而是：</p>
<p><strong>YAML 套上去了，<code>kubectl apply</code> 也成功了，但流量就是沒通。</strong></p>
<p>這時候如果你只盯著 <code>spec</code> 看，很容易越看越像在占卜。<br>
Gateway API 真正的救命資訊，很多都在 <code>status</code> 裡。</p>
<p>這篇的目標很簡單：幫你建立一套最短除錯路徑。讓你遇到 <code>Gateway</code>、<code>HTTPRoute</code>、<code>Listener</code> 不生效時，知道先看哪裡，而不是一開場就懷疑宇宙。</p>
<h2 id="先記住除錯先看-status不是先改-yaml">先記住：除錯先看 <code>status</code>，不是先改 YAML</h2>
<p>最常用的幾個指令：</p>

<p>重點不是把 YAML 再讀一百遍，而是看 controller 有沒有真的接受你的設定。</p>
<p>你可以把 <code>status</code> 想成考試成績單：</p>
<ul>
<li><code>spec</code> 是你交上去的答案</li>
<li><code>status</code> 是系統批改後的結果</li>
</ul>
<p>只看交卷內容，不看成績，很多時候真的只是心靈安慰。</p>
<h2 id="三個最常見的-condition先看懂這些就夠用了">三個最常見的 condition：先看懂這些就夠用了</h2>
<h3 id="accepted"><code>Accepted</code></h3>
<p>這通常表示資源有沒有被父層接納。<br>
以 route 來說，意思通常接近：</p>
<ul>
<li>有沒有成功附掛到對應 Gateway / listener</li>
<li>規則本身有沒有明顯衝突或不合法</li>
</ul>
<p>如果 <code>Accepted</code> 是 <code>False</code>，先懷疑：</p>
<ul>
<li><code>parentRefs</code> 指錯 Gateway 或 listener</li>
<li>hostname / listener 條件不匹配</li>
<li>該 listener 不接受這種 route 類型</li>
<li><code>allowedRoutes</code> 把你擋掉了</li>
</ul>
<h3 id="resolvedrefs"><code>ResolvedRefs</code></h3>
<p>這表示資源裡引用到的其他物件有沒有成功解析。<br>
例如：</p>
<ul>
<li><code>backendRefs</code> 指到的 Service 存不存在</li>
<li><code>certificateRefs</code> 指到的 Secret 能不能合法引用</li>
<li>跨 namespace 引用有沒有配好 <code>ReferenceGrant</code></li>
</ul>
<p>這個 condition 超實用。<br>
因為很多設定不是路由邏輯有錯，而是你引用的東西根本不存在，或沒有權限引用。</p>
<h3 id="programmed"><code>Programmed</code></h3>
<p>這通常代表設定有沒有真的被實作層落地。<br>
你可以把它理解成：</p>
<ul>
<li>controller 已經接受</li>
<li>也把設定推進資料面或基礎設施</li>
</ul>
<p>如果 <code>Accepted</code> 已經是 <code>True</code>，但實際流量還是不通，這時就值得去看 <code>Programmed</code>、Gateway address、listener 狀態，以及底下的 Envoy 相關資源。</p>
<blockquote>
<p>💡 不同資源會看到的 condition 可能不完全相同，但 <code>Accepted</code>、<code>ResolvedRefs</code>、<code>Programmed</code> 是最值得優先建立感覺的一組。</p>
</blockquote>
<h2 id="最短排錯流程照這個順序通常夠用">最短排錯流程：照這個順序通常夠用</h2>
<h3 id="第一步先看-gateway-有沒有真的站起來">第一步：先看 Gateway 有沒有真的站起來</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#A5D6FF"> eg</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span></code></pre></figure>
<p>先確認：</p>
<ul>
<li><code>status.addresses</code> 有沒有值</li>
<li>listener condition 有沒有異常</li>
<li>listener 的 hostname / protocol / port 是不是你以為的那組</li>
</ul>
<p>如果連 Gateway 都沒 address，後面 route 寫得再漂亮都只是文學創作。</p>
<h3 id="第二步看-route-有沒有被接上">第二步：看 Route 有沒有被接上</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#A5D6FF"> app-route</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span></code></pre></figure>
<p>優先看：</p>
<ul>
<li><code>status.parents</code></li>
<li><code>Accepted</code></li>
<li><code>ResolvedRefs</code></li>
<li><code>observedGeneration</code></li>
</ul>
<p><code>observedGeneration</code> 很值得注意。<br>
如果它還沒追上 <code>metadata.generation</code>，代表 controller 可能還沒處理到你最新那版設定。</p>
<h3 id="第三步看引用資源是不是都存在">第三步：看引用資源是不是都存在</h3>
<p>這一步超多人漏掉：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> svc</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> secret</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> referencegrant</span><span style="color:#79C0FF"> -A</span></span></code></pre></figure>
<p>常見問題像是：</p>
<ul>
<li>backend service 名字打錯</li>
<li>port 寫錯</li>
<li>Secret 不在你以為的 namespace</li>
<li>跨 namespace 引用少了 <code>ReferenceGrant</code></li>
</ul>
<p>如果 <code>ResolvedRefs</code> 是 <code>False</code>，幾乎就該沿著這條線查。</p>
<h3 id="第四步再看資料面與-controller">第四步：再看資料面與 controller</h3>
<p>如果 Gateway 與 Route 狀態都看起來差不多對了，但流量還是不通，再往下看：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> pods</span><span style="color:#79C0FF"> -n</span><span style="color:#A5D6FF"> envoy-gateway-system</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> logs</span><span style="color:#79C0FF"> -n</span><span style="color:#A5D6FF"> envoy-gateway-system</span><span style="color:#A5D6FF"> deployment/envoy-gateway</span></span></code></pre></figure>
<p>這時候你在查的已經不是「規則有沒有被接受」，而是控制平面與資料面有沒有正常工作。</p>
<p>如果你有裝 <code>egctl</code>，也可以用它快速看狀態。<br>
但就算沒有，<code>kubectl get/describe -o yaml</code> 其實已經能解大部分問題。</p>
