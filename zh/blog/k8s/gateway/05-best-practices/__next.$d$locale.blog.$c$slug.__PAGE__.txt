8:T225d,<p>功能跑得動，跟系統真的穩，完全是兩個宇宙。很多入口層事故不是因為 Envoy Gateway 不夠強，而是因為設定流程太隨興，最後維運像在拆驚喜包。這篇就把比較實戰的建議整理成清單。</p>
<h2 id="推薦做法">推薦做法</h2>
<h3 id="1-先分清楚誰管-gateway誰管-route">1. 先分清楚誰管 Gateway、誰管 Route</h3>
<p>如果團隊多人協作，建議把責任拆開：</p>
<ul>
<li>平台團隊管理 <code>GatewayClass</code>、<code>Gateway</code></li>
<li>應用團隊管理自己的 <code>HTTPRoute</code></li>
</ul>
<p>這樣做的好處是，入口層安全與暴露面不會被每個 app 隨手亂改，而應用團隊還是能保有路由彈性。這就是 Gateway API 設計很香的地方，別把它又用回單體大 YAML。</p>
<h3 id="2-tls-一開始就當基本配備">2. TLS 一開始就當基本配備</h3>
<p>不要想著「先 HTTP，之後再補 HTTPS」。<br>
通常這個「之後」最後就會變成某個禮拜五晚上。</p>
<p>至少做到：</p>
<ul>
<li>對外 listener 預設走 HTTPS</li>
<li>憑證來源有固定管理方式</li>
<li>測試、自簽、正式 CA 的流程分開</li>
</ul>
<p>如果你已經有 cert-manager，盡量整合它。憑證輪替自動化，比你每次手動 patch Secret 靠譜太多。</p>
<h3 id="3-route-規則盡量明確不要過度貪方便">3. Route 規則盡量明確，不要過度貪方便</h3>
<p>例如這種全吃規則雖然方便，但很容易變成黑洞：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">rules</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">      - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">backend</span></span>
<span data-line=""><span style="color:#85E89D">        port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">8080</span></span></code></pre></figure>
<p>它不是錯，只是當你的系統開始變大時，太多「預設全收」的規則會讓除錯很痛苦。<br>
能寫 <code>hostnames</code>、能寫 <code>path</code>，就盡量寫清楚。</p>
<h3 id="4-用小流量分流不要一次梭哈">4. 用小流量分流，不要一次梭哈</h3>
<p>新版本上線時，先切小比例流量：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">api-v1</span></span>
<span data-line=""><span style="color:#85E89D">    port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">8080</span></span>
<span data-line=""><span style="color:#85E89D">    weight</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">90</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">api-v2</span></span>
<span data-line=""><span style="color:#85E89D">    port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">8080</span></span>
<span data-line=""><span style="color:#85E89D">    weight</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">10</span></span></code></pre></figure>
<p>這比「整個 service selector 一把切過去」溫柔太多。<br>
遇到問題時，回切速度也會快得多，半夜起來救火時你會很感謝這件事。</p>
<h3 id="5-養成看-status-與事件的習慣">5. 養成看 <code>status</code> 與事件的習慣</h3>
<p>只看 YAML 不夠，你要看 controller 有沒有真的接受設定：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> gateway</span><span style="color:#79B8FF"> -A</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> httproute</span><span style="color:#79B8FF"> -A</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> describe</span><span style="color:#9ECBFF"> gateway</span><span style="color:#9ECBFF"> eg</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> describe</span><span style="color:#9ECBFF"> httproute</span><span style="color:#9ECBFF"> app-route</span></span></code></pre></figure>
<p>尤其是這幾類問題，光看 <code>spec</code> 常常看不出來：</p>
<ul>
<li>route 沒被接受</li>
<li>cross-namespace reference 被擋</li>
<li>listener 狀態異常</li>
</ul>
<p>工程師最怕的不是錯，而是「我以為有生效，結果根本沒接單」。</p>
<h2 id="常見誤區">常見誤區</h2>
<h3 id="誤區-1把-envoy-gateway-當成只會轉發的黑盒子">誤區 1：把 Envoy Gateway 當成只會轉發的黑盒子</h3>
<p>它不是只會把封包從 A 搬到 B。<br>
官方文件明確把它定位成 Kubernetes-native API Gateway，後面還能疊更多流量與安全策略。你如果只把它當 Ingress 替代品，會低估它很多能力。</p>
<h3 id="誤區-2跨-namespace-指憑證卻沒建-referencegrant">誤區 2：跨 namespace 指憑證卻沒建 <code>ReferenceGrant</code></h3>
<p>很多人看到 <code>certificateRefs</code> 能寫 namespace，就直接指過去，然後想說「怎麼沒反應」。<br>
答案通常不是鬧鬼，而是少了 <code>ReferenceGrant</code>。</p>
<h3 id="誤區-3只測-happy-path">誤區 3：只測 happy path</h3>
<p>不要只測：</p>
<ul>
<li><code>curl http://...</code> 成功一次</li>
</ul>
<p>還要測：</p>
<ul>
<li>不同 hostname</li>
<li>不同 path</li>
<li>TLS 憑證是否正確</li>
<li>新舊版本分流比例是否如預期</li>
</ul>
<p>入口層最怕的就是 happy path 很美，邊界情況一碰就裂。</p>
<h3 id="誤區-4把-demo-配置直接當-production">誤區 4：把 demo 配置直接當 production</h3>
<p>官方 quickstart 非常適合學習，但它的定位就是 quickstart。<br>
正式環境請至少補上：</p>
<ul>
<li>憑證自動化</li>
<li>監控與告警</li>
<li>變更流程</li>
<li>路由命名規範</li>
</ul>
<p>不然你今天是 quickstart，明天就是 quick-fall。</p>
<h2 id="一份最小上線清單">一份最小上線清單</h2>
<p>正式前可以對照這份 checklist：</p>
<ul>
<li><code>Gateway</code> listener 是否明確區分 HTTP / HTTPS</li>
<li>憑證 Secret 與輪替流程是否清楚</li>
<li><code>HTTPRoute</code> 是否有清楚的 <code>hostnames</code> / <code>matches</code></li>
<li>重要變更是否用小流量切分</li>
<li>是否能從 <code>status</code> 與事件快速定位問題</li>
</ul>
<p>如果這五件事都做到，至少已經比「能通就好」高一個檔次。</p>
<h2 id="一句話總結">一句話總結</h2>
<p>Envoy Gateway 真正的價值，不只是把流量導通，而是讓你的入口層配置變得更標準、可分工、可治理。功能是一時的，維運是長期的，對未來的自己好一點，真的很重要。</p>

<p>它不是錯，只是當你的系統開始變大時，太多「預設全收」的規則會讓除錯很痛苦。<br>
能寫 <code>hostnames</code>、能寫 <code>path</code>，就盡量寫清楚。</p>
<h3 id="4-用小流量分流不要一次梭哈">4. 用小流量分流，不要一次梭哈</h3>
<p>新版本上線時，先切小比例流量：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">api-v1</span></span>
<span data-line=""><span style="color:#85E89D">    port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">8080</span></span>
<span data-line=""><span style="color:#85E89D">    weight</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">90</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">api-v2</span></span>
<span data-line=""><span style="color:#85E89D">    port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">8080</span></span>
<span data-line=""><span style="color:#85E89D">    weight</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">10</span></span></code></pre></figure>
<p>這比「整個 service selector 一把切過去」溫柔太多。<br>
遇到問題時，回切速度也會快得多，半夜起來救火時你會很感謝這件事。</p>
<h3 id="5-養成看-status-與事件的習慣">5. 養成看 <code>status</code> 與事件的習慣</h3>
<p>只看 YAML 不夠，你要看 controller 有沒有真的接受設定：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> gateway</span><span style="color:#79B8FF"> -A</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> httproute</span><span style="color:#79B8FF"> -A</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> describe</span><span style="color:#9ECBFF"> gateway</span><span style="color:#9ECBFF"> eg</span></span>
<span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> describe</span><span style="color:#9ECBFF"> httproute</span><span style="color:#9ECBFF"> app-route</span></span></code></pre></figure>
<p>尤其是這幾類問題，光看 <code>spec</code> 常常看不出來：</p>
<ul>
<li>route 沒被接受</li>
<li>cross-namespace reference 被擋</li>
<li>listener 狀態異常</li>
</ul>
<p>工程師最怕的不是錯，而是「我以為有生效，結果根本沒接單」。</p>
<h2 id="常見誤區">常見誤區</h2>
<h3 id="誤區-1把-envoy-gateway-當成只會轉發的黑盒子">誤區 1：把 Envoy Gateway 當成只會轉發的黑盒子</h3>
<p>它不是只會把封包從 A 搬到 B。<br>
官方文件明確把它定位成 Kubernetes-native API Gateway，後面還能疊更多流量與安全策略。你如果只把它當 Ingress 替代品，會低估它很多能力。</p>
<h3 id="誤區-2跨-namespace-指憑證卻沒建-referencegrant">誤區 2：跨 namespace 指憑證卻沒建 <code>ReferenceGrant</code></h3>
<p>很多人看到 <code>certificateRefs</code> 能寫 namespace，就直接指過去，然後想說「怎麼沒反應」。<br>
答案通常不是鬧鬼，而是少了 <code>ReferenceGrant</code>。</p>
<h3 id="誤區-3只測-happy-path">誤區 3：只測 happy path</h3>
<p>不要只測：</p>
<ul>
<li><code>curl http://...</code> 成功一次</li>
</ul>
<p>還要測：</p>
<ul>
<li>不同 hostname</li>
<li>不同 path</li>
<li>TLS 憑證是否正確</li>
<li>新舊版本分流比例是否如預期</li>
</ul>
<p>入口層最怕的就是 happy path 很美，邊界情況一碰就裂。</p>
<h3 id="誤區-4把-demo-配置直接當-production">誤區 4：把 demo 配置直接當 production</h3>
<p>官方 quickstart 非常適合學習，但它的定位就是 quickstart。<br>
正式環境請至少補上：</p>
<ul>
<li>憑證自動化</li>
<li>監控與告警</li>
<li>變更流程</li>
<li>路由命名規範</li>
</ul>
<p>不然你今天是 quickstart，明天就是 quick-fall。</p>
<h2 id="一份最小上線清單">一份最小上線清單</h2>
<p>正式前可以對照這份 checklist：</p>
<ul>
<li><code>Gateway</code> listener 是否明確區分 HTTP / HTTPS</li>
<li>憑證 Secret 與輪替流程是否清楚</li>
<li><code>HTTPRoute</code> 是否有清楚的 <code>hostnames</code> / <code>matches</code></li>
<li>重要變更是否用小流量切分</li>
<li>是否能從 <code>status</code> 與事件快速定位問題</li>
</ul>
<p>如果這五件事都做到，至少已經比「能通就好」高一個檔次。</p>
<h2 id="一句話總結">一句話總結</h2>
<p>Envoy Gateway 真正的價值，不只是把流量導通，而是讓你的入口層配置變得更標準、可分工、可治理。功能是一時的，維運是長期的，對未來的自己好一點，真的很重要。</p>
