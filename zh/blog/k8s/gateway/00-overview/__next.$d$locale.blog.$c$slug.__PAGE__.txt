3:T3768,<p>如果你以前接觸 Kubernetes 對外流量，多半是從 <code>Ingress</code> 開始。它能用，而且很多場景真的夠用。但一碰到更複雜的需求，例如多 listener、多團隊分工、gRPC、TCP、TLS passthrough、精細流量政策，常常就會變成「靠 annotation 撐世界」的局面，最後 YAML 長得像咒語，維運的人也像在解封印。</p>
<p>這時候，<code>Gateway API + Envoy Gateway</code> 就很像新版裝備。它不是把事情搞更複雜，而是把原本混在一起的責任拆清楚，讓入口流量、路由規則、TLS 安全設定、協定類型與團隊分工都比較好理解。</p>
<h2 id="它到底是什麼">它到底是什麼</h2>
<p>先用一句白話講完：</p>
<ul>
<li><code>Envoy Proxy</code>：真正接流量、轉送請求的資料面，也可視為 Gateway Proxy</li>
<li><code>Envoy Gateway</code>：幫你管理 Envoy Proxy 的控制平面</li>
<li><code>Gateway API</code>：你在 Kubernetes 裡宣告流量規則的標準介面</li>
</ul>
<p>可以把它想成：</p>
<ul>
<li><code>Gateway API</code> 是你寫需求單</li>
<li><code>Envoy Gateway</code> 是負責翻譯與派工的主管</li>
<li><code>Envoy Proxy</code> 是真的在門口站崗的保全</li>
</ul>
<p>這樣拆開的好處是，你不用直接手刻低階 Envoy 設定，也不需要再把各種控制器私有 annotation 背到滾瓜爛熟。你宣告的是 Kubernetes 資源，Envoy Gateway 會幫你把它們翻譯成 Envoy Proxy 真正能執行的設定。</p>
<h2 id="gateway-vs-ingress差在哪裡">Gateway vs Ingress：差在哪裡</h2>
<p>先講結論：<strong>Ingress 沒有過時，但 Gateway API 更適合中大型、需要進一步治理的場景。</strong></p>
<table>
<thead>
<tr>
<th>比較項目</th>
<th>Ingress</th>
<th>Gateway API</th>
</tr>
</thead>
<tbody>
<tr>
<td>入口資源模型</td>
<td>大多把入口與路由寫在同一個物件</td>
<td>把 <code>GatewayClass</code>、<code>Gateway</code>、<code>Route</code> 拆開</td>
</tr>
<tr>
<td>表達能力</td>
<td>以 HTTP/HTTPS 為主，進階需求常靠 annotation</td>
<td>原生支援多種 route 類型與更清楚欄位</td>
</tr>
<tr>
<td>擴充方式</td>
<td>很多能力仰賴不同 controller 的私有 annotation</td>
<td>有標準欄位，也允許實作方提供 CRD 擴充</td>
</tr>
<tr>
<td>協定支援</td>
<td>多數聚焦 Web/HTTP</td>
<td>可處理 <code>HTTPRoute</code>、<code>GRPCRoute</code>、<code>TCPRoute</code>、<code>TLSRoute</code></td>
</tr>
<tr>
<td>團隊分工</td>
<td>比較容易把平台與應用設定混在一起</td>
<td>更適合平台團隊管入口、應用團隊管路由</td>
</tr>
<tr>
<td>可攜性</td>
<td>annotation 常與特定 controller 綁死</td>
<td>標準化程度更高，跨實作可讀性較好</td>
</tr>
</tbody>
</table>
<p>如果你的需求只是：</p>
<ul>
<li>單一網站或簡單 API</li>
<li>基本 path/host 路由</li>
<li>團隊規模不大</li>
</ul>
<p>那 Ingress 還是能打。但如果你的需求開始包含：</p>
<ul>
<li>一個入口要服務多個協定</li>
<li>多 listener、多網域、多憑證</li>
<li>HTTP 和 gRPC 並存</li>
<li>想把平台入口和應用路由拆權限</li>
<li>想讓設定更像正式 API，而不是 annotation 許願池</li>
</ul>
<p>那 Gateway API 就會開始顯得很香。</p>
<h2 id="為什麼不是只用-ingress">為什麼不是只用 Ingress</h2>
<p>官方 Gateway API 的目標，就是解決 Ingress 在大型場景常見的幾個痛點：</p>
<ul>
<li><strong>表達力更好</strong>：路由、TLS、流量政策、協定類型更清楚</li>
<li><strong>可攜性更高</strong>：少一點綁死某家 controller 的私房 annotation</li>
<li><strong>角色分工更自然</strong>：平台團隊管入口，應用團隊管路由</li>
</ul>
<p>舉例來說，Ingress 常常會長這樣：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">metadata</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  annotations</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/rewrite-target</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/auth-type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">basic</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/ssl-redirect</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"true"</span></span></code></pre></figure>
<p>不是說它不能用，而是當需求變多時，annotation 很容易變成 YAML 版神祕黑魔法。Gateway API 比較像把這些需求拉回正式欄位，讀起來更像「設定」，不是「許願池」。</p>
<h2 id="這套東西的分層結構">這套東西的分層結構</h2>
<p>官方概念頁把 Envoy Gateway 分成三層，這個腦圖值得先記住：</p>
<ul>
<li><strong>User Configuration</strong>：你寫的 <code>Gateway API</code> 與 Envoy Gateway 擴充 CRD</li>
<li><strong>Envoy Gateway Controller</strong>：讀取這些資源，轉換成可執行設定</li>
<li><strong>Envoy Proxy</strong>：真正接住線上流量的資料面</li>
</ul>
<p>也就是說，平常你大部分時間是在改「上層宣告」，不是直接 SSH 進代理層改低階設定。這就是 Kubernetes-native 的舒服之處。</p>

<h2 id="你會遇到的核心資源">你會遇到的核心資源</h2>
<p>初學者最容易卡住的點，是以為 Gateway API 只有 <code>Gateway</code> 跟 <code>HTTPRoute</code>。其實它是一整個資源家族。</p>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>定義「這個叢集要用哪個 Gateway 實作」。<br>
對 Envoy Gateway 來說，核心是 <code>controllerName</code> 要指向正確的 controller。</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>定義「入口長什麼樣」。<br>
例如要開哪個 port、聽哪個 protocol、TLS 怎麼掛、允許哪些 route 附掛。</p>
<h3 id="listener"><code>Listener</code></h3>
<p><code>Listener</code> 是 <code>Gateway</code> 裡最重要的單位之一。<br>
你可以把它想成 Gateway 上的一個對外插槽，每個插槽會定義：</p>
<ul>
<li>port</li>
<li>protocol</li>
<li>hostname</li>
<li>TLS 設定</li>
<li><code>allowedRoutes</code></li>
</ul>
<p>很多人把 <code>Gateway</code> 想成一個黑盒子，但實際上真正決定入口行為的，通常是裡面的每個 <code>listener</code>。</p>
<h3 id="route-家族">Route 家族</h3>
<ul>
<li><code>HTTPRoute</code>：HTTP/HTTPS 流量，最常用</li>
<li><code>GRPCRoute</code>：gRPC 流量，能以 service/method 為匹配條件</li>
<li><code>TCPRoute</code>：原始 TCP 流量，不解析 HTTP 語意</li>
<li><code>TLSRoute</code>：根據 TLS SNI 做路由，常見於 TLS passthrough 場景</li>
</ul>
<p>這些 route 的共通點都是：<br>
<strong>它們不負責「開門」，而是負責「進門後怎麼分流」。</strong></p>
<h2 id="最小心智模型">最小心智模型</h2>
<p>先記住這張腦內地圖：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#A5D6FF">GatewayClass</span><span style="color:#8B949E">  # 這個叢集要用哪一種 Gateway 實作</span></span>
<span data-line=""><span style="color:#A5D6FF">Gateway</span><span style="color:#8B949E">       # 這個入口開哪些 listener</span></span>
<span data-line=""><span style="color:#A5D6FF">Listener</span><span style="color:#8B949E">      # 某個 port / protocol / hostname / TLS 插槽</span></span>
<span data-line=""><span style="color:#A5D6FF">Route</span><span style="color:#8B949E">         # 進來後要怎麼分流</span></span>
<span data-line=""><span style="color:#A5D6FF">Service</span><span style="color:#8B949E">       # 叢集內真正提供服務的後端</span></span>
<span data-line=""><span style="color:#A5D6FF">Envoy Proxy</span><span style="color:#8B949E">   # 最終實際承接流量的資料面</span></span></code></pre></figure>
<p>最小範例長這樣：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">apiVersion</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">gateway.networking.k8s.io/v1</span></span>
<span data-line=""><span style="color:#7EE787">kind</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTPRoute</span></span>
<span data-line=""><span style="color:#7EE787">metadata</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">demo</span></span>
<span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">  hostnames</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#A5D6FF">"www.example.com"</span></span>
<span data-line=""><span style="color:#7EE787">  rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">backend</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">3000</span></span></code></pre></figure>
<p>你現在不用把每個欄位都背起來，只要先知道它在做什麼：</p>
<ul>
<li><code>parentRefs</code>：這條規則要掛到哪個 Gateway</li>
<li><code>hostnames</code>：哪個網域進來要吃這條規則</li>
<li><code>backendRefs</code>：最後要送到哪個 Service</li>
</ul>
<h2 id="一眼看懂什麼時候用哪個-route">一眼看懂什麼時候用哪個 Route</h2>

<th>需求</th>
<th>建議資源</th>
</tr>

<td>網站、REST API、Header / Path 路由</td>

<p>這個判斷方式很實用。看到需求先別急著寫 YAML，先問自己一句：</p>
<p>「我現在在處理的是 HTTP、gRPC，還是單純 TCP / TLS 流量？」</p>
<h2 id="一句話總結">一句話總結</h2>
<p><code>Envoy Gateway</code> 不是另一個你非學不可的新名詞，而是把 Kubernetes 對外流量這件事，從「能用就好」提升到「比較像工程系統」的做法。</p>
<blockquote>
<p>💡 如果你是第一次碰這套東西，不要一開始就想把所有 CRD 全學完。先裝起來、先打通第一個請求，再回頭看概念，吸收會快很多。</p>
</blockquote>

9:T3768,<p>如果你以前接觸 Kubernetes 對外流量，多半是從 <code>Ingress</code> 開始。它能用，而且很多場景真的夠用。但一碰到更複雜的需求，例如多 listener、多團隊分工、gRPC、TCP、TLS passthrough、精細流量政策，常常就會變成「靠 annotation 撐世界」的局面，最後 YAML 長得像咒語，維運的人也像在解封印。</p>
<p>這時候，<code>Gateway API + Envoy Gateway</code> 就很像新版裝備。它不是把事情搞更複雜，而是把原本混在一起的責任拆清楚，讓入口流量、路由規則、TLS 安全設定、協定類型與團隊分工都比較好理解。</p>
<h2 id="它到底是什麼">它到底是什麼</h2>
<p>先用一句白話講完：</p>
<ul>
<li><code>Envoy Proxy</code>：真正接流量、轉送請求的資料面，也可視為 Gateway Proxy</li>
<li><code>Envoy Gateway</code>：幫你管理 Envoy Proxy 的控制平面</li>
<li><code>Gateway API</code>：你在 Kubernetes 裡宣告流量規則的標準介面</li>
</ul>
<p>可以把它想成：</p>
<ul>
<li><code>Gateway API</code> 是你寫需求單</li>
<li><code>Envoy Gateway</code> 是負責翻譯與派工的主管</li>
<li><code>Envoy Proxy</code> 是真的在門口站崗的保全</li>
</ul>
<p>這樣拆開的好處是，你不用直接手刻低階 Envoy 設定，也不需要再把各種控制器私有 annotation 背到滾瓜爛熟。你宣告的是 Kubernetes 資源，Envoy Gateway 會幫你把它們翻譯成 Envoy Proxy 真正能執行的設定。</p>
<h2 id="gateway-vs-ingress差在哪裡">Gateway vs Ingress：差在哪裡</h2>
<p>先講結論：<strong>Ingress 沒有過時，但 Gateway API 更適合中大型、需要進一步治理的場景。</strong></p>
<table>
<thead>
<tr>
<th>比較項目</th>
<th>Ingress</th>
<th>Gateway API</th>
</tr>
</thead>
<tbody>
<tr>
<td>入口資源模型</td>
<td>大多把入口與路由寫在同一個物件</td>
<td>把 <code>GatewayClass</code>、<code>Gateway</code>、<code>Route</code> 拆開</td>
</tr>
<tr>
<td>表達能力</td>
<td>以 HTTP/HTTPS 為主，進階需求常靠 annotation</td>
<td>原生支援多種 route 類型與更清楚欄位</td>
</tr>
<tr>
<td>擴充方式</td>
<td>很多能力仰賴不同 controller 的私有 annotation</td>
<td>有標準欄位，也允許實作方提供 CRD 擴充</td>
</tr>
<tr>
<td>協定支援</td>
<td>多數聚焦 Web/HTTP</td>
<td>可處理 <code>HTTPRoute</code>、<code>GRPCRoute</code>、<code>TCPRoute</code>、<code>TLSRoute</code></td>
</tr>
<tr>
<td>團隊分工</td>
<td>比較容易把平台與應用設定混在一起</td>
<td>更適合平台團隊管入口、應用團隊管路由</td>
</tr>
<tr>
<td>可攜性</td>
<td>annotation 常與特定 controller 綁死</td>
<td>標準化程度更高，跨實作可讀性較好</td>
</tr>
</tbody>
</table>
<p>如果你的需求只是：</p>
<ul>
<li>單一網站或簡單 API</li>
<li>基本 path/host 路由</li>
<li>團隊規模不大</li>
</ul>
<p>那 Ingress 還是能打。但如果你的需求開始包含：</p>
<ul>
<li>一個入口要服務多個協定</li>
<li>多 listener、多網域、多憑證</li>
<li>HTTP 和 gRPC 並存</li>
<li>想把平台入口和應用路由拆權限</li>
<li>想讓設定更像正式 API，而不是 annotation 許願池</li>
</ul>
<p>那 Gateway API 就會開始顯得很香。</p>
<h2 id="為什麼不是只用-ingress">為什麼不是只用 Ingress</h2>
<p>官方 Gateway API 的目標，就是解決 Ingress 在大型場景常見的幾個痛點：</p>
<ul>
<li><strong>表達力更好</strong>：路由、TLS、流量政策、協定類型更清楚</li>
<li><strong>可攜性更高</strong>：少一點綁死某家 controller 的私房 annotation</li>
<li><strong>角色分工更自然</strong>：平台團隊管入口，應用團隊管路由</li>
</ul>
<p>舉例來說，Ingress 常常會長這樣：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">metadata</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  annotations</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/rewrite-target</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/auth-type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">basic</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/ssl-redirect</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"true"</span></span></code></pre></figure>
<p>不是說它不能用，而是當需求變多時，annotation 很容易變成 YAML 版神祕黑魔法。Gateway API 比較像把這些需求拉回正式欄位，讀起來更像「設定」，不是「許願池」。</p>
<h2 id="這套東西的分層結構">這套東西的分層結構</h2>
<p>官方概念頁把 Envoy Gateway 分成三層，這個腦圖值得先記住：</p>
<ul>
<li><strong>User Configuration</strong>：你寫的 <code>Gateway API</code> 與 Envoy Gateway 擴充 CRD</li>
<li><strong>Envoy Gateway Controller</strong>：讀取這些資源，轉換成可執行設定</li>
<li><strong>Envoy Proxy</strong>：真正接住線上流量的資料面</li>
</ul>
<p>也就是說，平常你大部分時間是在改「上層宣告」，不是直接 SSH 進代理層改低階設定。這就是 Kubernetes-native 的舒服之處。</p>

<h2 id="你會遇到的核心資源">你會遇到的核心資源</h2>
<p>初學者最容易卡住的點，是以為 Gateway API 只有 <code>Gateway</code> 跟 <code>HTTPRoute</code>。其實它是一整個資源家族。</p>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>定義「這個叢集要用哪個 Gateway 實作」。<br>
對 Envoy Gateway 來說，核心是 <code>controllerName</code> 要指向正確的 controller。</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>定義「入口長什麼樣」。<br>
例如要開哪個 port、聽哪個 protocol、TLS 怎麼掛、允許哪些 route 附掛。</p>
<h3 id="listener"><code>Listener</code></h3>
<p><code>Listener</code> 是 <code>Gateway</code> 裡最重要的單位之一。<br>
你可以把它想成 Gateway 上的一個對外插槽，每個插槽會定義：</p>
<ul>
<li>port</li>
<li>protocol</li>
<li>hostname</li>
<li>TLS 設定</li>
<li><code>allowedRoutes</code></li>
</ul>
<p>很多人把 <code>Gateway</code> 想成一個黑盒子，但實際上真正決定入口行為的，通常是裡面的每個 <code>listener</code>。</p>
<h3 id="route-家族">Route 家族</h3>
<ul>
<li><code>HTTPRoute</code>：HTTP/HTTPS 流量，最常用</li>
<li><code>GRPCRoute</code>：gRPC 流量，能以 service/method 為匹配條件</li>
<li><code>TCPRoute</code>：原始 TCP 流量，不解析 HTTP 語意</li>
<li><code>TLSRoute</code>：根據 TLS SNI 做路由，常見於 TLS passthrough 場景</li>
</ul>
<p>這些 route 的共通點都是：<br>
<strong>它們不負責「開門」，而是負責「進門後怎麼分流」。</strong></p>
<h2 id="最小心智模型">最小心智模型</h2>
<p>先記住這張腦內地圖：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#A5D6FF">GatewayClass</span><span style="color:#8B949E">  # 這個叢集要用哪一種 Gateway 實作</span></span>
<span data-line=""><span style="color:#A5D6FF">Gateway</span><span style="color:#8B949E">       # 這個入口開哪些 listener</span></span>
<span data-line=""><span style="color:#A5D6FF">Listener</span><span style="color:#8B949E">      # 某個 port / protocol / hostname / TLS 插槽</span></span>
<span data-line=""><span style="color:#A5D6FF">Route</span><span style="color:#8B949E">         # 進來後要怎麼分流</span></span>
<span data-line=""><span style="color:#A5D6FF">Service</span><span style="color:#8B949E">       # 叢集內真正提供服務的後端</span></span>
<span data-line=""><span style="color:#A5D6FF">Envoy Proxy</span><span style="color:#8B949E">   # 最終實際承接流量的資料面</span></span></code></pre></figure>
<p>最小範例長這樣：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">apiVersion</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">gateway.networking.k8s.io/v1</span></span>
<span data-line=""><span style="color:#7EE787">kind</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTPRoute</span></span>

<span data-line=""><span style="color:#7EE787">  name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">demo</span></span>
<span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">  hostnames</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#A5D6FF">"www.example.com"</span></span>

<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">backend</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">3000</span></span></code></pre></figure>
<p>你現在不用把每個欄位都背起來，只要先知道它在做什麼：</p>
<ul>
<li><code>parentRefs</code>：這條規則要掛到哪個 Gateway</li>
<li><code>hostnames</code>：哪個網域進來要吃這條規則</li>
<li><code>backendRefs</code>：最後要送到哪個 Service</li>
</ul>

<p><code>Envoy Gateway</code> 不是另一個你非學不可的新名詞，而是把 Kubernetes 對外流量這件事，從「能用就好」提升到「比較像工程系統」的做法。</p>
<blockquote>
<p>💡 如果你是第一次碰這套東西，不要一開始就想把所有 CRD 全學完。先裝起來、先打通第一個請求，再回頭看概念，吸收會快很多。</p>
</blockquote>
