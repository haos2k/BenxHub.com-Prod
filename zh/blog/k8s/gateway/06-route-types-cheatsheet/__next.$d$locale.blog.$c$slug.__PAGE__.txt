b:T406f,<p>如果你前面幾篇都看了，現在最容易卡住的問題通常不是「我不懂 Gateway API」，而是：</p>
<p><strong>「幹，所以這次到底該寫 <code>HTTPRoute</code>、<code>GRPCRoute</code>、<code>TCPRoute</code> 還是 <code>TLSRoute</code>？」</strong></p>
<p>這篇就是專門拿來解這個結的。把它當成口袋速查表就好，之後要開新服務時，先翻這篇，比先亂寫 YAML 再被 condition 教做人省時間很多。</p>
<h2 id="先講結論四種-route-的差別">先講結論：四種 Route 的差別</h2>
<table>
<thead>
<tr>
<th>Route 類型</th>
<th>流量層級</th>
<th>會看什麼</th>
<th>適合場景</th>
<th>不適合場景</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>HTTPRoute</code></td>
<td>L7 HTTP/HTTPS</td>
<td>host、path、header、query、method</td>
<td>網站、REST API、一般 Web 流量</td>
<td>純 TCP 協定、TLS passthrough</td>
</tr>
<tr>
<td><code>GRPCRoute</code></td>
<td>L7 gRPC</td>
<td>hostname、service、method、header</td>
<td>gRPC service / method 路由</td>
<td>一般 REST API、原始 TCP</td>
</tr>
<tr>
<td><code>TCPRoute</code></td>
<td>L4 TCP</td>
<td>listener 與連線層資訊</td>
<td>資料庫、自訂 TCP 協定、非 HTTP 服務</td>
<td>想看 path/header 的場景</td>
</tr>
<tr>
<td><code>TLSRoute</code></td>
<td>L4/L5 TLS</td>
<td>TLS SNI hostname</td>
<td>TLS passthrough、端到端加密保留到後端</td>
<td>需要在 Gateway 解密後看 HTTP 細節</td>
</tr>
</tbody>
</table>
<p>如果你只想背一個超短版：</p>
<ul>
<li>想看 <code>path</code>、<code>header</code>，用 <code>HTTPRoute</code></li>
<li>想看 gRPC <code>service/method</code>，用 <code>GRPCRoute</code></li>
<li>只是在轉 TCP 連線，用 <code>TCPRoute</code></li>
<li>不解 TLS、只看 SNI，用 <code>TLSRoute</code></li>
</ul>
<h2 id="三步判斷法不要再用猜的">三步判斷法：不要再用猜的</h2>
<p>你可以用這個順序判斷：</p>
<ol>
<li>流量進來後，Gateway 會不會解開 HTTP 語意？</li>
<li>如果會，它是一般 HTTP/REST，還是 gRPC？</li>
<li>如果不會，它是單純 TCP，還是 TLS passthrough？</li>
</ol>
<p>對照起來就是：</p>
<ul>
<li>有 HTTP path/header/method 要看：<code>HTTPRoute</code></li>
<li>有 gRPC service/method 要看：<code>GRPCRoute</code></li>
<li>沒有 L7 規則，只是 TCP 轉送：<code>TCPRoute</code></li>
<li>想保留 TLS 到後端才解：<code>TLSRoute</code></li>
</ul>
<p>這個判斷超重要。很多人一看到 route 就先手滑寫 <code>HTTPRoute</code>，結果寫到一半才發現自己其實在處理資料庫流量，整份 YAML 瞬間進入「我到底在幹嘛」模式。</p>

<h2 id="最容易踩坑的四件事">最容易踩坑的四件事</h2>
<h3 id="1-grpc-不代表一定要寫-grpcroute">1. gRPC 不代表一定要寫 <code>GRPCRoute</code></h3>
<p>如果你只是想讓 gRPC 流量能通，某些實作下用 <code>HTTPRoute</code> 也可能跑得動，因為 gRPC 底層是 HTTP/2。<br>
但如果你想用 gRPC 的 service/method 當規則語意，<code>GRPCRoute</code> 才是比較正統、也比較好讀的選擇。</p>
<h3 id="2-tlsroute-不是https-的進階版">2. <code>TLSRoute</code> 不是「HTTPS 的進階版」</h3>
<p>這是最多人誤會的點。</p>
<ul>
<li><code>HTTPS listener + HTTPRoute</code>：Gateway 會終止 TLS，後面看 HTTP 規則</li>
<li><code>TLS listener + TLSRoute</code>：Gateway 不終止 TLS，只看 SNI 分流</li>
</ul>
<p>一個是解密後玩 L7，一個是保持加密做 passthrough，完全不同宇宙。</p>
<h3 id="3-tcproute-看不到-pathheader">3. <code>TCPRoute</code> 看不到 path/header</h3>
<p>你如果需求寫的是：</p>
<ul>
<li><code>/api</code> 走 A</li>
<li><code>/admin</code> 走 B</li>
</ul>
<p>那就不是 <code>TCPRoute</code> 的工作。<br>
<code>TCPRoute</code> 不會理解這些 HTTP 細節，硬塞進去只會變成技術版情勒。</p>
<h3 id="4-parentrefssectionname-很重要">4. <code>parentRefs.sectionName</code> 很重要</h3>
<p>如果同一個 Gateway 上有多個 listener，記得善用：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">    sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span></code></pre></figure>
<p>這樣 route 才會精準掛到你要的 listener。<br>
不然你以為自己在指定 VIP 包廂，實際上可能被安排去隔壁廳。</p>
<h2 id="一句話總結">一句話總結</h2>
<p>先判斷你手上的流量是 <strong>HTTP、gRPC、TCP，還是 TLS passthrough</strong>，再選對 route 類型。<br>
Route 選對，後面 80% 的 YAML 都會順；Route 選錯，後面就是一場你和 condition 的互相折磨。</p>

<h2 id="先講結論四種-route-的差別">先講結論：四種 Route 的差別</h2>
<table>
<thead>
<tr>
<th>Route 類型</th>
<th>流量層級</th>
<th>會看什麼</th>
<th>適合場景</th>
<th>不適合場景</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>HTTPRoute</code></td>
<td>L7 HTTP/HTTPS</td>
<td>host、path、header、query、method</td>
<td>網站、REST API、一般 Web 流量</td>
<td>純 TCP 協定、TLS passthrough</td>
</tr>
<tr>
<td><code>GRPCRoute</code></td>
<td>L7 gRPC</td>
<td>hostname、service、method、header</td>
<td>gRPC service / method 路由</td>
<td>一般 REST API、原始 TCP</td>
</tr>
<tr>

<td>L4 TCP</td>
<td>listener 與連線層資訊</td>

<td>想看 path/header 的場景</td>
</tr>
<tr>

<td>L4/L5 TLS</td>
<td>TLS SNI hostname</td>

<p>如果你只想背一個超短版：</p>
<ul>
<li>想看 <code>path</code>、<code>header</code>，用 <code>HTTPRoute</code></li>
<li>想看 gRPC <code>service/method</code>，用 <code>GRPCRoute</code></li>
<li>只是在轉 TCP 連線，用 <code>TCPRoute</code></li>
<li>不解 TLS、只看 SNI，用 <code>TLSRoute</code></li>
</ul>
<h2 id="三步判斷法不要再用猜的">三步判斷法：不要再用猜的</h2>
<p>你可以用這個順序判斷：</p>
<ol>
<li>流量進來後，Gateway 會不會解開 HTTP 語意？</li>
<li>如果會，它是一般 HTTP/REST，還是 gRPC？</li>
<li>如果不會，它是單純 TCP，還是 TLS passthrough？</li>
</ol>
<p>對照起來就是：</p>
<ul>
<li>有 HTTP path/header/method 要看：<code>HTTPRoute</code></li>
<li>有 gRPC service/method 要看：<code>GRPCRoute</code></li>
<li>沒有 L7 規則，只是 TCP 轉送：<code>TCPRoute</code></li>
<li>想保留 TLS 到後端才解：<code>TLSRoute</code></li>
</ul>
<p>這個判斷超重要。很多人一看到 route 就先手滑寫 <code>HTTPRoute</code>，結果寫到一半才發現自己其實在處理資料庫流量，整份 YAML 瞬間進入「我到底在幹嘛」模式。</p>

<h2 id="最容易踩坑的四件事">最容易踩坑的四件事</h2>
<h3 id="1-grpc-不代表一定要寫-grpcroute">1. gRPC 不代表一定要寫 <code>GRPCRoute</code></h3>
<p>如果你只是想讓 gRPC 流量能通，某些實作下用 <code>HTTPRoute</code> 也可能跑得動，因為 gRPC 底層是 HTTP/2。<br>
但如果你想用 gRPC 的 service/method 當規則語意，<code>GRPCRoute</code> 才是比較正統、也比較好讀的選擇。</p>
<h3 id="2-tlsroute-不是https-的進階版">2. <code>TLSRoute</code> 不是「HTTPS 的進階版」</h3>
<p>這是最多人誤會的點。</p>
<ul>
<li><code>HTTPS listener + HTTPRoute</code>：Gateway 會終止 TLS，後面看 HTTP 規則</li>
<li><code>TLS listener + TLSRoute</code>：Gateway 不終止 TLS，只看 SNI 分流</li>
</ul>
<p>一個是解密後玩 L7，一個是保持加密做 passthrough，完全不同宇宙。</p>
<h3 id="3-tcproute-看不到-pathheader">3. <code>TCPRoute</code> 看不到 path/header</h3>
<p>你如果需求寫的是：</p>
<ul>
<li><code>/api</code> 走 A</li>
<li><code>/admin</code> 走 B</li>
</ul>
<p>那就不是 <code>TCPRoute</code> 的工作。<br>
<code>TCPRoute</code> 不會理解這些 HTTP 細節，硬塞進去只會變成技術版情勒。</p>
<h3 id="4-parentrefssectionname-很重要">4. <code>parentRefs.sectionName</code> 很重要</h3>
<p>如果同一個 Gateway 上有多個 listener，記得善用：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">    sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span></code></pre></figure>
<p>這樣 route 才會精準掛到你要的 listener。<br>
不然你以為自己在指定 VIP 包廂，實際上可能被安排去隔壁廳。</p>
<h2 id="一句話總結">一句話總結</h2>
<p>先判斷你手上的流量是 <strong>HTTP、gRPC、TCP，還是 TLS passthrough</strong>，再選對 route 類型。<br>
Route 選對，後面 80% 的 YAML 都會順；Route 選錯，後面就是一場你和 condition 的互相折磨。</p>
