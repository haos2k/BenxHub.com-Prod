1b:T2efd,<p>高可用性（HA）的核心概念其實很樸素：<strong>某台機器掛了，上面的服務自動在別台機器重新跑起來。</strong> 就像餐廳的備用瓦斯爐——主爐壞了，菜不能停，換一台繼續炒。聽起來理所當然，但要做到「自動」且「安全」，底層有不少機制要搞對。HA 是建立在 <a href="08-cluster">叢集</a> 之上的功能，還沒組叢集的話請先回去看。</p>
<h2 id="ha-的腦與手">HA 的腦與手</h2>
<p>PVE 的 HA 架構分成兩層：</p>
<pre><code>┌─────────────────────────────────────┐
│         CRM（叢集資源管理器）          │
│      → 在 Master 節點上執行            │
│      → 決策中心：誰掛了、搬去哪         │
├────────┬────────┬───────────────────┤
│ LRM    │ LRM    │ LRM               │
│ Node 1 │ Node 2 │ Node 3            │
│ → 執行者│ → 執行者│ → 執行者           │
├────────┴────────┴───────────────────┤
│     Corosync + Quorum + Fencing     │
└─────────────────────────────────────┘
</code></pre>
<ul>
<li><strong>CRM（Cluster Resource Manager）</strong>：大腦，負責監控所有 HA 資源，判斷「誰掛了」「搬去哪」</li>
<li><strong>LRM（Local Resource Manager）</strong>：手腳，每個節點上都有一個，負責實際的開機、關機、遷移動作</li>
</ul>
<p>CRM 跟 LRM 的關係像是調度室跟現場工人——調度室下指令，工人動手做。</p>
<h2 id="fencing先確認倒下的人不會亂動">Fencing：先確認倒下的人不會亂動</h2>
<p>這是 HA 最關鍵也最常被忽略的一環。</p>
<p>想像一個場景：Node 1 的網路斷了，CRM 覺得它掛了，於是在 Node 2 啟動同一台 VM。但其實 Node 1 還活著，上面那台 VM 也還在跑。兩邊同時寫同一份資料——恭喜，資料毀了。</p>
<p>Fencing 就是為了防止這種事。PVE 使用 <strong>watchdog-based fencing</strong>：</p>
<ol>
<li>每個節點跑一個 <code>watchdog-mux</code> 守護程序，持續「餵狗」</li>
<li>節點失去 Quorum → 停止餵狗 → watchdog 超時</li>
<li>watchdog 超時 → <strong>強制重啟該節點</strong></li>
<li>節點重啟後，上面的 VM 自然就停了，CRM 才能安全地在其他節點啟動它們</li>
</ol>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#8B949E"># 確認 watchdog 狀態</span></span>
<span data-line=""><span style="color:#FFA657">systemctl</span><span style="color:#A5D6FF"> status</span><span style="color:#A5D6FF"> watchdog-mux</span></span>
<span data-line=""> </span>
<span data-line=""><span style="color:#8B949E"># 檢查有沒有硬體 watchdog</span></span>
<span data-line=""><span style="color:#FFA657">ls</span><span style="color:#A5D6FF"> /dev/watchdog</span><span style="color:#79C0FF">*</span></span></code></pre></figure>
<blockquote>
<p>PVE 預設用軟體 watchdog（<code>softdog</code>），能用但不是最可靠。如果你的伺服器有硬體 watchdog（多數 server 級主板都有），建議啟用它。硬體 watchdog 就算系統整個卡死也能強制重啟，軟體的做不到。</p>
</blockquote>
<h2 id="設定-ha-資源">設定 HA 資源</h2>
<p>把 VM 加入 HA 管理很簡單：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#8B949E"># 新增 HA 資源</span></span>

<span data-line=""> </span>
<span data-line=""><span style="color:#8B949E"># 查看 HA 狀態</span></span>
<span data-line=""><span style="color:#FFA657">ha-manager</span><span style="color:#A5D6FF"> status</span></span>
<span data-line=""> </span>
<span data-line=""><span style="color:#8B949E"># 移除 HA 資源</span></span>
<span data-line=""><span style="color:#FFA657">ha-manager</span><span style="color:#A5D6FF"> remove</span><span style="color:#A5D6FF"> vm:100</span></span></code></pre></figure>
<p>Web GUI 操作路徑：<code>Datacenter → HA → Add → 選 VM → 設定 Group</code></p>
<h2 id="ha-groups決定-vm-能住哪">HA Groups：決定 VM 能住哪</h2>
<p>HA Group 定義了資源可以在哪些節點上執行，以及優先順序：</p>
<ul>
<li><strong>Priority</strong>：數字越大越優先，故障轉移時優先選高優先順序的節點</li>
<li><strong>restricted</strong>：開啟後資源只能在 Group 內的節點跑，不會跑到外面</li>
<li><strong>nofailback</strong>：故障轉移後不自動搬回原來的節點，避免不必要的遷移</li>
</ul>
<p>就像員工排班——你可以指定某些人優先上早班，也可以限制某些人只能待在特定部門。</p>

<h2 id="live-migrationvm-搬家不斷線">Live Migration：VM 搬家不斷線</h2>
<p>Live Migration 是把正在跑的 VM 從 A 節點搬到 B 節點，過程中服務（幾乎）不中斷：</p>
<ol>
<li>開始複製 VM 記憶體到目標節點</li>
<li>持續同步變動的記憶體頁面</li>
<li>最終短暫暫停（通常不到 1 秒）→ 切換完成</li>
<li>VM 在目標節點繼續跑</li>
</ol>
<p>前提條件：</p>
<ul>
<li><strong>共享存儲</strong>（Ceph/NFS/iSCSI），或者用 Replication 先把磁碟同步過去——存儲怎麼選可以看 <a href="05-storage">存儲全攻略</a></li>
<li>兩台節點的 CPU 相容（同廠牌同世代最保險）</li>
</ul>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#8B949E"># 手動觸發 Live Migration</span></span>
<span data-line=""><span style="color:#FFA657">qm</span><span style="color:#A5D6FF"> migrate</span><span style="color:#79C0FF"> 100</span><span style="color:#A5D6FF"> node2</span><span style="color:#79C0FF"> --online</span></span></code></pre></figure>
<p>Live Migration 最常用在<strong>計劃維護</strong>——要更新 Node 1 的韌體？先把上面的 VM 全部 live migrate 到其他節點，更新完再搬回來。使用者完全無感，就像魔術師在你眼前把東西換掉，你卻什麼都沒察覺。</p>
<h2 id="affinity-rulespve-90">Affinity Rules（PVE 9.0+）</h2>
<p>PVE 9.0 開始支援 Affinity Rules，讓你控制 VM 之間的「距離」：</p>
<ul>
<li><strong>共置（Co-locate）</strong>：指定一群 VM 必須在同一節點。例如 Web Server 跟它的 Redis Cache，放一起延遲最低</li>
<li><strong>分離（Separate）</strong>：指定一群 VM 必須分散在不同節點。例如兩台 Database 主備，放一起就失去了備援的意義</li>
</ul>
<p>這就像安排座位——有些人要坐在一起方便討論，有些人必須分開坐避免作弊。</p>
<h2 id="故障轉移完整流程">故障轉移完整流程</h2>
<p>當一台節點真的掛了，整個流程是這樣的：</p>
<ol>
<li>Corosync 偵測到心跳消失</li>
<li>其他節點確認：「它真的掛了，不是網路抖一下」</li>
<li>CRM 觸發 Fencing → 等 watchdog 強制重啟故障節點</li>
<li>確認 Fencing 完成（故障節點上的 VM 確實停了）</li>
<li>CRM 指派 LRM 在目標節點啟動受影響的 HA 資源</li>
<li>持續監控直到資源恢復正常</li>
</ol>
<p>整個流程大概幾十秒到幾分鐘，取決於 watchdog 超時設定和 VM 啟動速度。</p>
<h2 id="ha-不是萬能的">HA 不是萬能的</h2>
<p>幾個前提得滿足，不然 HA 只是擺設：</p>
<ul>
<li><strong>最少 3 節點</strong>（或 2 節點 + QDevice）——Quorum 機制的硬需求</li>
<li><strong>共享存儲或 Replication</strong>——VM 磁碟搬不過去，HA 就沒用</li>
<li><strong>Fencing 正常運作</strong>——沒有 Fencing 的 HA 比沒有 HA 更危險</li>
<li>不適合<strong>所有 VM 都開 HA</strong>——資源吃緊的時候故障轉移也跑不動，挑關鍵服務就好</li>
<li>就算有 HA，<a href="07-backup-restore">備份</a>還是要做——HA 防的是節點故障，不防人為誤刪或資料損壞</li>
</ul>
<blockquote>
<p>維護節點之前，記得先把 HA 資源手動遷走。直接關機會觸發故障轉移流程——不是不行，但沒必要讓系統白跑一趟驚嚇反應。更多 Homelab 維運的眉角，可以參考 <a href="14-homelab-best-practices">最佳實踐總整理</a>。</p>
</blockquote>

<h2 id="常見問題">常見問題</h2>
<h3 id="q-pve-ha-最少需要幾個節點">Q: PVE HA 最少需要幾個節點？</h3>
<p>最少 3 個節點（或 2 節點加 QDevice）。HA 依賴 Quorum 機制運作，過半數節點存活才能做決策。2 節點不加 QDevice 的話，掛一台整個 HA 就停擺了。</p>
<h3 id="q-live-migration-需要共享存儲嗎">Q: Live Migration 需要共享存儲嗎？</h3>
<p>標準做法是需要的，Ceph、NFS 或 iSCSI 都可以。如果沒有共享存儲，可以用 ZFS Replication 先同步磁碟到目標節點，但遷移速度會受磁碟大小影響。</p>
<h3 id="q-proxmox-高可用的-fencing-是什麼">Q: Proxmox 高可用的 Fencing 是什麼？</h3>
<p>Fencing 是確保故障節點上的 VM 真正停止後，才在其他節點重新啟動的安全機制。PVE 用 watchdog 實現——節點失去 Quorum 後停止餵狗，watchdog 超時就強制重啟該節點，避免兩邊同時跑同一台 VM 導致資料損壞。</p>
<h3 id="q-ha-故障轉移要多久">Q: HA 故障轉移要多久？</h3>

26:T2efd,<p>高可用性（HA）的核心概念其實很樸素：<strong>某台機器掛了，上面的服務自動在別台機器重新跑起來。</strong> 就像餐廳的備用瓦斯爐——主爐壞了，菜不能停，換一台繼續炒。聽起來理所當然，但要做到「自動」且「安全」，底層有不少機制要搞對。HA 是建立在 <a href="08-cluster">叢集</a> 之上的功能，還沒組叢集的話請先回去看。</p>
<h2 id="ha-的腦與手">HA 的腦與手</h2>
<p>PVE 的 HA 架構分成兩層：</p>
<pre><code>┌─────────────────────────────────────┐
│         CRM（叢集資源管理器）          │
│      → 在 Master 節點上執行            │
│      → 決策中心：誰掛了、搬去哪         │
├────────┬────────┬───────────────────┤
│ LRM    │ LRM    │ LRM               │
│ Node 1 │ Node 2 │ Node 3            │
│ → 執行者│ → 執行者│ → 執行者           │
├────────┴────────┴───────────────────┤
│     Corosync + Quorum + Fencing     │
└─────────────────────────────────────┘
</code></pre>
<ul>
<li><strong>CRM（Cluster Resource Manager）</strong>：大腦，負責監控所有 HA 資源，判斷「誰掛了」「搬去哪」</li>
<li><strong>LRM（Local Resource Manager）</strong>：手腳，每個節點上都有一個，負責實際的開機、關機、遷移動作</li>
</ul>
<p>CRM 跟 LRM 的關係像是調度室跟現場工人——調度室下指令，工人動手做。</p>
<h2 id="fencing先確認倒下的人不會亂動">Fencing：先確認倒下的人不會亂動</h2>
<p>這是 HA 最關鍵也最常被忽略的一環。</p>
<p>想像一個場景：Node 1 的網路斷了，CRM 覺得它掛了，於是在 Node 2 啟動同一台 VM。但其實 Node 1 還活著，上面那台 VM 也還在跑。兩邊同時寫同一份資料——恭喜，資料毀了。</p>
<p>Fencing 就是為了防止這種事。PVE 使用 <strong>watchdog-based fencing</strong>：</p>
<ol>
<li>每個節點跑一個 <code>watchdog-mux</code> 守護程序，持續「餵狗」</li>
<li>節點失去 Quorum → 停止餵狗 → watchdog 超時</li>
<li>watchdog 超時 → <strong>強制重啟該節點</strong></li>
<li>節點重啟後，上面的 VM 自然就停了，CRM 才能安全地在其他節點啟動它們</li>
</ol>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#8B949E"># 確認 watchdog 狀態</span></span>
<span data-line=""><span style="color:#FFA657">systemctl</span><span style="color:#A5D6FF"> status</span><span style="color:#A5D6FF"> watchdog-mux</span></span>
<span data-line=""> </span>
<span data-line=""><span style="color:#8B949E"># 檢查有沒有硬體 watchdog</span></span>
<span data-line=""><span style="color:#FFA657">ls</span><span style="color:#A5D6FF"> /dev/watchdog</span><span style="color:#79C0FF">*</span></span></code></pre></figure>
<blockquote>
<p>PVE 預設用軟體 watchdog（<code>softdog</code>），能用但不是最可靠。如果你的伺服器有硬體 watchdog（多數 server 級主板都有），建議啟用它。硬體 watchdog 就算系統整個卡死也能強制重啟，軟體的做不到。</p>
</blockquote>
<h2 id="設定-ha-資源">設定 HA 資源</h2>
<p>把 VM 加入 HA 管理很簡單：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#8B949E"># 新增 HA 資源</span></span>

<h2 id="ha-groups決定-vm-能住哪">HA Groups：決定 VM 能住哪</h2>
<p>HA Group 定義了資源可以在哪些節點上執行，以及優先順序：</p>
<ul>
<li><strong>Priority</strong>：數字越大越優先，故障轉移時優先選高優先順序的節點</li>
<li><strong>restricted</strong>：開啟後資源只能在 Group 內的節點跑，不會跑到外面</li>
<li><strong>nofailback</strong>：故障轉移後不自動搬回原來的節點，避免不必要的遷移</li>
</ul>
<p>就像員工排班——你可以指定某些人優先上早班，也可以限制某些人只能待在特定部門。</p>

<h2 id="live-migrationvm-搬家不斷線">Live Migration：VM 搬家不斷線</h2>
<p>Live Migration 是把正在跑的 VM 從 A 節點搬到 B 節點，過程中服務（幾乎）不中斷：</p>
<ol>
<li>開始複製 VM 記憶體到目標節點</li>
<li>持續同步變動的記憶體頁面</li>
<li>最終短暫暫停（通常不到 1 秒）→ 切換完成</li>
<li>VM 在目標節點繼續跑</li>
</ol>
<p>前提條件：</p>
<ul>
<li><strong>共享存儲</strong>（Ceph/NFS/iSCSI），或者用 Replication 先把磁碟同步過去——存儲怎麼選可以看 <a href="05-storage">存儲全攻略</a></li>
<li>兩台節點的 CPU 相容（同廠牌同世代最保險）</li>
</ul>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#8B949E"># 手動觸發 Live Migration</span></span>
<span data-line=""><span style="color:#FFA657">qm</span><span style="color:#A5D6FF"> migrate</span><span style="color:#79C0FF"> 100</span><span style="color:#A5D6FF"> node2</span><span style="color:#79C0FF"> --online</span></span></code></pre></figure>
<p>Live Migration 最常用在<strong>計劃維護</strong>——要更新 Node 1 的韌體？先把上面的 VM 全部 live migrate 到其他節點，更新完再搬回來。使用者完全無感，就像魔術師在你眼前把東西換掉，你卻什麼都沒察覺。</p>
<h2 id="affinity-rulespve-90">Affinity Rules（PVE 9.0+）</h2>
<p>PVE 9.0 開始支援 Affinity Rules，讓你控制 VM 之間的「距離」：</p>
<ul>
<li><strong>共置（Co-locate）</strong>：指定一群 VM 必須在同一節點。例如 Web Server 跟它的 Redis Cache，放一起延遲最低</li>
<li><strong>分離（Separate）</strong>：指定一群 VM 必須分散在不同節點。例如兩台 Database 主備，放一起就失去了備援的意義</li>
</ul>
<p>這就像安排座位——有些人要坐在一起方便討論，有些人必須分開坐避免作弊。</p>
<h2 id="故障轉移完整流程">故障轉移完整流程</h2>
<p>當一台節點真的掛了，整個流程是這樣的：</p>
<ol>
<li>Corosync 偵測到心跳消失</li>
<li>其他節點確認：「它真的掛了，不是網路抖一下」</li>
<li>CRM 觸發 Fencing → 等 watchdog 強制重啟故障節點</li>
<li>確認 Fencing 完成（故障節點上的 VM 確實停了）</li>
<li>CRM 指派 LRM 在目標節點啟動受影響的 HA 資源</li>
<li>持續監控直到資源恢復正常</li>
</ol>
<p>整個流程大概幾十秒到幾分鐘，取決於 watchdog 超時設定和 VM 啟動速度。</p>
<h2 id="ha-不是萬能的">HA 不是萬能的</h2>
<p>幾個前提得滿足，不然 HA 只是擺設：</p>
<ul>
<li><strong>最少 3 節點</strong>（或 2 節點 + QDevice）——Quorum 機制的硬需求</li>
<li><strong>共享存儲或 Replication</strong>——VM 磁碟搬不過去，HA 就沒用</li>
<li><strong>Fencing 正常運作</strong>——沒有 Fencing 的 HA 比沒有 HA 更危險</li>
<li>不適合<strong>所有 VM 都開 HA</strong>——資源吃緊的時候故障轉移也跑不動，挑關鍵服務就好</li>
<li>就算有 HA，<a href="07-backup-restore">備份</a>還是要做——HA 防的是節點故障，不防人為誤刪或資料損壞</li>
</ul>
<blockquote>
<p>維護節點之前，記得先把 HA 資源手動遷走。直接關機會觸發故障轉移流程——不是不行，但沒必要讓系統白跑一趟驚嚇反應。更多 Homelab 維運的眉角，可以參考 <a href="14-homelab-best-practices">最佳實踐總整理</a>。</p>
</blockquote>
