3:T28bf,<p>很多人用 CrewAI 第一次翻車，不是 API 問題，也不是環境設定——是<strong>角色設計從一開始就亂了</strong>。</p>
<p>你可能會想：一個 Agent 搞定全部不是更省事嗎？讓它既研究、又寫作、又審稿，聽起來很高效。但實際跑起來你會發現，一個 Agent 同時扮演三種性質完全不同的角色，通常是三件事都做得普普通通，而且你完全不知道哪一步出了問題。</p>
<p>只要記住這個核心原則：<strong>一個 Agent 一種專長，一個 Task 一件事</strong>，大多數設計問題就迎刃而解了。</p>
<h2 id="agenttaskcontext-分別負責什麼">Agent、Task、Context 分別負責什麼</h2>
<p>用最直白的方式理解這三者：</p>
<ul>
<li><strong>Agent</strong> 是「誰來做」——角色定義、專長方向、有沒有工具</li>
<li><strong>Task</strong> 是「做什麼」——具體指令、輸出格式、完成標準</li>
<li><strong>Context</strong> 是「前一步給後一步什麼」——讓任務之間真的有資料流動</li>
</ul>
<p>如果你讓一個 Agent 同時研究、寫作、審稿，它通常會每件事都沾一點、每件事都不夠深。就像你不會在求職廣告上寫「需要全端工程師，同時負責 PM 和設計」，那個人就算存在，你也管不動他。</p>

<p><code>allow_delegation: false</code> 建議一開始就關掉。它預設開啟，但會讓 Agent 自行決定把子任務轉包給其他 Agent——聽起來很聰明，但新手階段等於把除錯難度直接翻倍。先跑穩、再開啟動態分派。</p>
<p><code>backstory</code> 不只是裝飾用的——模型會把它當成角色設定讀進去，影響輸出的語氣和判斷方式。短短三行可以明顯改變同一個 Agent 的表現差異。</p>
<h2 id="設計一個好的-task">設計一個好的 Task</h2>
<p>Task 最常見的問題是「寫太短」——模型不知道你要什麼格式，輸出就會每次都不一樣。</p>

<p><code>expected_output</code> 越具體越好——不是「寫個報告」，而是「markdown 格式、3 個 H2 段落、結尾有 next steps」。這個欄位直接決定輸出的穩定性。</p>
<h2 id="新手最常踩的-3-個坑">新手最常踩的 3 個坑</h2>
<p><strong>1. Task 描述太短</strong></p>
<p>「Research about AI tools」這種描述給模型太多空間自己發揮，結果每次輸出都不一樣。描述要像在跟一個聰明但不了解你業務的人說明清楚，什麼要做、什麼不要做、格式是什麼。</p>
<p><strong>2. 沒有 expected_output</strong></p>
<p>這是輸出格式每次都漂移的主因。它不是可選欄位——它是你跟模型簽的格式契約。缺了它，你只能看模型心情。</p>
<p><strong>3. 後續任務忘記加 context</strong></p>
<p>寫完 <code>research_task</code> 之後，你以為 <code>write_task</code> 會自動知道前面的研究結果——不會的。<code>context: [research_task]</code> 這行少了，writer 就會自己憑空生出資料，而不是真的用研究員的成果。</p>
<h2 id="每次寫完-yaml-前過這-5-個問題">每次寫完 YAML 前過這 5 個問題</h2>
<p>拿起你的 agents.yaml 和 tasks.yaml，對這 5 個問題逐一確認：</p>
<ol>
<li>這個 Agent 是不是只有一個明確專長？</li>
<li>這個 Task 是不是只做一件事？</li>
<li><code>expected_output</code> 有沒有寫清楚格式、長度、結構？</li>
<li>任務之間有依賴關係的，有沒有加 <code>context</code>？</li>
<li>需要輸出到檔案的，有沒有設 <code>output_file</code>？</li>
</ol>
<p>這 5 個問題答對了，80% 的設計地雷就排掉了。</p>
<h2 id="常見問題">常見問題</h2>
<p><strong>Q：一個 Crew 要有幾個 Agent 才合適？</strong><br>
初期 2-3 個就夠了。Agent 數量增加，成本和 debug 難度都會上升。先讓少量 Agent 跑穩，再評估是否需要增加角色。</p>
<p><strong>Q：backstory 一定要寫嗎？</strong><br>
不是強制的，但寫了效果明顯更好。特別是當你需要模型在輸出時保持特定立場或語氣，backstory 就是你設定角色框架的地方。</p>
<p><strong>Q：<code>allow_delegation: true</code> 什麼時候才應該開？</strong><br>
當你有穩定的監控機制、知道系統在哪種條件下會轉包任務、成本有可控制方式的時候。新手階段先關掉，省麻煩。</p>

<span data-line=""> </span>
<span data-line=""><span style="color:#7EE787">writer</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  role</span><span style="color:#E6EDF3">: </span><span style="color:#FF7B72">></span></span>
<span data-line=""><span style="color:#A5D6FF">    Technical Writer</span></span>
<span data-line=""><span style="color:#7EE787">  goal</span><span style="color:#E6EDF3">: </span><span style="color:#FF7B72">></span></span>
<span data-line=""><span style="color:#A5D6FF">    Turn raw research findings into clear, practical documentation</span></span>
<span data-line=""><span style="color:#7EE787">  backstory</span><span style="color:#E6EDF3">: </span><span style="color:#FF7B72">></span></span>
<span data-line=""><span style="color:#A5D6FF">    You have a talent for making complex ideas accessible.</span></span>
<span data-line=""><span style="color:#A5D6FF">    You structure content so readers can quickly find what they need.</span></span>
<span data-line=""><span style="color:#7EE787">  allow_delegation</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">false</span></span></code></pre></figure>
<p><code>allow_delegation: false</code> 建議一開始就關掉。它預設開啟，但會讓 Agent 自行決定把子任務轉包給其他 Agent——聽起來很聰明，但新手階段等於把除錯難度直接翻倍。先跑穩、再開啟動態分派。</p>
<p><code>backstory</code> 不只是裝飾用的——模型會把它當成角色設定讀進去，影響輸出的語氣和判斷方式。短短三行可以明顯改變同一個 Agent 的表現差異。</p>
<h2 id="設計一個好的-task">設計一個好的 Task</h2>
<p>Task 最常見的問題是「寫太短」——模型不知道你要什麼格式，輸出就會每次都不一樣。</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">research_task</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  description</span><span style="color:#E6EDF3">: </span><span style="color:#FF7B72">></span></span>
<span data-line=""><span style="color:#A5D6FF">    Find 8-10 important updates about {topic} in 2026.</span></span>
<span data-line=""><span style="color:#A5D6FF">    Focus on: what changed, why it matters, and where it came from.</span></span>
<span data-line=""><span style="color:#A5D6FF">    Prioritize content published in the last 3 months.</span></span>
<span data-line=""><span style="color:#7EE787">  expected_output</span><span style="color:#E6EDF3">: </span><span style="color:#FF7B72">></span></span>
<span data-line=""><span style="color:#A5D6FF">    A markdown bullet list with 8-10 items.</span></span>
<span data-line=""><span style="color:#A5D6FF">    Each item must include:</span></span>
<span data-line=""><span style="color:#A5D6FF">    - Title (bold)</span></span>
<span data-line=""><span style="color:#A5D6FF">    - Summary (2-3 sentences)</span></span>
<span data-line=""><span style="color:#A5D6FF">    - Source URL (if available)</span></span>
<span data-line=""><span style="color:#7EE787">  agent</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">researcher</span></span>
<span data-line=""> </span>
<span data-line=""><span style="color:#7EE787">write_task</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  description</span><span style="color:#E6EDF3">: </span><span style="color:#FF7B72">></span></span>
<span data-line=""><span style="color:#A5D6FF">    Convert the research bullets into a tutorial article for developers new to {topic}.</span></span>
<span data-line=""><span style="color:#A5D6FF">    Do not add information that wasn't in the research notes.</span></span>
<span data-line=""><span style="color:#7EE787">  expected_output</span><span style="color:#E6EDF3">: </span><span style="color:#FF7B72">></span></span>
<span data-line=""><span style="color:#A5D6FF">    A markdown article with:</span></span>
<span data-line=""><span style="color:#A5D6FF">    - Introduction (1 paragraph)</span></span>
<span data-line=""><span style="color:#A5D6FF">    - 3 main sections with H2 headings</span></span>

<p><code>expected_output</code> 越具體越好——不是「寫個報告」，而是「markdown 格式、3 個 H2 段落、結尾有 next steps」。這個欄位直接決定輸出的穩定性。</p>
<h2 id="新手最常踩的-3-個坑">新手最常踩的 3 個坑</h2>
<p><strong>1. Task 描述太短</strong></p>
<p>「Research about AI tools」這種描述給模型太多空間自己發揮，結果每次輸出都不一樣。描述要像在跟一個聰明但不了解你業務的人說明清楚，什麼要做、什麼不要做、格式是什麼。</p>
<p><strong>2. 沒有 expected_output</strong></p>
<p>這是輸出格式每次都漂移的主因。它不是可選欄位——它是你跟模型簽的格式契約。缺了它，你只能看模型心情。</p>
<p><strong>3. 後續任務忘記加 context</strong></p>
<p>寫完 <code>research_task</code> 之後，你以為 <code>write_task</code> 會自動知道前面的研究結果——不會的。<code>context: [research_task]</code> 這行少了，writer 就會自己憑空生出資料，而不是真的用研究員的成果。</p>
<h2 id="每次寫完-yaml-前過這-5-個問題">每次寫完 YAML 前過這 5 個問題</h2>
<p>拿起你的 agents.yaml 和 tasks.yaml，對這 5 個問題逐一確認：</p>
<ol>
<li>這個 Agent 是不是只有一個明確專長？</li>
<li>這個 Task 是不是只做一件事？</li>
<li><code>expected_output</code> 有沒有寫清楚格式、長度、結構？</li>
<li>任務之間有依賴關係的，有沒有加 <code>context</code>？</li>
<li>需要輸出到檔案的，有沒有設 <code>output_file</code>？</li>
</ol>
<p>這 5 個問題答對了，80% 的設計地雷就排掉了。</p>
<h2 id="常見問題">常見問題</h2>
<p><strong>Q：一個 Crew 要有幾個 Agent 才合適？</strong><br>
初期 2-3 個就夠了。Agent 數量增加，成本和 debug 難度都會上升。先讓少量 Agent 跑穩，再評估是否需要增加角色。</p>
<p><strong>Q：backstory 一定要寫嗎？</strong><br>
不是強制的，但寫了效果明顯更好。特別是當你需要模型在輸出時保持特定立場或語氣，backstory 就是你設定角色框架的地方。</p>
<p><strong>Q：<code>allow_delegation: true</code> 什麼時候才應該開？</strong><br>
當你有穩定的監控機制、知道系統在哪種條件下會轉包任務、成本有可控制方式的時候。新手階段先關掉，省麻煩。</p>
