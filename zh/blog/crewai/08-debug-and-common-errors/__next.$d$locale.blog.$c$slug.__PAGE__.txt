<h2 id="除錯要按順序別一出問題就怪模型">除錯要按順序，別一出問題就怪模型</h2>
<p>很多人碰到問題，第一反應是「是不是模型不夠聰明」或者「要不要換 GPT-4o」——這個直覺大多數時候是錯的。</p>
<p>按這個順序查，命中率最高：</p>
<p><strong>第一步：查配置</strong><br>
先看 <code>agents.yaml</code> 和 <code>tasks.yaml</code>。角色設定是不是有意義？Task 描述是不是清楚？<code>expected_output</code> 有沒有格式要求？<code>context</code> 有沒有串好？80% 的問題在這裡。</p>
<p><strong>第二步：查輸入</strong><br>
<code>inputs</code> 的資料是不是穩定的？如果你用動態資料做測試，你根本沒辦法判斷輸出是否變好或變差。先用固定輸入，確認行為可重現。</p>
<p><strong>第三步：查工具</strong><br>
Tool 有沒有被呼叫（看 verbose 輸出）？參數對不對？回傳格式有沒有模型能解析的結構？</p>
<p><strong>第四步：才考慮模型</strong><br>
確認前三步都沒問題了，再考慮是否要調模型的溫度、上下文長度，或換一個模型試試。</p>
<p>順序不要反過來。大部分的「模型問題」，查下去都是 YAML 少一行或者 Task 描述太模糊。</p>
<h2 id="一個被低估的除錯技巧">一個被低估的除錯技巧</h2>
<p>每個 Task 加一個「輸出自我檢查」的要求，像這樣：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">research_task</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  expected_output</span><span style="color:#E6EDF3">: </span><span style="color:#FF7B72">></span></span>
<span data-line=""><span style="color:#A5D6FF">    A markdown bullet list with 8-10 items.</span></span>
<span data-line=""><span style="color:#A5D6FF">    Each item MUST include: title, summary (2 sentences), and source URL.</span></span>
<span data-line=""><span style="color:#A5D6FF">    At the end, add a one-line self-check: "✅ All items have title, summary, and source."</span></span></code></pre></figure>
<p>讓模型在完成任務之後自己確認輸出是否符合格式，是一種低成本的「流程內單元測試」。不是 100% 可靠，但可以抓到很多格式不符的情況。</p>
<p>另一個有效的做法是加「負面要求」——明確告訴模型什麼不要做：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">description</span><span style="color:#E6EDF3">: </span><span style="color:#FF7B72">></span></span>
<span data-line=""><span style="color:#A5D6FF">  Research {topic}. Use the search tool to find current information.</span></span>
<span data-line=""><span style="color:#A5D6FF">  Do NOT include information published before 2025.</span></span>
<span data-line=""><span style="color:#A5D6FF">  Do NOT make up sources — if you don't have a URL, write "source not found".</span></span></code></pre></figure>
<p>這兩種寫法比「加長 expected_output 到 200 字」效果好很多。</p>
<h2 id="verbose-模式開著永遠開著">verbose 模式：開著，永遠開著</h2>
<p>開發期間 <code>verbose=True</code> 一定要開——它會讓你在終端看到每個 Agent 的思考過程、工具呼叫記錄、和每個 Task 的輸出。沒有這個，你只能看到最終結果，完全不知道哪一步出了問題。</p>
<p>生產環境可以關掉，開發和測試期間這個開關值那個 API 費的。</p>
<h2 id="常見問題">常見問題</h2>
<p><strong>Q：<code>expected_output</code> 寫很詳細了，輸出還是會飄，怎麼辦？</strong><br>
試試 <code>output_pydantic</code>——把格式從「文字描述」變成「強制 schema 驗證」。如果連 Pydantic 也過不了，才要考慮是不是任務本身太複雜需要拆分。</p>
<p><strong>Q：Tool 有被呼叫，但回傳的資料 Agent 沒有用到，怎麼辦？</strong><br>
可能是 Tool 回傳的格式太難解析。把 Tool 的回傳改成清楚的結構化字串，並在 Task description 裡說明「根據工具回傳的 X 欄位來...」。</p>
<p><strong>Q：流程有時候會突然超出 context window，怎麼辦？</strong><br>
把任務拆小，每個 Task 只做一件事，不要讓單一任務的輸出太長。有些情況也可以加 <code>max_iter</code>（最大迭代次數）來限制模型的回答長度。</p>
<p><strong>Q：同一個流程，今天跑和明天跑結果差很多，怎麼辦？</strong><br>
兩個方向：一是固定測試輸入，確認是輸入造成的差異還是模型本身的隨機性；二是調低模型溫度（temperature），降低輸出的隨機程度。</p>

<p>讓模型在完成任務之後自己確認輸出是否符合格式，是一種低成本的「流程內單元測試」。不是 100% 可靠，但可以抓到很多格式不符的情況。</p>
<p>另一個有效的做法是加「負面要求」——明確告訴模型什麼不要做：</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">description</span><span style="color:#E6EDF3">: </span><span style="color:#FF7B72">></span></span>
<span data-line=""><span style="color:#A5D6FF">  Research {topic}. Use the search tool to find current information.</span></span>
<span data-line=""><span style="color:#A5D6FF">  Do NOT include information published before 2025.</span></span>
<span data-line=""><span style="color:#A5D6FF">  Do NOT make up sources — if you don't have a URL, write "source not found".</span></span></code></pre></figure>
<p>這兩種寫法比「加長 expected_output 到 200 字」效果好很多。</p>
<h2 id="verbose-模式開著永遠開著">verbose 模式：開著，永遠開著</h2>
<p>開發期間 <code>verbose=True</code> 一定要開——它會讓你在終端看到每個 Agent 的思考過程、工具呼叫記錄、和每個 Task 的輸出。沒有這個，你只能看到最終結果，完全不知道哪一步出了問題。</p>
<p>生產環境可以關掉，開發和測試期間這個開關值那個 API 費的。</p>
<h2 id="常見問題">常見問題</h2>
<p><strong>Q：<code>expected_output</code> 寫很詳細了，輸出還是會飄，怎麼辦？</strong><br>
試試 <code>output_pydantic</code>——把格式從「文字描述」變成「強制 schema 驗證」。如果連 Pydantic 也過不了，才要考慮是不是任務本身太複雜需要拆分。</p>
<p><strong>Q：Tool 有被呼叫，但回傳的資料 Agent 沒有用到，怎麼辦？</strong><br>
可能是 Tool 回傳的格式太難解析。把 Tool 的回傳改成清楚的結構化字串，並在 Task description 裡說明「根據工具回傳的 X 欄位來...」。</p>
<p><strong>Q：流程有時候會突然超出 context window，怎麼辦？</strong><br>
把任務拆小，每個 Task 只做一件事，不要讓單一任務的輸出太長。有些情況也可以加 <code>max_iter</code>（最大迭代次數）來限制模型的回答長度。</p>
<p><strong>Q：同一個流程，今天跑和明天跑結果差很多，怎麼辦？</strong><br>
兩個方向：一是固定測試輸入，確認是輸入造成的差異還是模型本身的隨機性；二是調低模型溫度（temperature），降低輸出的隨機程度。</p>
