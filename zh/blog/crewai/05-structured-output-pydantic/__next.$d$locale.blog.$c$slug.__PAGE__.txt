3:T2d56,<p>如果你有遇過「同一個 Task，這次回 markdown 格式、下次回純文字、再下次回了個 JSON 但 key 名又不一樣」——你不是一個人。</p>
<p>這是 LLM 輸出的本質問題：模型產生的是「看起來合理的文字」，不是「保證符合你期待格式的結構化資料」。你在 <code>expected_output</code> 裡寫得再清楚，模型還是有一定機率自己改個格式。</p>
<p>解法很直接：<strong>用 Pydantic 把輸出格式鎖死</strong>。</p>
<h2 id="為什麼要結構化輸出">為什麼要結構化輸出？</h2>
<p>不是為了程式碼好看，是為了讓下游任務有固定的資料可以用。</p>
<p>假設你的研究員 Agent 輸出了一份報告，後面的編輯 Agent 要讀它——如果格式每次都不一樣，你要嘛每次手動確認，要嘛寫一堆防禦性的字串解析邏輯。這兩個方向都在製造麻煩。</p>
<p>用 Pydantic 定義輸出結構之後：</p>
<ul>
<li>下游任務直接存取固定欄位，不用猜格式</li>
<li>格式不符就直接報錯，比跑完才發現資料壞了快很多</li>
<li>整個流程的資料契約是明確的，好維護</li>
</ul>
<p>這就像 REST API 有 schema——有規格才有穩定協作。</p>

<h2 id="expected_output-還要不要寫">expected_output 還要不要寫？</h2>
<p>要。</p>
<p>很多人以為有了 <code>output_pydantic</code> 就不用寫 <code>expected_output</code>，但這兩個是不同層次的東西。</p>
<p><code>output_pydantic</code> 定義的是資料結構——有哪些欄位、型別是什麼。<code>expected_output</code> 定義的是<strong>內容品質</strong>——你希望每個欄位裡裝的是什麼等級的內容。兩個合在一起，才能讓輸出又有固定格式、又有足夠的內容品質。</p>
<h2 id="新手常見的-3-個誤區">新手常見的 3 個誤區</h2>
<p><strong>欄位太少，資訊不足</strong>：如果你的 <code>Finding</code> 只有 <code>title</code> 和 <code>summary</code>，下游任務可能沒有足夠的資訊繼續工作。欄位要包含後面步驟真的需要的資料。</p>
<p><strong>欄位太多太細，模型容易漏</strong>：另一個極端是把模型當資料庫用，要求它填 20 個欄位，結果很多欄位都是空的或者亂填的。從 3-5 個關鍵欄位開始，夠用再擴。</p>
<p><strong>把 Pydantic 欄位設計成你的 UI 欄位</strong>：Pydantic 模型是 LLM 的輸出契約，不是前端的資料模型。兩者的關心點不一樣，不要混在一起設計。</p>
<h2 id="常見問題">常見問題</h2>
<p><strong>Q：output_pydantic 和 output_json 有什麼差別？</strong><br>
<code>output_json</code> 回傳的是一個 dict，你還是要自己存取 key。<code>output_pydantic</code> 直接給你 Pydantic 物件，有型別提示、有驗證、有自動補全。能用 <code>output_pydantic</code> 就用它。</p>
<p><strong>Q：如果模型沒有回傳所有欄位，會怎樣？</strong><br>
Pydantic 驗證會失敗，task 會拋出錯誤。這是好事——比讓壞資料悄悄流進下游任務要好很多。在 <code>expected_output</code> 裡寫清楚每個欄位的要求，可以降低這種情況的發生機率。</p>
<p><strong>Q：list 欄位可以設最小和最大長度嗎？</strong><br>
可以，用 <code>Field(min_length=5, max_length=10)</code> 就好。這會讓模型知道你期待多少條資料，不會出現一條都沒有或者輸出 50 條的情況。</p>

<h2 id="為什麼要結構化輸出">為什麼要結構化輸出？</h2>
<p>不是為了程式碼好看，是為了讓下游任務有固定的資料可以用。</p>
<p>假設你的研究員 Agent 輸出了一份報告，後面的編輯 Agent 要讀它——如果格式每次都不一樣，你要嘛每次手動確認，要嘛寫一堆防禦性的字串解析邏輯。這兩個方向都在製造麻煩。</p>
<p>用 Pydantic 定義輸出結構之後：</p>
<ul>
<li>下游任務直接存取固定欄位，不用猜格式</li>
<li>格式不符就直接報錯，比跑完才發現資料壞了快很多</li>
<li>整個流程的資料契約是明確的，好維護</li>
</ul>
<p>這就像 REST API 有 schema——有規格才有穩定協作。</p>

<h2 id="expected_output-還要不要寫">expected_output 還要不要寫？</h2>
<p>要。</p>
<p>很多人以為有了 <code>output_pydantic</code> 就不用寫 <code>expected_output</code>，但這兩個是不同層次的東西。</p>
<p><code>output_pydantic</code> 定義的是資料結構——有哪些欄位、型別是什麼。<code>expected_output</code> 定義的是<strong>內容品質</strong>——你希望每個欄位裡裝的是什麼等級的內容。兩個合在一起，才能讓輸出又有固定格式、又有足夠的內容品質。</p>
<h2 id="新手常見的-3-個誤區">新手常見的 3 個誤區</h2>
<p><strong>欄位太少，資訊不足</strong>：如果你的 <code>Finding</code> 只有 <code>title</code> 和 <code>summary</code>，下游任務可能沒有足夠的資訊繼續工作。欄位要包含後面步驟真的需要的資料。</p>
<p><strong>欄位太多太細，模型容易漏</strong>：另一個極端是把模型當資料庫用，要求它填 20 個欄位，結果很多欄位都是空的或者亂填的。從 3-5 個關鍵欄位開始，夠用再擴。</p>
<p><strong>把 Pydantic 欄位設計成你的 UI 欄位</strong>：Pydantic 模型是 LLM 的輸出契約，不是前端的資料模型。兩者的關心點不一樣，不要混在一起設計。</p>
<h2 id="常見問題">常見問題</h2>
<p><strong>Q：output_pydantic 和 output_json 有什麼差別？</strong><br>
<code>output_json</code> 回傳的是一個 dict，你還是要自己存取 key。<code>output_pydantic</code> 直接給你 Pydantic 物件，有型別提示、有驗證、有自動補全。能用 <code>output_pydantic</code> 就用它。</p>
<p><strong>Q：如果模型沒有回傳所有欄位，會怎樣？</strong><br>
Pydantic 驗證會失敗，task 會拋出錯誤。這是好事——比讓壞資料悄悄流進下游任務要好很多。在 <code>expected_output</code> 裡寫清楚每個欄位的要求，可以降低這種情況的發生機率。</p>
<p><strong>Q：list 欄位可以設最小和最大長度嗎？</strong><br>
可以，用 <code>Field(min_length=5, max_length=10)</code> 就好。這會讓模型知道你期待多少條資料，不會出現一條都沒有或者輸出 50 條的情況。</p>
