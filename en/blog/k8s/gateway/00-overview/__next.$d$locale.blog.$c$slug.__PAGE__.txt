3:T3a79,<p>If you've worked with Kubernetes external traffic before, chances are you started with <code>Ingress</code>. It works, and for many scenarios it's genuinely sufficient. But once you hit more complex requirements — multiple listeners, multi-team ownership, gRPC, TCP, TLS passthrough, fine-grained traffic policies — you inevitably end up in a situation where "keep it alive with annotations" becomes the norm. The YAML starts looking like an incantation, and the people maintaining it feel like they're breaking a seal.</p>
<p>That's where <code>Gateway API + Envoy Gateway</code> comes in — it's the new kit. It doesn't make things more complicated; it cleanly separates the responsibilities that used to be tangled together, making ingress traffic, routing rules, TLS security settings, protocol types, and team ownership much easier to reason about.</p>
<h2 id="what-is-it-exactly">What Is It, Exactly</h2>
<p>Let's say it plainly in one sentence:</p>
<ul>
<li><code>Envoy Proxy</code>: The data plane that actually receives traffic and forwards requests — also called a Gateway Proxy</li>
<li><code>Envoy Gateway</code>: The control plane that manages Envoy Proxy for you</li>
<li><code>Gateway API</code>: The standard interface you use in Kubernetes to declare traffic rules</li>
</ul>
<p>Think of it this way:</p>
<ul>
<li><code>Gateway API</code> is where you write the requirements</li>
<li><code>Envoy Gateway</code> is the manager who translates and delegates</li>
<li><code>Envoy Proxy</code> is the actual guard standing at the door</li>
</ul>
<p>The benefit of this separation is that you don't need to hand-craft low-level Envoy config, nor do you need to memorize every private annotation from various controllers. You declare Kubernetes resources, and Envoy Gateway translates them into configuration that Envoy Proxy can actually execute.</p>
<h2 id="gateway-vs-ingress-whats-the-difference">Gateway vs Ingress: What's the Difference</h2>
<p>The short answer: <strong>Ingress isn't obsolete, but Gateway API is better suited for medium-to-large systems that need more governance.</strong></p>

<p>If your requirements are simply:</p>
<ul>
<li>A single website or simple API</li>
<li>Basic path/host routing</li>
<li>Small team</li>
</ul>
<p>Then Ingress is still fine. But if your requirements start to include:</p>
<ul>
<li>One ingress serving multiple protocols</li>
<li>Multiple listeners, domains, or certificates</li>
<li>HTTP and gRPC coexisting</li>
<li>Separating platform ingress from application route permissions</li>
<li>Config that reads like a proper API, not an annotation wishlist</li>
</ul>
<p>Then Gateway API will start to look very appealing.</p>
<h2 id="why-not-just-use-ingress">Why Not Just Use Ingress</h2>
<p>The official Gateway API goal is to address several common pain points with Ingress at scale:</p>
<ul>
<li><strong>Better expressiveness</strong>: Routing, TLS, traffic policies, and protocol types are more clearly defined</li>
<li><strong>Better portability</strong>: Less reliance on controller-specific private annotations</li>
<li><strong>More natural role separation</strong>: Platform teams own ingress, app teams own routes</li>
</ul>
<p>For example, Ingress configs often look like this:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">metadata</span><span style="color:#E6EDF3">:</span></span>

<span data-line=""><span style="color:#7EE787">    some.ingress.controller/rewrite-target</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/auth-type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">basic</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/ssl-redirect</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"true"</span></span></code></pre></figure>
<p>Not that it doesn't work — but as requirements grow, annotations easily become mysterious YAML black magic. Gateway API pulls these needs into proper fields. It reads like "configuration," not a "wishlist."</p>
<h2 id="the-layered-structure">The Layered Structure</h2>
<p>The official concept page breaks Envoy Gateway into three layers — worth memorizing as a mental map:</p>
<ul>
<li><strong>User Configuration</strong>: The <code>Gateway API</code> resources and Envoy Gateway extension CRDs you write</li>
<li><strong>Envoy Gateway Controller</strong>: Reads these resources, translates them into executable config</li>
<li><strong>Envoy Proxy</strong>: The data plane that actually handles live traffic</li>
</ul>
<p>In practice, you'll spend most of your time modifying the "declarative layer," not SSH-ing into proxy instances to tweak low-level config. This is the elegance of being Kubernetes-native.</p>

<h2 id="core-resources-youll-encounter">Core Resources You'll Encounter</h2>
<p>Beginners often stumble because they assume Gateway API only has <code>Gateway</code> and <code>HTTPRoute</code>. It's actually a whole family of resources.</p>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>Defines "which Gateway implementation to use in this cluster."
For Envoy Gateway, the key is getting <code>controllerName</code> to point to the right controller.</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>Defines "what the ingress looks like."
For example: which ports to open, which protocols to listen on, how TLS is attached, which routes are allowed.</p>
<h3 id="listener"><code>Listener</code></h3>
<p><code>Listener</code> is one of the most important units inside a <code>Gateway</code>.
Think of it as an outward-facing slot on the Gateway — each slot defines:</p>
<ul>
<li>port</li>
<li>protocol</li>
<li>hostname</li>
<li>TLS config</li>
<li><code>allowedRoutes</code></li>
</ul>
<p>Many people think of <code>Gateway</code> as a black box, but what actually determines ingress behavior is each individual <code>listener</code> inside it.</p>
<h3 id="the-route-family">The Route Family</h3>
<ul>
<li><code>HTTPRoute</code>: HTTP/HTTPS traffic — the most common</li>
<li><code>GRPCRoute</code>: gRPC traffic — can match on service/method</li>
<li><code>TCPRoute</code>: Raw TCP traffic — doesn't parse HTTP semantics</li>
<li><code>TLSRoute</code>: Routes based on TLS SNI — common for TLS passthrough</li>
</ul>
<p>What all routes share:
<strong>They don't "open the door" — they decide "how to route traffic after it enters."</strong></p>

9:T3a79,<p>If you've worked with Kubernetes external traffic before, chances are you started with <code>Ingress</code>. It works, and for many scenarios it's genuinely sufficient. But once you hit more complex requirements — multiple listeners, multi-team ownership, gRPC, TCP, TLS passthrough, fine-grained traffic policies — you inevitably end up in a situation where "keep it alive with annotations" becomes the norm. The YAML starts looking like an incantation, and the people maintaining it feel like they're breaking a seal.</p>
<p>That's where <code>Gateway API + Envoy Gateway</code> comes in — it's the new kit. It doesn't make things more complicated; it cleanly separates the responsibilities that used to be tangled together, making ingress traffic, routing rules, TLS security settings, protocol types, and team ownership much easier to reason about.</p>
<h2 id="what-is-it-exactly">What Is It, Exactly</h2>
<p>Let's say it plainly in one sentence:</p>
<ul>
<li><code>Envoy Proxy</code>: The data plane that actually receives traffic and forwards requests — also called a Gateway Proxy</li>
<li><code>Envoy Gateway</code>: The control plane that manages Envoy Proxy for you</li>
<li><code>Gateway API</code>: The standard interface you use in Kubernetes to declare traffic rules</li>
</ul>
<p>Think of it this way:</p>
<ul>
<li><code>Gateway API</code> is where you write the requirements</li>
<li><code>Envoy Gateway</code> is the manager who translates and delegates</li>
<li><code>Envoy Proxy</code> is the actual guard standing at the door</li>
</ul>
<p>The benefit of this separation is that you don't need to hand-craft low-level Envoy config, nor do you need to memorize every private annotation from various controllers. You declare Kubernetes resources, and Envoy Gateway translates them into configuration that Envoy Proxy can actually execute.</p>
<h2 id="gateway-vs-ingress-whats-the-difference">Gateway vs Ingress: What's the Difference</h2>
<p>The short answer: <strong>Ingress isn't obsolete, but Gateway API is better suited for medium-to-large systems that need more governance.</strong></p>

<p>If your requirements are simply:</p>
<ul>
<li>A single website or simple API</li>
<li>Basic path/host routing</li>
<li>Small team</li>
</ul>
<p>Then Ingress is still fine. But if your requirements start to include:</p>
<ul>
<li>One ingress serving multiple protocols</li>
<li>Multiple listeners, domains, or certificates</li>
<li>HTTP and gRPC coexisting</li>
<li>Separating platform ingress from application route permissions</li>
<li>Config that reads like a proper API, not an annotation wishlist</li>
</ul>
<p>Then Gateway API will start to look very appealing.</p>
<h2 id="why-not-just-use-ingress">Why Not Just Use Ingress</h2>
<p>The official Gateway API goal is to address several common pain points with Ingress at scale:</p>
<ul>
<li><strong>Better expressiveness</strong>: Routing, TLS, traffic policies, and protocol types are more clearly defined</li>
<li><strong>Better portability</strong>: Less reliance on controller-specific private annotations</li>
<li><strong>More natural role separation</strong>: Platform teams own ingress, app teams own routes</li>
</ul>
<p>For example, Ingress configs often look like this:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">metadata</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  annotations</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/rewrite-target</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/auth-type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">basic</span></span>
<span data-line=""><span style="color:#7EE787">    some.ingress.controller/ssl-redirect</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"true"</span></span></code></pre></figure>
<p>Not that it doesn't work — but as requirements grow, annotations easily become mysterious YAML black magic. Gateway API pulls these needs into proper fields. It reads like "configuration," not a "wishlist."</p>
<h2 id="the-layered-structure">The Layered Structure</h2>
<p>The official concept page breaks Envoy Gateway into three layers — worth memorizing as a mental map:</p>
<ul>
<li><strong>User Configuration</strong>: The <code>Gateway API</code> resources and Envoy Gateway extension CRDs you write</li>
<li><strong>Envoy Gateway Controller</strong>: Reads these resources, translates them into executable config</li>
<li><strong>Envoy Proxy</strong>: The data plane that actually handles live traffic</li>
</ul>
<p>In practice, you'll spend most of your time modifying the "declarative layer," not SSH-ing into proxy instances to tweak low-level config. This is the elegance of being Kubernetes-native.</p>

<h2 id="core-resources-youll-encounter">Core Resources You'll Encounter</h2>
<p>Beginners often stumble because they assume Gateway API only has <code>Gateway</code> and <code>HTTPRoute</code>. It's actually a whole family of resources.</p>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>Defines "which Gateway implementation to use in this cluster."
For Envoy Gateway, the key is getting <code>controllerName</code> to point to the right controller.</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>Defines "what the ingress looks like."
For example: which ports to open, which protocols to listen on, how TLS is attached, which routes are allowed.</p>
<h3 id="listener"><code>Listener</code></h3>
<p><code>Listener</code> is one of the most important units inside a <code>Gateway</code>.
Think of it as an outward-facing slot on the Gateway — each slot defines:</p>
<ul>
<li>port</li>
<li>protocol</li>
<li>hostname</li>
<li>TLS config</li>
<li><code>allowedRoutes</code></li>
</ul>
<p>Many people think of <code>Gateway</code> as a black box, but what actually determines ingress behavior is each individual <code>listener</code> inside it.</p>
<h3 id="the-route-family">The Route Family</h3>
<ul>
<li><code>HTTPRoute</code>: HTTP/HTTPS traffic — the most common</li>
<li><code>GRPCRoute</code>: gRPC traffic — can match on service/method</li>
<li><code>TCPRoute</code>: Raw TCP traffic — doesn't parse HTTP semantics</li>
<li><code>TLSRoute</code>: Routes based on TLS SNI — common for TLS passthrough</li>
</ul>
<p>What all routes share:
<strong>They don't "open the door" — they decide "how to route traffic after it enters."</strong></p>
<h2 id="minimal-mental-model">Minimal Mental Model</h2>
<p>Keep this map in your head:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#A5D6FF">GatewayClass</span><span style="color:#8B949E">  # Which Gateway implementation to use in this cluster</span></span>

<ul>
<li><code>parentRefs</code>: Which Gateway this rule attaches to</li>
<li><code>hostnames</code>: Which domain should match this rule</li>
<li><code>backendRefs</code>: Which Service to send traffic to</li>
</ul>
