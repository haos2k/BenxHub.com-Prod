1d:T5075,<p>A lot of people's first impression of Gateway API is something like: "The term count isn't that high, but my brain feels like it's watching a cast list full of characters with similar names — I can't tell who's the protagonist and who's a side character." This post is here to cut through that confusion, and cover the common route types along the way.</p>
<h2 id="the-overall-architecture">The Overall Architecture</h2>
<p>The official Envoy Gateway concepts break the system into three layers:</p>
<ul>
<li><strong>User Configuration</strong>: The <code>Gateway API</code> resources and Envoy Gateway extension CRDs you write</li>
<li><strong>Envoy Gateway Controller</strong>: Reads resources, validates them, and translates config</li>
<li><strong>Envoy Proxy</strong>: The data plane that actually handles traffic</li>
</ul>
<p>This means what you're usually editing is not Envoy Proxy itself — you're "declaring what you want."
Envoy Gateway translates those declarations into config that Envoy Proxy can execute. That's what makes it nicer than writing proxy config by hand.</p>
<h2 id="the-key-roles">The Key Roles</h2>
<p>Just remember these for now:</p>
<ul>
<li><code>GatewayClass</code>: Defines "which Gateway implementation to use in this cluster"</li>
<li><code>Gateway</code>: Defines "where the ingress is and what protocol it speaks"</li>
<li><code>Listener</code>: Defines a specific port/protocol/hostname ingress slot</li>
<li><code>Route</code>: Defines "which requests go to which Service"</li>
<li><code>Envoy Proxy</code>: The actual Gateway Proxy that receives and forwards traffic</li>
</ul>
<p>In plain English:</p>
<ul>
<li><code>GatewayClass</code> is the spec sheet</li>
<li><code>Gateway</code> is the building's front entrance</li>
<li><code>Listener</code> is the front desk</li>
<li><code>Route</code> is the signage inside the building</li>
<li><code>Envoy Proxy</code> is the security system doing access control and escorting</li>
</ul>
<p>Without any one of these, traffic won't get where you want it to go.</p>

<h2 id="understanding-each-field">Understanding Each Field</h2>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>This is a cluster-level ingress type definition. The most critical field is usually:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  controllerName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">gateway.envoyproxy.io/gatewayclass-controller</span></span></code></pre></figure>
<p>This simply means:
"This <code>GatewayClass</code> is managed by the Envoy Gateway controller."</p>
<p>If the controllerName doesn't match, it's like ordering delivery to the wrong company — nobody picks it up.</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>This defines "what the ingress looks like." The most-referenced field is <code>listeners</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">listeners</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">http</span></span>
<span data-line=""><span style="color:#7EE787">    protocol</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTP</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">80</span></span></code></pre></figure>
<p>This means:</p>
<ul>
<li>Open a listener named <code>http</code></li>
<li>Accept HTTP traffic</li>
<li>Listen externally on port <code>80</code></li>
</ul>
<p>For HTTPS, you'd typically add another listener with <code>protocol: HTTPS</code> and attach TLS config.</p>
<p><code>Gateway</code> commonly manages:</p>
<ul>
<li>External port and protocol</li>
<li>Per-listener hostname</li>
<li>TLS termination location</li>
<li>Which namespaces' routes can attach</li>
</ul>
<p><code>Gateway</code> is more of a platform-layer concern — its ownership typically sits with the platform team.</p>
<h3 id="listener"><code>Listener</code></h3>
<p>This is the most commonly overlooked role for beginners, but it's actually crucial.</p>
<p>A <code>listener</code> is an outward-facing ingress slot on the Gateway. It defines:</p>
<ul>
<li><code>name</code></li>
<li><code>port</code></li>
<li><code>protocol</code></li>
<li><code>hostname</code></li>
<li><code>tls</code></li>
<li><code>allowedRoutes</code></li>
</ul>
<p>Example:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">listeners</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span>
<span data-line=""><span style="color:#7EE787">    protocol</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTPS</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">443</span></span>
<span data-line=""><span style="color:#7EE787">    hostname</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api.example.com</span></span></code></pre></figure>
<p>This means:</p>
<ul>
<li>This slot is named <code>https</code></li>
<li>Accepts HTTPS</li>
<li>Listens on port <code>443</code></li>
<li>Dedicated to <code>api.example.com</code></li>
</ul>
<p>If you have multiple listeners like:</p>
<ul>
<li><code>http</code> for port 80</li>
<li><code>https</code> for port 443</li>
<li><code>grpc</code> for port 50051</li>
</ul>
<p>You're opening multiple ingress slots on the same Gateway, each capable of attaching different routes.</p>
<h3 id="envoy-proxy"><code>Envoy Proxy</code></h3>
<p>Many people focus only on the YAML and forget that <code>Envoy Proxy</code> is what actually handles live traffic.</p>
<p>Its role is:</p>
<ul>
<li>Receiving client requests</li>
<li>Matching against config pushed by Envoy Gateway</li>
<li>Forwarding traffic to the appropriate backend</li>
<li>Handling TLS, headers, timeouts, retries, and other data-plane behaviors</li>
</ul>
<p>So think of Envoy Gateway as the "control plane," and Envoy Proxy as the "data plane / Gateway Proxy."</p>
<h3 id="the-route-family">The Route Family</h3>
<p><code>Route</code> isn't just <code>HTTPRoute</code>. The whole family is central to Gateway API's design.</p>

<span data-line=""><span style="color:#7EE787">  hostnames</span><span style="color:#E6EDF3">:</span></span>

<span data-line=""><span style="color:#7EE787">  rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">backend</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">3000</span></span></code></pre></figure>
<ul>
<li><code>parentRefs</code>: Which Gateway to attach to</li>
<li><code>hostnames</code>: Which Host header triggers this rule</li>
<li><code>backendRefs</code>: Where to send matched requests</li>
</ul>
<p>The most common confusion: <code>Gateway</code> is not where you write fine-grained routing — <code>HTTPRoute</code> is what actually decides "how to split traffic."</p>
<h4 id="grpcroute"><code>GRPCRoute</code></h4>
<p>If you're handling gRPC, <code>GRPCRoute</code> is more natural than forcing it into <code>HTTPRoute</code>.</p>
<p>It can match on:</p>
<ul>
<li>gRPC hostname</li>
<li>gRPC service</li>
<li>gRPC method</li>
<li>headers</li>
</ul>
<p>Example:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">matches</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">method</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">      service</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">com.example.User</span></span>
<span data-line=""><span style="color:#7EE787">      method</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">Login</span></span></code></pre></figure>
<p>This semantics aligns naturally with gRPC — you're not just matching URL paths, you're matching directly against the gRPC service/method model.</p>
<p>The official docs also note: if <code>GRPCRoute</code> and <code>HTTPRoute</code> share the same listener and have conflicting hostnames, implementations should reject one. Basically, don't let HTTP and gRPC fight over the same hostname.</p>
<h4 id="tcproute"><code>TCPRoute</code></h4>
<p><code>TCPRoute</code> handles raw TCP traffic.
Unlike <code>HTTPRoute</code>, it doesn't understand path or header semantics at L7 — it's closer to L4 forwarding.</p>
<p>Appropriate scenarios:</p>
<ul>
<li>Non-HTTP protocol services</li>
<li>Pure TCP services</li>
<li>Routing connections to different backends based only on listener port</li>
</ul>
<p>Databases with custom protocols or proprietary TCP protocols are typical <code>TCPRoute</code> use cases.</p>
<h4 id="tlsroute"><code>TLSRoute</code></h4>
<p><code>TLSRoute</code> handles TLS traffic and is particularly common in <strong>TLS passthrough</strong> scenarios.</p>
<p>Core concept:</p>
<ul>
<li>The Gateway doesn't necessarily terminate TLS</li>
<li>It may route traffic based solely on the SNI hostname in the TLS handshake</li>
<li>Encrypted traffic is preserved all the way to the backend</li>
</ul>
<p>This matters for scenarios requiring end-to-end encryption, or where you don't want TLS terminated at the Gateway.</p>
<h2 id="how-to-choose-a-route-type">How to Choose a Route Type</h2>
<table>
<thead>
<tr>
<th>Requirement</th>
<th>Use This</th>
</tr>
</thead>
<tbody>
<tr>
<td>Websites, REST APIs, general web traffic</td>
<td><code>HTTPRoute</code></td>
</tr>
<tr>
<td>gRPC service/method routing</td>
<td><code>GRPCRoute</code></td>
</tr>
<tr>
<td>Raw TCP traffic</td>
<td><code>TCPRoute</code></td>
</tr>
<tr>
<td>TLS passthrough / SNI-based routing</td>
<td><code>TLSRoute</code></td>
</tr>
</tbody>
</table>
<p>This table matters because many people instinctively write <code>HTTPRoute</code> for everything. But if you're actually dealing with gRPC or TCP, forcing it into <code>HTTPRoute</code> just makes the YAML increasingly awkward.</p>
<h2 id="why-routes-are-easier-to-reason-about-than-ingress">Why Routes Are Easier to Reason About Than Ingress</h2>
<p>Old Ingress configs often squeezed too many responsibilities into a single resource, leading to some persistent pain points:</p>
<ul>
<li>Platform config and app routing mixed together</li>
<li>Advanced features expressed via annotations with poor readability</li>
<li>Limited expressiveness for non-HTTP protocols</li>
</ul>
<p>Gateway API's approach is to split responsibilities:</p>
<ul>
<li>Platform teams manage <code>GatewayClass</code> / <code>Gateway</code></li>
<li>App teams manage their own <code>HTTPRoute</code></li>
</ul>
<p>This separation works well for multi-person collaboration. You don't need to touch the entire ingress layer just to change a path — team stepping-on-each-other rates drop significantly.</p>
<h2 id="start-paying-attention-to-status">Start Paying Attention to Status</h2>
<p>Beyond <code>spec</code>, gradually build the habit of checking <code>status</code>. Especially for <code>HTTPRoute</code> and <code>Gateway</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#A5D6FF"> eg</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#A5D6FF"> backend</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span></code></pre></figure>
<p>Start by checking:</p>
<ul>
<li>Whether the route was <code>Accepted</code></li>
<li>Whether the gateway listener is Ready</li>
<li>Whether an address was successfully assigned</li>
</ul>
<p>It's like checking exam results. Don't just verify that you submitted — verify that it was graded and passed.</p>
<h2 id="one-line-summary">One-Line Summary</h2>
<p>Think of <code>GatewayClass</code>, <code>Gateway</code>, <code>Listener</code>, <code>Route</code>, and <code>Envoy Proxy</code> as "who manages it, how the ingress opens, how each slot connects, how traffic splits, and who executes it" — and you've already grasped 80% of the core concepts.</p>
<blockquote>
<p>💡 Beginners often dive straight into CRD details. Don't rush — get these roles straight first, and the YAML will stop feeling like meeting strangers every time.</p>
</blockquote>

2a:T5075,<p>A lot of people's first impression of Gateway API is something like: "The term count isn't that high, but my brain feels like it's watching a cast list full of characters with similar names — I can't tell who's the protagonist and who's a side character." This post is here to cut through that confusion, and cover the common route types along the way.</p>
<h2 id="the-overall-architecture">The Overall Architecture</h2>
<p>The official Envoy Gateway concepts break the system into three layers:</p>
<ul>
<li><strong>User Configuration</strong>: The <code>Gateway API</code> resources and Envoy Gateway extension CRDs you write</li>
<li><strong>Envoy Gateway Controller</strong>: Reads resources, validates them, and translates config</li>
<li><strong>Envoy Proxy</strong>: The data plane that actually handles traffic</li>
</ul>
<p>This means what you're usually editing is not Envoy Proxy itself — you're "declaring what you want."
Envoy Gateway translates those declarations into config that Envoy Proxy can execute. That's what makes it nicer than writing proxy config by hand.</p>
<h2 id="the-key-roles">The Key Roles</h2>
<p>Just remember these for now:</p>
<ul>
<li><code>GatewayClass</code>: Defines "which Gateway implementation to use in this cluster"</li>
<li><code>Gateway</code>: Defines "where the ingress is and what protocol it speaks"</li>
<li><code>Listener</code>: Defines a specific port/protocol/hostname ingress slot</li>
<li><code>Route</code>: Defines "which requests go to which Service"</li>
<li><code>Envoy Proxy</code>: The actual Gateway Proxy that receives and forwards traffic</li>
</ul>
<p>In plain English:</p>
<ul>
<li><code>GatewayClass</code> is the spec sheet</li>
<li><code>Gateway</code> is the building's front entrance</li>
<li><code>Listener</code> is the front desk</li>
<li><code>Route</code> is the signage inside the building</li>
<li><code>Envoy Proxy</code> is the security system doing access control and escorting</li>
</ul>
<p>Without any one of these, traffic won't get where you want it to go.</p>

<li><code>HTTPRoute</code> says requests for <code>www.example.com</code> should go to <code>backend:3000</code></li>
<li><code>Envoy Gateway</code> translates all of this for <code>Envoy Proxy</code></li>
</ol>
<h2 id="understanding-each-field">Understanding Each Field</h2>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>This is a cluster-level ingress type definition. The most critical field is usually:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  controllerName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">gateway.envoyproxy.io/gatewayclass-controller</span></span></code></pre></figure>
<p>This simply means:
"This <code>GatewayClass</code> is managed by the Envoy Gateway controller."</p>
<p>If the controllerName doesn't match, it's like ordering delivery to the wrong company — nobody picks it up.</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>This defines "what the ingress looks like." The most-referenced field is <code>listeners</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">listeners</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">http</span></span>
<span data-line=""><span style="color:#7EE787">    protocol</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTP</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">80</span></span></code></pre></figure>
<p>This means:</p>
<ul>
<li>Open a listener named <code>http</code></li>
<li>Accept HTTP traffic</li>
<li>Listen externally on port <code>80</code></li>
</ul>
<p>For HTTPS, you'd typically add another listener with <code>protocol: HTTPS</code> and attach TLS config.</p>
<p><code>Gateway</code> commonly manages:</p>
<ul>
<li>External port and protocol</li>
<li>Per-listener hostname</li>
<li>TLS termination location</li>
<li>Which namespaces' routes can attach</li>
</ul>
<p><code>Gateway</code> is more of a platform-layer concern — its ownership typically sits with the platform team.</p>
<h3 id="listener"><code>Listener</code></h3>
<p>This is the most commonly overlooked role for beginners, but it's actually crucial.</p>
<p>A <code>listener</code> is an outward-facing ingress slot on the Gateway. It defines:</p>
<ul>
<li><code>name</code></li>
<li><code>port</code></li>
<li><code>protocol</code></li>
<li><code>hostname</code></li>
<li><code>tls</code></li>
<li><code>allowedRoutes</code></li>
</ul>
<p>Example:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">listeners</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span>
<span data-line=""><span style="color:#7EE787">    protocol</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTPS</span></span>
<span data-line=""><span style="color:#7EE787">    port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">443</span></span>
<span data-line=""><span style="color:#7EE787">    hostname</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api.example.com</span></span></code></pre></figure>
<p>This means:</p>
<ul>
<li>This slot is named <code>https</code></li>
<li>Accepts HTTPS</li>
<li>Listens on port <code>443</code></li>
<li>Dedicated to <code>api.example.com</code></li>
</ul>
<p>If you have multiple listeners like:</p>
<ul>
<li><code>http</code> for port 80</li>
<li><code>https</code> for port 443</li>
<li><code>grpc</code> for port 50051</li>
</ul>
<p>You're opening multiple ingress slots on the same Gateway, each capable of attaching different routes.</p>
<h3 id="envoy-proxy"><code>Envoy Proxy</code></h3>
<p>Many people focus only on the YAML and forget that <code>Envoy Proxy</code> is what actually handles live traffic.</p>
<p>Its role is:</p>
<ul>
<li>Receiving client requests</li>
<li>Matching against config pushed by Envoy Gateway</li>
<li>Forwarding traffic to the appropriate backend</li>
<li>Handling TLS, headers, timeouts, retries, and other data-plane behaviors</li>
</ul>
<p>So think of Envoy Gateway as the "control plane," and Envoy Proxy as the "data plane / Gateway Proxy."</p>
<h3 id="the-route-family">The Route Family</h3>
<p><code>Route</code> isn't just <code>HTTPRoute</code>. The whole family is central to Gateway API's design.</p>
<h4 id="httproute"><code>HTTPRoute</code></h4>
<p>This is what you'll write and modify most often. Three key fields:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">  hostnames</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#A5D6FF">"www.example.com"</span></span>
<span data-line=""><span style="color:#7EE787">  rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">backend</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">3000</span></span></code></pre></figure>
<ul>
<li><code>parentRefs</code>: Which Gateway to attach to</li>
<li><code>hostnames</code>: Which Host header triggers this rule</li>
<li><code>backendRefs</code>: Where to send matched requests</li>
</ul>
<p>The most common confusion: <code>Gateway</code> is not where you write fine-grained routing — <code>HTTPRoute</code> is what actually decides "how to split traffic."</p>
<h4 id="grpcroute"><code>GRPCRoute</code></h4>
<p>If you're handling gRPC, <code>GRPCRoute</code> is more natural than forcing it into <code>HTTPRoute</code>.</p>
<p>It can match on:</p>
<ul>
<li>gRPC hostname</li>
<li>gRPC service</li>
<li>gRPC method</li>
<li>headers</li>
</ul>
<p>Example:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">matches</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">method</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">      service</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">com.example.User</span></span>
<span data-line=""><span style="color:#7EE787">      method</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">Login</span></span></code></pre></figure>
<p>This semantics aligns naturally with gRPC — you're not just matching URL paths, you're matching directly against the gRPC service/method model.</p>
<p>The official docs also note: if <code>GRPCRoute</code> and <code>HTTPRoute</code> share the same listener and have conflicting hostnames, implementations should reject one. Basically, don't let HTTP and gRPC fight over the same hostname.</p>
<h4 id="tcproute"><code>TCPRoute</code></h4>
<p><code>TCPRoute</code> handles raw TCP traffic.
Unlike <code>HTTPRoute</code>, it doesn't understand path or header semantics at L7 — it's closer to L4 forwarding.</p>
<p>Appropriate scenarios:</p>
<ul>
<li>Non-HTTP protocol services</li>
<li>Pure TCP services</li>
<li>Routing connections to different backends based only on listener port</li>
</ul>
<p>Databases with custom protocols or proprietary TCP protocols are typical <code>TCPRoute</code> use cases.</p>
<h4 id="tlsroute"><code>TLSRoute</code></h4>
<p><code>TLSRoute</code> handles TLS traffic and is particularly common in <strong>TLS passthrough</strong> scenarios.</p>
<p>Core concept:</p>
<ul>
<li>The Gateway doesn't necessarily terminate TLS</li>
<li>It may route traffic based solely on the SNI hostname in the TLS handshake</li>
<li>Encrypted traffic is preserved all the way to the backend</li>
</ul>
<p>This matters for scenarios requiring end-to-end encryption, or where you don't want TLS terminated at the Gateway.</p>
<h2 id="how-to-choose-a-route-type">How to Choose a Route Type</h2>
<table>
<thead>
<tr>
<th>Requirement</th>
<th>Use This</th>
</tr>
</thead>
<tbody>
<tr>
<td>Websites, REST APIs, general web traffic</td>
<td><code>HTTPRoute</code></td>
</tr>
<tr>
<td>gRPC service/method routing</td>
<td><code>GRPCRoute</code></td>
</tr>
<tr>
<td>Raw TCP traffic</td>
<td><code>TCPRoute</code></td>
</tr>
<tr>
<td>TLS passthrough / SNI-based routing</td>
<td><code>TLSRoute</code></td>
</tr>
</tbody>
</table>
<p>This table matters because many people instinctively write <code>HTTPRoute</code> for everything. But if you're actually dealing with gRPC or TCP, forcing it into <code>HTTPRoute</code> just makes the YAML increasingly awkward.</p>
<h2 id="why-routes-are-easier-to-reason-about-than-ingress">Why Routes Are Easier to Reason About Than Ingress</h2>
<p>Old Ingress configs often squeezed too many responsibilities into a single resource, leading to some persistent pain points:</p>
<ul>
<li>Platform config and app routing mixed together</li>
<li>Advanced features expressed via annotations with poor readability</li>
<li>Limited expressiveness for non-HTTP protocols</li>
</ul>
<p>Gateway API's approach is to split responsibilities:</p>
<ul>
<li>Platform teams manage <code>GatewayClass</code> / <code>Gateway</code></li>
<li>App teams manage their own <code>HTTPRoute</code></li>
</ul>
<p>This separation works well for multi-person collaboration. You don't need to touch the entire ingress layer just to change a path — team stepping-on-each-other rates drop significantly.</p>
<h2 id="start-paying-attention-to-status">Start Paying Attention to Status</h2>
<p>Beyond <code>spec</code>, gradually build the habit of checking <code>status</code>. Especially for <code>HTTPRoute</code> and <code>Gateway</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#A5D6FF"> eg</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#A5D6FF"> backend</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span></code></pre></figure>
<p>Start by checking:</p>
<ul>
<li>Whether the route was <code>Accepted</code></li>
<li>Whether the gateway listener is Ready</li>
<li>Whether an address was successfully assigned</li>
</ul>
<p>It's like checking exam results. Don't just verify that you submitted — verify that it was graded and passed.</p>
<h2 id="one-line-summary">One-Line Summary</h2>
<p>Think of <code>GatewayClass</code>, <code>Gateway</code>, <code>Listener</code>, <code>Route</code>, and <code>Envoy Proxy</code> as "who manages it, how the ingress opens, how each slot connects, how traffic splits, and who executes it" — and you've already grasped 80% of the core concepts.</p>
<blockquote>
<p>💡 Beginners often dive straight into CRD details. Don't rush — get these roles straight first, and the YAML will stop feeling like meeting strangers every time.</p>
</blockquote>
