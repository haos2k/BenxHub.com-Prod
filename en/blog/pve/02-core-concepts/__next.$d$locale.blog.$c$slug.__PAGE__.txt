3:T1761,<p>Before clicking buttons at random, get these four concepts into your head: you'll be clearer on "should I use a VM or LXC, where should I put the disk, how do I connect the network." Like reading the skill descriptions before playing a game — otherwise you'll keep dying.</p>
<h2 id="concept-1-the-difference-between-vms-and-lxc">Concept 1: The Difference Between VMs and LXC</h2>
<table>
<thead>
<tr>
<th>Type</th>
<th>Technology</th>
<th>Characteristics</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>VM</strong></td>
<td>KVM/QEMU</td>
<td>Full OS, high isolation, runs both Windows and Linux</td>
</tr>
<tr>
<td><strong>LXC</strong></td>
<td>Linux Containers</td>
<td>Lightweight, fast startup, high density, but <strong>Linux only</strong></td>
</tr>
</tbody>
</table>
<p><strong>One-sentence decision</strong>: need full isolation or running Windows → VM; want to save resources and the service is Linux → LXC. Choosing wrong is like wearing flip-flops to go hiking — not impossible, but you'll suffer.</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#6A737D"># Create a VM (example)</span></span>

<span data-line=""> </span>
<span data-line=""><span style="color:#6A737D"># Create an LXC container (example)</span></span>
<span data-line=""><span style="color:#B392F0">pct</span><span style="color:#9ECBFF"> create</span><span style="color:#79B8FF"> 200</span><span style="color:#9ECBFF"> local:vztmpl/debian-12-standard_12.2-1_amd64.tar.zst</span><span style="color:#79B8FF"> --hostname</span><span style="color:#9ECBFF"> my-ct</span><span style="color:#79B8FF"> --memory</span><span style="color:#79B8FF"> 512</span></span></code></pre></figure>
<h2 id="concept-2-your-storage-choice-determines-how-far-you-can-go">Concept 2: Your Storage Choice Determines How Far You Can Go</h2>
<p>Choose storage wrong and you'll hit walls with HA and migration later. Common types:</p>
<ul>
<li><strong>local</strong>: single-node directory storage, beginner-friendly</li>
<li><strong>local-lvm</strong>: local LVM, good for snapshots and clones</li>
<li><strong>NFS/CIFS</strong>: shared network storage, cross-node capable</li>
<li><strong>ZFS/Ceph</strong>: advanced solutions for replication and high availability</li>
</ul>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#6A737D"># Check current storage status</span></span>
<span data-line=""><span style="color:#B392F0">pvesm</span><span style="color:#9ECBFF"> status</span></span>
<span data-line=""><span style="color:#B392F0">pvesm</span><span style="color:#9ECBFF"> list</span><span style="color:#9ECBFF"> local</span></span></code></pre></figure>
<blockquote>
<p>For live migration or HA, disks generally need to be on <strong>shared storage</strong> — otherwise the VM can't be moved. Like trying to move house but the furniture is still locked in someone else's place.</p>
</blockquote>
<h2 id="concept-3-the-network-model-vmbr0">Concept 3: The Network Model (vmbr0)</h2>
<p>PVE uses bridged networking by default: <code>vmbr0</code> bridges to a physical NIC, making VMs look like they're directly connected to the physical switch. Simply put: <strong>one virtual cable, everyone shares the outgoing NIC.</strong></p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="text" data-theme="github-dark"><code data-language="text" data-theme="github-dark" style="display: grid;"><span data-line=""><span>[Physical NIC] --> [vmbr0] --> [VM1] [VM2] [VM3]</span></span></code></pre></figure>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#6A737D"># Check current network configuration</span></span>
<span data-line=""><span style="color:#B392F0">cat</span><span style="color:#9ECBFF"> /etc/network/interfaces</span></span></code></pre></figure>
<h2 id="concept-4-nodes-and-clusters">Concept 4: Nodes and Clusters</h2>
<ul>
<li><strong>Single node</strong>: one machine handles everything, good for getting started and homelabs</li>
<li><strong>Cluster</strong>: multiple hosts managed together, supports migration and HA — like forming a party for a dungeon</li>
</ul>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="text" data-theme="github-dark"><code data-language="text" data-theme="github-dark" style="display: grid;"><span data-line=""><span>[Node1] &#x3C;--> [Node2] &#x3C;--> [Node3]</span></span>
<span data-line=""><span>   \\_______ shared config (pmxcfs) _______//</span></span></code></pre></figure>
<p>The key point in one sentence: unified management plane, schedulable resources, failure can be taken over. Understanding this concept first makes the advanced section much easier to follow.</p>
