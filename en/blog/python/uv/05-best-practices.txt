1b:T1484,<p>In practice, environments tend to break not because "uv isn't powerful enough," but because of <strong>process and habits</strong>. This checklist can be used as daily guidelines — every pitfall avoided is another time you leave work on time.</p>
<h2 id="recommended-practices">Recommended Practices</h2>
<h3 id="1-always-commit-uvlock">1) Always Commit uv.lock</h3>
<p>The lockfile is the foundation of reproducibility. Not committing it means everyone, every machine, every CI run may install different dependencies — reproducing bugs becomes hell mode. A project without a lockfile is like new shoes you've never tried on: you only find out they hurt when you're in battle.</p>
<h3 id="2-never-commit-venv">2) Never Commit .venv</h3>
<p>The virtual environment is a local artifact — it should be in <code>.gitignore</code>. uv automatically adds <code>.venv</code> to the project's ignore file; just double-check it's there.</p>
<h3 id="3-constrain-dependencies-when-possible">3) Constrain Dependencies When Possible</h3>
<p>In <code>pyproject.toml</code>, avoid bare <code>requests</code> — prefer <code>requests>=2.31,&#x3C;3</code> or more specific. <code>uv add</code> adds reasonable constraints by default; when editing manually, don't leave the range too wide.</p>
<h3 id="4-use-uv-sync-or-uv-pip-sync-in-ci">4) Use uv sync or uv pip sync in CI</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#6A737D"># GitHub Actions example</span></span>
<span data-line=""><span style="color:#E1E4E8">- </span><span style="color:#85E89D">run</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">uv sync</span></span>
<span data-line=""><span style="color:#E1E4E8">- </span><span style="color:#85E89D">run</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">uv run pytest</span></span></code></pre></figure>
<p>Sync first, then run — ensures the environment matches the lockfile. Don't run <code>uv add</code> in CI; that modifies the lockfile and can create unexpected diffs.</p>
<h3 id="5-put-dev-tools-in-optional--dev">5) Put Dev Tools in optional / dev</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">uv</span><span style="color:#9ECBFF"> add</span><span style="color:#79B8FF"> --dev</span><span style="color:#9ECBFF"> pytest</span><span style="color:#9ECBFF"> ruff</span><span style="color:#9ECBFF"> mypy</span></span></code></pre></figure>
<p>Tests, lint, and type checking don't affect production dependencies and won't be packed into the wheel. Production images only need <code>uv sync --no-dev</code>.</p>
<h2 id="common-pitfalls">Common Pitfalls</h2>
<h3 id="pitfall-1-mixing-pip-and-uv-add">Pitfall 1: Mixing pip and uv add</h3>
<p>Don't use both <code>pip install</code> and <code>uv add</code> in the same venv — the lockfile will get out of sync. Pick one path and stick to it.</p>
<h3 id="pitfall-2-using-uvx-for-project-tools">Pitfall 2: Using uvx for Project Tools</h3>
<p>Project tools that need a pinned version (like pytest, mypy) → use <code>uv add --dev</code> + <code>uv run</code>.
Temporary one-off use → use <code>uvx</code>.</p>
<h3 id="pitfall-3-editing-pyprojecttoml-manually-without-reading-it-first">Pitfall 3: Editing pyproject.toml Manually Without Reading It First</h3>
<p>For dependency changes, prefer <code>uv add</code> / <code>uv remove</code> — avoids format issues and missing lockfile updates.</p>
<h3 id="pitfall-4-not-installing-uv-in-ci">Pitfall 4: Not Installing uv in CI</h3>
<p>Many CI systems now support uv — it installs fast and runs even faster. Use the official installer or <code>pip install uv</code>; don't stick with pip for dependency resolution forever.</p>
<h3 id="pitfall-5-no-requires-python-in-the-project">Pitfall 5: No requires-python in the Project</h3>
<p>In <code>pyproject.toml</code>, specify <code>requires-python = ">=3.12"</code> etc., so tools and collaborators know the minimum version requirement. Prevents the disaster of "it runs on my 3.12, it crashes on your 3.8."</p>
<hr>
<p>Following this checklist won't guarantee zero failures, but you'll avoid a lot of unnecessary detours. Check the official docs when in doubt — most pitfalls have been stumbled into before.
Happy developing — may your dependencies install cleanly, tests stay green, and CI stop making you wait forever! 🦦
(By the way, after using uv, you'll realize: the time you used to spend waiting for pip's spinner is now enough to pet the cat three times.)</p>
