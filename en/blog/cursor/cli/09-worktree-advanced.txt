1b:T2974,<p>The previous post <a href="08-worktree-merge">08-worktree-merge</a> covered Cursor’s automatic worktree and Apply. This one goes further on two things: <strong>Best-of-N</strong> (same prompt, multiple models in parallel, then pick one to Apply) and <strong>worktrees.json</strong> (auto install deps, run migrations, copy <code>.env</code> when a worktree is created).</p>
<h2 id="best-of-n-one-prompt-multiple-models-at-once">Best-of-N: One prompt, multiple models at once</h2>
<p><strong>Best-of-N</strong> means: you send one task, Cursor runs <strong>multiple models</strong> in separate worktrees, and you get multiple “cards,” each with one model’s changes—<strong>choose one and hit Apply</strong>.</p>
<h3 id="when-to-use-best-of-n">When to use Best-of-N?</h3>
<table>
<thead>
<tr>
<th>Situation</th>
<th>Why it helps</th>
</tr>
</thead>
<tbody>
<tr>
<td>Not sure which model fits your codebase best</td>
<td>Run once, compare outputs, small benchmark</td>
</tr>
<tr>
<td>Hard problem, worried one model misses edge cases</td>
<td>Different models, different approaches, more coverage</td>
</tr>
<tr>
<td>Compare code quality</td>
<td>Same request, different style and structure side by side</td>
</tr>
<tr>
<td>Task is hard, want higher “first try” success</td>
<td>Multiple models each try once, Apply the best</td>
</tr>
</tbody>
</table>
<p>In short: <strong>multiple models do the same task, you pick one</strong>—especially for hard tasks or when you care about quality.</p>
<h3 id="how-to-use-it">How to use it</h3>
<p>In Cursor, when starting an Agent, choose “multiple models” or the Best-of-N option (per current UI). After sending the prompt you’ll see multiple cards; switch between them to compare, then <strong>Apply</strong> the one you want onto main.</p>
<p>If you Apply more than one card from the same Best-of-N run (e.g. Apply A then B), Cursor may ask: <strong>merge with conflict resolution</strong>, or <strong>Full Overwrite</strong> (replace whole file).</p>
<h2 id="worktreesjson-prepare-the-environment-when-a-worktree-is-created">worktrees.json: Prepare the environment when a worktree is created</h2>
<p>When Cursor creates a worktree, it copies <strong>tracked files</strong> from the main directory by default, but doesn’t install deps, copy <code>.env</code>, or run DB migrations.<br>
With <strong><code>.cursor/worktrees.json</code></strong> you can specify <strong>commands to run after each new worktree is created</strong>, e.g. <code>npm ci</code>, <code>cp .env</code>, <code>npm run db:migrate</code>.</p>
<h3 id="where-does-the-config-live">Where does the config live?</h3>
<p>Cursor looks in order:</p>
<ol>
<li>Project root: <code>.cursor/worktrees.json</code></li>
<li>Worktree path</li>
</ol>
<p>Usually put it at <strong>project root</strong>: <code>.cursor/worktrees.json</code>.</p>
<h3 id="three-config-keys">Three config keys</h3>
<table>
<thead>
<tr>
<th>Key</th>
<th>Description</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>setup-worktree</code></td>
<td>Generic; used on all OSes if no OS-specific key is set</td>
</tr>
<tr>
<td><code>setup-worktree-windows</code></td>
<td>Windows only; overrides <code>setup-worktree</code></td>
</tr>
<tr>
<td><code>setup-worktree-unix</code></td>
<td>macOS / Linux only; overrides <code>setup-worktree</code></td>
</tr>
</tbody>
</table>
<p>Each key can be:</p>
<ul>
<li><strong>String</strong>: path to a script (relative to the directory containing <code>.cursor/worktrees.json</code>)</li>
<li><strong>Array</strong>: list of shell commands, run in order</li>
</ul>

<h3 id="more-complex-use-script-files">More complex: use script files</h3>
<p>For many commands or logic, use a script and reference it in <code>worktrees.json</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="json" data-theme="github-dark"><code data-language="json" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#E1E4E8">{</span></span>

<span data-line=""><span style="color:#79B8FF">  "setup-worktree-windows"</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">"setup-worktree-windows.ps1"</span><span style="color:#E1E4E8">,</span></span>
<span data-line=""><span style="color:#79B8FF">  "setup-worktree"</span><span style="color:#E1E4E8">: [</span><span style="color:#9ECBFF">"echo 'Using generic fallback'"</span><span style="color:#E1E4E8">]</span></span>

<p>Put scripts under <code>.cursor/</code>, e.g. <code>.cursor/setup-worktree-unix.sh</code>, with <code>npm ci</code>, copy <code>.env</code>, <code>chmod</code>, migrations, etc.<br>
On Windows use <code>.ps1</code> and in the script use <code>$env:ROOT_WORKTREE_PATH</code> for the main directory path.</p>
<blockquote>
<p>Tip: avoid symlinking deps into the worktree—it can clash with the main worktree; use <code>npm ci</code>, <code>pnpm</code>, <code>bun</code>, <code>uv</code>, etc. to install fresh.</p>
</blockquote>
<h2 id="worktree-cleanup-and-limits">Worktree cleanup and limits</h2>
<p>Cursor manages worktree count so disk doesn’t blow up:</p>
<ul>
<li>Each workspace has a <strong>max number of worktrees</strong> (e.g. 20)</li>
<li>When over the limit, the <strong>least recently used</strong> are removed</li>
<li>Cleanup is <strong>per workspace</strong>; different repos don’t affect each other</li>
</ul>
<p>To tune (if your Cursor version supports it), look for settings like:</p>
<ul>
<li><code>cursor.worktreeMaxCount</code>: max worktrees to keep</li>
<li><code>cursor.worktreeCleanupIntervalHours</code>: how often to run cleanup</li>
</ul>
<p>Exact key names depend on Cursor’s current settings.</p>
<h2 id="debugging-worktree-setup">Debugging worktree setup</h2>
<p>If after creating a worktree deps aren’t installed or migrations didn’t run, open Cursor’s <strong>Output</strong> panel, choose <strong>“Worktrees Setup”</strong> in the dropdown, and check the commands and errors run at creation time—helps debug <code>worktrees.json</code> or script issues.</p>
<h2 id="summary">Summary</h2>
<ul>
<li><strong>Best-of-N</strong>: Same prompt, multiple models in parallel in separate worktrees; compare and Apply one card; good for benchmarking, hard tasks, and quality</li>
<li><strong>worktrees.json</strong>: In <code>.cursor/worktrees.json</code> use <code>setup-worktree</code> / <code>setup-worktree-windows</code> / <code>setup-worktree-unix</code> to run commands or scripts after creation</li>
<li>Use <code>$ROOT_WORKTREE_PATH</code> (Unix) or <code>%ROOT_WORKTREE_PATH%</code> / <code>$env:ROOT_WORKTREE_PATH</code> (Windows) to copy <code>.env</code> etc. from main</li>
<li>Worktrees have a limit and auto-cleanup; debug via Output → Worktrees Setup</li>
</ul>

This one goes further on two things: <strong>Best-of-N</strong> (same prompt, multiple models in parallel, then pick one to Apply) and <strong>worktrees.json</strong> (auto install deps, run migrations, copy <code>.env</code> when a worktree is created).</p>
<h2 id="best-of-n-one-prompt-multiple-models-at-once">Best-of-N: One prompt, multiple models at once</h2>
<p><strong>Best-of-N</strong> means: you send one task, Cursor runs <strong>multiple models</strong> in separate worktrees, and you get multiple “cards,” each with one model’s changes—<strong>choose one and hit Apply</strong>.</p>
<h3 id="when-to-use-best-of-n">When to use Best-of-N?</h3>
<table>
<thead>
<tr>
<th>Situation</th>
<th>Why it helps</th>
</tr>
</thead>
<tbody>
<tr>
<td>Not sure which model fits your codebase best</td>
<td>Run once, compare outputs, small benchmark</td>
</tr>
<tr>
<td>Hard problem, worried one model misses edge cases</td>
<td>Different models, different approaches, more coverage</td>
</tr>
<tr>
<td>Compare code quality</td>
<td>Same request, different style and structure side by side</td>
</tr>
<tr>
<td>Task is hard, want higher “first try” success</td>
<td>Multiple models each try once, Apply the best</td>
</tr>
</tbody>
</table>
<p>In short: <strong>multiple models do the same task, you pick one</strong>—especially for hard tasks or when you care about quality.</p>
<h3 id="how-to-use-it">How to use it</h3>
<p>In Cursor, when starting an Agent, choose “multiple models” or the Best-of-N option (per current UI). After sending the prompt you’ll see multiple cards; switch between them to compare, then <strong>Apply</strong> the one you want onto main.</p>
<p>If you Apply more than one card from the same Best-of-N run (e.g. Apply A then B), Cursor may ask: <strong>merge with conflict resolution</strong>, or <strong>Full Overwrite</strong> (replace whole file).</p>
<h2 id="worktreesjson-prepare-the-environment-when-a-worktree-is-created">worktrees.json: Prepare the environment when a worktree is created</h2>
<p>When Cursor creates a worktree, it copies <strong>tracked files</strong> from the main directory by default, but doesn’t install deps, copy <code>.env</code>, or run DB migrations.<br>
With <strong><code>.cursor/worktrees.json</code></strong> you can specify <strong>commands to run after each new worktree is created</strong>, e.g. <code>npm ci</code>, <code>cp .env</code>, <code>npm run db:migrate</code>.</p>
<h3 id="where-does-the-config-live">Where does the config live?</h3>
<p>Cursor looks in order:</p>
<ol>
<li>Project root: <code>.cursor/worktrees.json</code></li>
<li>Worktree path</li>
</ol>
<p>Usually put it at <strong>project root</strong>: <code>.cursor/worktrees.json</code>.</p>
<h3 id="three-config-keys">Three config keys</h3>
<table>
<thead>
<tr>
<th>Key</th>
<th>Description</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>setup-worktree</code></td>
<td>Generic; used on all OSes if no OS-specific key is set</td>
</tr>
<tr>
<td><code>setup-worktree-windows</code></td>
<td>Windows only; overrides <code>setup-worktree</code></td>
</tr>
<tr>
<td><code>setup-worktree-unix</code></td>
<td>macOS / Linux only; overrides <code>setup-worktree</code></td>
</tr>
</tbody>
</table>
<p>Each key can be:</p>
<ul>
<li><strong>String</strong>: path to a script (relative to the directory containing <code>.cursor/worktrees.json</code>)</li>
<li><strong>Array</strong>: list of shell commands, run in order</li>
</ul>

<h3 id="more-complex-use-script-files">More complex: use script files</h3>
<p>For many commands or logic, use a script and reference it in <code>worktrees.json</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="json" data-theme="github-dark"><code data-language="json" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#E1E4E8">{</span></span>
<span data-line=""><span style="color:#79B8FF">  "setup-worktree-unix"</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">"setup-worktree-unix.sh"</span><span style="color:#E1E4E8">,</span></span>
<span data-line=""><span style="color:#79B8FF">  "setup-worktree-windows"</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">"setup-worktree-windows.ps1"</span><span style="color:#E1E4E8">,</span></span>
<span data-line=""><span style="color:#79B8FF">  "setup-worktree"</span><span style="color:#E1E4E8">: [</span><span style="color:#9ECBFF">"echo 'Using generic fallback'"</span><span style="color:#E1E4E8">]</span></span>
<span data-line=""><span style="color:#E1E4E8">}</span></span></code></pre></figure>
<p>Put scripts under <code>.cursor/</code>, e.g. <code>.cursor/setup-worktree-unix.sh</code>, with <code>npm ci</code>, copy <code>.env</code>, <code>chmod</code>, migrations, etc.<br>
On Windows use <code>.ps1</code> and in the script use <code>$env:ROOT_WORKTREE_PATH</code> for the main directory path.</p>
<blockquote>
<p>Tip: avoid symlinking deps into the worktree—it can clash with the main worktree; use <code>npm ci</code>, <code>pnpm</code>, <code>bun</code>, <code>uv</code>, etc. to install fresh.</p>
</blockquote>
<h2 id="worktree-cleanup-and-limits">Worktree cleanup and limits</h2>
<p>Cursor manages worktree count so disk doesn’t blow up:</p>
<ul>
<li>Each workspace has a <strong>max number of worktrees</strong> (e.g. 20)</li>
<li>When over the limit, the <strong>least recently used</strong> are removed</li>
<li>Cleanup is <strong>per workspace</strong>; different repos don’t affect each other</li>
</ul>
<p>To tune (if your Cursor version supports it), look for settings like:</p>
<ul>
<li><code>cursor.worktreeMaxCount</code>: max worktrees to keep</li>
<li><code>cursor.worktreeCleanupIntervalHours</code>: how often to run cleanup</li>
</ul>
<p>Exact key names depend on Cursor’s current settings.</p>
<h2 id="debugging-worktree-setup">Debugging worktree setup</h2>
<p>If after creating a worktree deps aren’t installed or migrations didn’t run, open Cursor’s <strong>Output</strong> panel, choose <strong>“Worktrees Setup”</strong> in the dropdown, and check the commands and errors run at creation time—helps debug <code>worktrees.json</code> or script issues.</p>
<h2 id="summary">Summary</h2>
<ul>
<li><strong>Best-of-N</strong>: Same prompt, multiple models in parallel in separate worktrees; compare and Apply one card; good for benchmarking, hard tasks, and quality</li>
<li><strong>worktrees.json</strong>: In <code>.cursor/worktrees.json</code> use <code>setup-worktree</code> / <code>setup-worktree-windows</code> / <code>setup-worktree-unix</code> to run commands or scripts after creation</li>
<li>Use <code>$ROOT_WORKTREE_PATH</code> (Unix) or <code>%ROOT_WORKTREE_PATH%</code> / <code>$env:ROOT_WORKTREE_PATH</code> (Windows) to copy <code>.env</code> etc. from main</li>
<li>Worktrees have a limit and auto-cleanup; debug via Output → Worktrees Setup</li>
</ul>
