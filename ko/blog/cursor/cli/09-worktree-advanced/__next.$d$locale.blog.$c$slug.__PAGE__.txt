3:T2b23,<p>이전 글 <a href="08-worktree-merge">08-worktree-merge</a>에서는 Cursor의 자동 worktree와 Apply를 다뤘다. 이번에는 <strong>Best-of-N</strong>(같은 프롬프트를 여러 모델로 병렬 실행한 뒤 하나를 골라 Apply)과 <strong>worktrees.json</strong>(worktree 생성 시 deps 설치·마이그레이션 실행·<code>.env</code> 복사) 두 가지를 다룬다.</p>
<h2 id="best-of-n-한-프롬프트-여러-모델-동시에">Best-of-N: 한 프롬프트, 여러 모델 동시에</h2>
<p><strong>Best-of-N</strong>이란: 작업 하나를 보내면 Cursor가 <strong>여러 모델</strong>을 각각 다른 worktree에서 실행하고, 모델별 변경이 “카드”로 여러 개 나옴 — <strong>하나를 골라 Apply</strong>하는 방식.</p>
<h3 id="언제-쓰나">언제 쓰나</h3>
<table>
<thead>
<tr>
<th>상황</th>
<th>이점</th>
</tr>
</thead>
<tbody>
<tr>
<td>어떤 모델이 코드베이스에 맞는지 모르겠음</td>
<td>한 번 돌려서 출력 비교, 간단 벤치마크</td>
</tr>
<tr>
<td>난제라 한 모델이 엣지 케이스를 놓칠까 봄</td>
<td>모델이 다르면 접근도 달라서 커버리지 확대</td>
</tr>
<tr>
<td>코드 품질 비교</td>
<td>같은 요청으로 스타일·구조를 나란히 비교</td>
</tr>
<tr>
<td>난이도 높아 “한 방” 성공률을 올리고 싶음</td>
<td>여러 모델이 각각 한 번씩 시도하고, 최선을 Apply</td>
</tr>
</tbody>

<p>요약: <strong>여러 모델이 같은 작업을 하고, 그중 하나를 고른다</strong> — 난이도 높은 작업이나 품질을 중시할 때 유리.</p>
<h3 id="사용법">사용법</h3>
<p>Cursor에서 Agent를 시작할 때 “여러 모델” 또는 Best-of-N 옵션(현재 UI에 따름)을 선택한다. 프롬프트를 보낸 뒤 카드가 여러 개 나오면 전환해서 비교한 다음, main에 <strong>Apply</strong>할 한 장을 고른다.</p>
<p>같은 Best-of-N 실행에서 두 장 이상 Apply하면(예: A Apply 후 B), Cursor가 <strong>머지(충돌 해결)</strong> 또는 <strong>Full Overwrite</strong>(파일 전체 교체)를 물을 수 있다.</p>
<h2 id="worktreesjson-worktree-생성-시-환경-준비">worktrees.json: worktree 생성 시 환경 준비</h2>
<p>Cursor가 worktree를 만들 때 기본적으로 <strong>추적된 파일</strong>만 메인 디렉터리에서 복사하고, deps 설치·<code>.env</code> 복사·DB 마이그레이션은 하지 않는다.<br>
**<code>.cursor/worktrees.json</code>**으로 <strong>새 worktree 생성 후 실행할 명령</strong>을 지정할 수 있다(예: <code>npm ci</code>, <code>cp .env</code>, <code>npm run db:migrate</code>).</p>
<h3 id="설정-위치">설정 위치</h3>
<p>Cursor는 다음 순서로 찾는다:</p>
<ol>
<li>프로젝트 루트: <code>.cursor/worktrees.json</code></li>
<li>worktree 경로</li>
</ol>
<p>보통 <strong>프로젝트 루트</strong>에 둔다: <code>.cursor/worktrees.json</code>.</p>
<h3 id="설정-키-3개">설정 키 3개</h3>
<table>
<thead>
<tr>
<th>키</th>
<th>설명</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>setup-worktree</code></td>
<td>공통；OS별 키가 없으면 모든 OS에서 사용</td>
</tr>
<tr>
<td><code>setup-worktree-windows</code></td>
<td>Windows 전용；<code>setup-worktree</code> 덮어씀</td>
</tr>
<tr>
<td><code>setup-worktree-unix</code></td>
<td>macOS / Linux 전용；<code>setup-worktree</code> 덮어씀</td>
</tr>
</tbody>
</table>
<p>각 키는 다음 중 하나:</p>
<ul>
<li><strong>문자열</strong>: 스크립트 경로(<code>.cursor/worktrees.json</code>이 있는 디렉터리 기준 상대)</li>
<li><strong>배열</strong>: 셸 명령 목록. 순서대로 실행</li>
</ul>

<p>명령이나 로직이 많으면 스크립트를 만들고 <code>worktrees.json</code>에서 참조한다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="json" data-theme="github-dark"><code data-language="json" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#E1E4E8">{</span></span>

<span data-line=""><span style="color:#79B8FF">  "setup-worktree"</span><span style="color:#E1E4E8">: [</span><span style="color:#9ECBFF">"echo 'Using generic fallback'"</span><span style="color:#E1E4E8">]</span></span>
<span data-line=""><span style="color:#E1E4E8">}</span></span></code></pre></figure>
<p>스크립트는 <code>.cursor/</code> 아래에 둔다(예: <code>.cursor/setup-worktree-unix.sh</code>). 내용은 <code>npm ci</code>, <code>.env</code> 복사, <code>chmod</code>, 마이그레이션 등.<br>
Windows에서는 <code>.ps1</code>을 쓰고, 스크립트 안에서 메인 디렉터리 경로는 <code>$env:ROOT_WORKTREE_PATH</code>를 쓴다.</p>
<blockquote>
<p>팁: worktree에 deps를 심링크로 넣는 건 피하기 — 메인 worktree와 충돌할 수 있음. <code>npm ci</code>, <code>pnpm</code>, <code>bun</code>, <code>uv</code> 등으로 새로 설치.</p>
</blockquote>
<h2 id="worktree-정리와-한도">worktree 정리와 한도</h2>
<p>Cursor는 worktree 개수를 관리해 디스크가 부풀지 않게 한다:</p>
<ul>
<li>워크스페이스마다 <strong>최대 worktree 수</strong>(예: 20)가 있음</li>
<li>한도를 넘으면 <strong>가장 최근에 쓰지 않은</strong> 것부터 제거됨</li>
<li>정리는 <strong>워크스페이스 단위</strong>；다른 리포지토리끼리는 영향 없음</li>
</ul>
<p>조정하려면(Cursor 버전이 지원하면) 다음 같은 설정을 찾는다:</p>
<ul>
<li><code>cursor.worktreeMaxCount</code>: 유지할 worktree 최대 개수</li>
<li><code>cursor.worktreeCleanupIntervalHours</code>: 정리 실행 간격</li>
</ul>
<p>정확한 키 이름은 Cursor 현재 설정에 따름.</p>
<h2 id="worktree-셋업-디버깅">worktree 셋업 디버깅</h2>
<p>worktree 생성 후 deps가 안 깔렸거나 마이그레이션이 안 돌아가면, Cursor <strong>Output</strong> 패널을 열고 드롭다운에서 **「Worktrees Setup」**을 선택한다. 생성 시 실행된 명령과 에러를 볼 수 있어 <code>worktrees.json</code>이나 스크립트 문제 디버깅에 쓴다.</p>
<h2 id="요약">요약</h2>
<ul>
<li><strong>Best-of-N</strong>: 같은 프롬프트를 여러 모델로 병렬 실행하고, 카드 한 장을 골라 Apply. 벤치마크·난제·품질 중시에 유리</li>
<li><strong>worktrees.json</strong>: <code>.cursor/worktrees.json</code>에서 <code>setup-worktree</code> / <code>setup-worktree-windows</code> / <code>setup-worktree-unix</code>로 생성 후 명령·스크립트 실행</li>
<li>main에서 <code>.env</code> 등을 복사할 때는 <code>$ROOT_WORKTREE_PATH</code>(Unix) 또는 <code>%ROOT_WORKTREE_PATH%</code> / <code>$env:ROOT_WORKTREE_PATH</code>(Windows) 사용</li>
<li>worktree에는 한도와 자동 정리가 있음；디버깅은 Output → Worktrees Setup</li>
</ul>

9:T2b23,<p>이전 글 <a href="08-worktree-merge">08-worktree-merge</a>에서는 Cursor의 자동 worktree와 Apply를 다뤘다. 이번에는 <strong>Best-of-N</strong>(같은 프롬프트를 여러 모델로 병렬 실행한 뒤 하나를 골라 Apply)과 <strong>worktrees.json</strong>(worktree 생성 시 deps 설치·마이그레이션 실행·<code>.env</code> 복사) 두 가지를 다룬다.</p>
<h2 id="best-of-n-한-프롬프트-여러-모델-동시에">Best-of-N: 한 프롬프트, 여러 모델 동시에</h2>
<p><strong>Best-of-N</strong>이란: 작업 하나를 보내면 Cursor가 <strong>여러 모델</strong>을 각각 다른 worktree에서 실행하고, 모델별 변경이 “카드”로 여러 개 나옴 — <strong>하나를 골라 Apply</strong>하는 방식.</p>
<h3 id="언제-쓰나">언제 쓰나</h3>
<table>
<thead>
<tr>
<th>상황</th>
<th>이점</th>
</tr>
</thead>
<tbody>
<tr>
<td>어떤 모델이 코드베이스에 맞는지 모르겠음</td>
<td>한 번 돌려서 출력 비교, 간단 벤치마크</td>
</tr>
<tr>
<td>난제라 한 모델이 엣지 케이스를 놓칠까 봄</td>
<td>모델이 다르면 접근도 달라서 커버리지 확대</td>
</tr>
<tr>
<td>코드 품질 비교</td>
<td>같은 요청으로 스타일·구조를 나란히 비교</td>
</tr>
<tr>
<td>난이도 높아 “한 방” 성공률을 올리고 싶음</td>

</tr>

<p>요약: <strong>여러 모델이 같은 작업을 하고, 그중 하나를 고른다</strong> — 난이도 높은 작업이나 품질을 중시할 때 유리.</p>
<h3 id="사용법">사용법</h3>
<p>Cursor에서 Agent를 시작할 때 “여러 모델” 또는 Best-of-N 옵션(현재 UI에 따름)을 선택한다. 프롬프트를 보낸 뒤 카드가 여러 개 나오면 전환해서 비교한 다음, main에 <strong>Apply</strong>할 한 장을 고른다.</p>
<p>같은 Best-of-N 실행에서 두 장 이상 Apply하면(예: A Apply 후 B), Cursor가 <strong>머지(충돌 해결)</strong> 또는 <strong>Full Overwrite</strong>(파일 전체 교체)를 물을 수 있다.</p>
<h2 id="worktreesjson-worktree-생성-시-환경-준비">worktrees.json: worktree 생성 시 환경 준비</h2>
<p>Cursor가 worktree를 만들 때 기본적으로 <strong>추적된 파일</strong>만 메인 디렉터리에서 복사하고, deps 설치·<code>.env</code> 복사·DB 마이그레이션은 하지 않는다.<br>
**<code>.cursor/worktrees.json</code>**으로 <strong>새 worktree 생성 후 실행할 명령</strong>을 지정할 수 있다(예: <code>npm ci</code>, <code>cp .env</code>, <code>npm run db:migrate</code>).</p>
<h3 id="설정-위치">설정 위치</h3>
<p>Cursor는 다음 순서로 찾는다:</p>
<ol>
<li>프로젝트 루트: <code>.cursor/worktrees.json</code></li>
<li>worktree 경로</li>
</ol>
<p>보통 <strong>프로젝트 루트</strong>에 둔다: <code>.cursor/worktrees.json</code>.</p>

<h2 id="worktree-정리와-한도">worktree 정리와 한도</h2>
<p>Cursor는 worktree 개수를 관리해 디스크가 부풀지 않게 한다:</p>
<ul>
<li>워크스페이스마다 <strong>최대 worktree 수</strong>(예: 20)가 있음</li>
<li>한도를 넘으면 <strong>가장 최근에 쓰지 않은</strong> 것부터 제거됨</li>
<li>정리는 <strong>워크스페이스 단위</strong>；다른 리포지토리끼리는 영향 없음</li>
</ul>
<p>조정하려면(Cursor 버전이 지원하면) 다음 같은 설정을 찾는다:</p>
<ul>
<li><code>cursor.worktreeMaxCount</code>: 유지할 worktree 최대 개수</li>
<li><code>cursor.worktreeCleanupIntervalHours</code>: 정리 실행 간격</li>
</ul>
<p>정확한 키 이름은 Cursor 현재 설정에 따름.</p>
<h2 id="worktree-셋업-디버깅">worktree 셋업 디버깅</h2>
<p>worktree 생성 후 deps가 안 깔렸거나 마이그레이션이 안 돌아가면, Cursor <strong>Output</strong> 패널을 열고 드롭다운에서 **「Worktrees Setup」**을 선택한다. 생성 시 실행된 명령과 에러를 볼 수 있어 <code>worktrees.json</code>이나 스크립트 문제 디버깅에 쓴다.</p>
<h2 id="요약">요약</h2>
<ul>
<li><strong>Best-of-N</strong>: 같은 프롬프트를 여러 모델로 병렬 실행하고, 카드 한 장을 골라 Apply. 벤치마크·난제·품질 중시에 유리</li>
<li><strong>worktrees.json</strong>: <code>.cursor/worktrees.json</code>에서 <code>setup-worktree</code> / <code>setup-worktree-windows</code> / <code>setup-worktree-unix</code>로 생성 후 명령·스크립트 실행</li>
<li>main에서 <code>.env</code> 등을 복사할 때는 <code>$ROOT_WORKTREE_PATH</code>(Unix) 또는 <code>%ROOT_WORKTREE_PATH%</code> / <code>$env:ROOT_WORKTREE_PATH</code>(Windows) 사용</li>
<li>worktree에는 한도와 자동 정리가 있음；디버깅은 Output → Worktrees Setup</li>
</ul>
