1c:T29ed,<p>"돌아간다"와 "시스템이 실제로 안정적이다"는 완전히 다른 우주입니다. ingress 계층 사고의 대부분은 Envoy Gateway가 부족해서가 아니라, 설정을 너무 가볍게 잡아 운영이 끝없는 놀라움 상자로 바뀌기 때문에 생깁니다. 이 글에서는 가장 실용적인 권장사항을 체크리스트 형태로 정리합니다.</p>
<h2 id="권장-사항">권장 사항</h2>
<h3 id="1-gateway-소유자와-route-소유자를-명확히-나누기">1. Gateway 소유자와 Route 소유자를 명확히 나누기</h3>
<p>여러 사람이 관여한다면 책임을 분리하세요:</p>
<ul>
<li>플랫폼 팀이 <code>GatewayClass</code>, <code>Gateway</code>를 관리</li>
<li>앱 팀은 각자의 <code>HTTPRoute</code>를 관리</li>
</ul>
<p>이점은 명확합니다. ingress 계층의 보안과 노출 범위를 모든 앱이 제멋대로 바꾸지 못하게 하면서도, 앱 팀은 라우팅 유연성을 유지할 수 있습니다. 이것이 Gateway API 설계를 쓸 가치가 있는 이유입니다. 다시 거대한 단일 YAML 덩어리로 납작하게 만들지 마세요.</p>
<h3 id="2-처음부터-tls를-기본값으로-취급하기">2. 처음부터 TLS를 기본값으로 취급하기</h3>
<p>"일단 HTTP로 시작하고 HTTPS는 나중에 붙이자"라고 생각하지 마세요.
그 "나중"은 거의 항상 금요일 밤 긴급 작업으로 돌아옵니다.</p>
<p>최소한 다음은 갖추세요:</p>
<ul>
<li>외부 listener는 기본적으로 HTTPS</li>
<li>인증서 소스는 관리 절차가 명확함</li>
<li>테스트, self-signed, 운영 CA 워크플로는 분리됨</li>
</ul>
<p>이미 cert-manager가 있다면 연동하세요. 인증서 갱신 때마다 Secret을 손으로 patch하는 것보다 자동 회전이 훨씬 믿을 만합니다.</p>
<h3 id="3-route-규칙은-명시적으로-쓰기-편의성만-보고-과도하게-최적화하지-말기">3. Route 규칙은 명시적으로 쓰기, 편의성만 보고 과도하게 최적화하지 말기</h3>
<p>이런 규칙은 편하긴 하지만 블랙홀로 변하기 쉽습니다:</p>

<p>틀린 건 아닙니다. 하지만 시스템이 커질수록 이런 "전부 받기" 규칙이 많아지면 디버깅이 고통스러워집니다.
<code>hostnames</code>를 쓸 수 있다면 쓰고, <code>path</code>를 쓸 수 있다면 분명하게 써두세요.</p>
<h3 id="4-트래픽은-조금씩-잘라-보내기-한-번에-올인하지-말기">4. 트래픽은 조금씩 잘라 보내기, 한 번에 올인하지 말기</h3>

<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>

문제가 생겼을 때 롤백도 훨씬 빠릅니다. 새벽 3시에는 이 차이가 정말 크게 느껴집니다.</p>
<h3 id="5-status와-이벤트를-확인하는-습관-들이기">5. <code>status</code>와 이벤트를 확인하는 습관 들이기</h3>
<p>YAML만 읽어서는 부족합니다. 컨트롤러가 실제로 설정을 받아들였는지 봐야 합니다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> gateway</span><span style="color:#79B8FF"> -A</span></span>

<p>이런 문제들은 <code>spec</code>만 보고는 잘 보이지 않습니다:</p>
<ul>

<li>네임스페이스 간 참조가 막힘</li>

</ul>
<p>가장 최악인 상황은 버그 자체가 아니라, "적용된 줄 알았는데 애초에 받아들여지지도 않은 경우"입니다.</p>
<h2 id="흔한-함정">흔한 함정</h2>
<h3 id="함정-1-envoy-gateway를-멍청한-포워딩-블랙박스로-취급하기">함정 1: Envoy Gateway를 멍청한 포워딩 블랙박스로 취급하기</h3>
<p>이건 단순히 패킷을 A에서 B로 옮기는 도구가 아닙니다.
공식 문서도 이를 Kubernetes 네이티브 API Gateway로 위치시키며, 여기에 더 많은 트래픽 정책과 보안 정책을 쌓을 수 있다고 설명합니다. 단지 Ingress 대체재로만 쓰면 잠재력을 지나치게 덜 쓰는 셈입니다.</p>
<h3 id="함정-2-referencegrant-없이-네임스페이스-간-인증서를-참조하기">함정 2: <code>ReferenceGrant</code> 없이 네임스페이스 간 인증서를 참조하기</h3>
<p>많은 사람이 <code>certificateRefs</code>가 namespace 필드를 지원하는 걸 보고 곧바로 다른 네임스페이스를 가리킨 뒤, 왜 아무 일도 일어나지 않는지 궁금해합니다.
대개 귀신이 장난치는 게 아니라 <code>ReferenceGrant</code>가 빠진 것입니다.</p>
<h3 id="함정-3-해피-패스만-테스트하기">함정 3: 해피 패스만 테스트하기</h3>
<p>이것만 테스트하지 마세요:</p>
<ul>
<li><code>curl http://...</code> 한 번 성공</li>
</ul>
<p>이것도 함께 테스트하세요:</p>
<ul>
<li>서로 다른 hostname</li>
<li>서로 다른 path</li>
<li>TLS 인증서 유효성</li>
<li>트래픽 분할 비율이 기대대로 동작하는지</li>
</ul>
<p>ingress 계층은 해피 패스는 멀쩡해 보여도 엣지 케이스가 바로 깨질 때 가장 위험합니다.</p>
<h3 id="함정-4-데모-설정을-운영에-그대로-가져가기">함정 4: 데모 설정을 운영에 그대로 가져가기</h3>
<p>공식 quickstart는 학습용으로 아주 훌륭하지만, 어디까지나 quickstart입니다.
운영 환경에서는 최소한 다음을 추가해야 합니다:</p>
<ul>
<li>인증서 자동화</li>
<li>모니터링과 알림</li>
<li>변경 관리 프로세스</li>
<li>Route 네이밍 규칙</li>
</ul>
<p>그렇지 않으면 오늘의 quickstart가 내일의 quick-fall이 됩니다.</p>
<h2 id="최소한의-배포-전-체크리스트">최소한의 배포 전 체크리스트</h2>
<p>라이브 전에는 이것을 확인하세요:</p>
<ul>
<li><code>Gateway</code> listener가 HTTP / HTTPS를 명확히 분리하는가?</li>
<li>인증서 Secret과 회전 절차가 분명한가?</li>
<li><code>HTTPRoute</code>에 명확한 <code>hostnames</code> / <code>matches</code>가 있는가?</li>
<li>중요한 변경은 작은 트래픽 컷으로 배포되는가?</li>
<li><code>status</code>와 이벤트만으로 문제를 빠르게 찾을 수 있는가?</li>
</ul>
<p>이 다섯 가지가 갖춰져 있다면, 이미 "일단 되니까 괜찮다" 수준보다 훨씬 높은 곳에서 운영하고 있는 겁니다.</p>

28:T29ed,<p>"돌아간다"와 "시스템이 실제로 안정적이다"는 완전히 다른 우주입니다. ingress 계층 사고의 대부분은 Envoy Gateway가 부족해서가 아니라, 설정을 너무 가볍게 잡아 운영이 끝없는 놀라움 상자로 바뀌기 때문에 생깁니다. 이 글에서는 가장 실용적인 권장사항을 체크리스트 형태로 정리합니다.</p>
<h2 id="권장-사항">권장 사항</h2>
<h3 id="1-gateway-소유자와-route-소유자를-명확히-나누기">1. Gateway 소유자와 Route 소유자를 명확히 나누기</h3>
<p>여러 사람이 관여한다면 책임을 분리하세요:</p>
<ul>
<li>플랫폼 팀이 <code>GatewayClass</code>, <code>Gateway</code>를 관리</li>
<li>앱 팀은 각자의 <code>HTTPRoute</code>를 관리</li>
</ul>
<p>이점은 명확합니다. ingress 계층의 보안과 노출 범위를 모든 앱이 제멋대로 바꾸지 못하게 하면서도, 앱 팀은 라우팅 유연성을 유지할 수 있습니다. 이것이 Gateway API 설계를 쓸 가치가 있는 이유입니다. 다시 거대한 단일 YAML 덩어리로 납작하게 만들지 마세요.</p>
<h3 id="2-처음부터-tls를-기본값으로-취급하기">2. 처음부터 TLS를 기본값으로 취급하기</h3>
<p>"일단 HTTP로 시작하고 HTTPS는 나중에 붙이자"라고 생각하지 마세요.
그 "나중"은 거의 항상 금요일 밤 긴급 작업으로 돌아옵니다.</p>
<p>최소한 다음은 갖추세요:</p>
<ul>
<li>외부 listener는 기본적으로 HTTPS</li>
<li>인증서 소스는 관리 절차가 명확함</li>
<li>테스트, self-signed, 운영 CA 워크플로는 분리됨</li>
</ul>
<p>이미 cert-manager가 있다면 연동하세요. 인증서 갱신 때마다 Secret을 손으로 patch하는 것보다 자동 회전이 훨씬 믿을 만합니다.</p>
<h3 id="3-route-규칙은-명시적으로-쓰기-편의성만-보고-과도하게-최적화하지-말기">3. Route 규칙은 명시적으로 쓰기, 편의성만 보고 과도하게 최적화하지 말기</h3>
<p>이런 규칙은 편하긴 하지만 블랙홀로 변하기 쉽습니다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">rules</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">      - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">backend</span></span>
<span data-line=""><span style="color:#85E89D">        port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">8080</span></span></code></pre></figure>
<p>틀린 건 아닙니다. 하지만 시스템이 커질수록 이런 "전부 받기" 규칙이 많아지면 디버깅이 고통스러워집니다.
<code>hostnames</code>를 쓸 수 있다면 쓰고, <code>path</code>를 쓸 수 있다면 분명하게 써두세요.</p>
<h3 id="4-트래픽은-조금씩-잘라-보내기-한-번에-올인하지-말기">4. 트래픽은 조금씩 잘라 보내기, 한 번에 올인하지 말기</h3>

<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">api-v1</span></span>

<span data-line=""><span style="color:#85E89D">    weight</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">90</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">api-v2</span></span>

<p>이 방식은 "서비스 selector를 한 번에 통째로 뒤집는 것"보다 훨씬 부드럽습니다.
문제가 생겼을 때 롤백도 훨씬 빠릅니다. 새벽 3시에는 이 차이가 정말 크게 느껴집니다.</p>
<h3 id="5-status와-이벤트를-확인하는-습관-들이기">5. <code>status</code>와 이벤트를 확인하는 습관 들이기</h3>
<p>YAML만 읽어서는 부족합니다. 컨트롤러가 실제로 설정을 받아들였는지 봐야 합니다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="bash" data-theme="github-dark"><code data-language="bash" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#B392F0">kubectl</span><span style="color:#9ECBFF"> get</span><span style="color:#9ECBFF"> gateway</span><span style="color:#79B8FF"> -A</span></span>

<p>이런 문제들은 <code>spec</code>만 보고는 잘 보이지 않습니다:</p>
<ul>
<li>Route가 accepted 되지 않음</li>
<li>네임스페이스 간 참조가 막힘</li>
<li>Listener 상태 이상</li>
</ul>
<p>가장 최악인 상황은 버그 자체가 아니라, "적용된 줄 알았는데 애초에 받아들여지지도 않은 경우"입니다.</p>
<h2 id="흔한-함정">흔한 함정</h2>
<h3 id="함정-1-envoy-gateway를-멍청한-포워딩-블랙박스로-취급하기">함정 1: Envoy Gateway를 멍청한 포워딩 블랙박스로 취급하기</h3>
<p>이건 단순히 패킷을 A에서 B로 옮기는 도구가 아닙니다.
공식 문서도 이를 Kubernetes 네이티브 API Gateway로 위치시키며, 여기에 더 많은 트래픽 정책과 보안 정책을 쌓을 수 있다고 설명합니다. 단지 Ingress 대체재로만 쓰면 잠재력을 지나치게 덜 쓰는 셈입니다.</p>
<h3 id="함정-2-referencegrant-없이-네임스페이스-간-인증서를-참조하기">함정 2: <code>ReferenceGrant</code> 없이 네임스페이스 간 인증서를 참조하기</h3>
<p>많은 사람이 <code>certificateRefs</code>가 namespace 필드를 지원하는 걸 보고 곧바로 다른 네임스페이스를 가리킨 뒤, 왜 아무 일도 일어나지 않는지 궁금해합니다.
대개 귀신이 장난치는 게 아니라 <code>ReferenceGrant</code>가 빠진 것입니다.</p>
<h3 id="함정-3-해피-패스만-테스트하기">함정 3: 해피 패스만 테스트하기</h3>
