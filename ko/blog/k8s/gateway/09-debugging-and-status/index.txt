<p><code>status</code>를 시험 성적표라고 생각하세요:</p>

<p>제출한 답안만 보고, 채점 결과를 안 보는 건 디버깅이 아니라 감정적 위안입니다.</p>
<h2 id="가장-중요한-세-가지-condition-이것만-익혀도-대부분-해결된다">가장 중요한 세 가지 Condition: 이것만 익혀도 대부분 해결된다</h2>
<h3 id="accepted"><code>Accepted</code></h3>
<p>보통 이 condition은 리소스가 상위 주체에 의해 받아들여졌는지를 나타냅니다.
route라면 일반적으로 다음을 뜻합니다:</p>
<ul>
<li>의도한 Gateway/listener에 성공적으로 attach 되었는가</li>
<li>규칙에 명백한 충돌이나 invalid 설정이 없는가</li>
</ul>
<p><code>Accepted</code>가 <code>False</code>라면 우선 의심할 것:</p>
<ul>
<li><code>parentRefs</code>가 잘못된 Gateway나 listener를 가리킴</li>
<li>hostname/listener 조건이 맞지 않음</li>
<li>listener가 이 route 타입을 거부함</li>
<li><code>allowedRoutes</code>에 막힘</li>
</ul>
<h3 id="resolvedrefs"><code>ResolvedRefs</code></h3>
<p>이 condition은 리소스 내부에서 참조한 객체들이 성공적으로 resolve 되었는지를 뜻합니다.
예를 들면:</p>
<ul>
<li><code>backendRefs</code>에서 참조한 <code>Service</code>가 존재하는가</li>
<li><code>certificateRefs</code>의 <code>Secret</code>을 합법적으로 참조할 수 있는가</li>
<li>네임스페이스 간 참조를 위한 <code>ReferenceGrant</code>가 올바르게 구성되었는가</li>
</ul>
<p>이 condition은 매우 유용합니다.
많은 설정 실패는 라우팅 로직이 틀려서가 아니라, 참조 대상이 아예 없거나 접근 권한이 없어서 생기기 때문입니다.</p>
<h3 id="programmed"><code>Programmed</code></h3>
<p>이 condition은 설정이 구현 계층에 실제로 반영되었는지를 보통 나타냅니다.
이렇게 생각하면 됩니다:</p>
<ul>
<li>컨트롤러가 설정을 수용했고</li>
<li>그 설정을 데이터 플레인이나 인프라에 밀어 넣었다</li>
</ul>
<p><code>Accepted</code>는 이미 <code>True</code>인데도 트래픽이 흐르지 않는다면, 이제 <code>Programmed</code>, Gateway 주소, listener 상태, 하부 Envoy 리소스를 확인해 볼 가치가 있습니다.</p>
<blockquote>
<p>💡 리소스마다 노출하는 condition 집합은 조금씩 다를 수 있지만, 직관을 키우기 위해 가장 먼저 익혀야 할 1차 그룹은 <code>Accepted</code>, <code>ResolvedRefs</code>, <code>Programmed</code>입니다.</p>
</blockquote>
<h2 id="가장-짧은-디버깅-흐름-보통-이-순서가-잘-먹힌다">가장 짧은 디버깅 흐름: 보통 이 순서가 잘 먹힌다</h2>
<h3 id="1단계-gateway가-실제로-떠-있는지-확인">1단계: Gateway가 실제로 떠 있는지 확인</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#79C0FF"> -A</span></span>

<li><code>Accepted</code></li>
<li><code>ResolvedRefs</code></li>
<li><code>observedGeneration</code></li>
</ul>
<p><code>observedGeneration</code>은 꽤 볼 가치가 있습니다.
이 값이 <code>metadata.generation</code>을 따라잡지 못했다면, 컨트롤러가 아직 최신 설정 버전을 처리하지 않았을 수 있습니다.</p>
<h3 id="3단계-참조한-리소스가-실제로-존재하는지-확인">3단계: 참조한 리소스가 실제로 존재하는지 확인</h3>
<p>이 단계는 다른 어떤 단계보다 자주 건너뛰어집니다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> svc</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> secret</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> referencegrant</span><span style="color:#79C0FF"> -A</span></span></code></pre></figure>
<p>흔한 문제:</p>
<ul>
<li>백엔드 서비스 이름이 틀림</li>
<li>포트가 틀림</li>
<li>Secret이 생각한 네임스페이스에 없음</li>
<li>네임스페이스 간 참조에 <code>ReferenceGrant</code>가 없음</li>
</ul>
<p><code>ResolvedRefs</code>가 <code>False</code>라면 이 경로를 따라 추적하세요.</p>
<h3 id="4단계-데이터-플레인과-컨트롤러-확인">4단계: 데이터 플레인과 컨트롤러 확인</h3>
<p>Gateway와 Route 상태가 대체로 멀쩡해 보이는데도 트래픽이 흐르지 않는다면, 더 아래를 봐야 합니다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> pods</span><span style="color:#79C0FF"> -n</span><span style="color:#A5D6FF"> envoy-gateway-system</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> logs</span><span style="color:#79C0FF"> -n</span><span style="color:#A5D6FF"> envoy-gateway-system</span><span style="color:#A5D6FF"> deployment/envoy-gateway</span></span></code></pre></figure>
<p>이 시점에는 "규칙이 받아들여졌는가"를 디버깅하는 것이 아니라, 컨트롤 플레인과 데이터 플레인이 정상 동작하는지를 보는 단계입니다.</p>
<p><code>egctl</code>이 설치돼 있다면 상태를 빠르게 보는 데 도움이 됩니다.
하지만 그것이 없어도 <code>kubectl get/describe -o yaml</code>만으로 대부분의 문제는 해결할 수 있습니다.</p>
<h2 id="가장-흔한-실패-패턴-네-가지">가장 흔한 실패 패턴 네 가지</h2>
<h3 id="1-route는-맞는데-의도한-listener에-attach되지-않았다">1. Route는 맞는데, 의도한 Listener에 Attach되지 않았다</h3>
<p>증상:</p>
<ul>
<li>YAML은 맞아 보임</li>
<li>그런데 트래픽이 규칙에 들어오지 않음</li>
</ul>
<p>확인할 것:</p>
<ul>
<li><code>parentRefs.name</code></li>
<li><code>parentRefs.sectionName</code></li>
<li>Gateway listener 이름이 정확히 일치하는지</li>
</ul>
<p>멀티 listener 환경에서는 <code>sectionName</code> 오타 하나로도 디버깅 세션 하나를 통째로 날릴 수 있습니다.</p>
<h3 id="2-accepted는-성공했는데-resolvedrefs가-실패한다">2. <code>Accepted</code>는 성공했는데 <code>ResolvedRefs</code>가 실패한다</h3>
<p>보통 이건 attach 자체는 가능한데, 참조된 무언가에 문제가 있다는 뜻입니다.
가장 흔한 원인:</p>
<ul>
<li>백엔드 Service가 존재하지 않음</li>
<li>Secret 이름이 틀림</li>
<li>네임스페이스 간 참조가 승인 없이 이뤄짐</li>
</ul>
<p>이 실패 유형이 가장 짜증 나는 이유는 거의 다 온 것처럼 보이는데, 실제로는 참조 계층에서 멈춰 있기 때문입니다.</p>
<h3 id="3-gateway에는-listener가-있는데-기대한-주소가-없다">3. Gateway에는 Listener가 있는데 기대한 주소가 없다</h3>
<p>이건 로컬 클러스터나 <code>LoadBalancer</code> 구현이 없는 환경에서 자주 보입니다.
Gateway API가 고장 난 것이 아니라, 아래 인프라가 외부 주소를 프로비저닝하지 못하는 것입니다.</p>
<p>선택지:</p>
<ul>
<li>클러스터에 <code>LoadBalancer</code> 기능이 있는지 확인</li>
<li><code>port-forward</code>로 라우팅 경로를 검증</li>
</ul>
<h3 id="4-yaml은-반영됐지만-요청이-404--503을-반환한다">4. YAML은 반영됐지만 요청이 404 / 503을 반환한다</h3>
<p>이 단계에서는 보통 한 필드만 틀린 것이 아니라, 체인 어딘가가 끊어진 경우가 많습니다:</p>
<ul>
<li>잘못된 Host header</li>
<li>어떤 규칙과도 매칭되지 않는 path</li>
<li>백엔드 Pod 비정상</li>
<li>Service selector가 어떤 Pod도 선택하지 못함</li>
</ul>
<p>Ingress 문제는 프록시 실패처럼 보여도 실제로는 백엔드가 준비되지 않은 경우가 많습니다. 모든 걸 프록시 탓으로 돌리지는 마세요. 그쪽도 이미 할 일이 많습니다.</p>
<h2 id="한-줄-요약">한 줄 요약</h2>
<p>Gateway API를 가장 효과적으로 디버깅하는 방법은 YAML을 계속 바꾸는 것이 아니라, <code>status</code>를 읽는 법을 익히는 것입니다.
<code>Accepted</code>는 주문이 접수됐는지 알려주고, <code>ResolvedRefs</code>는 참조가 해결됐는지 알려주며, <code>Programmed</code>는 설정이 실제로 반영됐는지 알려줍니다. 이 세 계층을 분리해서 보면 문제 해결 속도가 크게 올라갑니다.</p>

<p>핵심은 YAML을 백 번 더 읽는 것이 아니라, 컨트롤러가 여러분 설정을 실제로 받아들였는지 확인하는 것입니다.</p>
<p><code>status</code>를 시험 성적표라고 생각하세요:</p>
<ul>
<li><code>spec</code>은 여러분이 제출한 답안</li>
<li><code>status</code>는 시스템이 채점한 결과</li>
</ul>
<p>제출한 답안만 보고, 채점 결과를 안 보는 건 디버깅이 아니라 감정적 위안입니다.</p>
<h2 id="가장-중요한-세-가지-condition-이것만-익혀도-대부분-해결된다">가장 중요한 세 가지 Condition: 이것만 익혀도 대부분 해결된다</h2>
<h3 id="accepted"><code>Accepted</code></h3>
<p>보통 이 condition은 리소스가 상위 주체에 의해 받아들여졌는지를 나타냅니다.
route라면 일반적으로 다음을 뜻합니다:</p>
<ul>
<li>의도한 Gateway/listener에 성공적으로 attach 되었는가</li>
<li>규칙에 명백한 충돌이나 invalid 설정이 없는가</li>
</ul>
<p><code>Accepted</code>가 <code>False</code>라면 우선 의심할 것:</p>
<ul>
<li><code>parentRefs</code>가 잘못된 Gateway나 listener를 가리킴</li>
<li>hostname/listener 조건이 맞지 않음</li>
<li>listener가 이 route 타입을 거부함</li>
<li><code>allowedRoutes</code>에 막힘</li>
</ul>
<h3 id="resolvedrefs"><code>ResolvedRefs</code></h3>
<p>이 condition은 리소스 내부에서 참조한 객체들이 성공적으로 resolve 되었는지를 뜻합니다.
예를 들면:</p>
<ul>
<li><code>backendRefs</code>에서 참조한 <code>Service</code>가 존재하는가</li>
<li><code>certificateRefs</code>의 <code>Secret</code>을 합법적으로 참조할 수 있는가</li>
<li>네임스페이스 간 참조를 위한 <code>ReferenceGrant</code>가 올바르게 구성되었는가</li>
</ul>
<p>이 condition은 매우 유용합니다.
많은 설정 실패는 라우팅 로직이 틀려서가 아니라, 참조 대상이 아예 없거나 접근 권한이 없어서 생기기 때문입니다.</p>
<h3 id="programmed"><code>Programmed</code></h3>
<p>이 condition은 설정이 구현 계층에 실제로 반영되었는지를 보통 나타냅니다.
이렇게 생각하면 됩니다:</p>
<ul>
<li>컨트롤러가 설정을 수용했고</li>
<li>그 설정을 데이터 플레인이나 인프라에 밀어 넣었다</li>
</ul>
<p><code>Accepted</code>는 이미 <code>True</code>인데도 트래픽이 흐르지 않는다면, 이제 <code>Programmed</code>, Gateway 주소, listener 상태, 하부 Envoy 리소스를 확인해 볼 가치가 있습니다.</p>
<blockquote>
<p>💡 리소스마다 노출하는 condition 집합은 조금씩 다를 수 있지만, 직관을 키우기 위해 가장 먼저 익혀야 할 1차 그룹은 <code>Accepted</code>, <code>ResolvedRefs</code>, <code>Programmed</code>입니다.</p>
</blockquote>
<h2 id="가장-짧은-디버깅-흐름-보통-이-순서가-잘-먹힌다">가장 짧은 디버깅 흐름: 보통 이 순서가 잘 먹힌다</h2>
<h3 id="1단계-gateway가-실제로-떠-있는지-확인">1단계: Gateway가 실제로 떠 있는지 확인</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> gateway</span><span style="color:#A5D6FF"> eg</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span></code></pre></figure>
<p>확인할 것:</p>
<ul>
<li><code>status.addresses</code>에 값이 있는가</li>
<li>listener condition 중 이상한 것이 없는가</li>
<li>listener의 hostname/protocol/port가 기대와 일치하는가</li>
</ul>
<p>Gateway에 주소가 없다면, 아무리 예쁜 route YAML도 결국은 창작 글쓰기일 뿐입니다.</p>
<h3 id="2단계-route가-성공적으로-attach되었는지-확인">2단계: Route가 성공적으로 Attach되었는지 확인</h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> httproute</span><span style="color:#A5D6FF"> app-route</span><span style="color:#79C0FF"> -o</span><span style="color:#A5D6FF"> yaml</span></span></code></pre></figure>
<p>우선순위:</p>
<ul>
<li><code>status.parents</code></li>
<li><code>Accepted</code></li>
<li><code>ResolvedRefs</code></li>
<li><code>observedGeneration</code></li>
</ul>
<p><code>observedGeneration</code>은 꽤 볼 가치가 있습니다.
이 값이 <code>metadata.generation</code>을 따라잡지 못했다면, 컨트롤러가 아직 최신 설정 버전을 처리하지 않았을 수 있습니다.</p>
<h3 id="3단계-참조한-리소스가-실제로-존재하는지-확인">3단계: 참조한 리소스가 실제로 존재하는지 확인</h3>
<p>이 단계는 다른 어떤 단계보다 자주 건너뛰어집니다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> svc</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> secret</span><span style="color:#79C0FF"> -A</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> referencegrant</span><span style="color:#79C0FF"> -A</span></span></code></pre></figure>
<p>흔한 문제:</p>
<ul>
<li>백엔드 서비스 이름이 틀림</li>
<li>포트가 틀림</li>
<li>Secret이 생각한 네임스페이스에 없음</li>
<li>네임스페이스 간 참조에 <code>ReferenceGrant</code>가 없음</li>
</ul>
<p><code>ResolvedRefs</code>가 <code>False</code>라면 이 경로를 따라 추적하세요.</p>
<h3 id="4단계-데이터-플레인과-컨트롤러-확인">4단계: 데이터 플레인과 컨트롤러 확인</h3>
<p>Gateway와 Route 상태가 대체로 멀쩡해 보이는데도 트래픽이 흐르지 않는다면, 더 아래를 봐야 합니다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> get</span><span style="color:#A5D6FF"> pods</span><span style="color:#79C0FF"> -n</span><span style="color:#A5D6FF"> envoy-gateway-system</span></span>
<span data-line=""><span style="color:#FFA657">kubectl</span><span style="color:#A5D6FF"> logs</span><span style="color:#79C0FF"> -n</span><span style="color:#A5D6FF"> envoy-gateway-system</span><span style="color:#A5D6FF"> deployment/envoy-gateway</span></span></code></pre></figure>
<p>이 시점에는 "규칙이 받아들여졌는가"를 디버깅하는 것이 아니라, 컨트롤 플레인과 데이터 플레인이 정상 동작하는지를 보는 단계입니다.</p>
<p><code>egctl</code>이 설치돼 있다면 상태를 빠르게 보는 데 도움이 됩니다.
하지만 그것이 없어도 <code>kubectl get/describe -o yaml</code>만으로 대부분의 문제는 해결할 수 있습니다.</p>
<h2 id="가장-흔한-실패-패턴-네-가지">가장 흔한 실패 패턴 네 가지</h2>
<h3 id="1-route는-맞는데-의도한-listener에-attach되지-않았다">1. Route는 맞는데, 의도한 Listener에 Attach되지 않았다</h3>
<p>증상:</p>
<ul>
<li>YAML은 맞아 보임</li>
<li>그런데 트래픽이 규칙에 들어오지 않음</li>
</ul>
<p>확인할 것:</p>
<ul>
<li><code>parentRefs.name</code></li>
<li><code>parentRefs.sectionName</code></li>
<li>Gateway listener 이름이 정확히 일치하는지</li>
</ul>
<p>멀티 listener 환경에서는 <code>sectionName</code> 오타 하나로도 디버깅 세션 하나를 통째로 날릴 수 있습니다.</p>
<h3 id="2-accepted는-성공했는데-resolvedrefs가-실패한다">2. <code>Accepted</code>는 성공했는데 <code>ResolvedRefs</code>가 실패한다</h3>
<p>보통 이건 attach 자체는 가능한데, 참조된 무언가에 문제가 있다는 뜻입니다.
가장 흔한 원인:</p>
<ul>
<li>백엔드 Service가 존재하지 않음</li>
<li>Secret 이름이 틀림</li>
<li>네임스페이스 간 참조가 승인 없이 이뤄짐</li>
</ul>
<p>이 실패 유형이 가장 짜증 나는 이유는 거의 다 온 것처럼 보이는데, 실제로는 참조 계층에서 멈춰 있기 때문입니다.</p>
<h3 id="3-gateway에는-listener가-있는데-기대한-주소가-없다">3. Gateway에는 Listener가 있는데 기대한 주소가 없다</h3>
<p>이건 로컬 클러스터나 <code>LoadBalancer</code> 구현이 없는 환경에서 자주 보입니다.
Gateway API가 고장 난 것이 아니라, 아래 인프라가 외부 주소를 프로비저닝하지 못하는 것입니다.</p>
<p>선택지:</p>
<ul>
<li>클러스터에 <code>LoadBalancer</code> 기능이 있는지 확인</li>
<li><code>port-forward</code>로 라우팅 경로를 검증</li>
</ul>
<h3 id="4-yaml은-반영됐지만-요청이-404--503을-반환한다">4. YAML은 반영됐지만 요청이 404 / 503을 반환한다</h3>
<p>이 단계에서는 보통 한 필드만 틀린 것이 아니라, 체인 어딘가가 끊어진 경우가 많습니다:</p>
<ul>
<li>잘못된 Host header</li>
<li>어떤 규칙과도 매칭되지 않는 path</li>
<li>백엔드 Pod 비정상</li>
<li>Service selector가 어떤 Pod도 선택하지 못함</li>
</ul>
<p>Ingress 문제는 프록시 실패처럼 보여도 실제로는 백엔드가 준비되지 않은 경우가 많습니다. 모든 걸 프록시 탓으로 돌리지는 마세요. 그쪽도 이미 할 일이 많습니다.</p>
<h2 id="한-줄-요약">한 줄 요약</h2>
<p>Gateway API를 가장 효과적으로 디버깅하는 방법은 YAML을 계속 바꾸는 것이 아니라, <code>status</code>를 읽는 법을 익히는 것입니다.
<code>Accepted</code>는 주문이 접수됐는지 알려주고, <code>ResolvedRefs</code>는 참조가 해결됐는지 알려주며, <code>Programmed</code>는 설정이 실제로 반영됐는지 알려줍니다. 이 세 계층을 분리해서 보면 문제 해결 속도가 크게 올라갑니다.</p>
