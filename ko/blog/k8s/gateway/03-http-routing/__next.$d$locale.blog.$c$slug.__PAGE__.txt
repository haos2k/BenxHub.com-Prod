<p><code>HTTPRoute</code>를 들어오는 트래픽을 위한 라우팅 스크립트라고 생각해 보세요. 다만 Nginx 규칙을 쓰거나 컨트롤러 annotation을 외우는 대신, Kubernetes 네이티브 리소스를 쓴다는 점이 다릅니다.</p>
<p>먼저 분명히 해둘 점이 하나 있습니다. 이 글은 <code>HTTPRoute</code>만 다룹니다. <code>HTTPRoute</code>는 HTTP/HTTPS 의미 체계를 처리하기 때문입니다. gRPC라면 <code>GRPCRoute</code>, raw TCP라면 <code>TCPRoute</code>, TLS passthrough라면 <code>TLSRoute</code> 쪽이 맞습니다. 모든 걸 <code>HTTPRoute</code>에 우겨 넣지 마세요. 그러면 YAML 전체에서 "일단 되는 대로 맞춰 쓰는" 기운이 나기 시작합니다.</p>

<h2 id="matches는-무엇을-매칭할-수-있나"><code>matches</code>는 무엇을 매칭할 수 있나</h2>
<p><code>matches</code>는 <code>HTTPRoute</code>에서 가장 중심이 되는 개념 중 하나입니다.

<p>자주 쓰는 매칭 조건:</p>
<ul>
<li><code>path</code></li>
<li><code>headers</code></li>
<li><code>queryParams</code></li>
<li><code>method</code></li>
</ul>

<h2 id="filters-전달-전에-요청을-가공하기"><code>filters</code>: 전달 전에 요청을 가공하기</h2>
<p><code>HTTPRoute</code>는 단순히 "매칭하고 전달"만 하는 것이 아닙니다. 전달 전후로 변환도 적용할 수 있습니다. 그 역할을 하는 것이 <code>filters</code>입니다.</p>

<ul>
<li>백엔드로 보내기 전에 tracing metadata 주입</li>

<li>요청/응답 변환</li>

<p>다만 filters가 강력하다고 해서 ingress 계층을 거대한 middleware 덩어리로 만들라는 뜻은 아닙니다. route에 로직을 너무 많이 쌓아 올리면 디버깅이 따로 상담이 필요할 정도로 피곤해집니다.</p>

<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-v1</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span>
<span data-line=""><span style="color:#7EE787">          weight</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">90</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-v2</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span>
<span data-line=""><span style="color:#7EE787">          weight</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">10</span></span></code></pre></figure>
<p>이것이 기본적인 canary / traffic splitting입니다.</p>
<p>트래픽 실험을 하려고 굳이 전체 service mesh가 필요한 것은 아닙니다. 많은 API 서비스에서는 이것만으로도 충분하고, 설정도 훨씬 깔끔합니다.</p>
<blockquote>
<p>💡 <code>weight</code>는 상대값이며 반드시 100이 될 필요는 없습니다. <code>9</code>와 <code>1</code>은 <code>90</code>과 <code>10</code>과 같은 비율을 의미합니다.</p>
</blockquote>
<h2 id="timeouts-요청이-영원히-매달리지-않게-하자"><code>timeouts</code>: 요청이 영원히 매달리지 않게 하자</h2>
<p>HTTPRoute는 rule 수준의 timeout 설정을 지원합니다. 이건 꽤 중요합니다. ingress 계층에 제한이 없으면, 나쁜 요청이 마치 안 나가는 손님처럼 계속 자리를 차지하게 됩니다.</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">matches</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">path</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">          type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">PathPrefix</span></span>
<span data-line=""><span style="color:#7EE787">          value</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/reports</span></span>
<span data-line=""><span style="color:#7EE787">    timeouts</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">      request</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">10s</span></span>
<span data-line=""><span style="color:#7EE787">      backendRequest</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">2s</span></span>
<span data-line=""><span style="color:#7EE787">    backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">report-service</span></span>
<span data-line=""><span style="color:#7EE787">        port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span></code></pre></figure>
<p>두 필드의 의미:</p>
<ul>
<li><code>request</code>: 클라이언트 요청 전체에 대해 허용하는 최대 대기 시간</li>
<li><code>backendRequest</code>: 백엔드로 보내는 단일 요청에 대한 최대 대기 시간</li>
</ul>
<p><code>backendRequest</code>가 <code>request</code>보다 크면 안 된다는 점도 기억하세요. 전체 여행이 10분인데 버스 한 구간을 20분 기다릴 수 있다는 말과 같아서, 우주가 혼란스러워집니다.</p>
<h2 id="자주-놓치는-두-가지-뉘앙스">자주 놓치는 두 가지 뉘앙스</h2>
<h3 id="1-parentrefs는-특정-listener를-지정할-수-있다">1. <code>parentRefs</code>는 특정 Listener를 지정할 수 있다</h3>
<p>Gateway에 listener가 여러 개 있다면, 그중 하나에만 바인딩할 수 있습니다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">    sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">http</span></span></code></pre></figure>
<p>이 뜻은 이 route가 <code>http</code> listener에만 attach된다는 것입니다.
멀티 listener 환경에서는 모든 곳에 붙게 두는 것보다 훨씬 예측 가능합니다.</p>
<h3 id="2-matches가-없으면-전부-매칭된다">2. <code>matches</code>가 없으면 전부 매칭된다</h3>
<p>rule에 <code>matches</code>가 없으면 기본적으로 <code>/</code>에 매칭되는, 사실상 catch-all 규칙이 됩니다.</p>
<p>편리하긴 하지만, 여러분이 더 구체적이라고 생각한 규칙들을 조용히 집어삼킬 수 있습니다. 귀찮다고 생략했다가 왜 정밀한 규칙이 안 먹는지 한 시간 동안 헤매지 마세요.</p>
<h2 id="라우팅이-실제로-동작하는지-검증하기">라우팅이 실제로 동작하는지 검증하기</h2>

<p>먼저 분명히 해둘 점이 하나 있습니다. 이 글은 <code>HTTPRoute</code>만 다룹니다. <code>HTTPRoute</code>는 HTTP/HTTPS 의미 체계를 처리하기 때문입니다. gRPC라면 <code>GRPCRoute</code>, raw TCP라면 <code>TCPRoute</code>, TLS passthrough라면 <code>TLSRoute</code> 쪽이 맞습니다. 모든 걸 <code>HTTPRoute</code>에 우겨 넣지 마세요. 그러면 YAML 전체에서 "일단 되는 대로 맞춰 쓰는" 기운이 나기 시작합니다.</p>

<span data-line=""><span style="color:#7EE787">      backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-service</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span></code></pre></figure>
<p>의미는 다음과 같습니다:</p>
<ul>
<li><code>Host: app.example.com</code>일 때만 이 route에 매칭됨</li>
<li>path는 <code>/api</code>로 시작해야 함</li>
<li>트래픽은 <code>api-service:8080</code>으로 전달됨</li>
</ul>
<p><code>hostnames</code>를 제거하면 이 route는 "경로만 보고, 도메인은 아무거나"가 됩니다.</p>
<h2 id="matches는-무엇을-매칭할-수-있나"><code>matches</code>는 무엇을 매칭할 수 있나</h2>
<p><code>matches</code>는 <code>HTTPRoute</code>에서 가장 중심이 되는 개념 중 하나입니다.
"어떤 조건일 때 이 규칙을 발동할 것인가"라고 생각하면 됩니다.</p>
<p>자주 쓰는 매칭 조건:</p>
<ul>
<li><code>path</code></li>
<li><code>headers</code></li>
<li><code>queryParams</code></li>
<li><code>method</code></li>
</ul>
<p>예시:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">matches</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">method</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">GET</span></span>
<span data-line=""><span style="color:#7EE787">    path</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">      type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">PathPrefix</span></span>
<span data-line=""><span style="color:#7EE787">      value</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/api</span></span>
<span data-line=""><span style="color:#7EE787">    headers</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">version</span></span>
<span data-line=""><span style="color:#7EE787">        value</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">v2</span></span></code></pre></figure>
<p>의미:</p>
<ul>
<li><code>GET</code> 요청만</li>
<li>path가 <code>/api</code>로 시작해야 함</li>
<li>요청에 <code>version: v2</code> header가 포함되어야 함</li>
</ul>
<p>이 패턴은 API 버전 시험 운영이나 특정 사용자만 대상으로 한 단계적 rollout에 이상적입니다.</p>
<h2 id="하나의-route-여러-개의-규칙">하나의 Route, 여러 개의 규칙</h2>
<p>하나의 <code>HTTPRoute</code> 안에서 서로 다른 path를 서로 다른 서비스로 보낼 수 있습니다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">matches</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">path</span><span style="color:#E6EDF3">:</span></span>

<span data-line=""><span style="color:#7EE787">          value</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/api</span></span>
<span data-line=""><span style="color:#7EE787">    backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-service</span></span>
<span data-line=""><span style="color:#7EE787">        port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span>

<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">path</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">          type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">PathPrefix</span></span>
<span data-line=""><span style="color:#7EE787">          value</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/admin</span></span>
<span data-line=""><span style="color:#7EE787">    backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">admin-service</span></span>
<span data-line=""><span style="color:#7EE787">        port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span></code></pre></figure>
<p>하나의 도메인 아래에서 하위 path를 나눌 때 아주 좋습니다. 예를 들면:</p>
<ul>
<li><code>/api</code>는 API 서비스로</li>
<li><code>/admin</code>은 admin 백엔드로</li>
</ul>
<p>라우팅 로직이 바로 눈에 들어옵니다. 오래된 설정 파일처럼 반쯤 읽다가 "내가 지금 뭘 보고 있지"라는 실존적 고민에 빠지지 않아도 됩니다.</p>
<h2 id="header-method-query를-조건으로-쓰기">Header, Method, Query를 조건으로 쓰기</h2>
<p><code>HTTPRoute</code>는 path 매칭에만 제한되지 않습니다. 요청 header, method, query param으로도 매칭할 수 있습니다.</p>
<p>예를 들어 <code>version: v2</code>가 붙은 요청만 새 서비스로 보내고 싶다면:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">apiVersion</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">gateway.networking.k8s.io/v1</span></span>
<span data-line=""><span style="color:#7EE787">kind</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTPRoute</span></span>

<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">matches</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">path</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">            type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">PathPrefix</span></span>
<span data-line=""><span style="color:#7EE787">            value</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/api</span></span>
<span data-line=""><span style="color:#7EE787">          headers</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">            - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">version</span></span>

<span data-line=""><span style="color:#7EE787">      backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-v2</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">matches</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">path</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">            type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">PathPrefix</span></span>
<span data-line=""><span style="color:#7EE787">            value</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/api</span></span>
<span data-line=""><span style="color:#7EE787">      backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-v1</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span></code></pre></figure>
<p>이 패턴은 다음에 잘 맞습니다:</p>
<ul>
<li>Canary 배포</li>
<li>특정 고객에게만 새 버전을 먼저 체험하게 하기</li>
<li>새 기능 수동 검증</li>
</ul>
<p>새 도메인을 통째로 전환하는 것보다, header 기반 라우팅은 더 세밀하고 실험하기 쉽습니다.</p>
<h2 id="filters-전달-전에-요청을-가공하기"><code>filters</code>: 전달 전에 요청을 가공하기</h2>
<p><code>HTTPRoute</code>는 단순히 "매칭하고 전달"만 하는 것이 아닙니다. 전달 전후로 변환도 적용할 수 있습니다. 그 역할을 하는 것이 <code>filters</code>입니다.</p>
<p>가장 흔한 사용 사례는 header 추가입니다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">filters</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">RequestHeaderModifier</span></span>
<span data-line=""><span style="color:#7EE787">        requestHeaderModifier</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">          add</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">            - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">x-env</span></span>
<span data-line=""><span style="color:#7EE787">              value</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">prod</span></span>
<span data-line=""><span style="color:#7EE787">    backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-service</span></span>
<span data-line=""><span style="color:#7EE787">        port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span></code></pre></figure>
<p>이건 다음에 유용합니다:</p>
<ul>
<li>백엔드로 보내기 전에 tracing metadata 주입</li>
<li>ingress 계층에서 고정 header 추가</li>
<li>요청/응답 변환</li>
</ul>
<p>다만 filters가 강력하다고 해서 ingress 계층을 거대한 middleware 덩어리로 만들라는 뜻은 아닙니다. route에 로직을 너무 많이 쌓아 올리면 디버깅이 따로 상담이 필요할 정도로 피곤해집니다.</p>
<h2 id="weighted-traffic-splitting-가장-흔한-canary-패턴">Weighted Traffic Splitting: 가장 흔한 Canary 패턴</h2>
<p>기존 버전에 90%, 새 버전에 10%를 보내고 싶다면 <code>weight</code>를 사용합니다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">apiVersion</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">gateway.networking.k8s.io/v1</span></span>
<span data-line=""><span style="color:#7EE787">kind</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">HTTPRoute</span></span>
<span data-line=""><span style="color:#7EE787">metadata</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">canary-route</span></span>
<span data-line=""><span style="color:#7EE787">spec</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">  parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">  hostnames</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#A5D6FF">"app.example.com"</span></span>
<span data-line=""><span style="color:#7EE787">  rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">    - </span><span style="color:#7EE787">backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-v1</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span>
<span data-line=""><span style="color:#7EE787">          weight</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">90</span></span>
<span data-line=""><span style="color:#E6EDF3">        - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">api-v2</span></span>
<span data-line=""><span style="color:#7EE787">          port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span>
<span data-line=""><span style="color:#7EE787">          weight</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">10</span></span></code></pre></figure>
<p>이것이 기본적인 canary / traffic splitting입니다.</p>
<p>트래픽 실험을 하려고 굳이 전체 service mesh가 필요한 것은 아닙니다. 많은 API 서비스에서는 이것만으로도 충분하고, 설정도 훨씬 깔끔합니다.</p>
<blockquote>
<p>💡 <code>weight</code>는 상대값이며 반드시 100이 될 필요는 없습니다. <code>9</code>와 <code>1</code>은 <code>90</code>과 <code>10</code>과 같은 비율을 의미합니다.</p>
</blockquote>
<h2 id="timeouts-요청이-영원히-매달리지-않게-하자"><code>timeouts</code>: 요청이 영원히 매달리지 않게 하자</h2>
<p>HTTPRoute는 rule 수준의 timeout 설정을 지원합니다. 이건 꽤 중요합니다. ingress 계층에 제한이 없으면, 나쁜 요청이 마치 안 나가는 손님처럼 계속 자리를 차지하게 됩니다.</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">rules</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">matches</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">path</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">          type</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">PathPrefix</span></span>
<span data-line=""><span style="color:#7EE787">          value</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">/reports</span></span>
<span data-line=""><span style="color:#7EE787">    timeouts</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#7EE787">      request</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">10s</span></span>
<span data-line=""><span style="color:#7EE787">      backendRequest</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">2s</span></span>
<span data-line=""><span style="color:#7EE787">    backendRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">      - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">report-service</span></span>
<span data-line=""><span style="color:#7EE787">        port</span><span style="color:#E6EDF3">: </span><span style="color:#79C0FF">8080</span></span></code></pre></figure>
<p>두 필드의 의미:</p>
<ul>
<li><code>request</code>: 클라이언트 요청 전체에 대해 허용하는 최대 대기 시간</li>
<li><code>backendRequest</code>: 백엔드로 보내는 단일 요청에 대한 최대 대기 시간</li>
</ul>
<p><code>backendRequest</code>가 <code>request</code>보다 크면 안 된다는 점도 기억하세요. 전체 여행이 10분인데 버스 한 구간을 20분 기다릴 수 있다는 말과 같아서, 우주가 혼란스러워집니다.</p>
<h2 id="자주-놓치는-두-가지-뉘앙스">자주 놓치는 두 가지 뉘앙스</h2>
<h3 id="1-parentrefs는-특정-listener를-지정할-수-있다">1. <code>parentRefs</code>는 특정 Listener를 지정할 수 있다</h3>
<p>Gateway에 listener가 여러 개 있다면, 그중 하나에만 바인딩할 수 있습니다:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">    sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">http</span></span></code></pre></figure>
<p>이 뜻은 이 route가 <code>http</code> listener에만 attach된다는 것입니다.
멀티 listener 환경에서는 모든 곳에 붙게 두는 것보다 훨씬 예측 가능합니다.</p>
<h3 id="2-matches가-없으면-전부-매칭된다">2. <code>matches</code>가 없으면 전부 매칭된다</h3>
<p>rule에 <code>matches</code>가 없으면 기본적으로 <code>/</code>에 매칭되는, 사실상 catch-all 규칙이 됩니다.</p>
<p>편리하긴 하지만, 여러분이 더 구체적이라고 생각한 규칙들을 조용히 집어삼킬 수 있습니다. 귀찮다고 생략했다가 왜 정밀한 규칙이 안 먹는지 한 시간 동안 헤매지 마세요.</p>
