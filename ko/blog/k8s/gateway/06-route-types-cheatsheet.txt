1d:T4518,<p>앞선 글들을 읽었다면 지금 여러분을 가장 많이 막고 있는 질문은 "Gateway API를 이해 못하겠다"가 아니라, 아마 이쪽일 겁니다:</p>
<p><strong>"그래서 실제로 뭘 써야 하죠? <code>HTTPRoute</code>, <code>GRPCRoute</code>, <code>TCPRoute</code>, 아니면 <code>TLSRoute</code>?"</strong></p>
<p>이 글은 바로 그 실타래를 풀기 위해 존재합니다. 주머니 속 참고표처럼 두세요. 새로운 서비스가 생길 때마다 먼저 이것부터 확인하면, YAML을 감으로 쓰다가 condition status에게 교육당하는 일을 줄일 수 있습니다.</p>
<h2 id="결론부터-route-네-종류-목적도-네-가지">결론부터: Route 네 종류, 목적도 네 가지</h2>
<table>
<thead>
<tr>
<th>Route 타입</th>
<th>트래픽 계층</th>
<th>무엇을 검사하나</th>
<th>가장 잘 맞는 용도</th>
<th>맞지 않는 용도</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>HTTPRoute</code></td>
<td>L7 HTTP/HTTPS</td>
<td>host, path, header, query, method</td>
<td>웹사이트, REST API, 일반 웹 트래픽</td>
<td>raw TCP, TLS passthrough</td>
</tr>
<tr>
<td><code>GRPCRoute</code></td>
<td>L7 gRPC</td>
<td>hostname, service, method, header</td>
<td>gRPC service/method 라우팅</td>
<td>일반 REST API, raw TCP</td>
</tr>
<tr>
<td><code>TCPRoute</code></td>
<td>L4 TCP</td>
<td>Listener와 연결 수준 정보</td>
<td>데이터베이스, 커스텀 TCP 프로토콜, 비 HTTP 서비스</td>
<td>path/header 검사가 필요한 시나리오</td>
</tr>
<tr>
<td><code>TLSRoute</code></td>
<td>L4/L5 TLS</td>
<td>TLS SNI hostname</td>
<td>TLS passthrough, end-to-end 암호화 유지</td>
<td>복호화 후 HTTP 세부 정보를 봐야 하는 경우</td>
</tr>
</tbody>
</table>
<p>아주 짧게 말하면:</p>
<ul>
<li><code>path</code>나 <code>header</code>를 봐야 한다 → <code>HTTPRoute</code></li>
<li>gRPC <code>service/method</code>를 봐야 한다 → <code>GRPCRoute</code></li>
<li>TCP 연결만 전달하면 된다 → <code>TCPRoute</code></li>
<li>TLS termination 없이 SNI로만 라우팅한다 → <code>TLSRoute</code></li>
</ul>
<h2 id="3단계-판단법-감으로-고르지-말자">3단계 판단법: 감으로 고르지 말자</h2>
<p>이 순서로 생각하세요:</p>
<ol>
<li>Gateway가 이 트래픽에서 HTTP 의미 체계를 파싱해야 하는가?</li>
<li>그렇다면 일반 HTTP/REST인가, 아니면 gRPC인가?</li>
<li>아니라면 raw TCP인가, 아니면 TLS passthrough인가?</li>
</ol>
<p>정리하면:</p>
<ul>
<li>HTTP path/header/method를 검사해야 한다 → <code>HTTPRoute</code></li>
<li>gRPC service/method를 검사해야 한다 → <code>GRPCRoute</code></li>
<li>L7 규칙 없이 TCP 포워딩만 한다 → <code>TCPRoute</code></li>
<li>TLS를 백엔드까지 유지하고 싶다 → <code>TLSRoute</code></li>
</ul>
<p>이 결정은 정말 중요합니다. 많은 사람이 본능적으로 먼저 <code>HTTPRoute</code>부터 쓰다가, 반쯤 가서 자신이 다루는 게 데이터베이스 트래픽이라는 사실을 깨닫습니다. 그러면 YAML 전체가 "내가 지금 대체 뭘 하고 있지" 모드로 들어갑니다.</p>

<span data-line=""><span style="color:#85E89D">      backendRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">        - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">user-grpc-service</span></span>
<span data-line=""><span style="color:#85E89D">          port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">50051</span></span></code></pre></figure>
<p><code>method.service</code>와 <code>method.method</code>가 보이면 일반 HTTP가 아니라 gRPC 의미 체계를 매칭하고 있는 것입니다.</p>
<h3 id="tcproute"><code>TCPRoute</code></h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">apiVersion</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.networking.k8s.io/v1alpha2</span></span>
<span data-line=""><span style="color:#85E89D">kind</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">TCPRoute</span></span>
<span data-line=""><span style="color:#85E89D">metadata</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">postgres-route</span></span>
<span data-line=""><span style="color:#85E89D">spec</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  parentRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">eg</span></span>
<span data-line=""><span style="color:#85E89D">      sectionName</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">postgres</span></span>
<span data-line=""><span style="color:#85E89D">  rules</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">        - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">postgres</span></span>
<span data-line=""><span style="color:#85E89D">          port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">5432</span></span></code></pre></figure>
<p><code>TCPRoute</code>에는 path/header 개념이 거의 없습니다. 왜냐하면 그걸 보지 않기 때문입니다.
좀 더 정확히 말하면 "이 listener로 들어오는 TCP 연결은 이 backend로 보낸다"에 가깝습니다.</p>
<h3 id="tlsroute"><code>TLSRoute</code></h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">apiVersion</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.networking.k8s.io/v1alpha2</span></span>
<span data-line=""><span style="color:#85E89D">kind</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">TLSRoute</span></span>
<span data-line=""><span style="color:#85E89D">metadata</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">passthrough-route</span></span>
<span data-line=""><span style="color:#85E89D">spec</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  parentRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">eg</span></span>
<span data-line=""><span style="color:#85E89D">      sectionName</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">tls</span></span>
<span data-line=""><span style="color:#85E89D">  hostnames</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#9ECBFF">"db.example.com"</span></span>
<span data-line=""><span style="color:#85E89D">  rules</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">        - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">db-service</span></span>
<span data-line=""><span style="color:#85E89D">          port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">5432</span></span></code></pre></figure>
<p>보통 <code>protocol: TLS</code> listener와 짝을 이룹니다. 핵심은 복호화가 아니라 SNI 기반 라우팅입니다.</p>
<blockquote>
<p>💡 <code>TCPRoute</code>와 <code>TLSRoute</code>는 Gateway API 버전에 따라 experimental 채널에 있는 경우가 많습니다. 적용 전에 클러스터에 설치된 CRD 버전을 꼭 확인하세요.</p>
</blockquote>
<h2 id="흔한-함정-네-가지">흔한 함정 네 가지</h2>
<h3 id="1-grpc가-반드시-grpcroute를-요구하는-것은-아니다">1. gRPC가 반드시 <code>GRPCRoute</code>를 요구하는 것은 아니다</h3>
<p>gRPC 트래픽을 그냥 흐르게만 하면 되는 경우, 구현체에 따라 gRPC가 HTTP/2 위에서 동작하므로 <code>HTTPRoute</code>로도 지원될 수 있습니다.
하지만 gRPC service/method 의미 체계로 매칭하고 싶다면, <code>GRPCRoute</code>가 더 올바르고 읽기 쉬운 선택입니다.</p>
<h3 id="2-tlsroute는-고급-https가-아니다">2. <code>TLSRoute</code>는 "고급 HTTPS"가 아니다</h3>
<p>이게 가장 흔한 오해입니다.</p>
<ul>
<li><code>HTTPS listener + HTTPRoute</code>: Gateway가 TLS를 종료하고, 그 뒤 HTTP 규칙 적용</li>
<li><code>TLS listener + TLSRoute</code>: Gateway가 TLS를 종료하지 않고, SNI만 보고 라우팅</li>
</ul>
<p>하나는 복호화해서 L7에서 동작합니다. 다른 하나는 트래픽을 암호화 상태로 유지한 채 passthrough 합니다. 완전히 다른 세계입니다.</p>
<h3 id="3-tcproute는-pathheader를-볼-수-없다">3. <code>TCPRoute</code>는 Path/Header를 볼 수 없다</h3>
<p>만약 요구사항이 다음과 같다면:</p>
<ul>
<li><code>/api</code>는 A로</li>
<li><code>/admin</code>은 B로</li>
</ul>
<p>이건 <code>TCPRoute</code>의 일이 아닙니다.
<code>TCPRoute</code>는 HTTP 세부 정보를 이해하지 못합니다. 여기에 그런 요구를 억지로 밀어 넣으면, 결국 본인만 괴로워집니다.</p>
<h3 id="4-parentrefssectionname은-중요하다">4. <code>parentRefs.sectionName</code>은 중요하다</h3>
<p>Gateway에 listener가 여러 개라면 <code>sectionName</code>을 쓰세요:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">parentRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">eg</span></span>
<span data-line=""><span style="color:#85E89D">    sectionName</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">https</span></span></code></pre></figure>
<p>이렇게 해야 route가 정확히 의도한 listener에 붙습니다.
이게 없으면 VIP 룸 예약했다고 생각했는데 엉뚱한 홀에 들어가는 일이 벌어질 수 있습니다.</p>
<h2 id="한-줄-요약">한 줄 요약</h2>
<p>먼저 내가 다루는 것이 <strong>HTTP, gRPC, TCP, 아니면 TLS passthrough</strong>인지 파악하고, 그다음 맞는 route 타입을 고르세요.
Route를 제대로 고르면 YAML의 80%는 자연스럽게 풀립니다. 반대로 잘못 고르면 condition status와 끝없는 싸움에 갇히게 됩니다.</p>

<h2 id="결론부터-route-네-종류-목적도-네-가지">결론부터: Route 네 종류, 목적도 네 가지</h2>

<p>아주 짧게 말하면:</p>
<ul>
<li><code>path</code>나 <code>header</code>를 봐야 한다 → <code>HTTPRoute</code></li>
<li>gRPC <code>service/method</code>를 봐야 한다 → <code>GRPCRoute</code></li>
<li>TCP 연결만 전달하면 된다 → <code>TCPRoute</code></li>
<li>TLS termination 없이 SNI로만 라우팅한다 → <code>TLSRoute</code></li>
</ul>
<h2 id="3단계-판단법-감으로-고르지-말자">3단계 판단법: 감으로 고르지 말자</h2>
<p>이 순서로 생각하세요:</p>
<ol>
<li>Gateway가 이 트래픽에서 HTTP 의미 체계를 파싱해야 하는가?</li>
<li>그렇다면 일반 HTTP/REST인가, 아니면 gRPC인가?</li>
<li>아니라면 raw TCP인가, 아니면 TLS passthrough인가?</li>
</ol>
<p>정리하면:</p>
<ul>
<li>HTTP path/header/method를 검사해야 한다 → <code>HTTPRoute</code></li>
<li>gRPC service/method를 검사해야 한다 → <code>GRPCRoute</code></li>
<li>L7 규칙 없이 TCP 포워딩만 한다 → <code>TCPRoute</code></li>
<li>TLS를 백엔드까지 유지하고 싶다 → <code>TLSRoute</code></li>
</ul>
<p>이 결정은 정말 중요합니다. 많은 사람이 본능적으로 먼저 <code>HTTPRoute</code>부터 쓰다가, 반쯤 가서 자신이 다루는 게 데이터베이스 트래픽이라는 사실을 깨닫습니다. 그러면 YAML 전체가 "내가 지금 대체 뭘 하고 있지" 모드로 들어갑니다.</p>
<h2 id="최소-yaml-예제-한눈에-각-타입-알아보기">최소 YAML 예제: 한눈에 각 타입 알아보기</h2>
<p>각 타입을 가장 짧고 알아보기 쉽게 보여주는 예시를 보겠습니다.</p>
<h3 id="httproute"><code>HTTPRoute</code></h3>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">apiVersion</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">gateway.networking.k8s.io/v1</span></span>

<span data-line=""><span style="color:#85E89D">spec</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  parentRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">eg</span></span>
<span data-line=""><span style="color:#85E89D">      sectionName</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">http</span></span>
<span data-line=""><span style="color:#85E89D">  hostnames</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#9ECBFF">"app.example.com"</span></span>
<span data-line=""><span style="color:#85E89D">  rules</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">matches</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">        - </span><span style="color:#85E89D">path</span><span style="color:#E1E4E8">:</span></span>

<h2 id="흔한-함정-네-가지">흔한 함정 네 가지</h2>
<h3 id="1-grpc가-반드시-grpcroute를-요구하는-것은-아니다">1. gRPC가 반드시 <code>GRPCRoute</code>를 요구하는 것은 아니다</h3>
<p>gRPC 트래픽을 그냥 흐르게만 하면 되는 경우, 구현체에 따라 gRPC가 HTTP/2 위에서 동작하므로 <code>HTTPRoute</code>로도 지원될 수 있습니다.
하지만 gRPC service/method 의미 체계로 매칭하고 싶다면, <code>GRPCRoute</code>가 더 올바르고 읽기 쉬운 선택입니다.</p>
<h3 id="2-tlsroute는-고급-https가-아니다">2. <code>TLSRoute</code>는 "고급 HTTPS"가 아니다</h3>
<p>이게 가장 흔한 오해입니다.</p>
<ul>
<li><code>HTTPS listener + HTTPRoute</code>: Gateway가 TLS를 종료하고, 그 뒤 HTTP 규칙 적용</li>
<li><code>TLS listener + TLSRoute</code>: Gateway가 TLS를 종료하지 않고, SNI만 보고 라우팅</li>
</ul>
<p>하나는 복호화해서 L7에서 동작합니다. 다른 하나는 트래픽을 암호화 상태로 유지한 채 passthrough 합니다. 완전히 다른 세계입니다.</p>
<h3 id="3-tcproute는-pathheader를-볼-수-없다">3. <code>TCPRoute</code>는 Path/Header를 볼 수 없다</h3>
<p>만약 요구사항이 다음과 같다면:</p>
<ul>
<li><code>/api</code>는 A로</li>
<li><code>/admin</code>은 B로</li>
</ul>
<p>이건 <code>TCPRoute</code>의 일이 아닙니다.
<code>TCPRoute</code>는 HTTP 세부 정보를 이해하지 못합니다. 여기에 그런 요구를 억지로 밀어 넣으면, 결국 본인만 괴로워집니다.</p>
<h3 id="4-parentrefssectionname은-중요하다">4. <code>parentRefs.sectionName</code>은 중요하다</h3>
<p>Gateway에 listener가 여러 개라면 <code>sectionName</code>을 쓰세요:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">parentRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">  - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">eg</span></span>
<span data-line=""><span style="color:#85E89D">    sectionName</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">https</span></span></code></pre></figure>
<p>이렇게 해야 route가 정확히 의도한 listener에 붙습니다.
이게 없으면 VIP 룸 예약했다고 생각했는데 엉뚱한 홀에 들어가는 일이 벌어질 수 있습니다.</p>
<h2 id="한-줄-요약">한 줄 요약</h2>
<p>먼저 내가 다루는 것이 <strong>HTTP, gRPC, TCP, 아니면 TLS passthrough</strong>인지 파악하고, 그다음 맞는 route 타입을 고르세요.
Route를 제대로 고르면 YAML의 80%는 자연스럽게 풀립니다. 반대로 잘못 고르면 condition status와 끝없는 싸움에 갇히게 됩니다.</p>
