<h2 id="الخلاصة-أولًا-أربعة-أنواع-route-وأربعة-استخدامات">الخلاصة أولًا: أربعة أنواع Route، وأربعة استخدامات</h2>

<p>إذا كنت تريد نسخة فائقة الاختصار:</p>
<ul>
<li>تحتاج إلى فحص <code>path</code> أو <code>header</code> → <code>HTTPRoute</code></li>
<li>تحتاج إلى فحص gRPC <code>service/method</code> → <code>GRPCRoute</code></li>
<li>تريد فقط تمرير اتصالات TCP → <code>TCPRoute</code></li>
<li>لا تريد TLS termination، بل توجيه SNI فقط → <code>TLSRoute</code></li>
</ul>
<h2 id="قرار-من-ثلاث-خطوات-توقّف-عن-التخمين">قرار من ثلاث خطوات: توقّف عن التخمين</h2>
<p>استخدم هذا الترتيب:</p>
<ol>
<li>هل سيقوم الـ Gateway بتحليل دلالات HTTP في هذا المرور؟</li>
<li>إذا كانت الإجابة نعم، فهل هو HTTP/REST عادي أم gRPC؟</li>
<li>إذا كانت الإجابة لا، فهل هو TCP خام أم TLS passthrough؟</li>
</ol>
<p>بشكل مباشر:</p>
<ul>
<li>لديك HTTP path/header/method تريد فحصه → <code>HTTPRoute</code></li>
<li>لديك gRPC service/method تريد فحصه → <code>GRPCRoute</code></li>
<li>لا توجد قواعد L7، فقط TCP forwarding → <code>TCPRoute</code></li>
<li>تريد الحفاظ على TLS حتى الـ backend → <code>TLSRoute</code></li>
</ul>
<p>هذا القرار مهم جدًا. كثير من الناس يبدؤون تلقائيًا بكتابة <code>HTTPRoute</code>، ثم يكتشفون في منتصف الطريق أنهم يتعاملون مع مرور قاعدة بيانات. وعندها يدخل الـ YAML كاملًا في وضعية "ماذا أفعل أنا هنا أصلًا؟"</p>
<h2 id="أمثلة-yaml-مصغّرة-تعرّف-على-كل-نوع-بنظرة-واحدة">أمثلة YAML مصغّرة: تعرّف على كل نوع بنظرة واحدة</h2>

<h2 id="أربعة-أخطاء-شائعة">أربعة أخطاء شائعة</h2>
<h3 id="1-grpc-لا-يتطلب-بالضرورة-grpcroute">1. ‏gRPC لا يتطلب بالضرورة <code>GRPCRoute</code></h3>
<p>إذا كان كل ما تريده هو مرور gRPC فقط، فقد تدعم بعض الـ implementations ذلك عبر <code>HTTPRoute</code> لأن gRPC يعمل فوق HTTP/2.
لكن إذا أردت المطابقة بحسب gRPC service/method semantics، فـ <code>GRPCRoute</code> هو الخيار الأصح والأوضح.</p>
<h3 id="2-tlsroute-ليس-https-لكن-بشكل-متقدم">2. ‏<code>TLSRoute</code> ليس "HTTPS لكن بشكل متقدم"</h3>
<p>هذا هو الالتباس الأكثر شيوعًا.</p>
<ul>
<li><code>HTTPS listener + HTTPRoute</code>: الـ Gateway ينهي TLS ثم يطبق قواعد HTTP</li>
<li><code>TLS listener + TLSRoute</code>: الـ Gateway لا ينهي TLS، بل يوجّه اعتمادًا على SNI فقط</li>
</ul>
<p>أحدهما يفك التشفير ويتعامل على L7، والآخر يُبقي المرور مشفرًا وينفذ passthrough. عالمان مختلفان تمامًا.</p>
<h3 id="3-tcproute-لا-يستطيع-رؤية-pathheader">3. ‏<code>TCPRoute</code> لا يستطيع رؤية Path/Header</h3>
<p>إذا كان مطلبك هو:</p>
<ul>
<li><code>/api</code> يذهب إلى A</li>
<li><code>/admin</code> يذهب إلى B</li>
</ul>
<p>فهذا ليس عمل <code>TCPRoute</code>.
لأن <code>TCPRoute</code> لا يفهم تفاصيل HTTP. وإجبار هذه المتطلبات عليه مجرد وصفة جاهزة للإحباط.</p>
<h3 id="4-parentrefssectionname-مهم-جدًا">4. ‏<code>parentRefs.sectionName</code> مهم جدًا</h3>
<p>عندما يكون لدى Gateway عدة listeners، استخدم <code>sectionName</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">    sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span></code></pre></figure>
<p>هذا يضمن أن يرتبط الـ route بدقة بالـ listener الذي تقصده.
ومن دونه قد تعتقد أنك حجزت قاعة VIP ثم تجد نفسك في الصالة الخطأ بالكامل.</p>
<h2 id="الخلاصة-في-سطر-واحد">الخلاصة في سطر واحد</h2>

إذا اخترت النوع الصحيح، فسيتدفق 80% من YAML لديك بشكل طبيعي. وإذا أخطأت، فستجد نفسك عالقًا في معركة مع condition statuses.</p>

<p>إذا كنت تريد نسخة فائقة الاختصار:</p>
<ul>
<li>تحتاج إلى فحص <code>path</code> أو <code>header</code> → <code>HTTPRoute</code></li>
<li>تحتاج إلى فحص gRPC <code>service/method</code> → <code>GRPCRoute</code></li>
<li>تريد فقط تمرير اتصالات TCP → <code>TCPRoute</code></li>
<li>لا تريد TLS termination، بل توجيه SNI فقط → <code>TLSRoute</code></li>
</ul>
<h2 id="قرار-من-ثلاث-خطوات-توقّف-عن-التخمين">قرار من ثلاث خطوات: توقّف عن التخمين</h2>
<p>استخدم هذا الترتيب:</p>
<ol>
<li>هل سيقوم الـ Gateway بتحليل دلالات HTTP في هذا المرور؟</li>
<li>إذا كانت الإجابة نعم، فهل هو HTTP/REST عادي أم gRPC؟</li>
<li>إذا كانت الإجابة لا، فهل هو TCP خام أم TLS passthrough؟</li>
</ol>
<p>بشكل مباشر:</p>
<ul>
<li>لديك HTTP path/header/method تريد فحصه → <code>HTTPRoute</code></li>
<li>لديك gRPC service/method تريد فحصه → <code>GRPCRoute</code></li>
<li>لا توجد قواعد L7، فقط TCP forwarding → <code>TCPRoute</code></li>
<li>تريد الحفاظ على TLS حتى الـ backend → <code>TLSRoute</code></li>
</ul>
<p>هذا القرار مهم جدًا. كثير من الناس يبدؤون تلقائيًا بكتابة <code>HTTPRoute</code>، ثم يكتشفون في منتصف الطريق أنهم يتعاملون مع مرور قاعدة بيانات. وعندها يدخل الـ YAML كاملًا في وضعية "ماذا أفعل أنا هنا أصلًا؟"</p>
<h2 id="أمثلة-yaml-مصغّرة-تعرّف-على-كل-نوع-بنظرة-واحدة">أمثلة YAML مصغّرة: تعرّف على كل نوع بنظرة واحدة</h2>

<h2 id="أربعة-أخطاء-شائعة">أربعة أخطاء شائعة</h2>
<h3 id="1-grpc-لا-يتطلب-بالضرورة-grpcroute">1. ‏gRPC لا يتطلب بالضرورة <code>GRPCRoute</code></h3>
<p>إذا كان كل ما تريده هو مرور gRPC فقط، فقد تدعم بعض الـ implementations ذلك عبر <code>HTTPRoute</code> لأن gRPC يعمل فوق HTTP/2.
لكن إذا أردت المطابقة بحسب gRPC service/method semantics، فـ <code>GRPCRoute</code> هو الخيار الأصح والأوضح.</p>
<h3 id="2-tlsroute-ليس-https-لكن-بشكل-متقدم">2. ‏<code>TLSRoute</code> ليس "HTTPS لكن بشكل متقدم"</h3>
<p>هذا هو الالتباس الأكثر شيوعًا.</p>
<ul>
<li><code>HTTPS listener + HTTPRoute</code>: الـ Gateway ينهي TLS ثم يطبق قواعد HTTP</li>
<li><code>TLS listener + TLSRoute</code>: الـ Gateway لا ينهي TLS، بل يوجّه اعتمادًا على SNI فقط</li>
</ul>
<p>أحدهما يفك التشفير ويتعامل على L7، والآخر يُبقي المرور مشفرًا وينفذ passthrough. عالمان مختلفان تمامًا.</p>
<h3 id="3-tcproute-لا-يستطيع-رؤية-pathheader">3. ‏<code>TCPRoute</code> لا يستطيع رؤية Path/Header</h3>
<p>إذا كان مطلبك هو:</p>
<ul>
<li><code>/api</code> يذهب إلى A</li>
<li><code>/admin</code> يذهب إلى B</li>
</ul>
<p>فهذا ليس عمل <code>TCPRoute</code>.
لأن <code>TCPRoute</code> لا يفهم تفاصيل HTTP. وإجبار هذه المتطلبات عليه مجرد وصفة جاهزة للإحباط.</p>
<h3 id="4-parentrefssectionname-مهم-جدًا">4. ‏<code>parentRefs.sectionName</code> مهم جدًا</h3>
<p>عندما يكون لدى Gateway عدة listeners، استخدم <code>sectionName</code>:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#0d1117;color:#e6edf3" tabindex="0" data-language="yaml" data-theme="github-dark-default"><code data-language="yaml" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#7EE787">parentRefs</span><span style="color:#E6EDF3">:</span></span>
<span data-line=""><span style="color:#E6EDF3">  - </span><span style="color:#7EE787">name</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">eg</span></span>
<span data-line=""><span style="color:#7EE787">    sectionName</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">https</span></span></code></pre></figure>
<p>هذا يضمن أن يرتبط الـ route بدقة بالـ listener الذي تقصده.
ومن دونه قد تعتقد أنك حجزت قاعة VIP ثم تجد نفسك في الصالة الخطأ بالكامل.</p>
