3:T47ce,<p>إذا سبق لك التعامل مع المرور الخارجي في Kubernetes، فالغالب أنك بدأت مع <code>Ingress</code>. هو يعمل، وبالنسبة لكثير من السيناريوهات فهو كافٍ فعلًا. لكن عندما تبدأ المتطلبات بالتعقّد أكثر، مثل وجود عدة listeners، وملكية مشتركة بين عدة فرق، و gRPC، و TCP، و TLS passthrough، وسياسات مرور دقيقة، فستجد نفسك حتمًا في وضع يصبح فيه "إبقاؤه حيًا عبر annotations" هو القاعدة. يبدأ الـ YAML وكأنه تعويذة، والناس الذين يصونونه يشعرون وكأنهم على وشك كسر ختم قديم.</p>
<p>وهنا يأتي دور <code>Gateway API + Envoy Gateway</code>، فهي العدة الجديدة. لا تجعل الأمور أعقد؛ بل تفصل المسؤوليات التي كانت متشابكة سابقًا بشكل نظيف، بحيث يصبح فهم مرور الدخول، وقواعد التوجيه، وإعدادات أمان TLS، وأنواع البروتوكولات، وملكية الفرق أسهل بكثير.</p>
<h2 id="ما-هذا-بالضبط">ما هذا بالضبط</h2>
<p>لنقلها بوضوح في جملة واحدة:</p>
<ul>
<li><code>Envoy Proxy</code>: مستوى البيانات الذي يستقبل المرور فعليًا ويحوّل الطلبات، ويُسمّى أيضًا Gateway Proxy</li>
<li><code>Envoy Gateway</code>: مستوى التحكم الذي يدير Envoy Proxy نيابةً عنك</li>
<li><code>Gateway API</code>: الواجهة المعيارية التي تستخدمها في Kubernetes للتصريح بقواعد المرور</li>
</ul>
<p>فكّر فيها هكذا:</p>
<ul>
<li><code>Gateway API</code> هو المكان الذي تكتب فيه المتطلبات</li>
<li><code>Envoy Gateway</code> هو المدير الذي يترجم ويفوّض</li>
<li><code>Envoy Proxy</code> هو الحارس الفعلي الواقف عند الباب</li>
</ul>
<p>فائدة هذا الفصل أنك لا تحتاج إلى صياغة إعدادات Envoy منخفضة المستوى يدويًا، ولا إلى حفظ كل annotation خاص من مختلف الـ controllers. أنت تصرّح بموارد Kubernetes، و Envoy Gateway يترجمها إلى إعدادات يستطيع Envoy Proxy تنفيذها فعلًا.</p>
<h2 id="gateway-مقابل-ingress-ما-الفرق">Gateway مقابل Ingress: ما الفرق</h2>
<p>الإجابة المختصرة: <strong>Ingress لم يصبح قديمًا، لكن Gateway API أنسب للأنظمة المتوسطة والكبيرة التي تحتاج إلى حوكمة أفضل.</strong></p>

<p>إذا كانت متطلباتك ببساطة:</p>
<ul>
<li>موقع واحد أو API بسيط</li>
<li>توجيه أساسي حسب path أو host</li>
<li>فريق صغير</li>
</ul>
<p>فلا يزال Ingress خيارًا مناسبًا. لكن إذا بدأت متطلباتك تشمل:</p>
<ul>
<li>مدخل دخول واحد يخدم عدة بروتوكولات</li>
<li>عدة listeners أو domains أو certificates</li>
<li>HTTP و gRPC معًا</li>
<li>فصل صلاحيات ingress الخاصة بالمنصة عن صلاحيات routes الخاصة بالتطبيق</li>
<li>إعدادات تُقرأ كأنها API حقيقي وليست قائمة أمنيات من annotations</li>
</ul>
<p>فعندها ستبدو Gateway API جذابة جدًا.</p>
<h2 id="لماذا-لا-نكتفي-بـ-ingress">لماذا لا نكتفي بـ Ingress</h2>
<p>الهدف الرسمي لـ Gateway API هو معالجة عدة نقاط ألم شائعة عند توسّع استخدام Ingress:</p>
<ul>
<li><strong>قدرة تعبيرية أفضل</strong>: التوجيه و TLS وسياسات المرور وأنواع البروتوكولات محددة بشكل أوضح</li>
<li><strong>قابلية نقل أفضل</strong>: اعتماد أقل على annotations خاصة بكل controller</li>
<li><strong>فصل أدوار أكثر طبيعية</strong>: فرق المنصة تملك ingress، وفرق التطبيقات تملك routes</li>
</ul>
<p>على سبيل المثال، كثير من إعدادات Ingress تبدو هكذا:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">metadata</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">  annotations</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/rewrite-target</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">/</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/auth-type</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">basic</span></span>
<span data-line=""><span style="color:#85E89D">    some.ingress.controller/ssl-redirect</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">"true"</span></span></code></pre></figure>
<p>ليس لأنها لا تعمل، لكن مع نمو المتطلبات تتحول annotations بسهولة إلى سحر أسود غامض داخل YAML. Gateway API تسحب هذه الاحتياجات إلى حقول واضحة. فتبدو كأنها "إعدادات" وليست "قائمة أمنيات".</p>
<h2 id="البنية-الطبقية">البنية الطبقية</h2>
<p>الصفحة الرسمية للمفاهيم تقسّم Envoy Gateway إلى ثلاث طبقات، ومن المفيد جدًا حفظها كخريطة ذهنية:</p>
<ul>
<li><strong>User Configuration</strong>: موارد <code>Gateway API</code> و CRDs التوسعية الخاصة بـ Envoy Gateway التي تكتبها</li>
<li><strong>Envoy Gateway Controller</strong>: يقرأ هذه الموارد ويترجمها إلى إعدادات قابلة للتنفيذ</li>
<li><strong>Envoy Proxy</strong>: مستوى البيانات الذي يتعامل فعليًا مع المرور الحي</li>
</ul>
<p>عمليًا، ستقضي معظم وقتك في تعديل "الطبقة التصريحية"، وليس في الدخول عبر SSH إلى instances البروكسي لتعديل إعدادات منخفضة المستوى. هذه هي أناقة العمل بطريقة Kubernetes-native.</p>
<h2 id="ماذا-ستتعلّم-في-هذه-السلسلة">ماذا ستتعلّم في هذه السلسلة</h2>
<p>تتبع هذه السلسلة ترتيب "ابنه أولًا ثم تعمّق" مع <strong>10 مقالات بما في ذلك هذه النظرة العامة</strong>:</p>
<ol>
<li><a href="01-quick-start">البداية السريعة</a>: ثبّت Envoy Gateway وشغّل أول طلب HTTP من البداية إلى النهاية</li>
<li><a href="02-core-concepts">المفاهيم الأساسية</a>: افهم <code>GatewayClass</code> و <code>Gateway</code> و <code>Listener</code> و <code>Envoy Proxy</code></li>
<li><a href="03-http-routing">التوجيه العملي لـ HTTP</a>: تعمّق في <code>HTTPRoute</code>، من host و path إلى header و filter و timeout</li>
<li><a href="04-tls-and-security">TLS والأمان</a>: اضبط HTTPS وافهم <code>certificateRefs</code> و TLS termination و <code>TLSRoute</code></li>
<li><a href="05-best-practices">أفضل الممارسات</a>: أهم العادات قبل الذهاب إلى الإنتاج</li>
<li><a href="06-route-types-cheatsheet">ورقة غش لأنواع Route</a>: قرّر بسرعة بين <code>HTTPRoute</code> و <code>GRPCRoute</code> و <code>TCPRoute</code> و <code>TLSRoute</code></li>
<li><a href="07-listener-design">دليل تصميم Listener</a>: أنماط تصميم multi-port و multi-hostname و multi-ingress</li>
<li><a href="08-multi-namespace-and-teamwork">تعدد الـ Namespace وملكية الفرق</a>: أتقن <code>allowedRoutes</code> و <code>ReferenceGrant</code> وحوكمة ingress المشتركة</li>
<li><a href="09-debugging-and-status">دليل الحالة واستكشاف الأخطاء</a>: اقرأ <code>Accepted</code> و <code>ResolvedRefs</code> و <code>Programmed</code> واتبع أقصر طريق للتشخيص</li>
</ol>
<p>إذا كنت فقط تريد أن تشعر بطبيعة Envoy Gateway، فاذهب مباشرة إلى المقالة التالية. تشغيله فعليًا أفضل من حفظ كل مصطلح قبل البدء، تمامًا مثل الذهاب إلى النادي الرياضي: الحضور الفعلي أفضل من مشاهدة 30 فيديو على YouTube أولًا.</p>
<h2 id="الموارد-الأساسية-التي-ستصادفها">الموارد الأساسية التي ستصادفها</h2>
<p>المبتدئون غالبًا يتعثرون لأنهم يفترضون أن Gateway API لا يحتوي إلا على <code>Gateway</code> و <code>HTTPRoute</code>. لكنه في الحقيقة عائلة كاملة من الموارد.</p>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>يعرّف "أي implementation من Gateway يجب استخدامه في هذا الـ cluster."
وبالنسبة إلى Envoy Gateway، فالنقطة الأساسية هي أن يوجَّه <code>controllerName</code> إلى الـ controller الصحيح.</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>يعرّف "كيف يبدو ingress."
على سبيل المثال: ما المنافذ التي ستُفتح، وما البروتوكولات التي ستُستمع إليها، وكيفية إرفاق TLS، وأي routes يُسمح بها.</p>
<h3 id="listener"><code>Listener</code></h3>
<p><code>Listener</code> هو إحدى أهم الوحدات داخل <code>Gateway</code>.
فكّر فيه على أنه فتحة مواجهة للخارج في الـ Gateway، وكل فتحة تعرّف:</p>
<ul>
<li>port</li>
<li>protocol</li>
<li>hostname</li>
<li>TLS config</li>
<li><code>allowedRoutes</code></li>
</ul>
<p>كثيرون ينظرون إلى <code>Gateway</code> كأنه صندوق أسود، لكن ما يحدد سلوك ingress فعليًا هو كل <code>listener</code> داخله على حدة.</p>
<h3 id="عائلة-route">عائلة Route</h3>
<ul>
<li><code>HTTPRoute</code>: مرور HTTP/HTTPS وهو الأكثر شيوعًا</li>
<li><code>GRPCRoute</code>: مرور gRPC ويمكنه المطابقة على service و method</li>
<li><code>TCPRoute</code>: مرور TCP خام، ولا يفسّر دلالات HTTP</li>
<li><code>TLSRoute</code>: يوجّه بناءً على TLS SNI، وهو شائع في TLS passthrough</li>
</ul>
<p>ما تشترك فيه كل الـ routes:
<strong>هي لا "تفتح الباب"، بل تقرر "كيف يُوجَّه المرور بعد دخوله".</strong></p>
<h2 id="نموذج-ذهني-مختصر">نموذج ذهني مختصر</h2>
<p>احتفظ بهذه الخريطة في رأسك:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#9ECBFF">GatewayClass</span><span style="color:#6A737D">  # Which Gateway implementation to use in this cluster</span></span>

<li><code>hostnames</code>: أي domain يجب أن يطابق هذه القاعدة</li>
<li><code>backendRefs</code>: إلى أي Service يجب إرسال المرور</li>
</ul>

<h2 id="الخلاصة-في-سطر-واحد">الخلاصة في سطر واحد</h2>
<p><code>Envoy Gateway</code> ليس مجرد مصطلح إضافي عليك حفظه، بل هو طريقة لرفع المرور الخارجي في Kubernetes من "يؤدي الغرض" إلى "شيء يشبه نظامًا هندسيًا حقيقيًا."</p>
<blockquote>
<p>💡 إذا كانت هذه أول مرة لك مع هذه المجموعة، فلا تحاول تعلّم كل CRD دفعة واحدة. ثبّته، واجعل أول طلب يمر، ثم ارجع إلى المفاهيم لاحقًا، فمعدل الاستيعاب سيكون أسرع بكثير بهذه الطريقة.</p>
</blockquote>

9:T47ce,<p>إذا سبق لك التعامل مع المرور الخارجي في Kubernetes، فالغالب أنك بدأت مع <code>Ingress</code>. هو يعمل، وبالنسبة لكثير من السيناريوهات فهو كافٍ فعلًا. لكن عندما تبدأ المتطلبات بالتعقّد أكثر، مثل وجود عدة listeners، وملكية مشتركة بين عدة فرق، و gRPC، و TCP، و TLS passthrough، وسياسات مرور دقيقة، فستجد نفسك حتمًا في وضع يصبح فيه "إبقاؤه حيًا عبر annotations" هو القاعدة. يبدأ الـ YAML وكأنه تعويذة، والناس الذين يصونونه يشعرون وكأنهم على وشك كسر ختم قديم.</p>
<p>وهنا يأتي دور <code>Gateway API + Envoy Gateway</code>، فهي العدة الجديدة. لا تجعل الأمور أعقد؛ بل تفصل المسؤوليات التي كانت متشابكة سابقًا بشكل نظيف، بحيث يصبح فهم مرور الدخول، وقواعد التوجيه، وإعدادات أمان TLS، وأنواع البروتوكولات، وملكية الفرق أسهل بكثير.</p>
<h2 id="ما-هذا-بالضبط">ما هذا بالضبط</h2>
<p>لنقلها بوضوح في جملة واحدة:</p>
<ul>
<li><code>Envoy Proxy</code>: مستوى البيانات الذي يستقبل المرور فعليًا ويحوّل الطلبات، ويُسمّى أيضًا Gateway Proxy</li>
<li><code>Envoy Gateway</code>: مستوى التحكم الذي يدير Envoy Proxy نيابةً عنك</li>
<li><code>Gateway API</code>: الواجهة المعيارية التي تستخدمها في Kubernetes للتصريح بقواعد المرور</li>
</ul>
<p>فكّر فيها هكذا:</p>
<ul>
<li><code>Gateway API</code> هو المكان الذي تكتب فيه المتطلبات</li>
<li><code>Envoy Gateway</code> هو المدير الذي يترجم ويفوّض</li>
<li><code>Envoy Proxy</code> هو الحارس الفعلي الواقف عند الباب</li>
</ul>
<p>فائدة هذا الفصل أنك لا تحتاج إلى صياغة إعدادات Envoy منخفضة المستوى يدويًا، ولا إلى حفظ كل annotation خاص من مختلف الـ controllers. أنت تصرّح بموارد Kubernetes، و Envoy Gateway يترجمها إلى إعدادات يستطيع Envoy Proxy تنفيذها فعلًا.</p>

<p>الإجابة المختصرة: <strong>Ingress لم يصبح قديمًا، لكن Gateway API أنسب للأنظمة المتوسطة والكبيرة التي تحتاج إلى حوكمة أفضل.</strong></p>

<p>إذا كانت متطلباتك ببساطة:</p>
<ul>
<li>موقع واحد أو API بسيط</li>
<li>توجيه أساسي حسب path أو host</li>
<li>فريق صغير</li>
</ul>
<p>فلا يزال Ingress خيارًا مناسبًا. لكن إذا بدأت متطلباتك تشمل:</p>
<ul>
<li>مدخل دخول واحد يخدم عدة بروتوكولات</li>
<li>عدة listeners أو domains أو certificates</li>
<li>HTTP و gRPC معًا</li>
<li>فصل صلاحيات ingress الخاصة بالمنصة عن صلاحيات routes الخاصة بالتطبيق</li>
<li>إعدادات تُقرأ كأنها API حقيقي وليست قائمة أمنيات من annotations</li>
</ul>
<p>فعندها ستبدو Gateway API جذابة جدًا.</p>
<h2 id="لماذا-لا-نكتفي-بـ-ingress">لماذا لا نكتفي بـ Ingress</h2>
<p>الهدف الرسمي لـ Gateway API هو معالجة عدة نقاط ألم شائعة عند توسّع استخدام Ingress:</p>
<ul>
<li><strong>قدرة تعبيرية أفضل</strong>: التوجيه و TLS وسياسات المرور وأنواع البروتوكولات محددة بشكل أوضح</li>
<li><strong>قابلية نقل أفضل</strong>: اعتماد أقل على annotations خاصة بكل controller</li>
<li><strong>فصل أدوار أكثر طبيعية</strong>: فرق المنصة تملك ingress، وفرق التطبيقات تملك routes</li>
</ul>
<p>على سبيل المثال، كثير من إعدادات Ingress تبدو هكذا:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#24292e;color:#e1e4e8" tabindex="0" data-language="yaml" data-theme="github-dark"><code data-language="yaml" data-theme="github-dark" style="display: grid;"><span data-line=""><span style="color:#85E89D">metadata</span><span style="color:#E1E4E8">:</span></span>

<p>ليس لأنها لا تعمل، لكن مع نمو المتطلبات تتحول annotations بسهولة إلى سحر أسود غامض داخل YAML. Gateway API تسحب هذه الاحتياجات إلى حقول واضحة. فتبدو كأنها "إعدادات" وليست "قائمة أمنيات".</p>
<h2 id="البنية-الطبقية">البنية الطبقية</h2>
<p>الصفحة الرسمية للمفاهيم تقسّم Envoy Gateway إلى ثلاث طبقات، ومن المفيد جدًا حفظها كخريطة ذهنية:</p>
<ul>
<li><strong>User Configuration</strong>: موارد <code>Gateway API</code> و CRDs التوسعية الخاصة بـ Envoy Gateway التي تكتبها</li>
<li><strong>Envoy Gateway Controller</strong>: يقرأ هذه الموارد ويترجمها إلى إعدادات قابلة للتنفيذ</li>
<li><strong>Envoy Proxy</strong>: مستوى البيانات الذي يتعامل فعليًا مع المرور الحي</li>
</ul>
<p>عمليًا، ستقضي معظم وقتك في تعديل "الطبقة التصريحية"، وليس في الدخول عبر SSH إلى instances البروكسي لتعديل إعدادات منخفضة المستوى. هذه هي أناقة العمل بطريقة Kubernetes-native.</p>

<h2 id="الموارد-الأساسية-التي-ستصادفها">الموارد الأساسية التي ستصادفها</h2>
<p>المبتدئون غالبًا يتعثرون لأنهم يفترضون أن Gateway API لا يحتوي إلا على <code>Gateway</code> و <code>HTTPRoute</code>. لكنه في الحقيقة عائلة كاملة من الموارد.</p>
<h3 id="gatewayclass"><code>GatewayClass</code></h3>
<p>يعرّف "أي implementation من Gateway يجب استخدامه في هذا الـ cluster."
وبالنسبة إلى Envoy Gateway، فالنقطة الأساسية هي أن يوجَّه <code>controllerName</code> إلى الـ controller الصحيح.</p>
<h3 id="gateway"><code>Gateway</code></h3>
<p>يعرّف "كيف يبدو ingress."
على سبيل المثال: ما المنافذ التي ستُفتح، وما البروتوكولات التي ستُستمع إليها، وكيفية إرفاق TLS، وأي routes يُسمح بها.</p>
<h3 id="listener"><code>Listener</code></h3>
<p><code>Listener</code> هو إحدى أهم الوحدات داخل <code>Gateway</code>.
فكّر فيه على أنه فتحة مواجهة للخارج في الـ Gateway، وكل فتحة تعرّف:</p>
<ul>
<li>port</li>
<li>protocol</li>
<li>hostname</li>
<li>TLS config</li>
<li><code>allowedRoutes</code></li>
</ul>
<p>كثيرون ينظرون إلى <code>Gateway</code> كأنه صندوق أسود، لكن ما يحدد سلوك ingress فعليًا هو كل <code>listener</code> داخله على حدة.</p>
<h3 id="عائلة-route">عائلة Route</h3>
<ul>
<li><code>HTTPRoute</code>: مرور HTTP/HTTPS وهو الأكثر شيوعًا</li>
<li><code>GRPCRoute</code>: مرور gRPC ويمكنه المطابقة على service و method</li>
<li><code>TCPRoute</code>: مرور TCP خام، ولا يفسّر دلالات HTTP</li>
<li><code>TLSRoute</code>: يوجّه بناءً على TLS SNI، وهو شائع في TLS passthrough</li>
</ul>
<p>ما تشترك فيه كل الـ routes:
<strong>هي لا "تفتح الباب"، بل تقرر "كيف يُوجَّه المرور بعد دخوله".</strong></p>
<h2 id="نموذج-ذهني-مختصر">نموذج ذهني مختصر</h2>
<p>احتفظ بهذه الخريطة في رأسك:</p>

<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">eg</span></span>
<span data-line=""><span style="color:#85E89D">  hostnames</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#9ECBFF">"www.example.com"</span></span>
<span data-line=""><span style="color:#85E89D">  rules</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">    - </span><span style="color:#85E89D">backendRefs</span><span style="color:#E1E4E8">:</span></span>
<span data-line=""><span style="color:#E1E4E8">        - </span><span style="color:#85E89D">name</span><span style="color:#E1E4E8">: </span><span style="color:#9ECBFF">backend</span></span>
<span data-line=""><span style="color:#85E89D">          port</span><span style="color:#E1E4E8">: </span><span style="color:#79B8FF">3000</span></span></code></pre></figure>
<p>لا تحتاج إلى حفظ كل حقل الآن. فقط افهم ما الذي يفعله:</p>
<ul>
<li><code>parentRefs</code>: إلى أي Gateway ترتبط هذه القاعدة</li>
<li><code>hostnames</code>: أي domain يجب أن يطابق هذه القاعدة</li>
<li><code>backendRefs</code>: إلى أي Service يجب إرسال المرور</li>
</ul>

<h2 id="الخلاصة-في-سطر-واحد">الخلاصة في سطر واحد</h2>
<p><code>Envoy Gateway</code> ليس مجرد مصطلح إضافي عليك حفظه، بل هو طريقة لرفع المرور الخارجي في Kubernetes من "يؤدي الغرض" إلى "شيء يشبه نظامًا هندسيًا حقيقيًا."</p>
<blockquote>
<p>💡 إذا كانت هذه أول مرة لك مع هذه المجموعة، فلا تحاول تعلّم كل CRD دفعة واحدة. ثبّته، واجعل أول طلب يمر، ثم ارجع إلى المفاهيم لاحقًا، فمعدل الاستيعاب سيكون أسرع بكثير بهذه الطريقة.</p>
</blockquote>
